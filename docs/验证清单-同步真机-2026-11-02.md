> 读者：执行验证的 agent。按顺序做，每一步都有「操作 / 预期 / 记录」。
> 背景先读 `docs/交接-同步重写-2026-11-02.md`（做了什么、已知缺口）。本清单只管「怎么验」。
> 被测代码：分支 `feat/sync-rewrite`，提交 `9bf041d` 或更新。开工前 `git log --oneline -1` 记下实际测的是哪个提交。

## 0. 规则（先读，全程遵守）

1. **这是验证，不是修复。** 发现问题：记录现象、证据、复现步骤，然后继续下一步（除非该步标了「失败即停」）。
   不改代码、不改 `docker-compose.yml`、不改服务器配置来「让它通过」，除非用户明确让你修。
2. **不推送、不合并、不打标签、不发版。** 需要构建安装包时只在本地构建。
3. **只用测试数据。** 前几个阶段用全新的测试笔记本；用户的真实笔记本只在 M 阶段用，而且先备份整个文件夹（`cp -R` 到别处）再动。
   绝不对真实笔记本点冲突区的「全部用远端」「全部用我的」，也不对删改冲突选会删文件的那一边。
4. **凭据不进报告。** 管理员密码、测试账号密码、加密口令、会话令牌、`.env` 内容、GitHub Client Secret 一律不写进报告和日志摘录；
   需要时写「（已设置，见用户）」。测试账号用 `@example.test` 结尾的邮箱。
5. **每台机器的身份要写清楚**：本清单里 `M1`、`M2`、`M3` 指三台物理机。开工时在报告里写下每台的系统、版本、机器名、运行方式（安装包 / 源码 `pnpm dev:electron`）。
6. 证据优先用文字（命令输出、页面文字、服务端活动日志），截图只在文字说不清时用。
7. 报告写到 `docs/验证记录-同步真机-<YYYY-MM-DD>.md`（格式见文末）。写完不要提交，交给用户。

### 失败即停的步骤

A3、A5、D3。它们失败说明环境不对，后面全部无意义 —— 停下来报告。

## A. 部署服务器

在服务器上，仓库根目录执行。

**A1 取代码**
- 操作：`git fetch && git checkout feat/sync-rewrite && git log --oneline -1`
- 预期：是要测的那个提交。
- 记录：提交号。

**A2 准备 `.env` 与数据目录**
- 操作：
  - `cp .env.example .env`（已有 `.env` 就先备份），由用户填或你生成长随机口令填：`EXTERNAL_BASE_URL`、`COUCH_ADMIN_PASSWORD`、`COUCH_SYNC_PASSWORD`；
    用 Cloudflare 命名隧道时 `TRUSTED_PROXY_HEADERS=cf-connecting-ip`。
  - `sudo mkdir -p ./data/sync && sudo chown 1000:1000 ./data/sync`（容器以 uid 1000 运行，不改归属会写不进 `control.db`）。
  - 如果服务器上有**旧版**数据：先备份 `./data` 整个目录。旧库在启动时会被迁移到 schema v6，旧账号保留但再也登录不了（设计如此）。
- 预期：`.env` 不在 git 里（`git status` 看不到它）。

**A3 启动（失败即停）**
- 操作：`docker compose up -d --build`，然后 `docker compose ps`、`docker compose logs sync --tail 50`
- 预期：
  - `couchdb` healthy，`sync` running；
  - 日志里依次出现 `已应用迁移 1` … `已应用迁移 6`（全新库）或只出现缺的那几条（旧库），以及 `协议版本 2`、`监听 0.0.0.0:8787`。
- 记录：迁移日志行。启动失败就贴最后 50 行日志并停。

**A4 建 CouchDB 运行时账号（首次部署必做）**
- 操作：`docker compose exec sync node dist/cli.js setup-couch-user`
- 预期：成功信息，没有报错。**不做这一步，之后每个笔记本请求都会 401。**

**A5 健康检查（失败即停）**
- 操作（服务器本机与任一台测试机各做一次）：`curl -s <EXTERNAL_BASE_URL>/v1/health`
- 预期：JSON，`ok: true`、`protocolVersion: 2`、`couchVersion` 不是 null（是 `3.3.x`）、`setupRequired: true`（全新库）、`auth.password: true`、`auth.github: false`。
- 记录：完整响应（不含敏感信息）。`couchVersion` 为 null = sync 连不上 CouchDB，查 `.env` 的 COUCH_* 并停。

**A6 端口暴露情况（只记录，不改）**
- 操作：在服务器上 `ss -ltnp | grep 8787`；从**另一台局域网机器** `curl -s -m 3 http://<服务器局域网IP>:8787/v1/health`。
- 背景：`docker-compose.yml` 里的注释说 sync 只绑宿主回环，但实际写的是 `0.0.0.0:${SYNC_HOST_PORT}:8787`。
- 记录：局域网能不能直连 8787。这是给用户的安全提示，不要自己改。

**A7（可选，推荐）用真实 CouchDB 跑一遍端到端测试**
- 在任一台装了 Docker 和 Node 的机器上（可以就是服务器），用**一次性**容器，别碰生产库：
  - `docker run -d --name couch-e2e -p 127.0.0.1:5985:5984 -e COUCHDB_USER=admin -e COUCHDB_PASSWORD=adminpw couchdb:3.3`
  - 仓库根：`pnpm install`，然后
    `OPENNOTE_TEST_REAL_COUCH=1 OPENNOTE_TEST_COUCH_URL=http://127.0.0.1:5985 npx vitest run tests/sync.e2e.test.ts`
  - 做完：`docker rm -f couch-e2e`
- 预期：全部通过，**包括**「真实 CouchDB」组里的置备验收与 SSE 两条（平时会跳过的那两条）。
- 记录：通过 / 失败条数，失败用例名与断言信息。SSE 那条失败意味着实时同步在真机上也大概率不工作，D/E 阶段重点看。

## B. 控制台

浏览器打开 `<EXTERNAL_BASE_URL>/admin`。

**B1 初始化**
- 预期：初始化表单（对外地址只读，显示 `.env` 里的值）。
- 操作：管理员邮箱（用户给的真实邮箱或 `admin@example.test`）、密码（≥10 位）、「谁可以注册」选「仅限邀请」，提交。
- 预期：直接进入概览；再刷新 `/admin` 仍是登录状态。`/v1/health` 的 `setupRequired` 变成 `false`。

**B2 cookie 属性**
- 操作：浏览器开发者工具看 `opennote_panel` cookie。
- 预期：`HttpOnly`、`SameSite=Lax`；https 地址下有 `Secure`。没有 `Secure` 而地址是 https = 记为问题。

**B3 建测试账号**
- 操作：「邀请」页生成两条邀请：
  - 绑定邮箱 `tester1@example.test`；
  - 通用链接，可用 5 次。
  分别在**无痕窗口**打开 `/join/…`，设密码建号（第二个用 `tester2@example.test`）。
- 预期：建号成功页显示服务器地址与邮箱，有「在 Opennote 中打开」按钮；回到控制台「用户」页能看到两个账号，「邀请」页对应邀请进入「已结束」。
- 后续阶段默认用 `tester1@example.test` 登录所有设备（多设备 = 同一账号）。`tester2` 用于隔离测试。

**B4 控制台其余页面冒烟**
- 逐页打开：概览、活动日志、用户（点开一个用户的抽屉）、笔记本、设备、服务设置。
- 预期：都能打开，没有「这一页没读出来」；活动日志里有初始化、邀请、接受邀请。
- 不要在这一步删账号、改设置（后面阶段会测）。

## C. 在每台物理机上准备客户端

**C1 安装或运行**
- 用安装包（推荐，深链与系统钥匙串只在打包版里可靠）：在该机器上从同一提交构建（`pnpm install && pnpm package:mac`，Windows/Linux 用 `pnpm package:desktop`），产物在 `release/`。
- 或源码运行：`pnpm install && pnpm dev:electron`（GitHub 深链在开发模式下可能唤不起本应用，L 阶段用打包版）。
- 记录：每台的运行方式与「设置 → 帮助」里显示的版本号。

**C2 升级场景（仅在装过旧版并开过同步的机器上）**
- 背景：旧版把「账号密钥」存在应用 userData 目录的 `sync-account-key.bin`；新版读到它会当作「没登录」，旧笔记本的同步配置指向旧服务器。
- 操作：先**备份**该机器上开过同步的笔记本文件夹，再打开新版，打开那个笔记本。
- 预期：不崩；状态栏同步位显示「未登录同步」（不是旧文案「此设备的密钥已被轮换」）；笔记文件不变。
- 之后在这台机器上按 D 阶段正常登录，再看这个旧笔记本：
  - 新服务器地址和旧的**不一样**：预期显示「服务器不一致」，设置页说明「关掉它的同步再打开，就会改绑到当前服务器」。照做，预期按名字合并上去。
  - 新服务器地址和旧的**一样**（同一个域名重新部署）：**预计会出问题**。旧配置里记着旧服务器上的笔记本 id，新服务器上没有它；
    代码里关掉再打开开关时，同一地址会保留旧 id，所以很可能一直报「笔记本不存在」之类的错误，开关重开也救不回来。
    确认这个推测是否成立；成立就记为 P1（升级用户会卡死）。
    可以试的绕法：旧 id 记在应用的笔记本列表里，不在笔记本文件夹里，所以删 `.opennote/sync.json` 没用；
    在应用里把这个笔记本从列表中移除（笔记本切换菜单里的移除 / 忘记入口），再重新打开同一个文件夹，新记录不带旧配置，然后正常开同步。
    记下这个绕法是否有效。
- 记录：实际文案与是否能恢复。

**C3 准备测试笔记本**
- 每台机器建一个**空文件夹**，用「打开本机文件夹」打开它，命名为 `同步测试`（文件夹名就是笔记本名，按名字配对靠它）。M1 上写 3 篇笔记：`a.md`、`子目录/b.md`、`c.md`（各写几行可辨认的内容），并粘贴一张图片（会进 `.assets/`）。

## D. M1：第一台设备

**D1 登录**
- 操作：状态栏同步图标 → 打开「设置 → 同步」→「登录同步账号」。服务器地址填 `<EXTERNAL_BASE_URL>`，移开焦点。
- 预期：输入框下方出现「已找到 Opennote 同步服务 · 协议 2 · 仅限邀请注册」。
- 操作：填 `tester1` 的邮箱密码，设备名改成能区分的（如 `M1-Mac`），点「登录」。
- 预期（桌面端）：第一次连这个服务器时弹出**系统原生**确认框（允许连接这个地址）；同意后进入「要同步哪些笔记本？」。
- 记录：有没有原生确认框。没有确认框不算失败，但要记。

**D2 选笔记本**
- 预期：「这台设备上的」列出 `同步测试（正在用）`，开关已开，说明是「云端没有 · 将新建并上传」；「新笔记本加密」默认「不加密」。
- 操作：点「开始同步 1 个笔记本」。

**D3 首次同步（失败即停）**
- 预期：几秒内顶部变成「已同步」，副标题「这一轮上传 N」（N = 文件数，含图片）；笔记本那一行「已同步 · 刚刚」；状态栏同步位回到只显示图标（正常时不写字是设计）。
- 交叉核对：控制台「笔记本」页出现 `同步测试`，所有者是 tester1，大小不为 0；「活动日志」有「新建了笔记本」与「写入 N 次」。
- 失败时：打开设置页最下面「诊断（排查问题时给开发者看）」，把日志全文贴进报告；同时 `docker compose logs sync --tail 100`。然后停。

**D4 设备与账号信息**
- 预期：「设备」一节只有 `M1-Mac`（带「这台」标签）；「账号」一节显示邮箱、服务器、已用空间；「加密口令」一节说「这个账号还没有加密口令」。
- 控制台「设备」页：`M1-Mac` 在线，平台与客户端版本正确。

## E. M2：同一账号的第二台设备，合并与实时

**E1 登录与按名字配对**
- 操作：M2 上 C3 已建空的 `同步测试`。按 D1 登录同一账号（设备名 `M2-…`）。
- 预期：选笔记本页里 `同步测试` 说明为「云端已有同名笔记本 · 将合并」。点开始同步。
- 预期：M2 拉下 M1 的 3 篇笔记与图片，内容逐字一致（打开核对），侧栏立即出现，不需要重启或手动刷新。
- 记录：从点「开始同步」到文件出现的大致秒数。

**E2 实时：M1 → M2**
- 操作：M1 上新建 `d.md` 写一句话，停笔等自动保存。
- 预期：**不点任何按钮**，M2 在约 10 秒内出现 `d.md` 且内容一致。
- 记录：大致延迟。超过 1 分钟没到 = 实时不工作（对照 A7 的 SSE 用例结果），再点 M2 的「立即同步」看能不能拉到（区分「实时坏了」与「同步坏了」）。

**E3 实时：M2 → M1**：同 E2 反方向，改 `a.md` 的一行。

**E4 两台都开着、各写不同篇**：M1 改 `b.md`、M2 改 `c.md`，几乎同时保存。
- 预期：两边最终都有对方的改动；没有冲突提示。

**E5 删除与重命名**
- 操作：M1 删除 `c.md`；M2 把 `d.md` 重命名为 `d2.md`；M1 新建文件夹 `新目录` 并把 `a.md` 移进去。
- 预期：两边最终一致；没有已删的文件「复活」；设置页没有出现「N 条删除已暂缓」（出现了要记）。

**E6 忽略规则**
- 操作：M1 在笔记本根目录建 `.gitignore`，写一行 `临时/`；建 `临时/x.md`。
- 预期：M2 收不到 `临时/x.md`；控制台活动日志里写入次数不因它增加。

**E7 附件与大小上限**
- 操作：M1 放一张几 MB 的图片；再放一个超过服务器单文件上限（默认 32 MB）的文件。
- 预期：图片到 M2；超限文件不到，且客户端有可读的提示或诊断日志说明原因（记下实际表现；没有任何提示也记下来）。

## F. 冲突

**F1 两边改同一篇**
- 操作：断开 M2 网络（关 Wi-Fi）。两台都改 `b.md` 的**同一行**为不同内容并保存。恢复 M2 网络。
- 预期：
  - 其中一台（后上传的）设置分类栏「同步」带红点，状态栏写「1 篇待处理」，设置页顶部「1 篇笔记需要你决定保留哪一份」，下面有冲突列表（类型「两边都改」）与「并排 / 统一」对比。
  - 未处理前，那一篇**不会**被任何一边覆盖（在另一台上也看不到对方的版本被悄悄套用）。
- 操作：在冲突列表里点「用我的」或「用远端」（对比视图里是「用我的版本 / 用远端版本」）。
- 预期：两边收敛到选中的版本，红点与「待处理」消失。

**F2 一边删、一边改**
- 操作：同 F1 的断网方法，M1 删 `子目录/b.md`，M2 改它。
- 预期：出现删改冲突，类型是「本地已删 · 远端改过」或「远端已删 · 本地改过」（看在哪台上报出来），出口仍是「用我的 / 用远端」；
  选「保留改过的那一边」后两边都有改后的版本，选另一边则两边都删除。
- 记录：在哪台报出、类型文案、选了哪边、两边的最终结果。

**F3 批量操作的确认框**：制造 2 处冲突后点「全部用我的」或「全部用远端」，只看确认框里写的「覆盖 N 篇 / 删除 N 篇」对不对，**点取消**。

## G. 离线与恢复

**G1** M2 断网，改 3 篇，等 1 分钟。预期：设置页顶部「连不上同步服务器」，说明改动都存在本机；状态栏写「离线」，是提醒色调（warn），不是错误（error）的红色。
**G2** 恢复网络，不点按钮。预期：自动重试并上传，M1 收到 3 篇改动。记录恢复耗时。
**G3** 服务器端 `docker compose restart sync`，期间两台各改一篇。预期：sync 起来后两边自动收敛；账号仍是登录状态（会话存在库里，重启不丢）。

## H. 设备、账号与权限

**H1 添加设备（配对码）—— 用 M3；没有 M3 就在 M2 上先「退出登录」再当新设备**
- M1：设置 → 同步 →「添加设备」。预期：6 位码 + 倒计时 + 「等待新设备…」。
- M3：「从另一台设备加入」，填服务器地址、6 位码、设备名 `M3-…`，点「加入」。
- 预期：两边显示**同一个** 6 位校验码；M1 弹出「`M3-…` 想要加入你的账号」。在 M1 点「确认加入」。
- 预期：M3 进入「要同步哪些笔记本？」；`同步测试`（M3 上建同名空文件夹）合并成功。
- 再测一次「拒绝」：M3 收到「另一台设备拒绝了这次加入」；码过期（等 10 分钟或关掉窗口）后再输入，提示码不对或过期。
- 记录：校验码是否一致（只写「一致」，不写码本身也可以）。

**H2 移除设备**
- M1「设备」一节移除 `M3-…`。
- 预期：M3 下一次同步（点「立即同步」或等实时）后状态栏变成红色「需要重新登录」，设置页切到「需要重新登录」表单；M3 本机文件不变。用密码重新登录后恢复同步。

**H3 改密码**
- M1「账号」→「修改密码…」。
- 预期：M1 继续正常；M2、M3 变成「需要重新登录」；用新密码登录后恢复。

**H4 管理员停用账号**
- 控制台「用户」→ tester1 →「停用账号」。
- 预期：所有设备（下一次同步时）状态栏红色「账号已被停用」（不是「需要重新登录」），设置页顶部「同步账号已被停用」。
- 再「重新启用」。预期：各设备**不用重新登录**就能恢复。可能需要的动作：打开「设置 → 同步」（会刷新账号状态），再编辑一篇笔记或等实时信号触发同步。
- 记录：恢复需要哪些动作；如果必须重新登录或重启应用才恢复，记为 P2。

**H5 管理员发设置密码链接**
- 控制台 tester1 抽屉 →「发送重置密码链接」，在无痕窗口打开链接设新密码。
- 预期：所有设备「需要重新登录」；新密码可登录。

**H6 账号隔离**
- 用 tester2 在任一台设备登录（先退出 tester1），开同名 `同步测试`。
- 预期：tester2 看不到 tester1 的笔记本内容；按名字配对会在 tester2 名下**新建**一个 `同步测试`，不会碰 tester1 的。控制台「笔记本」页出现两个同名但所有者不同的笔记本。做完退出 tester2，换回 tester1。

**H7 登录限流**
- 在某台设备上用错误密码登录 tester2 连续 5 次。
- 预期：第 6 次提示「登录失败次数太多，请 N 分钟后再试」；控制台活动日志有「登录失败次数太多，临时锁定 15 分钟」。不要用 tester1 做这一步。

## K. 端到端加密（含已知缺口，先读）

**已知缺口**：加密笔记本的「文件名对照表」（`m:pathmap`）没有接进同步引擎。因此：
- 一台设备上**新建**的加密笔记，另一台设备**收不到**（对方认不出它叫什么，会被如实跳过）；
- 两台设备都**已经有**的同名文件，修改可以互相同步。
- 设置页会显示「云端有 N 篇加密笔记这台设备还认不出来」—— 这是预期表现，不是新 bug。

本阶段只验证：口令流程、解锁、配对带口令、服务器上没有明文、缺口的表现与上面描述一致。

**K1 设口令并建加密笔记本**
- M1 新建空文件夹 `加密测试`，打开它；设置 → 同步 → 「新笔记本加密」选「端到端加密」，按提示设加密口令（勾「记在这台设备上」），再打开 `加密测试` 的同步开关。写一篇 `机密.md`，内容含一个独特字符串（如 `ZQX-测试-7731`）。
- 预期：上传成功；控制台「笔记本」页 `加密测试` 类型是「端到端加密」。
- 服务器上确认没有明文（在服务器执行，CouchDB 不对宿主暴露，所以进容器查）：
  `docker compose exec couchdb sh -c 'curl -s -u "$COUCHDB_USER:$COUCHDB_PASSWORD" "http://localhost:5984/_all_dbs"'` 找到对应的 `nb-…` 库，
  再 `…/<库名>/_all_docs?include_docs=true`，在输出里搜那个独特字符串与文件名 `机密`。
- 预期：**搜不到**。搜到 = 严重问题，立即报告。
- 说明：`_all_docs?include_docs=true` 不含附件正文。附件（正文、图片）是否也只存了密文，由 A7 的端到端测试逐个解码附件核对过；A7 没跑的话在报告里注明「附件未在真机上核对」。

**K2 记住口令**：完全退出并重开 M1。预期：`加密测试` 直接同步，不要求输口令。
**K3 不记住口令**：设置「加密口令」→「不再记在这台设备上」，退出重开。预期：状态栏「待解锁」，分类栏「同步」有红点；输口令解锁后恢复同步。输错口令提示「加密口令不对」。
**K4 第二台设备用口令解锁**：M2 建空的 `加密测试` 并打开同步开关。预期：要求输入加密口令；输入后接上，并出现上面「认不出来」的提示（`机密.md` 收不到 —— 符合已知缺口）。
**K5 配对带过口令**：H1 那样把一台新设备配对进来（或复用 M3），**不输口令**直接打开 `加密测试`。预期：不要求输口令（口令随配对带过来了）。
**K6 改口令**：M1「修改加密口令…」。预期：M1 继续；其它没记住口令的设备下次解锁要用新口令，旧口令提示不对。

记录：每步的实际表现；K4 中认不出的篇数是否与 M1 上的加密笔记数一致。

## L. GitHub 登录（可选，需要用户先在 GitHub 建 OAuth App）

**L1 配置**：控制台「服务设置」→「GitHub」：打开开关，填 Client ID / Secret，回调地址用页面上显示的 `<EXTERNAL_BASE_URL>/auth/github/callback`（让用户填到 GitHub 的 OAuth App 里），保存。点「测试登录」。
- 预期：管理员账号还没绑 GitHub，所以「测试登录」会进入结果页说「不在这台服务器的用户里」—— 这是对的。`/v1/health` 的 `auth.github` 变成 `true`。
**L2 用 GitHub 接受邀请**：新发一个邀请（不绑邮箱），无痕窗口打开，点「用 GitHub 接受邀请」。预期：GitHub 授权后回到「账号建好了」，邮箱是 GitHub 上已验证的那个。
**L3 客户端 GitHub 登录（打包版桌面）**：退出当前账号 → 登录表单出现「使用 GitHub 登录」→ 点它。预期：系统浏览器打开 GitHub；授权后**自动回到 Opennote**（`opennote://sync/callback` 深链），设置页进入选笔记本。
- 记录：是否自动回到应用；没回来时设置页停在「等待 GitHub 授权」，可点「取消」。
**L4 绑定与解绑**：用密码账号登录的设备上，「账号」→「绑定 GitHub」，在浏览器完成后回来刷新，登录方式显示 `@用户名`。再「解绑 GitHub」。
**L5 关密码登录的保护**：GitHub 配好前，「邮箱和密码」开关关不掉（保存时报错）；配好后可以关，关了之后登录表单只剩 GitHub 按钮。**测完立刻打开回去。**
