## 0. 一句话

CouchDB 提供的是四样**原语**——文档级多主复制、变更流、检查点、显式冲突叶子；
「文件 ↔ 文档」的映射、冲突策略、`.opennote/` 边界仍然是我们自己的事。
**好消息是：`src/lib/github/sync.ts` 里的 `planPush` / `planPull` / `collectLocalFiles` 一行都不用改。**

## 1. CouchDB 给什么、不给什么

| 我们要的能力 | CouchDB 的对应件 | 一手依据 |
| --- | --- | --- |
| 增量（只问「缺什么」） | `GET /{db}/_changes?since=<seq>`；`POST /{db}/_revs_diff` 只问缺哪些 revision | [复制协议 v3](https://docs.couchdb.org/en/stable/replication/protocol.html) |
| 检查点（上次同步到哪） | `_local/<id>` 文档，官方明确 **"Local documents are not replicated to other databases."** | [Local (non-replicated) docs](https://docs.couchdb.org/en/stable/api/local.html) |
| 实时推送 | `_changes?feed=continuous`（每事件一行 JSON）、`feed=longpoll`（等到有变更再返回，最常配 `since=now`）、**`feed=eventsource`**（浏览器原生 DOM 事件，官方支持 `Last-Event-ID`） | [Changes feed](https://docs.couchdb.org/en/stable/api/database/changes.html) |
| 冲突 | `_rev` = MVCC token；并发写产生多个 leaf revision（revision tree），**不丢弃**，只用确定性算法选 winner | [冲突模型](https://docs.couchdb.org/en/stable/replication/conflicts.html) |
| 乐观锁 | `PUT` 带旧 `_rev` → 不匹配返回 **409**（比 GitHub 的「非快进」更好用，粒度是单篇） | 同上 |

**CouchDB 不负责的**（这些是本设计的主体）：
文件与文档的映射、大文件分块与去重、路径改名语义、`.opennote/` 哪些字段该同步、
UI 上的冲突队列、桌面端 CSP 下的 HTTP 代理、以及要不要做 E2EE。

## 2. 远端数据模型（v1：一文件一文档）

```jsonc
// 文件元数据文档 —— 唯一会冲突的文档类型
{
  "_id":  "f:<sha256(utf8(path)) 前 32 位十六进制>",
  "_rev": "3-abc…",
  "t":    "file",
  "path": "日记/九月.md",          // 明文路径：给人看、给跨设备比对用
  "size": 12345,
  "hash": "<整个文件字节的 sha256>",
  "b64":  "IyDkuZ3mnIgg…",        // 整个文件的字节（base64）
  "deleted": false                // 逻辑删除（tombstone）
}
```

三条刻意的决定：

1. **`_id` 用路径的哈希，而不是路径本身。**
   CouchDB 的 doc id 里放路径会同时踩到 `/` 的路由、Unicode、大小写、以及 Windows 保留名；
   哈希之后这些全部绕开，`path` 作为普通字段仍可读。代价：改名 = 换 `_id`（见 §4）。
2. **内容一律以「字节 + base64」存，不存字符串。**
   应用的两条读写通路是 `readBytes` / `writeBytes`；存字符串就必须在 EOL（`\r\n` vs `\n`）和编码上与磁盘逐字节对齐，
   一旦不同步就会出现「内容没变但哈希变了」的无限同步。字节存储从根上避免这类往返失真。
3. **`deleted` 是逻辑删除，且这条 tombstone 文档长期保留。**
   它有两个作用：① 删除成为一条带设备与时间的**显式记录**，而不是「文档凭空消失」；
   ② 避免「离线设备回来把已删的笔记又推上去」的复活竞态——删除本身也是一次 `_changes` 事件。
   §4.1 的 view 会过滤掉 `deleted:true`，于是「不在远端树里 = 远端删除」有确切含义。
   （清理策略见 §9；不要用 `_purge`。）

**v1 不做分块。** Markdown 笔记典型 1–50 KB，图片走同一套结构即可。
调研报告 §3.2 范式 E（思源 dejavu 的 `Index/File/Chunk/Ref`）确实更省流量，但那是**先量再优化**的事，
判据写在 §8 P4，不要在 P1 就把 chunk 层建起来。

## 3. 本地状态放哪（两条纪律）

| 状态 | 放哪 | 为什么 |
| --- | --- | --- |
| **共享基线**：`path → { hash, rev, imported }` | `.opennote/sync.json`（**跟随笔记本**） | 与 `src/lib/github/baseline.ts` 的 `github.json` 同构：换机器拷文件夹时判据跟着走。这是**同步的唯一事实源** |
| **每设备检查点**：`deviceId` + `lastSeq` | 远端 `_local/opennote-<deviceId>` | CouchDB 官方语义就是「本地文档不参与复制」。**不能**放 `.opennote/`——那个目录会被 Syncthing / 网盘 / U 盘二次搬运，设备态放进去必然互相踩 |
| `deviceId` 本身 | `localStorage` / IndexedDB（每安装一份） | 它是设备属性，不是笔记本属性；和 `workspaces.ts` 把工作区注册表放 localStorage 是同一类决定 |
| **凭据** | `localStorage`（记住）/ `sessionStorage`（不记住） | 沿用 `baseline.ts:1-13` 已写死的理由：`.opennote/` 会被同步、导出、拷贝，令牌放进去等于写进仓库 |

`.opennote/sync.json` 的形状刻意与 `GithubBaseline` 对齐：

```ts
interface SyncBaselineFile {
  /** 我们上次见到的远端内容哈希（注意：是内容哈希，不是 `_rev`）。 */
  hash: string;
  /** 远端 `_rev`，只给乐观锁用。 */
  rev: string;
  /** 我们有没有把这一条物化到本地；false = 只在基线里记账，同步永不触碰。 */
  imported: boolean;
}
interface SyncBaseline {
  version: 1;
  provider: "couchdb" | "github" | "s3" | "webdav";
  remote: string;
  files: Record<string, SyncBaselineFile>;
}
```

> **一个关键的语义选择**：`planPull` 判断「远端改没改」用的是 `known.remoteSha !== entry.sha`。
> 我们把喂给它的 `entry.sha` 填成**内容哈希**（而不是 `_rev`），于是 `planPull` 一个字都不用改；
> `_rev` 单独存 `rev` 字段，只用于 `put()` 的 CAS。
> 如果误把 `_rev` 当 `remoteSha`，任何一次「内容没变但被别的设备碰过」都会被判成「远端改了」。

## 4. 一次同步的算法

### 4.1 为什么要「整树列一次」，而不是只吃 `_changes`

`planPull` 的删除检测依赖**完整的远端树**：它遍历基线里的所有已物化条目，凡是「不在远端树里」就判定为远端删除。
如果只把 `_changes` 里的变化文档喂给它，那么**没出现在 `_changes` 里的文档会被误判成「远端删了」**。

所以 v1 采用与现有 GitHub 实现完全一致的形态：

- `_changes` 只当**「有东西变了，去同步一次」的信号**；
- 每次同步列一次**紧凑投影的全树** `{path, hash}`，靠一个服务端 view 完成（见下）。

**为什么用 view 而不是 `_all_docs`**：`_all_docs` 不带 `include_docs` 只给 `{id, rev}`，
而我们要的 `path`/`hash` 都在文档体里；一旦加 `include_docs=true`，就会把每个文档的 `b64` 正文
（含图片）整包拉下来——正是要避免的事。
正确做法是客户端首次连接时幂等写入一个 design document，让服务端投影出我们需要的两个字段：

```jsonc
// _design/opennote  —— 客户端首次连接时 PUT，幂等
{ "_id": "_design/opennote",
  "views": { "files": { "map":
    "function (doc) { if (doc.t === 'file' && !doc.deleted) emit(doc.path, doc.hash); }" } },
  "language": "javascript" }
```

于是 `list()` = `GET /{db}/_design/opennote/_view/files`（可配 `limit`/`startkey` 分页），
返回的就是 `path → hash`，**不含正文**。注意两点：
① `_changes` 里也会出现 `_design/*`，要按 `_id` 前缀过滤掉；
② view 里**不需要、也不要**取 `_rev`——CAS 用的 `_rev` 来自我们自己的基线，
拉取单个文档时再学新的（见 §5 第 2 层）；
③ **不要用 `stale=ok`**：view 必须在本次查询前更新到当前 update_seq，否则会漏掉变化、
把「远端没改」误判成真。

这不是退步——现有 GitHub 通道每次也是全树取一遍 `git/trees?recursive=1`，成本同量级；
而 `_changes` 换来的是「什么时候该跑」和「实时推送」。
真正的省法（`_changes` + `_revs_diff` 的纯增量、不列全树）需要一个新的增量 planner，列为 P4。

### 4.2 伪代码

```ts
async function syncOnce(backend: FileSystemBackend, provider: SyncProvider): Promise<SyncReport> {
  const baseline = await readSyncBaseline(backend);            // .opennote/sync.json
  const checkpoint = await provider.readCheckpoint(deviceId);   // _local/opennote-<deviceId>

  // 1. 本地现状（复用，不改）
  const local = await collectLocalFiles(backend);               // LocalFile{path,hash,bytes}  sync.ts:144

  // 2. 远端现状（整树一次）+ 计划
  const remoteTree = await provider.list();                     // → 适配成 GithubTree{entries:[{path,sha:hash}]}
  const push = planPush(baseline, local);                       // 已有纯函数  sync.ts:52
  const pull = planPull(baseline, remoteTree, local);           // 已有纯函数  sync.ts:94

  if (pull.conflicts.length) {
    report.conflicts = pull.conflicts;                          // 不覆盖，进列表（沿用现有行为）
    pull.download = pull.download.filter(d => !conflicted(d));  // 冲突项本轮不落地
  }

  // 3. 先拉后推：远端落盘必须显式驱动刷新（自写过滤会吞掉 watcher 事件）
  for (const { path } of pull.download) {
    const bytes = await provider.read(path);
    await backend.writeBytes(path, bytes);                      // mkdir 由后端契约负责
  }
  for (const path of pull.removeLocal) await backend.remove(path);
  if (pull.download.length || pull.removeLocal.length) {
    applyExternalPaths([...])                                   // 新增：导出 library.ts:935 的 refreshPaths
  }

  // 4. 推送（逐文档 CAS；409 = 别人动过 → 该文档重新决策，不整轮失败）
  for (const file of [...push.added, ...push.modified]) {
    const known = baseline.files[file.path];
    try {
      const { rev } = await provider.put(file.path, await backend.readBytes(file.path), known?.rev ?? null);
      baseline.files[file.path] = { hash: file.hash, rev, imported: true };
    } catch (e) {
      if (isConflict409(e)) { rerunDecisionFor(file.path); continue; }   // §5 第 2 层
      throw e;
    }
  }
  for (const path of push.deleted) {                            // 逻辑 tombstone，不硬删
    await provider.remove(path, baseline.files[path]?.rev ?? null);
    baseline.files[path] = { ...baseline.files[path], imported: false };
  }

  // 5. 提交基线与检查点
  await writeSyncBaseline(backend, baseline);                   // 落盘成功才写
  await provider.writeCheckpoint(deviceId, checkpoint.cursor);  // _local/<id>
  return report;
}
```

## 5. 冲突：三层防线

D2 假设失效之后，「冲突」必须重新有名字。三层，从便宜到贵：

1. **预检（基线三方 diff）** —— `planPull` 已经实现了：远端改了、本地也改了 → 进 `conflicts`，
   **一个字节都不动**，等用户裁决。绝大多数情况止步于此。
2. **写入乐观锁（CouchDB 的 `_rev`）** —— 本轮要推的文档，`PUT` 时带上基线里的 `_rev`；
   别人已经推过 → **409**。此时**只对这一个文档**重新拉取 + 重新决策（不整轮失败、不覆盖）。
   这是 CouchDB 相比 GitHub「非快进」最舒服的一点：冲突粒度是单篇，而不是整次推送。
3. **服务端 leaf conflict** —— 两个设备都用了过期 `_rev` 之外的路径（例如 `_bulk_docs` + `new_edits=false`，
   或历史遗留）导致同一文档有多个 leaf：
   `GET /{db}/<id>?conflicts=true&open_revs=all` 取全部分支。
   ⚠️ 注意一个官方细节：`_changes` 的 `conflicts=true` **只在 `include_docs=true` 时才生效**。

**落地页（丢的那一版去哪）**：
- 当前路径归赢家；
- 输的一版写进 `.opennote/history/<笔记>/<时间戳>-before-sync.md`——这是**现成机制**（设计文档 §2 D3 的前像），
  且 `.opennote/` 永不推送，不会污染远端；
- 状态栏出一个**持久的「N 个冲突待处理」**入口，点开就是 `ConflictDialog`。

> 刻意**不**做：不往笔记目录写 `xxx.conflict-*.md`。
> D4 当初删掉冲突副本的理由是「同一篇不会被并发写」——这个理由现在不成立了，所以要恢复**冲突处理**；
> 但把冲突文件撒进用户的笔记文件夹（并同步到所有设备、进文件树、进搜索）代价太大，前像 + UI 更诚实。

## 6. 实时推送：一份逻辑，三种宿主

**核心原则：推送只当「来拉了」的信号，不携带内容。**
（LiveSync 的 `Announce / Follow changes` 就是这个模型。）
收到任何事件 → 置 `dirty` → 跑一次正常的 `syncOnce`。
这样「事件解析」「断线重连」「补漏」都不需要第二套逻辑，也天然不会因为丢事件而丢数据。

| 宿主 | 通道 | 关键约束 |
| --- | --- | --- |
| 网页版（PWA） | 首选 `_changes?feed=eventsource`——**浏览器原生 `EventSource`**，自带断线重连，且 CouchDB 官方支持 `Last-Event-ID` 续传 | ⚠️ **`EventSource` 不能带 `Authorization` 头**。要么走 `_session` cookie（需 `[cors] credentials = true` + `credentials: 'include'`），要么退回 `fetch` + `feed=continuous` 自己读流（可带自定义头） |
| 桌面版（Electron） | 同上，但**渲染进程 CSP 不放任何 https**（`electron/main.cjs` 的 `cspPolicy()`）→ HTTP 必须走主进程，新增一层窄 IPC | 主进程**不是浏览器，不需要 CORS**，这是桌面端反而更简单的地方 |
| Android（Capacitor） | **不保持后台连接**。`@capacitor/app` 的 `appStateChange` / `resume` + 一次增量 pull | 平台强制：WICG Page Lifecycle 的 Frozen 即 CPU 挂起；Apple 官方文档明说后台不再给执行时间 |

**降级链**（任何一段失败都往下走，不弹错）：
`feed=continuous` → `feed=longpoll`（最省，配 `since=now` 就是「等下一次变更」）→ `feed=normal` 每 15–30s 轮询
→ 再加 `visibilitychange` / `resume` 时立刻查一次。

后台不要用高频轮询：`heartbeat` 官方默认 60000 ms，连续/长轮询 feed 靠它保活；网络层断了要按指数退避重连。

## 7. 服务端配置与安全

- **一笔记本一 DB**。`_changes` 不跨库，安全边界也最干净。
- **CORS 只有网页端需要**：`[chttpd] enable_cors = true` + `[cors]` 段（默认所有 origin 被禁；
  3.2 起从 `[httpd]` 移到 `[chttpd]`，见 [HTTP 配置](https://docs.couchdb.org/en/stable/config/http.html)）。
  桌面端走主进程，完全不需要 CORS。
- **TLS 强制**：除 `127.0.0.1` 外拒绝明文 `http://`——与本仓「本地桥只绑 127.0.0.1」的既有纪律同源。
- **认证**：`_session` cookie 或 Basic over TLS。凭据存储沿用 GitHub token 那套（`localStorage` / `sessionStorage`，
  绝不进 `.opennote/`）。
- **主进程代理必须收窄**：只允许「配置好的 base URL + 相对路径」，**不能**做成通用 `fetch(url)`——
  否则渲染层一旦被 XSS，就能借主进程绕过 CSP 把笔记外发。这是本设计里唯一新增的安全面，值得单独 review。
- **E2EE 分期**：v1 **不做**。前提说清楚：自建单用户 + TLS，服务端能看到明文与路径。
  将来要做时按 LiveSync 的思路对 `b64` 与 `path` 加密，`_id` 仍用明文哈希
  （保留去重能力，代价是泄露「两处内容相等」这一事实）。

## 8. 分阶段与验收

| 阶段 | 内容 | 验收判据 |
| --- | --- | --- |
| **P0 前置** | 调研报告 §5.5 的五条：`deviceId`、mtime→内容哈希、冲突策略、`.opennote/` 同步边界、`applyExternalPaths` 导出 | 两台设备交替编辑同一篇 → 不丢内容、有据可查；现有测试全绿 |
| **P1 骨架** | 抽 `SyncProvider`；GitHub 降为 driver #1；CouchDB 为 driver #2。CouchDB 先只做「手动触发 + 全树列出 + 单文档读写」，不 chunk、不实时 | 两台设备手动同步同一篇能往返；**GitHub 既有用例行为不变** |
| **P2 自动** | 保存防抖 push；打开笔记本 / 回前台 / `visibilitychange` 自动 pull；冲突进列表 | 桌面改一篇 → 手机打开可见；冲突不静默覆盖 |
| **P3 实时** | `_changes` 当信号：网页 `eventsource`（或 continuous fetch）、主进程代理、移动端 resume | 在线且前台的另一端 ≤ 数秒自动出现；**断言 UI 刷新只读一次 view 投影 + 变化的文档，不触发整库重扫** |
| **P4 打磨** | 量了再优化：分块/去重、纯增量 planner（`_changes`+`_revs_diff` 不列全树）、E2EE、退避与限流 | 网络流量 ∝ 变化文件数；CouchDB 不可达时不阻塞编辑、恢复后自动补齐 |

每阶段都要有**离线降级**验收：服务器挂掉时，编辑、搜索、历史快照一律不受影响，错误只进状态栏，
`lastSeq` 不前进——这是「文件即真源」在同步失败时唯一正确的表现。

---

## 9. 不做什么、风险、未决问题

**不做**：CRDT；dejavu 式 chunk 仓库（P4 之前）；硬删除 + `_purge`；把同步元数据塞进 `.opennote/state.json`
（设计文档第 5 行的「数据变化只做加法」必须守）。

**风险**
1. **与「无后端」的产品定位冲突** —— CouchDB 是用户自己要跑的东西。必须做成**显式 opt-in 的第三种后端**，
   默认关闭；不能变成「打开笔记先要个服务器」。
2. **CORS + 凭据是网页端最容易卡住的一环**（cookie 的 SameSite、credentials、预检）。桌面端没有这个问题。
3. **`_rev` 历史膨胀**：每次保存都改文档 → revision tree 增长（CouchDB 有 `_revs_limit` 截断）。需要实测。
4. **路径改名 = `_id` 变更 = 删除 + 新增**。`titleOverrides` 等「以路径为键」的元数据会漂——已在调研 G 清单里。
5. tombstone 长期保留会让数据库与 revision 历史持续增长（它们不进 view，所以不影响投影体积，但影响存储与备份），需要清理策略（先观察量级）。

**动工前需要确认的具体项**（不要凭记忆写死）：
`_revs_limit` 的默认值与是否需要调整；`_bulk_docs` 批量推的收益与 `new_edits` 语义；
`[chttpd] max_http_request_size` 与单文档上限的关系；CouchDB 3.x 的加固清单（admin 用户、
`require_valid_user`、`[cors]` 白名单）；以及托管方案（自建 Docker / Cloudant）的可用区与费用。
