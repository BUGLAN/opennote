## 1. Syncthing

- **架构/判定**：无中心。设备互连跑 BEP（Block Exchange Protocol），协议栈最高层，下面强制 TLS 1.3，Device ID 就是 X.509 证书的 SHA-256；relay / discovery 只是打不通 NAT 时的可选基础设施，relay 只转发密文（能看到你的 IP、Device ID 与流量大小）。判定分两层：**扫描层**用 mtime/size/permission 决定要不要重算块哈希（SHA-256，块 128 KiB–16 MiB，组成 block list）；**决策层**每个文件带 version vector（每台设备一个自增 counter，key 是 Device ID 前 64 位），全局版本取「highest change version」，再用 `sequence` + `index_id` 做 delta index exchange，重连只传增量索引。文件内容按块请求，命中已有块就直接本地拷贝，未命中才走网络。
- **冲突**：双方同时改且内容真不同 → 旧 mtime 的一方被改名 `<filename>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>`；mtime 相同则由 Device ID 前 63 位较大者「输」。改 vs 删也走同一套。冲突文件生成后当普通文件传播（因为别的设备同样存在该冲突）。纯改名/大小写冲突（macOS/Windows 不区分大小写）只报错，不自动解决。
- **实时性**：watcher 有 10 s 聚合（`fsWatcherDelayS`），删除事件再延 1 min，默认还有每小时一次全量扫描兜底，官方明说「改完到出现在另一台设备之间有轻微延迟」——实际是秒级到十几秒。
- **Web/Android**：BEP 是长连接二进制协议 + 常驻进程 + 真实文件系统，**没有浏览器实现**（也非 HTTP，WASM 化没有意义）；Android 靠独立客户端 App（原生后台服务），无法作为库塞进 Capacitor WebView。
- **运维**：软件免费，但要有至少一台常开设备或依赖公共 relay；成本在升级、NAT/防火墙、冲突善后。

## 2. 网盘类（Dropbox / OneDrive / Google Drive / iCloud Drive / Nextcloud）

- **Dropbox**：判定靠服务端 `rev`（文件版本），客户端用 `files_list_folder` 的 cursor 翻页、用 `files_list_folder_longpoll` 等变更。并发写由 `WriteMode` 决定：`add` 遇到同名就 autorename；`update` 带上的 `rev` 与服务端不匹配时，官方类型文档写明「autorename 策略是给文件名追加 `conflicted copy`」，例如 `document.txt` → `document (conflicted copy).txt` 或 `document (Panda's conflicted copy).txt`。`content_hash`（SHA-256 变体）用于校验传输完整性。**可用作自研客户端后端**：官方 SDK 明确支持 Node 22+、现代浏览器与 Web Worker，浏览器走 OAuth PKCE。运维零（付费 + 配额）。
- **OneDrive**：Graph 的 `driveItem` 同时给 `eTag`（整项）与 `cTag`（仅内容变才变，文件夹不返回）；增量用 `/delta` 的 `@odata.deltaLink`（返回 `deleted` facet 表示删除）；推送用 change notification 订阅（webhook / Event Hubs / Event Grid）。冲突副本的命名策略 ⚠️ 只见于 Microsoft support 站点，本环境不可达，未验证。浏览器/Capacitor 均可用（纯 REST + OAuth）。
- **Google Drive**：官方 googleapis 客户端类型确认 `changes.getStartPageToken` → `changes.list` 返回 `newStartPageToken` / `nextPageToken`（页面 token 不过期）；推送用 `changes.watch` / `files.watch` 建 notification channel（服务端回调你的 HTTPS 端点）。冲突副本行为 ⚠️ 在 support.google.com，本环境不可达，未验证。浏览器/Capacitor 均可用。
- **iCloud Drive**：Apple 的官方语义是**保留冲突版本**——`NSFileVersion` 文档原文：「one version is chosen as the current version and any other versions are tagged as being in conflict with the original」，冲突版本交给 file presenter 尽快解决。Web/Android 不可用：没有跨平台的自研客户端文件同步 API，Android 侧完全缺席；Capacitor 方案里只能放弃 iCloud。
- **Nextcloud（重点）**：桌面客户端是自研 sync engine（`src/libsync/`），**不是** WebDAV 客户端库套壳。discovery 阶段把服务端 PROPFIND 返回的 `etag` / `fileid` 与本地 sync journal（SQLite）比对来判断谁变了；**内容判定优先用服务端 checksum header**，服务端不给 checksum 时退回 size+mtime 启发式，源码注释明说这是有意的取舍（可能漏判内容差异，但逐文件下载比对「waste 太大」）。并发写：服务端在 `If-Match` 不匹配时判定冲突，客户端把本地那份改名 `name (conflicted copy [user] yyyy-MM-dd hhmmss).ext`（冲突标记插在扩展名之前），并读取响应头 `OC-ConflictInitialBasePath` / `OC-ConflictBaseFileId` / `OC-ConflictBaseEtag` 记录冲突来源。**实时性：无服务端推送**，客户端按间隔轮询 PROPFIND，是「分钟级」而非秒级。Web/Capacitor 上自研客户端可行（WebDAV 是 HTTP，浏览器 fetch 可读写，注意 CORS），但要自己重写同步账本。运维最重：自建 PHP + 数据库 + 存储。

## 3. WebDAV 作为同步接口

- **能力**：RFC 4918 提供 `getetag`（ETag 属性）、`If-Match` 条件请求、`PROPFIND`（Depth 列目录，取 `getetag`/`getlastmodified`）、`PUT`/`MOVE`、`LOCK`。ETag 语义由服务端决定——可能是内容哈希，也可能只是版本号。
- **关键限制**：RFC 4918 §7.2「Avoiding Lost Updates」明确承认 WebDAV **无法防止 lost update**：不能强制所有客户端加锁（要兼容普通 HTTP 客户端）、不能要求服务端都支持锁、且协议无状态无法保证 LOCK→GET→PUT→UNLOCK 的顺序；结论是客户端应当用 `If-Match` 带 entity tag 自我保护。
- **轮询 vs 增量**：只靠 `PROPFIND Depth:1` 轮询时，每轮成本 ∝ 目录文件数，且要靠 ETag 变化推断差异。RFC 6578（WebDAV-Sync）补上了正确的做法：`DAV:sync-collection` REPORT + `DAV:sync-token` 属性，服务端只返回上次 token 之后的变更（`sync-level` 1 或 infinite，Depth 固定为 0）。**但这仍是被动拉取**：RFC 6578 没有任何推送机制，秒级只能靠高频轮询，实际适合分钟级。
- **Web/Android**：纯 HTTP，浏览器与 Capacitor 都能直接用（注意 CORS、每请求开销）；服务端零开发（Nginx/Nextcloud/任意 WebDAV 实现）。**运维成本**低，代价是客户端必须自己维护「上次同步基线」，否则无法区分「远端删了」与「没看见」。

## 4. Git 作为同步通道

- **判定**：Git 层的真源是 blob SHA + tree/commit hash。opennote 现实现（README 第 120–135 行所述行为）走的是 **GitHub REST API，不是 git 协议**：`.opennote/github.json` 基线给每个文件记 `remoteSha`（远端 blob sha，判「远端改没改」）与 `localHash`（本地内容 sha256，判「本地改没改」），`planPush`/`planPull` 是纯函数。**用内容哈希而非 mtime** 的理由写在源码注释里：Git 克隆、网盘同步、手工拷贝都会改 mtime 而不改内容，用 mtime 会让整库每次都被判成「改过」。
- **增量**：推送 = blob → tree（`base_tree`，未变文件复用旧 sha、不重复上传）→ commit（`parents` = 记录的分支头）→ `updateRef`，且 `force:false`；远端前进则 GitHub 返回 409/422，opennote 直接中止并提示先拉取，**绝不静默强推**。真正的 git 协议增量是另一回事：protocol v2 的 fetch 靠 `have`/`want` 协商「发送满足更新的最小数据量」，并支持 `packfile-uris` 把 packfile 放到 CDN（partial clone / blobless）。
- **并发**：git 原生是 merge，冲突以 `CONFLICT` 与冲突标记呈现，需要人合并；opennote 选了更保守的策略——两边都改的文件**逐条列出、一个字节都不动**，由用户点「用远端覆盖这些文件」。
- **实时性**：无推送，只有 pull 时才协商 → 手动/定时触发。
- **Web/Android**：isomorphic-git 能在浏览器跑（fs 层用 BrowserFS/IndexedDB 或自建适配层，HTTP 传输是可插拔插件，受目标站点 CORS 约束）；libgit2 是 C99 库，官方支持 Linux/macOS/iOS/Windows，Android 需 FFI/JNI 绑定，不便于 Capacitor 直接用。Capacitor 里用 isomorphic-git 更现实。
- **运维**：托管成本最低（GitHub/Gitea），但仓库不适合二进制大附件；语义上「谁赢」需要自己定义，Git 本身不提供单向覆盖保护。

## 5. rsync / Unison / rclone bisync

- **rsync**：定位是单向传输/镜像。核心是官方技术报告里的 rsync 算法：发送方对源文件分块算 32 位 rolling checksum + 128 位 MD4，接收方在目标内容里找「任意偏移」的匹配块，只回传不匹配的 literal 数据。它**不维护双方状态，因此没有冲突概念**（`--update` 之类的旗标只解决「别用旧的覆盖新的」这种局部问题）。无实时（需配 inotify/定时），不可用于浏览器/Android。运维低。⚠️ 官方 man page 在 samba.org（本机 403），未抓取正文。
- **Unison**：双向同步，靠每端一个 archive 文件记录「上次同步时各路径的状态」，用「当前状态 vs archive」推断哪边更新；Unix 实现用 inode + modtime 近似（可选 `fastcheck` 用 ctime，或全量内容比对）。**冲突定义**（官方手册）：两侧都更新、且当前内容不同 → 只展示给用户，不自动改；「false conflict」（两侧都动但内容相同）静默标记为已同步。支持 `repeat`/文件系统监控做连续同步，所以能做到秒级。Web/Android 完全不可用；两端必须装**同版本** Unison；官方 README 自述长期只有约 2.5 人维护。
- **rclone bisync**：保留上一轮两侧的 listing 快照做差异比较，默认比 `size,modtime`（可加 checksum）。两侧都新/都改且当前内容不同 = 冲突，默认 `--conflict-resolve none` → 双方各改名 `file.txt.conflict1` / `.conflict2` 并互相拷贝（两侧都拿到两份）；`--conflict-resolve newer` 才用 mtime 挑赢家。有 `--resync`（首次/异常恢复，会「复制而非同步」导致删除文件复活）、lock file、`--max-delete 50%` 安全阀、`--resilient/--recover` 自动恢复。**只能 cron 定时跑，无实时**；Go 二进制，浏览器/Android 不可用。

## 6. S3 兼容 + 客户端自研同步

- **怎么检测远端变化**：`ListObjectsV2` 分页列出（`max-keys` / `NextContinuationToken`），每项给 `ETag`、`Size`、`LastModified`。但 **ETag 不能当内容指纹**：AWS 文档写明只有「非 multipart 上传，且未加密或 SSE-S3」时 ETag 才是 MD5，其余（multipart、SSE-KMS）不是。要拿到真正的版本号得开 Versioning（每个对象有唯一 `versionId`，历史对象为 `null`）。工程上可靠做法只有两条：把内容哈希写进对象 metadata，或自建一份清单对象（manifest：path → hash/mtime）并优先拉它。
- **并发写**：S3 对 PUT/DELETE 提供强 read-after-write 一致性；`PutObject` 支持条件写——`If-None-Match` 保证 key 不存在才写（否则 412 `Precondition Failed`，并发竞争返回 409，官方建议重试），`If-Match` 保证 ETag 未变才覆盖。这就是可用的乐观锁 / CAS，且官方说明条件请求**不加价**。不用条件写就只能「最后写入赢」。
- **实时性**：客户端默认拿不到服务端事件——S3 Event Notifications 只能投递到 SNS/SQS/Lambda/EventBridge，要「秒级感知远端变化」必须自建一个转发服务（长连接/WebSocket 推到浏览器与手机），否则只能轮询 `ListObjectsV2`（按请求计费，PUT/LIST 与 GET 分档按每 1000 次请求计价，文件多时每轮成本 ∝ 文件数 × 分页数）。R2 等兼容实现有部分 API 未实现，需按官方兼容表逐项核对。
- **Web/Android**：都可以（SigV4 或 presigned URL + 自建签名服务；浏览器注意 CORS 与「别在前端放长期密钥」），Capacitor 同理。**运维成本**：存储本身便宜，成本在自建的清单/通知服务与轮询请求费。
