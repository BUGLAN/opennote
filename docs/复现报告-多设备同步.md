# 复现报告：多设备同步「B 卡住 / 对不上 / 慢」

> 环境：本机两个真实 Electron 客户端（`--user-data-dir` 隔离）+ 一台远程 CouchDB 同步服务
> （`http://<自建同步服务>:8787`，CouchDB 3.3.3，2 G 带宽）。联调台见 `E:\repo\fake_note`。
> 部署地址刻意不写进仓库 —— 这个仓库是公开的。
> 日期：2026-10-22。全部数字都是实测，不是估算。

## 0. 一句话结论

**「B 设备卡住」不是网络问题，是两处确定性缺陷叠加**：

1. **`/v1/tree` 默认只返回 500 条**，而客户端 `syncOnce()` **从不翻页** ——
   只要远端文档数 > ~499，新设备就**永远只能拿到前 500 篇**，剩下的**永远不会来**（不是慢，是丢掉）。
2. **每一篇笔记 = 一个独立 HTTP 请求，且严格串行** —— 500 篇 ≈ 500 次往返；
   再叠加服务端**每账号 120 请求/分钟**的限流，一次全量拉取被硬压到 **~4 分钟**，
   中途撞 429 还要按 `Retry-After` 干等 **35 秒**。

## 1. 证据一：500 条截断（决定性）

### 1.1 服务端行为

`GET /v1/tree` 的 `limit` 缺省值写死在 `server/src/routes/v1.ts:223`：

```ts
const limit = clampLimit(c.req.query("limit"), deps.config.maxFileBytes > 0 ? 500 : 500);
```

`clampLimit` 上限 2000（`v1.ts:706`）。实测同一个 555 篇的笔记本：

```
limit=(default)    status=200 files=499 truncated=true
limit=&limit=500   status=200 files=499 truncated=true
limit=&limit=2000  status=200 files=555 truncated=false
```

（499 而不是 500：500 行里有一条是 `syncinfo`，被过滤掉了。）

### 1.2 客户端行为

`src/sync/engine.ts:174`：

```ts
const tree = await provider.tree({ limit: input.maxFiles });
```

`maxFiles` 在真实接线里**从来没被传过**（`attach.ts` 不传 `maxFiles`），
所以 `limit` 是 `undefined` ⇒ 服务端默认 500 ⇒ `truncated: true`。
**而引擎拿到 `truncated` 只做一件事：`applyTruncationGuard()` 挂起删除（`engine.ts:439`）。
它不翻页、不重试、不取第二页。** `startKey` 分页能力 provider 里是有的，
但**调用方一次都没用过**（全仓只有 `providerContract.test.ts` 用过）。

### 1.3 后果（实测）

| 设备 | 拉取结果 | 磁盘 md 数 | 远端 md 数 |
| --- | --- | --- | --- |
| C（全新空目录） | `pulled: 499` | 499 | 556 |
| D（全新空目录，生产重试默认） | `pulled: 499` | 499 | 556 |

两次都是「**状态 idle、0 冲突、错误为 null**」——**它认为自己同步完成了**。
再同步一次（C 第二次）返回 `pulled: 0`，**仍然只有 499**。

> 差集实测：`missingInB: 56`，全是路径排在后面的（`more/d06/` 之后）。

### 1.4 更糟的一点：漏掉的那批**永远不会补上**

因为漏掉的 56 篇**不在第 1 页里**，下一轮同步列树还是只拿到同一批 499 条，
`planPull` 判「远端没变化」⇒ 不下载 ⇒ 永远 499。

### 1.5 同一根因还让「删除」永久失效

`truncated: true` ⇒ `applyTruncationGuard()` **挂起全部删除**。
实测：在 555 篇的笔记本上删掉一篇并同步，返回 `remoteDeleted: 1` 但
`suspendedDeletes: 56`——**这台设备的每一次同步都在挂起 56 条删除**。
也就是说在 >499 篇的笔记本上，**删除永不传播**（不是偶发，是恒定）。

## 2. 证据二：串行 + 限流 = 全量要 4 分钟

### 2.1 完全是单线程：一篇一个请求

`engine.ts` 的推送与拉取都是 `for … of` + `await`，**一次只有一请求在飞**：

```ts
for (const item of pullPlan.download) {
  const read = await provider.read(did);   // ← 串行
  await deps.writeLocal(item.path, read.bytes);
}
```

实测单请求往返（本机 → 服务器）：

```
health rtt 438ms（首包）之后稳定
GET /v1/file  p50 = 192ms, p90 = 199ms, max = 202ms
```

串行吞吐：**5.18 请求/秒**；把并发抬到 8 就变成 **27.99 请求/秒**（快 5.4 倍）。
也就是说**引擎只要肯并发，全量拉取能快 5 倍**。

### 2.2 服务端限流把上限压得更低

`ACCOUNT_REQUESTS_PER_MINUTE=120`（见服务器容器环境变量）——**每分钟 120 个请求**。
一篇笔记恰好一个请求，所以**理论上限 = 2 篇/秒**。实测稳态：

```
200 次请求 / 40 秒 = 4.99 req/s
其中 109 次 200，91 次 429
```

也就是说**接近一半的请求被限流打回**。而客户端的处理是
（`src/sync/http.ts:266-271`）：读 `Retry-After` 然后 **sleep 那么久**。
服务端返回的 `Retry-After` 实测是 **35 秒**：

```
{"retryAfter":"35","limit":"120","at":24243}
{"retryAfter":"35","limit":"120","at":24429}
```

于是 UI 上就是「**同步中…卡住 35 秒不动**」，进度条也不涨 —— 用户看到的就是「卡住」。

### 2.3 一次 500 篇的全量实测

| 设备 | 拉取篇数 | 耗时 | 平均 |
| --- | --- | --- | --- |
| C | 499 | **248 s** | 2.0 篇/秒 |
| D | 499 | **267 s** | 1.9 篇/秒 |
| A 推 400 篇 | 400 | **163 s** | 2.5 篇/秒 |

三次都是 **≈2 篇/秒**，正好压在 `120 req/min` 这个天花板上。
**2 G 带宽完全没用上** —— 瓶颈是「请求数」不是「字节数」。

> 用户真实笔记本：远端 **879** 条文档 / 本地 499 篇 md。
> 按上面的机制，第二台设备**最多只能同步到 499 篇**，其余 380 条永远不来。
> 这与他说的「A 设备同步了、B 设备堵在那里」完全吻合。

## 3. 证据三：中断一次，从头再来（进度不落账）

`syncOnce()` 中途抛异常（429 重试耗尽 / 关窗 / 断网）时，
**账本一次都不落盘** —— 唯一的落盘点在 `appSync.ts:201` 的 `onSynced`，
而 `onSynced` 只在**整轮成功**后触发。

实测：让一次拉取在 15 秒时被杀（`timeout 15`）：

```
F 设备：磁盘上已有 65 篇 md
F 设备：.opennote/ 目录不存在  ← 账本根本没写
```

再跑一次：**又从第 1 篇开始拉**。对大笔记本 + 2 篇/秒的速率，
这意味着「永远同步不完」：每轮跑到 200 篇撞限流 → 失败 → 进度清零 → 重来。

## 4. 证据四：仅仅把 limit 抬到 2000，问题就消失

同一个 555 篇笔记本、全新空目录（H 设备），**只把 `tree()` 的 limit 改成 2000，其余一行不改**：

```json
{ "elapsedMs": 261251, "pulled": 555, "ledgerFiles": 555, "status": { "phase": "idle" } }
```

**555 篇全部到达**，`truncated` 为 false ⇒ 删除闸门也解开了。
这说明根因就是「不翻页 / limit 太小」，不是任何数据损坏。

（耗时仍是 261 秒 —— 那是**另一个**问题：串行 + 限流，见第 2 节。）

## 5. 还有两处会放大「B 看起来卡住」的地方

### 5.1 拉取落盘后 UI 不刷新

`engine` 会返回 `appliedPaths`，`runner` 会调 `onApplied`，
但**`attach.ts` 从来没把 `onApplied` 接给 `createSyncSession()`** ——
`applyExternalPaths()` 在整个仓库里**没有任何一处被调用**。

实测：客户端 A 磁盘上已有 **500 篇** md，而 UI 里 `notes: 1`；
手动 `rescanWorkspace()` 之后才变成 500。

⇒ **用户看到的是「A 同步完了，B 的侧栏还是空的」** —— 文件其实已经在盘上了，
只是界面没刷新。这一条在用户眼里和「同步失败」完全一样。

### 5.2 墓碑（删除）在截断树下永远挂起

见 1.5。在 >499 篇的笔记本上，`suspendedDeletes` 恒为 50+，
删除永不传播；而 UI 上**这个数字根本不显示**（`LastSyncSummary` 里没有它），
所以用户只会觉得「我删掉的笔记又回来了」。

## 6. 修复建议（按性价比排序）

| 优先级 | 改哪 | 怎么改 |
| --- | --- | --- |
| **P0** | `src/sync/engine.ts:174` | **翻页取完整棵树**：循环 `tree({ startKey: lastDid })` 直到 `truncated === false`；或者至少把 `limit` 提到服务端上限 2000 并断言 `truncated === false`，否则**不执行删除推断**并且**在 UI 上明确报「树没取全」** |
| **P0** | `src/sync/attach.ts` | 把 `onApplied` 接上 `applyExternalPaths()`（一行），否则拉下来的东西界面看不到 |
| **P1** | `src/sync/engine.ts` 的推/拉循环 | 改成**有界并发**（8~16），实测 5.2 → 28 req/s。注意服务端限流，配合 P1 第二条 |
| **P1** | 服务端 `ACCOUNT_REQUESTS_PER_MINUTE` | 120 太低（每篇一请求）。要么抬到 600~1200，要么加**批量端点**（`/v1/files?dids=…` 一次取多条 / 一次提交多条） |
| **P2** | `appSync.ts` 的 `onSynced` | 失败也要落账（或每 N 条落一次），否则中断即清零 |
| **P2** | 状态栏 / 同步对话框 | 显示 `truncated` 与 `suspendedDeletes`，不要静默 |

### 8.8 第三轮：变更驱动 + 桌面端实时推送（同日）

第二轮的「收到变更时仍然整树比对」和「桌面端没有实时推送」这一轮都做掉了。

#### ① 变更驱动：不再整树比对

| 改哪 | 做了什么 |
| --- | --- |
| `server/src/routes/v1.ts` | `/v1/changes` 改用 `include_docs=true`，每条变更**带上内容标识**（`hash`/`ehash`）与明文模式的 `path`；并如实回 `truncated`（来自 CouchDB 的 `pending`）。 |
| `shared/contract.ts` | `changesResponseSchema` 增加可选的 `path` / `hash` / `ehash` / `truncated`。 |
| `src/sync/engine.ts` | 新增 `resolveChangedPaths()` + `buildPartialTree()`：把「变了的路径」和账本里**没变的那些**拼成一棵**与整树等价**的树，`planPull()` 一行不改。 |
| `src/sync/engine.ts` | `syncOnceIncremental()` 三条路：远端没变 ⇒ 不列树；变了但认得全 ⇒ 只按变更比对；其余 ⇒ 整树。 |

**为什么「拼树」是安全的**：账本里每条都记着上次同步时的 `remoteHash` —— 那正是「如果它没变，现在应该是什么」。
把没变的填回去，`planPull` 的判据与整树比对**逐条一致**；而删除只可能来自远端**显式**的墓碑（§6.4 规则 7），
比「我列的树里没有它」更安全。拿不准时（这一页没装完 / 认不出 did / 缺内容标识 / 变更 > 200 条 /
账本里有 `imported && remoteHash === null` 的条目）**一律退回整树**。

**实测**（556 篇的笔记本，另一台设备改了 2 篇）：**3 个请求、0 次列树、946 ms**。

### 8.9 第四轮：触发链收敛（连上时比对游标）

有了实时推送之后，`startup` 那轮「打开应用先同步一次」就变成了**无条件开销**（实测 2 个请求、约 650ms），
哪怕一个字都没变。这一轮把它换成**按需**：

> 流连上时服务端先发 `ready`，里面带着当前游标。拿它和本机记的游标比一比 ——
> **一样就什么都不做**，不一样才补一轮。

这一条同时覆盖了三种情况（它们本质上是同一件事：此刻服务端与我们记的位置是否一致）：

| 场景 | 谁发现 |
| --- | --- |
| 冷启动，离线期间别人改过 | 连上 → `ready` 游标 ≠ 本机 → 补 |
| 睡觉/断网后重连 | 看门狗重连 → `ready` 游标 ≠ 本机 → 补 |
| 什么都没发生 | 连上 → 游标相同 → **0 个请求** |

改动：

| 改哪 | 做了什么 |
| --- | --- |
| `src/sync/stream.ts` | 新增 `knownCursor`：`ready` 到达时比游标；一致走 `onUpToDate`，不一致才 `onSignal`。新增 `reconcilesCursor()`，让 controller 知道「这条路能不能替代无条件启动同步」。 |
| `src/sync/controller.ts` | `start()` 只在流**不会**比对游标时才无条件拉一轮；删掉 `resume()`（它唯一的调用方是从没接上的那段）。 |
| `src/sync/runner.ts` | 新增 `noteUpToDate()`：游标一致时只把「上次同步时间」推到现在 —— 否则跳过后状态栏会停在「尚未同步」，而我们其实刚核对过他确实是最新的。 |
| `src/sync/binding.ts` | 删掉 `subscribeResume`（**从没被接上过**：`appSync.ts` 从来没传它）。 |
| `src/sync/resume.ts` / `resume.test.ts` | **整个删除**。它是「回前台」那套的底层，而上面那条订阅从来没接上 —— 留着只会让后来者以为它在工作。 |

**净效果**：没变化时打开应用 **0 个请求**；有变化时行为不变。

**实测**：两台客户端（游标都已到 `1136-g1AAA…`）重新加载、远端无变化 ⇒ 12 秒内状态栏稳定在「已同步」，
磁盘内容一个字没变；随后把 A 的工作区和游标都清空再加载 ⇒ **10 秒内重新拉满 558 个文件**（首同步路径没坏）。

**测试**：`vitest run` 全量 **1988 passed / 0 failed**（删了 `resume` 相关的 13 条，新增游标比对 5 条 + `noteUpToDate` 1 条）。

**一处如实说的代价**：开机时如果网络就是断的，流连不上 ⇒ `ready` 不会来 ⇒ 这一轮不拉。
此时状态栏会停在「已连接」而不是「离线」（`syncUiStore.status` 还是 null）。手动同步、本地写盘推送都照常；
网络恢复后流重连、游标比对会把它补上。要让「断网开机」立刻显示离线，得把流的 phase 接到状态栏上 —— 那是下一步。

### 8.10 第五轮：429 的真正来源（限流器本身）与客户端限速

> 触发场景：用户报「A 设备同步成功、B 设备无法同步」，日志里满屏
> `远端 429，32000ms 后重试（第 1 次）`。

#### ① 根因不在带宽，在「请求个数」

429 数的是**请求**，不是字节。协议是「一篇笔记 = 一个请求」，所以一台设备首次接入
几百篇就是几百个请求。当时线上的两条限流：

| 配置 | 值 | 说明 |
| --- | --- | --- |
| `ACCOUNT_REQUESTS_PER_MINUTE` | 1200 | 上一轮从 120 提上来的 |
| `GLOBAL_REQUESTS_PER_MINUTE` | **600** | 没动过；而且**注册在账号限流之前**，所以它先触发 |

也就是说「提到 1200」这条修复**从未生效过** —— 600 那道闸门先拦下了。

#### ② 更糟：那道 600 的桶根本没按 IP 分

全局桶的键只从 `cf-connecting-ip` 取；客户端连的是 `http://<host>:8787` **直连**，
这个头不存在（`TRUSTED_PROXY_HEADERS=cf-connecting-ip` 那次修复在这条链路上是空转）。
于是键退化成 `ip:unknown` —— **全体客户端共用一个 600/分钟**（10 请求/秒）。

#### ③ 客户端策略把「偶尔 429」放大成「每 60 秒一波」

- 并发 8、RTT≈190ms ⇒ 突发 **28~43 请求/秒** ⇒ 十几秒打空桶；
- 429 之后**每个请求各自** `sleep(Retry-After)`（实测 31~32 秒 = 窗口剩余时间），
  6~8 个 worker 一起睡 ⇒ 整轮停摆、进度条不动；
- 窗口一重置，8 个 worker 同时醒来再冲 ⇒ 下一个窗口再撞；
- **整轮失败之后没有重试**（状态栏却写着「网络恢复后会自动重试」）⇒ B 永远停在那里。
- 附带放大器：批量取撞 429 时，引擎把它当「端点不存在」，**退化成逐条 GET** ——
  一次 429 变成 50 个请求。

#### ④ 改了什么

| 改哪 | 做了什么 |
| --- | --- |
| `server/src/ratelimit.ts` | 固定窗口 → **令牌桶**（`perMinute` + `burst`）。`Retry-After` 改成「再攒一个令牌」的时间（1~2 秒），不再让客户端等一整分钟。429 响应带 `x-ratelimit-limit` / `x-ratelimit-burst`。 |
| `server/src/app.ts` | 全局键：**可信头 → socket 对端地址 → unknown** 三级退化（`getConnInfo`）。直连客户端不再共用一个桶。 |
| `server/src/config.ts` | 默认值 120→**1200**、600→**6000**；新增 `ACCOUNT_BURST`（120）/ `GLOBAL_BURST`（600）。 |
| `src/sync/http.ts` | 新增 **Pacer**：客户端令牌桶（默认 12 请求/秒、突发 24）。429 是**全局冷却**：所有 worker 一起停到 `Retry-After`，恢复时**速率减半**、成功后慢慢加回。日志带上「限额」与「哪条请求」。 |
| `src/sync/engine.ts` | 默认并发 8→**4**（速率由 Pacer 控制）；`readMany` 只有 **404/413** 才退化成逐条，**429/5xx/网络一律如实抛**。 |
| `src/sync/runner.ts` | 失败后**自动重试**（5s 起、翻倍、2 分钟封顶；只对 `network`/`server`）。`dispose` 取消。 |
| `docker-compose.yml` / `.env.example` | 透传 burst 配置，默认值同步。 |

#### ⑤ 实测（同一台服务器、同一个 556 篇笔记本）

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 429 的 `Retry-After` | 31~32 秒 | **1 秒** |
| 429 的 `x-ratelimit-*` | 无 | `limit=1200` / `burst=120` |
| 推送 400 篇 | 163 s（2.5 篇/秒，全程撞 429） | **300 篇 / 24.4 s（12.3 请求/秒，0 次 429）** |
| 新设备拉 558 篇 | — | **6.9 s / 12 个请求 / 0 次 429** |
| 失败之后 | 停住，等人点 | 5s / 10s / 20s… 自动重试 |

  ratelimit 重写 14 条、批量接口遇 429 不退化 1 条）。

### 8.11 第六轮：每次打开应用都全量同步（尾斜杠事故）

> 现象：**每次**打开应用都是「同步中… 文件 0/880」，跑 2~3 分钟；远端文档被反复改写。

#### 根因：一个尾斜杠让账本「每次都被判成换了一台服务器」

| 位置 | 值 |
| --- | --- |
| 工作区配置（localStorage） | `http://45.202.241.98:8787/` ← **带斜杠** |
| 账本 `.opennote/sync.json` | `http://45.202.241.98:8787` ← `createSyncLedger` 会剥掉 |

`loadLedger()` 当时是**逐字**比较这两个字符串 ⇒ 不相等 ⇒ 判成「换了笔记本/服务器」
⇒ **丢弃账本、用一份空的重新开始** ⇒ `planPush` 把 880 个文件全判成「新增」
⇒ 全量重推（2~3 分钟）。推完写回的账本又是（被剥过的）无斜杠形式 —— 于是下次打开
再来一遍，**无限循环**。

#### 证据

- localStorage 的 `000095.log` 里 `"baseUrl":"http://45.202.241.98:8787/"` × 6；账本里是无斜杠的。
- 远端 880 篇的 `_rev` 代数分布：`4: 341, 6: 434, 12: 32, 14: 73` —— 每一轮全量推送都给所有文档 +1~2 代。
- 用**真实账本 + 真实目录**跑一遍计划（不联网）：修复前 `pushAdded: 880`，修复后 `0 / 0 / 0`。

#### 修复

| 改哪 | 做了什么 |
| --- | --- |
| `src/data/workspaces.ts` | `normalizeSyncConfig()` 去掉 baseUrl 的**尾部斜杠**（地址是同一个东西，不该在 UI / 账本 / URL 拼接三处各有一套等价判定） |
| `src/sync/state.ts` | 新增 `stripBaseUrlSlashes()` 与 `isSameRemote()`：账本身份判定**规范化后**比较（子路径保留） |
| `src/sync/appSync.ts` | `loadLedger()` 改用 `isSameRemote()`；**丢账本时留一行日志**（`为什么又全量了` 的唯一线索） |

#### 测试

- `state.test.ts` +3（带不带斜杠是同一个、换笔记本/模式不是、子路径要保留）。
- `workspaces.sync.test.ts` +1（规范化会剥斜杠、且剥完仍然 `enabled`）。
- 全量：**2052 passed / 0 failed**。
