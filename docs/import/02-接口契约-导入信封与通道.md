## 1. 分层总览

本契约把「导入」拆成三层。**任何新客户端只允许产出 L0、只允许经由 L1 之一送达**，不得自己发明写盘逻辑。

```
L3  客户端       浏览器插件 · CLI · AI Skill · MCP Server · 分享面板 · 快捷指令
                        ↓ 都产出同一种东西
L0  导入信封     opennote.import/v1 —— 与传输无关的数据契约
                        ↓ 通过某种介质送达
L1  传输通道     本地桥(HTTP 127.0.0.1) · 命令行 · MCP(stdio) · URL scheme
                 · 页面内桥(postMessage) · 收件箱目录(.opennote/inbox/)
                        ↓ 交给应用
L2  应用内接收   落点决策 · 去重与冲突 · 直接入库或进收件箱 · 提示与撤销 · 重扫刷新
```

### 1.1 各层职责边界

| 层 | 负责 | **明确不负责** |
| --- | --- | --- |
| **L0 信封** | 定义一次导入的完整语义：标题、正文、来源信息、落点、冲突策略、标签、附件、幂等键、客户端标识；定义字段的类型/必填/上限/默认值 | 不关心怎么送达；不定义重试与限流；不定义 UI；不定义存储格式（存储格式见第 3 章） |
| **L1 通道** | 把信封从客户端搬到「能落盘的那个进程」：鉴权、传输编码、大小限制、失败与离线语义、平台可用性 | **不做落点决策**（不解析标题、不生成文件名、不选目录）；不做去重判断；不改写信封内容 |
| **L2 应用内接收** | 校验信封 → 幂等与冲突判定 → 生成确定性的相对路径 → 写入 `.md` 与 `assets/` → 通知界面刷新 → 提供「撤销」入口 | 不定义信封字段；不实现传输；不长期保存未经确认的外部内容（收件箱条目除外） |

### 1.2 三条贯穿全文的硬约束

1. **标题只在正文 H1 里**。`deriveTitle()`（`src/lib/utils.ts:61`）取正文首个标题行，`splitFrontMatter()`（`:54`）把 front-matter 当元数据跳过；**写 `title:` 不会改变笔记标题**。因此「导入标题」的唯一正确写法是正文第一行 `# {title}`（第 3 章给出精确拼装顺序）。
2. **front-matter 里除 `tags:` 外全部是惰性的**。`deriveTags()`（`src/lib/utils.ts:132`）只认识 `tags: [a, b]` 与 `tags:` 块列表两种写法；`source:` / `author:` / `captured_at:` / `opennote_import_id:` 都会被解析器忽略。这带来两个后果：一是来源信息可以安全地写进 front-matter（Obsidian 兼容、纯文本承诺不破）；二是**任何依赖 front-matter 键去驱动应用行为的设计都是错的**——去重索引必须自己维护（见 4.3）。
3. **落盘是「外部写入」，界面不会自动知道**。主进程已有工作区监听管道（`opennote:fs:watchWorkspace` / 频道 `opennote:fs:workspace-changed`，见第 8 章），但该管道**显式跳过 `.opennote/**`**，且它是「去抖广播」而非「本次导入成功回执」。所以：桥必须自己返回确定性的成功响应（`API-02`），收件箱必须自己设计「投递即重扫」（5.8.4）。

### 1.3 一次导入的端到端时序（以本地桥为例）

```
插件/AI               本地桥(主进程)                        渲染层
  │  POST /v1/import       │                                  │
  │───────────────────────>│ 1 校验 Host / Origin / token      │
  │                        │ 2 解析信封 → 字段校验             │
  │                        │ 3 落点计算（sanitizeName/uniquePath）│
  │                        │ 4 写 assets/ → 写 .md（原子写）    │
  │                        │ 5 写「最近导入」记录              │
  │  201 {path, importId}  │                                  │
  │<───────────────────────│ 6 广播 opennote:import:notice ───>│ 7 若目标笔记已打开
  │                        │    （或复用 workspace-changed）   │     则在编辑器中重新载入
  │                        │                                  │ 8 toast「已从网页剪藏：xxx · 撤销」
```

关键点：**第 5 步之前不能返回**。响应里的 `path` 必须来自实际写入后的路径分配结果，不能是「预期路径」。

## 2. L0 导入信封 `opennote.import/v1` 字段规范

字段名逐字沿用 00 号简报 6.1 节，**不得改名、不得新增必填字段**（新增一律是可选的、可忽略的）。

### 2.1 完整示例

```json
{
  "spec": "opennote.import/v1",
  "importId": "0f1d6d9a-6c2f-4a7e-9d31-5b0f2a7c1e88",
  "title": "写给工程师的本地优先笔记",
  "body": "在浏览器里剪下的一段话。\n\n## 为什么\n\n……",
  "source": {
    "url": "https://example.com/posts/local-first",
    "title": "Local-first notes for engineers",
    "site": "example.com",
    "author": "张三",
    "publishedAt": "2026-08-14T09:30:00+08:00",
    "capturedAt": "2026-09-29T21:04:11+08:00",
    "selection": true
  },
  "target": { "folder": "剪藏/技术", "notePath": null },
  "conflict": "new",
  "tags": ["剪藏", "本地优先"],
  "assets": [
    { "name": "diagram.png", "mime": "image/png", "dataBase64": "iVBORw0KGgoAAAANSUhEUg…" }
  ],
  "client": { "name": "chrome-extension", "version": "0.1.4" }
}
```

### 2.2 顶层字段

| 字段 | 类型 | 必填 | 默认 | 约束 | 示例 |
| --- | --- | --- | --- | --- | --- |
| `spec` | string | 是 | — | 必须精确等于 `opennote.import/v1`（大小写敏感、无空白容忍）；不匹配 → `IMP-4002` | `"opennote.import/v1"` |
| `importId` | string | 是 | — | 幂等键。UUIDv4/UUIDv7 优先；允许 8–128 字符的 `[A-Za-z0-9_-]`（CLI/插件可用内容哈希，见 4.2） | `"0f1d6d9a-…-1e88"` |
| `title` | string | 是 | — | 1–200 字符（**UTF-16 码元计数**）；超长截断到 200 并返回 `warning`；空串 → `IMP-4003` | `"写给工程师的本地优先笔记"` |
| `body` | string | 是（与 `bodyFile` 二选一） | — | Markdown。UTF-8 解码后 ≤ 8 MiB（`IMP-4004`）；允许为空串但**不得缺字段**（缺字段 → `IMP-4003`）。`body: ""` 的行为见 2.6。通道级扩展字段 `bodyFile`（工作区相对路径，`body` 置 `null`）见 5.8.2；**本地桥与 CLI 必须同时支持内联与 file 两种形态**（00 号 §6.8③） | `"在浏览器里剪下的一段话。…"` |
| `source` | object | 是 | — | 见 2.3。AI/CLI 场景允许 `url: null`，但**必须带 `capturedAt`** | `{ … }` |
| `target` | object | 否 | `{ "folder": null, "notePath": null }` | 见 2.4 | `{ "folder": "剪藏" }` |
| `conflict` | string 枚举 | 否 | `"new"` | `new` \| `append` \| `skip` \| `overwrite`。`overwrite` **仅桌面版本地桥接受**（00 号 §6.7①）：浏览器扩展 / CLI / Skill / MCP / `opennote://` / 收件箱目录**一律拒绝或降级**；且需设置里显式开启（默认关闭）＋ 写入前留下可回退前像（3.3.3、`IMP-W008`）。四条件任一不满足 → 降级为 `new` 并回 `IMP-4011`。**另有应用侧设置优先于本字段：`UiSettings.importConflict === "inbox"` 且通道非 `in-app` 时，本次导入强制 `pending`（进收件箱），跳过判定链第 2–6 步；第 1 步同 `importId` 幂等仍优先**（00 号 §6.14㉕） | `"new"` |
| `tags` | string[] | 否 | `[]` | ≤ 32 个，**客户端必须在写入前自行过滤**（应用侧没有可复用的公开清洗函数，00 号 §6.11③）：①去掉逗号 `,`——`deriveTags()` 按逗号拆 `tags: [a,b]`，含逗号必被拆成两个标签（静默漂移）；②去掉换行与 `[` `]`；③每个 ≤ 32 字符；④丢弃纯数字；⑤字符集按 `[\p{L}\p{N}_\-/]` 收紧。重复项去重。应用侧 `normalizeTag()`（`src/lib/utils.ts:163`，**模块私有、未导出**）只做：去行首 `#`、去掉所有单/双引号、trim、拒纯数字、截断 32 字符——**它没有任何字符白名单过滤**；`[\p{L}\p{N}_\-/]` 属于**行内 `#tag` 扫描正则**（`src/lib/utils.ts:153`），不是 `normalizeTag()` 的能力。**不得**在文档或实现注释里声称「已由 `normalizeTag()` 清洗」 | `["剪藏", "本地优先"]` |
| `assets` | object[] | 否 | `[]` | ≤ 32 个；单件解码后 ≤ 8 MiB；合计解码后 ≤ 24 MiB；MIME 限白名单（2.5） | `[{ … }]` |
| `client` | object | 否 | `{ "name": "manual", "version": "" }` | `name` ∈ `chrome-extension` \| `cli` \| `mcp` \| `share-target` \| `manual` \| `other`；未知值归一到 `other`（不报错，向后兼容）：**只用于日志与 UI 展示，不得作为鉴权或授权依据** | `{ "name": "cli", "version": "0.3.0" }` |

**未知字段一律忽略**（不报错，不写入文件），以保证 v1 客户端在 v2 服务端上仍可工作。`spec` 是唯一允许拒绝请求的版本字段，见第 9 章。

### 2.3 `source` 对象（来源信息）

| 字段 | 类型 | 必填 | 默认 | 约束 |
| --- | --- | --- | --- | --- |
| `url` | string \| null | 是 | — | `http:` / `https:` 之一；其它协议（`javascript:`、`data:`、`file:`）→ `IMP-4003`。仅用于**存储与展示**，应用绝不对它发起请求（00 号简报 6.6「不做服务端抓取」） |
| `title` | string \| null | 否 | `null` | 网页标题原样保留，≤ 300 字符 |
| `site` | string \| null | 否 | `null` | 站点名或域名，≤ 120 字符 |
| `author` | string \| null | 否 | `null` | 作者，≤ 120 字符 |
| `publishedAt` | string \| null | 否 | `null` | ISO 8601，含时区偏移优先；无法解析 → 写 `null` 并返回 `warning`（**不失败**，网页发布时间经常取不到） |
| `capturedAt` | string | 是 | — | ISO 8601，**必须含时区**（`Z` 或 `±HH:MM`）。缺失或不可解析 → `IMP-4003`。这是「剪藏时间」，与文件 `mtime` 无关 |
| `selection` | boolean | 否 | `false` | `true` = 用户选中的片段，`false`/缺省 = 整页正文。仅供 UI 与统计 |

时间格式统一为 **RFC 3339 / ISO 8601**：`2026-09-29T21:04:11+08:00`。写入 front-matter 时保留原字符串（不做时区换算），因为「用户当时的当地时间」比 UTC 规范化更有信息量。

### 2.4 `target` 对象（落点）

| 字段 | 类型 | 必填 | 默认 | 约束 |
| --- | --- | --- | --- | --- |
| `folder` | string \| null | 否 | `null` | 工作区相对目录，POSIX 风格（`剪藏/技术`）。`null` 或 `""` = 工作区根目录。校验：拒绝绝对路径与盘符、拒绝 `\` 段、拒绝 `..` 段、拒绝 `\0`、拒绝含 `:` 的段（沿用 `assertSafeRelative()`，`src/fs/paths.ts:21`；桌面 IPC 侧另拒 ADS，见 7.3）；每段经 `sanitizeName()`（`:79`）清洗；层级 ≤ 10；单段 ≤ 80 字。违规 → `IMP-4008` |
| `notePath` | string \| null | 否 | `null` | 仅当 `conflict` 为 `append` / `overwrite` 时有效：指向一个**已存在**的笔记（工作区相对路径，含 `.md`）。不存在 → `IMP-4009`。`conflict: "new"` 时该字段被忽略并返回 `warning` |

**`target.folder` 不存在时的默认行为是创建**（L2 负责，逐段 `mkdir`），不是失败。这一点与「落点目录不存在」的错误码 `IMP-4009` 不冲突：`IMP-4009` 只针对 `notePath` 指向的文件不存在，或目录创建被拒（权限/只读）。

### 2.5 `assets[]` 元素

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `name` | string | 是 | 原始文件名（含扩展名）。经 `sanitizeName()` 清洗；扩展名必须落在 MIME 白名单对应集合内。最终落盘名**不是** `name`，见 3.4 |
| `mime` | string | 是 | 白名单：`image/png`、`image/jpeg`、`image/gif`、`image/webp`、`image/avif`、`image/svg+xml`（**SVG 需净化，见 7.2**）、`image/bmp`。其它 → `IMP-4012` |
| `dataBase64` | string | 是（与 `file` 二选一） | 标准 base64（允许 `+/=`；允许含换行）。解码后 ≤ 8 MiB；解码失败 → `IMP-4012` |
| `file` | string | 通道级扩展（与 `dataBase64` 二选一） | 附件外置形态：工具**可解析的相对路径**（收件箱里是相对条目目录的路径，如 `assets/3f9a1c02-diagram.png`；本地桥与 CLI 里是相对工作区的路径）。读取后走 3.4 的同一套落盘流程。**桥与 CLI 必须同时支持两种形态**（00 号 §6.8③）；路径必须经 `assertSafeRelative()`，越界 → `IMP-4012` |

### 2.6 边界行为的明确定义

| 情形 | 规定行为 |
| --- | --- |
| `body: ""` 且 `title` 非空 | **允许**。写入文件为 `# {title}\n`（一个 H1 行 + 末尾换行）。响应带 `warnings[]` 项 `{ "code": "IMP-W001", "message": "正文为空，只写入了标题。" }`（文案以 6.2 的 `IMP-W001` 为准，本文不另写一套）。理由：AI 场景常见「先占位、稍后填」，报错会打断工作流 |
| `body: ""` 且 `title: ""` | 拒绝，`IMP-4003`。理由是落盘会得到一个没有标题、没有正文、文件名退化成时间戳的空文件 |
| `title` 与 `body` 首个标题不一致 | **以 `title` 为准**：正文里的原有 H1 被降级为 H2（`# ` → `## `，仅当它是正文第一行标题时）。原因见 3.2 |
| `body` 过长（> 8 MiB） | 拒绝 `IMP-4004`，不截断。截断用户正文属于静默数据损坏 |
| `assets` 单件过大 | 拒绝 `IMP-4012`，并给出**是哪一件**（`detail.assetIndex`）|
| 整个请求体过大（> 16 MiB） | 在解析 JSON **之前**按 `Content-Length` 拒绝 `IMP-4005`，并 `Connection: close`。不读完整 body，避免内存放大 |
| 请求体为空 / 非 JSON | `IMP-4001` |
| 同一 `importId` 重复投递 | **不是错误**：返回 200 + `deduped: true` + 首次的 `path`（4.4） |
| `tags` 里有纯数字 | 静默丢弃（`normalizeTag()` 的既有规则），返回 `warning` |
| 附件被正文引用但未声明 | 正文里的 `./assets/xxx.png` 若不在 `assets[]` 里，**保留原样**，但返回 `warning: IMP-W002 有未声明的本地附件引用`。不做静默删除（可能是用户自己写好的相对链接） |
| `assets[]` 声明了但正文没引用 | 照常写入 `assets/`（用户可能稍后引用），响应的 `assets[]` 里列出实际路径 |

### 2.7 载荷上限汇总

| 维度 | 上限 | 错误码 |
| --- | --- | --- |
| HTTP 请求体（本地桥） | 16 MiB | `IMP-4005` |
| `body`（UTF-8 字节） | 8 MiB | `IMP-4004` |
| 单个附件（base64 解码后） | 8 MiB | `IMP-4012` |
| 附件合计（base64 解码后） | 24 MiB | `IMP-4013` |
| 附件数量 | 32 | `IMP-4013` |
| `title` 长度 | 200 字符 | 截断 + `warning` |
| `tags` 数量 | 32 | 截断 + `warning` |
| 收件箱单条目（序列化后） | 32 MiB（沿用 `MAX_ENTRY_BYTES`，`src/lib/import.ts:37` 同量级） | `IMP-4013` |

上限的设计依据：现有导入路径的 `MAX_ENTRY_BYTES = 32 * 1024 * 1024`（`src/lib/import.ts:37`），OPFS 导入的 `maxBytes` 默认 `64 * 1024 * 1024`（`src/fs/opfs.ts:56`）。导入信封的上限取更保守的值，因为桥是一次性内存解析（JSON + base64 双份驻留）。

## 3. 信封 → 文件的确定性映射算法

本章是契约的核心：**给定同一个信封与同一个工作区快照，任何实现都必须得到同一个文件路径与同一份字节**。伪代码中的函数名沿用现有代码的符号名。

### 3.0 总流程（伪代码）

```text
function commitImport(env, workspace) -> ImportResult:
    # 阶段 A：校验（纯函数，无副作用）
    V = validateEnvelope(env)                       # 第 2 章规则；失败抛 IMP-4xxx
    title   = V.title
    folder  = normalizeFolder(V.target.folder)      # assertSafeRelative + sanitizeName 逐段
    assets  = V.assets                              # 已解码为 Uint8Array

    # 阶段 B：幂等（第 4 章）
    hit = lookupImportIndex(V.importId) ?? lookupDedupeIndex(V)
    if hit and hit.pathExists:  return ImportResult(deduped=true, path=hit.path)

    # 阶段 C：落点分配（唯一决定文件名的地方）
    requested = joinPath(folder, sanitizeName(title, "未命名") + ".md")
    if V.conflict == "append" or V.conflict == "overwrite":
        requested = V.target.notePath ?? appendTargetByConflictIndex(V)   # 见 3.3.3
    taken = Set(keys(libraryStore.notes))           # 内存中的相对路径集合（src/lib/import.ts:50 同源）
    path  = resolveAvailablePath(backend, requested, taken)   # 逐次 exists() 探测（src/data/library.ts:450）

    # 阶段 C2：前像（00 号 §6.7④ —— append / overwrite 改变既有内容，必须可回退）
    revertible = true
    preimage   = null
    if op in ("append", "overwrite"):                # op 由 conflict + 判定链决定
        preimage = recordPreimage(path)              # 逐字节副本 → .opennote/import-preimages/
        if preimage == null:
            revertible = false
            if op == "overwrite": return downgradeToNew("IMP-4011")   # overwrite 的必要条件之一
            warn("IMP-W008")                         # append 仍可入库，但撤销降级

    # 阶段 D：先附件、后正文（保证正文里的相对链接指向真实存在的文件）
    mkdirAll(folder)
    assetsDir = joinPath(parentPath(path), ASSETS_DIR)         # 与笔记同目录（src/lib/import.ts:91）
    writtenAssets = []
    for a in assets:
        final = joinPath(assetsDir, contentHash8(a.bytes) + "-" + sanitizeName(a.name, "attachment"))
        final = resolveAvailablePath(backend, final, taken)    # 同批次内不覆盖
        backend.writeBytes(final, a.bytes)                     # 原子写
        writtenAssets.push(final)

    # 阶段 E：拼装正文并原子写入
    text = renderMarkdown(V, title, assets, writtenAssets)     # 见 3.2 / 3.5
    backend.writeText(path, text)                              # 桌面端已是 tmp+rename 原子写

    # 阶段 F：记录（幂等与最近导入）
    importIndex.put(V.importId, { path, sourceHash, contentHash, at: now() })
    recentImports.append({ importId: V.importId, path, title, at: now(), client: V.client })

    # 阶段 G：通知界面（第 8 章）
    emitImportNotice({ importId: V.importId, path, action: "created", conflict: V.conflict })

    return ImportResult(status="created", importId=V.importId, path=path, assets=writtenAssets)
```

### 3.1 边界一：标题 → 文件名

```text
requested = joinPath(folder, sanitizeName(title, "未命名") + ".md")
```

- `sanitizeName()`（`src/fs/paths.ts:79`）：把 `\ / : * ? " < > |` 与控制字符替换成空格、折叠空白、去掉首尾的 `.` 与空白、**截断到 80 字**，全空时用 fallback。CJK 保持可读（不做音译、不做 pinyin）。
- 标题为 200 字符时，文件名只取清洗后的前 80 字符——**文件名与 H1 允许不一致**，这是既有行为（`deriveTitle()` 的上限是 90，`src/lib/utils.ts:51`）。
- 清洗后为空（例如标题全是 `***`）→ 文件名用 `未命名.md`。
- 扩展名固定 `.md`（小写）。
- **不使用** `capturedAt` 做文件名前缀。理由：用户要的是「一眼能认出这篇是什么」，而不是「按时间排序」；时间排序由文件的 `mtime` 与 `updatedAt` 提供。

### 3.2 边界二：H1 与 front-matter 的拼装顺序

**字节级模板**（`\n` = LF，文件末尾恰好一个换行）：

```text
---
source: <url 或 省略该行>
source_title: <网页标题 或 省略该行>
source_site: <站点名 或 省略该行>
author: <作者 或 省略该行>
published_at: <ISO8601 或 省略该行>
captured_at: <ISO8601>
tags: [<t1>, <t2>]
opennote_import_id: <importId>
---

# <title>

<body>

```

规则：

1. **`---` 必须在文件最开头**（允许 BOM，但本契约**不写 BOM**）。`splitFrontMatter()`（`src/lib/utils.ts:54`）的正则是 `^\uFEFF?---\r?\n([\s\S]*?)\r?\n---[ \t]*(?:\r?\n|$)`——所以 `---` 之前**不能有任何空行、注释或正文**，否则整段 front-matter 会被当成正文，`deriveTags()` 拿不到标签。
2. front-matter 与正文之间恰好一个空行。`splitFrontMatter()` 会把闭合 `---` 之后的换行一起吃掉，因此正文第一个字符就是 `#`。
3. 值为 `null` 的键**整行省略**（不写 `source: null`）。写空值会让 front-matter 里出现无意义行，且 `deriveTags()` 的正则对空值不友好。
4. 键的顺序固定为第 00 号简报 6.2 节的顺序（`source` → `source_title` → `source_site` → `author` → `published_at` → `captured_at` → `tags` → `opennote_import_id`），以保证同一信封产出的文件字节完全一致（便于测试做全字节断言）。
5. **只允许这 8 个键**（00 号简报 6.2「仅使用下列键」）。`source_site` / `published_at` 是 v2 新增（采纳 02 号异议 2，00 号 §6.2 已更新），使站点名与发布时间能**随文件迁移**（换机器、在 Obsidian 里打开都不丢）。`source.selection` 仍不落盘——它只影响判定与 UI 标签（4.1 第 3/4 步）。
6. **正文首行必须是 `# {title}`**。因为 `deriveTitle()`（`src/lib/utils.ts:61`）取正文（去 front-matter 后）第一个标题行，写 `title:` 键**完全无效**。
7. 若客户端提交的 `body` 第一行本身已是 H1（`# 别的标题`），把它降级为 `## 别的标题`，避免同一文件出现两个 H1。只在「第一个非空行是 H1」时降级一次，不做全局改写。
8. YAML 标量转义：
   ```text
   function yamlScalar(v):
       if v == "": return '""'
       if /^[A-Za-z0-9\u4e00-\u9fff][A-Za-z0-9\u4e00-\u9fff ._\/:@+-]*$/.test(v) and not endswith(" ") and not contains(" #"):
           return v                                  # 裸标量：中文、URL、普通句子都走这里
       return '"' + v.replace(/\\/g, "\\\\").replace(/"/g, '\\"') + '"'
   ```
   `deriveTags()` 的 `normalizeTag()` 会 `replace(/["']/g, "")` 去掉引号（`src/lib/utils.ts:164`），所以给标签加引号是安全的。
9. 标签数组：`tags: [a, b]`（行内数组，`deriveTags()` 的第一种识别形式，`src/lib/utils.ts:136`）。规则：
   - **客户端必须已按 2.2 的过滤要求清掉 `,`**（00 号 §6.11③）；服务端作为纵深防御再检一次：标签含 `,` / 换行 / `[` `]` → 丢弃并 `warning`（`IMP-W007`），**不尝试替用户改标签**；
   - 标签若匹配 `/^[\p{L}\p{N}_\-\/]+$/u` 则裸写，否则双引号包裹；
   - 全部标签都被丢弃时省略整个 `tags:` 行。
   - **不要用块列表**（`tags:\n  - a`）：两种写法等价，但行内数组占一行，字节更稳定。

### 3.3 边界三：路径分配与 `uniquePath` 序号语义

#### 3.3.1 `uniquePath` 的精确语义

```ts
// src/fs/paths.ts:89
uniquePath(candidate, taken):
    if not taken.has(candidate): return candidate
    dir = parentPath(candidate); ext = extName(candidate); base = baseName(stripExtension(candidate))
    n = 2
    while taken.has(joinPath(dir, `${base} ${n}${ext}`)): n += 1
    return joinPath(dir, `${base} ${n}${ext}`)
```

- 序号从 **2** 开始，格式为**一个半角空格 + 数字**：`标题.md` → `标题 2.md` → `标题 3.md`。
- 序号加在**扩展名之前、原文件名之后**，目录不变。
- 计数基准是**原始 candidate**，不是上一次的结果。
- `taken` 是大小写敏感的 `Set`，因此 `uniquePath` 单独使用无法处理大小写不敏感的磁盘（D30 的成因，`docs/缺陷审计报告-2026-09-29.md`）。

#### 3.3.2 与磁盘探测的组合：`resolveAvailablePath`

`resolveAvailablePath()`（`src/data/library.ts:450`）把两者合起来：

```ts
candidate = requested; guard = 0
while (await backend.exists(candidate)):      # 磁盘真实探测
    taken.add(candidate)
    candidate = uniquePath(requested, taken)  # 内存集合去重
    guard += 1; if guard > 500: break         # 上限保护
return candidate
```

契约要求：

- **导入必须走 `resolveAvailablePath`，不得只用 `uniquePath`。** 理由：`taken` 只来自内存（`Object.keys(libraryStore.get().notes)`，`src/lib/import.ts:50`），而「上次扫描之后由外部程序创建的同名文件」不在内存里——这正是 D03 的机制。未提交的工作区改动已经在 `importIntoWorkspace()` 里改用了 `resolveAvailablePath`（`src/lib/import.ts:84`，**未提交状态**），桥与收件箱必须复用同一函数，不要各写一份。
- `taken` 必须在**一次导入内部跨路径共享**：写附件与写正文用同一个 `taken`，否则 `assets/a.png` 与 `assets/a 2.png` 会在并发批次里互相覆盖。
- 大小写不敏感磁盘上，`exists()` 会命中大小写变体 → 自动退化成 ` 2`。这是可接受的行为（不覆盖优先于名字好看），与 D30 的修复方向一致。
- 序号上限：`guard > 500` 时放弃并返回 `IMP-4014`（内部错误），不允许无界循环。

#### 3.3.3 `append` / `overwrite` 的目标解析顺序

```text
1. env.target.notePath 非空 → 直接使用（必须 exists()，否则 IMP-4009）
2. 否则：按「来源索引」找同一 URL 的既有笔记      # 00 号 §6.8⑦：url 决定 new/append/收件箱
   importIndex.findBySourceUrl(source.url) → path
   （bodyHash 不参与目标解析；它只用于「判为重复」与异常提示，见 4.1）
3. 都没有 → 退化为 conflict: "new"（分配新文件），响应 warning: IMP-W003
```

`append` 的写入形态（选区二次剪藏；00 号 §6.7②/§6.8⑦：整页二次剪藏默认进收件箱、不静默追加）：

```text
existing = backend.readText(path)                              # ① 读前像内容
preimage = recordPreimage(path, existing)                      # ② 落前像（00 号 §6.7④）
separator = "\n\n---\n\n"
stamp = "> 再次剪藏于 " + formatStamp(capturedAt) + "\n"       # src/fs/paths.ts:109 的时间格式
next = normalizeEol(existing).trimEnd() + separator + stamp + "\n" + renderBody(V)
backend.writeText(path, next)                                  # ③ 原子写
```

`recordPreimage(path, existing)` 的规定动作（前像必须**逐字节**，不能用「读回来再拼」的近似）：

```text
preimagePath = joinPath(META_DIR, "import-preimages", `<importId>.md`)   # META_DIR = ".opennote"（src/fs/paths.ts:78，截至撰写时）
backend.mkdir(parentDir) ; backend.writeBytes(preimagePath, bytes(existing))   # 原字节
importLog.append({ importId, op, path, preimagePath, preimageBytes: len(existing),
                   preimageSha256: sha256(bytes(existing)), revertible: true, at: now() })
```

`recordPreimage` 返回 `null` 的两种情形：读原文件失败；或写前像/写日志失败（磁盘满、只读、`.opennote/` 被删且无法重建）。此时按操作类型分流（见下方 `overwrite` 的第 4 条）。

- 追加是**纯文本拼接**，不改动已有内容。这是「不许静默改用户文件」的最低限度满足：追加是加法，不是替换。
- 追加前必须 `stat()` 比对 `knownStats`（D08 的机制，`src/data/library.ts:504`）：若磁盘版本与内存版本不一致（用户正在编辑、外部改了），**放弃追加**，改为分配新文件并在响应里 `status: "created"`、`warning: IMP-W004 目标笔记有外部改动，已另存为新文件`。
- **`append` 也必须留前像**（00 号 §6.7④）。理由：历史快照有约 **3 分钟**节流（`src/data/library.ts:98-99`，截至撰写时），两次连续追加之间**不保证**产生新快照——只靠快照就无法逐字节回退第二次追加。前像不可得时 `append` 仍可入库，但回执必须写 `revertible: false` 并回 `IMP-W008`，UI 的撤销按钮降级为「移入回收站 / 查看历史快照」并**如实说明**。
- `overwrite` 是**唯一会替换既有正文**的策略，四条件**同时**满足才生效（00 号 §6.7①）：
  1. 客户端**显式**传 `conflict: "overwrite"`（永不作为默认值）；
  2. 通道是**桌面版本地桥**（CLI / MCP / Skill / 扩展 / `opennote://` / 收件箱一律拒绝或降级）；
  3. 用户已在设置里**显式开启**该开关（默认关闭，属进阶项）；
  4. **写入前留下可回退前像**（`recordPreimage` 返回非 `null`）。
  任一不满足 → **降级为 `new`** 并回 `IMP-4011`，既不静默替换、也不静默失败。第 4 条不满足时**不得**用「写一份 `.opennote/history/` 快照」顶替——快照可能被节流吃掉，而 `overwrite` 是破坏性操作，必须逐字节可回退。
- 撤销语义（`opennote:import:undo`）：有前像 → 用前像覆盖回退（`revertible: true`）；无前像 → 只能「移入回收站」或提示用户去看历史快照，UI 文案必须说明是**降级撤销**。

#### 3.3.4 前像日志 `.opennote/import-log.json`

前像本体是**逐字节副本**，放在 **`.opennote/import-preimages/<importId>.md`**；日志本身只存元数据（不塞正文，避免单文件膨胀与半写风险）：

> **为什么前像不放在 `.opennote/history/` 之下**（00 号 §6.10① 裁定）：`history/` 是**版本快照**域，有既成的保留策略与导出语义（自动快照上限 60 份；导出整库 zip 的 `includeHistory` 选项可整体排除）。把撤销依赖的前像放进去，等于把「可恢复性」交给另一套无关的保留策略——快照被清理或不被导出时，撤销会静默失效。前像因此与 `.opennote/import-log.json` **同域**，保留策略**同源**（500 条上限见下表）。**仍然禁止**用历史快照顶替前像（00 号 §6.7④）。

```json
{
  "version": 1,
  "updatedAt": "2026-09-29T21:04:11+08:00",
  "entries": [
    {
      "importId": "0f1d6d9a-6c2f-4a7e-9d31-5b0f2a7c1e88",
      "op": "appended",
      "path": "剪藏/技术/写给工程师的本地优先笔记.md",
      "preimagePath": ".opennote/import-preimages/0f1d6d9a-6c2f-4a7e-9d31-5b0f2a7c1e88.md",
      "preimageBytes": 4213,
      "preimageSha256": "sha256:7d1e0c4a9b3f5826",
      "revertible": true,
      "at": "2026-09-29T21:04:11+08:00",
      "undoneAt": null
    }
  ]
}
```

| 规则 | 规定 |
| --- | --- |
| 谁写 | **渲染层**（与 `.opennote/import-index.json` 同一条写盘路径，3.3.3）。主进程不碰它 |
| 写入方式 | `import-log.json.tmp` + `move`（沿用 `writeStateFile()` 模式，`src/data/library.ts:847`，截至撰写时）；失败**不影响**本次导入成功，但回执 `revertible` 必须据实返回 `false` 并回 `IMP-W008` |
| 上限 | **500 条**（与 `.opennote/import-log.json` 同源）：超出时丢弃最旧的日志条目，**并同步删除其前像文件**（否则前像会无限堆积）；两者必须同一次操作里完成，不允许只删日志或只删前像 |
| `undoneAt` | 撤销后置为时间戳（保留记录便于排障，不删行） |
| 与 `.opennote/history/` 的关系 | **无保留策略耦合**（00 号 §6.10①）：`history/` 是版本快照域（自动快照上限 60 份、`includeHistory` 可整体排除），其清理与导出**不涉及**前像；前像按 `importId` 一一对应一次操作，逐字节、不节流——这是它能替代快照支撑撤销的原因（历史快照有约 3 分钟节流，`src/data/library.ts:98-99`，截至撰写时） |
| 目录被删 | 与 `.opennote/` 既有语义一致：删掉只影响「撤销能逐字节回退」，不损失正文与标签 |

### 3.4 边界四：附件落盘与正文引用改写

**客户端引用附件的约定**（写入信封时）：

- 正文里用 `](./assets/<name>)` 引用附件（与现有粘贴图片的产物一致，`src/lib/import.ts:88`），其中 `<name>` 精确等于 `assets[].name`。
- 允许 `](${name})`（不含目录的裸名）与 `assets/${name}`（无 `./` 前缀）两种变体。

**服务端落盘命名**：

```text
finalName = contentHash8(bytes) + "-" + sanitizeName(name, "attachment")
# contentHash8 = sha256(bytes) 的前 8 个十六进制字符
# 例：assets/3f9a1c02-diagram.png
```

为什么加内容哈希前缀（**这是本契约新增的、与现状不同的一点**）：

1. **重试幂等**：部分成功后的重试会用同样的哈希前缀命中同一路径，不会产生 `assets/diagram 2.png`、`assets/diagram 3.png` 的垃圾堆积（第 3.6 节）。
2. **同名不同内容的附件**（同一页面两张都叫 `image.png`）天然区分，无需靠序号。
3. 单件哈希不同即路径不同，因此 `assets/` 目录下不会出现「同名不同内容被覆盖」。同哈希同名的文件即使重复写入，**字节相同**，覆盖无害。

**正文改写算法**（对 `body` 做三次字面替换，顺序不可颠倒）：

```text
for (name, final) in zip(assetNames, writtenAssets):
    base     = `./assets/${name}`
    finalRef = `./assets/${baseName(final)}`
    body = body.split(base).join(finalRef)              # 1 精确相对路径
    body = body.split(`assets/${name}`).join(`assets/${baseName(final)}`)   # 2 无 ./ 前缀
    body = body.split(`](${name})`).join(`](${finalRef})`)                  # 3 裸名链接
```

先在「带 `./assets/` 的完整形态」上替换，再替换更宽松的形态，最后处理 `](name)`。第 1 步之后 `./assets/diagram.png` 已变成 `./assets/3f9a1c02-diagram.png`，不会在第 2 步被二次改写（因为替换串里已不含原来的 `assets/diagram.png`——注意第 2 步的匹配串是 `assets/diagram.png`，而第 1 步的结果里 `./assets/3f9a1c02-diagram.png` **包含** `assets/3f9a1c02-diagram.png` 但不包含 `assets/diagram.png`，所以安全）。

**附件目录**：`joinPath(parentPath(notePath), ASSETS_DIR)`，即**与笔记同级**的 `assets/`（`ASSETS_DIR = "assets"`，`src/fs/paths.ts:73`）。不放进 `.opennote/`：附件是正文的一部分，删掉 `.opennote/` 不能丢图（00 号简报事实基线第 12 条）。

**SVG 附件必须净化**（`image/svg+xml` 在白名单里，但 SVG 可携带 `<script>`）：拒绝 `<script`、`on*=` 事件属性、`javascript:`、外部 `href`/`xlink:href`，并加 `Content-Security-Policy` 无关——因为它作为文件被 `<img>` 引用。净化失败 → `IMP-4012`。

### 3.5 边界五：EOL 归一化与编码

| 项 | 规定 | 依据 |
| --- | --- | --- |
| 换行 | 全部归一为 `\n`（LF）。`normalizeEol()` = `text.replace(/\r\n?/g, "\n")` | `src/lib/utils.ts:36`，现有导入路径即如此（`src/lib/import.ts:86`） |
| 末尾 | 文件末尾恰好一个 `\n`（无多余空行） | 便于全字节断言；`trimEnd()` 后再补一个 |
| 编码 | UTF-8，**不写 BOM** | `splitFrontMatter()` 允许 BOM 但没必要；BOM 会污染 `git diff` |
| 非法字符 | 正文里的孤立代理项（lone surrogate）在编码时替换为 U+FFFD，不拒绝请求 | 避免整篇因一个字符失败 |
| 附件字节 | 原样写入，不做任何重编码 | 图片是二进制 |
| 文件名编码 | 文件名用 UTF-8（Windows 上 NTFS 原生支持），CJK 不做转义 | `sanitizeName()` 的目标就是 CJK 可读（`src/fs/paths.ts:78` 注释） |

### 3.6 操作顺序与「部分成功」

写入**不是事务**：三个后端（Node fs / FSA / OPFS）都没有跨文件事务。因此契约必须规定顺序与失败后的语义。

顺序：`mkdir 目录` → `写附件（逐个）` → `写正文（原子）` → `写索引` → `通知`。

失败处理矩阵：

| 失败点 | 已完成 | 响应 | 重试语义 |
| --- | --- | --- | --- |
| 目录创建失败 | 无 | `IMP-4009`（含具体段名） | 可重试（幂等：目录创建是 `recursive`） |
| 第 k 个附件失败 | 前 k−1 个附件已在 `assets/` | `IMP-4012`，`detail.assetIndex = k`，`partial: { assets: [已写入路径] }` | 重试安全：已写入的附件用内容哈希命名，重试命中同一路径；**不会**产生 ` 2` 序号垃圾 |
| 正文写入失败 | 全部附件 | `IMP-5001`，`partial.assets` 列出附件 | 重试安全（附件同前）；不会留下半截正文（桌面端 `writeFileAtomic`，`electron/main.cjs` 的 `writeFileAtomic`；未提交的工作区改动） |
| 索引写入失败 | 正文已写入 | **仍然返回 201**，`warning: IMP-W005 幂等索引写入失败`，`deduped` 下次可能失效 | 不需要重试正文。索引失败只影响去重，不影响用户数据 |
| 通知渲染层失败 | 全部写入成功 | **仍然返回 201** | 通知失败只影响 UI 刷新速度，下一次重扫会补上 |

**核心承诺**：`IMP-4012` 这类「部分成功」的失败响应里，`partial.assets` 必须列出**已经真实落盘**的路径。客户端据此可以决定「重试（推荐）」还是「放弃」。这条是「可测」的关键——测试可以直接断言失败后 `assets/` 里到底有什么。

### 3.7 「front-matter 里除 `tags` 外都是惰性的」带来的后果

这一条必须单独写清楚，因为它是本方案里最容易踩的坑。

| 惰性键 | 直接后果 | 契约的应对 |
| --- | --- | --- |
| `source` | 应用**不会**因为 front-matter 里有 URL 就显示「来源」按钮或做来源索引 | UI 侧的来源展示必须读 **`.opennote/import-index.json`**，不能读笔记文件的 front-matter |
| `source_title` | 同上 | 同上 |
| `source_site` | 同上（v2 新增键） | 同上 |
| `author` | 同上 | 同上 |
| `published_at` | 应用不会把它当排序键（v2 新增键） | UI 侧读索引里的 `publishedAt` 展示；文件里的这份保证换机器不丢（异议 2 的初衷） |
| `captured_at` | 笔记的 `updatedAt` 来自文件 `mtime`，**不是** `captured_at` | 排序必须用 `mtime`；不要把 `captured_at` 当排序键 |
| `opennote_import_id` | 应用**不会**自动识别重复导入 | 幂等必须靠 `.opennote/import-index.json`（第 4 章），front-matter 里的该键只是**给人和外部工具看的**（Obsidian 兼容、可被 grep、可在别的机器上重建索引） |
| `tags` | **唯一生效的键**。生效方式是 `deriveTags()` 重新解析整个文件 | 标签可以只写 front-matter，也可以只写正文 `#tag`；两者都会被收集 |

**为什么仍然要把惰性键写进文件**：

1. **纯文本承诺**（00 号简报 6.6）：换个编辑器（Obsidian / VSCode / Typora）打开，来源信息仍在文件里，不是锁在应用私有数据库里。
2. **可重建索引**：`.opennote/import-index.json` 丢失（用户删了 `.opennote/`，或被 D10 类问题损坏）时，可以用 `grep -r "opennote_import_id"` 从正文重建。契约要求在「索引缺失」时提供这条降级路径（4.3.3）。
3. **跨机器/跨人协作**：front-matter 随文件走（git / 同步盘），`.opennote/` 通常被 `.gitignore` 排除。

**为什么不干脆把来源信息放 `.opennote/`**：那会违反「删掉 `.opennote/` 不影响正文」的承诺——正文里的信息才是用户的。所以策略是：**文件里存一份（人可读、可迁移），索引里存一份（机器可查、可快速去重）**，两边内容一致。

### 3.8 一个容易被忽略的副作用：正文里的 `#tag` 会被当标签

`deriveTags()` 除了 front-matter，还扫描正文里的 `#tag`（正则 `src/lib/utils.ts:153`，跳过围栏代码块 `stripFencedCode()`）。

后果：剪藏一条带话题标签的社交媒体内容（`#前端 #笔记`）会**自动**给笔记加上这些标签；剪藏含 `#include <stdio.h>` 的**行内代码**（反引号内）也会被误判成标签 `include`（`stripFencedCode()` 只去掉围栏代码块，不去行内代码）。

契约不禁止该行为（它是既有解析器的语义，改动属于数据层工作，不在本契约范围），但要求：

- 桥的响应里返回**最终生效的标签集合** `tags: [...]`，让客户端知道实际写了什么；
- 导入提示（toast）不承诺「只加了信封里的标签」；
- 若产品希望「剪藏内容不产生隐式标签」，需要单独开一条数据层需求（改 `deriveTags()` 或引入「导入来源笔记不做行内标签扫描」的标记）——**记入第 12 章开放问题**。

## 4. 幂等与去重

重复投递在实际场景里是**常态**而非异常：插件会因为「桥没起来」重试、AI 会因为工具调用失败重试、用户会连点两次、收件箱会在应用重启后重新扫一遍。契约必须让「同一件事做两次」与「做一次」的最终状态相同。

### 4.1 判定优先级

去重**不依赖 front-matter**（因为除 `tags` 外的键都是惰性的，见 3.7），而是依赖一份工作区内的索引文件。判定顺序固定，从上到下第一个命中者胜出：

判定链以 00 号 §6.8⑦ 为准（**本节是 §6.8⑦ 的可实现展开**）：

| 步 | 条件 | 判定 | 行为 | 回执 | HTTP |
| --- | --- | --- | --- | --- | --- |
| 1 | 同一 `importId` | 幂等命中 | **完全不写盘**，返回**首次**落点 | `status: "deduped"`、`deduped: true`、`dedupedBy: "importId"` | 200 |
| 2 | 同 `source.url` 且 `bodyHash` 相同 | **重复** | **不追加、不写盘**，返回既有落点 | `status: "duplicate"`、`deduped: true`、`dedupedBy: "contentHash"` | 200 |
| 3 | 同 `source.url` 但 `bodyHash` 不同，且 `source.selection === true` | 选区二次剪藏 | **`append`**（追加到既有笔记，带时间分隔；前像见 3.3.3） | `status: "appended"` | 200 |
| 4 | 同 `source.url` 但 `bodyHash` 不同，且 `source.selection !== true` | 整页二次剪藏 | **进收件箱**（不静默追加） | `status: "pending"`（收件箱条目 id 一并返回） | 202 |
| 5 | 仅 `bodyHash` 相同、`url` 不同 | 两条不同来源的同文内容 | **视为两条独立笔记**（拒绝误合并） | `status: "created"` | 201 |
| 6 | 都不命中 | 新导入 | 正常落盘 | `status: "created"` | 201 |

四条必须牢记的推论：

1. **`bodyHash` 不能单独作为去重键**（第 5 步）。同一篇通稿被两家媒体转载、同一段代码出现在两个仓库，都是真实场景，误合并比多一篇笔记糟得多。`bodyHash` 只在「同一 URL」的前提下参与判定。
2. **整页二次剪藏不追加**（第 4 步，00 号 §6.7②/§6.8⑦）。整页重复剪藏往往意味着用户想重新取一份（页面改版、上次漏了图），静默追加会让笔记长出一份重复全文。进收件箱让用户决定。
3. **`selection` 是判定输入**，不只是 UI 标签。插件必须在选区剪藏时置 `selection: true`，整页时置 `false`（或省略）。
4. **优先级 3/4 可被客户端的显式 `conflict` 覆盖**：`conflict: "new"` 就新开一份、`"skip"` 就什么都不做、`"append"` 强制追加（仅第 4 步的整页场景会被它改写为追加）；但第 1、2 步**不受 `conflict` 影响**——幂等与重复判定的语义是「同一次导入 / 同一份内容」，不是「用户想怎么处理冲突」。
5. **`url: null` 视为「同一个空来源」**：两次都不带 URL 且正文相同 → 第 2 步判重复（AI/CLI 反复「记录一下这段文字」不会产生副本）；一次带 URL、一次不带 → 两者 URL 不同 → 第 5 步视为两条独立笔记。

### 4.2 三个哈希的精确定义

```text
sourceHash  = "sha256:" + hex(sha256(utf8(source.url ?? "")))[0..16]
bodyHash    = "sha256:" + hex(sha256(utf8(normalizeEol(body))))[0..16]
contentHash = "sha256:" + hex(sha256(utf8(sourceHash + "\n" + bodyHash)))[0..16]
```

要点：

- **只哈希「来源 URL + 正文」**，不哈希 `title` / `tags` / `capturedAt`。理由：同一篇文章换个标题、补个标签、隔十分钟再剪，仍然应该被认出来。
- 哈希前先 `normalizeEol()`（`src/lib/utils.ts:36`），避免 `\r\n` 与 `\n` 的差异造成「同一段文字两个哈希」。
- 截断到 16 个十六进制字符（64 bit）。碰撞概率在「单工作区十万条导入」量级下可忽略，且碰撞的后果只是「误判为重复」——对一个本地笔记应用而言，代价远小于存储完整 256 bit。
- 正文为空串时 `bodyHash` 仍然计算（空串的哈希），不会退化成「全部空正文互相重复」——因为 `sourceHash` 不同。

各客户端的 `importId` 生成建议（不强制，但要写进各自的实现）：

| 客户端 | 建议 |
| --- | --- |
| 浏览器插件 | `crypto.randomUUID()`，每次点击剪藏生成一次；重试时**复用**同一个 id |
| CLI | `--id` 显式传入；**缺省时用 `randomUUID()`**（与插件一致）。不要用 `contentHash` 当 id：那会把「同一份内容再次剪藏」误报成「同一次导入」（回执 `deduped` 而非 4.1 第 2 步的 `duplicate`），也会绕开 `source.url` 的判定 |
| MCP | 由工具实现生成 `randomUUID()`，并在工具返回里回传，便于模型/用户核对 |
| 收件箱 | 文件名里的 id 就是 `importId`（5.8.2）；从收件箱入库后 `importId` 不变 |

### 4.3 幂等索引：`.opennote/import-index.json`

#### 4.3.1 位置与格式

放在 `.opennote/`（00 号简报事实基线第 12 条：新增元数据必须放进 `.opennote/`），文件名 `import-index.json`。**不放 `.opennote/inbox/`**，因为索引是活跃数据、收件箱是待处理队列，清理策略不同。

```json
{
  "version": 1,
  "updatedAt": "2026-09-29T21:04:11+08:00",
  "entries": [
    {
      "importId": "0f1d6d9a-6c2f-4a7e-9d31-5b0f2a7c1e88",
      "path": "剪藏/技术/写给工程师的本地优先笔记.md",
      "title": "写给工程师的本地优先笔记",
      "sourceUrl": "https://example.com/posts/local-first",
      "site": "example.com",
      "publishedAt": "2026-08-14T09:30:00+08:00",
      "selection": true,
      "sourceHash": "sha256:9f2c4a1b7e0d3856",
      "bodyHash": "sha256:1a7f0c93b4e28d51",
      "contentHash": "sha256:c53b8e17a90d4f26",
      "tags": ["剪藏", "本地优先"],
      "client": "chrome-extension",
      "at": "2026-09-29T21:04:11+08:00",
      "action": "created"
    }
  ]
}
```

- `entries` 按 `at` 倒序，**上限 2000 条**，超出时丢弃最旧的。2000 条 ≈ 一个重度用户两年的剪藏量；索引体积约 2000 × 400 B ≈ 800 KB，`splitFrontMatter`/扫描都不会读它。
- 写入方式：`import-index.json.tmp` + `move`（沿用 `writeStateFile()` 的既有模式，`src/data/library.ts:847`，截至撰写时）；写入失败不影响本次导入的成功（3.6 矩阵）。
- `.opennote/**` 的写入**不会**触发 `opennote:fs:workspace-changed` 广播（主进程显式跳过，见第 8 章）——所以写索引不会造成「自写→自读重扫」的反馈循环。这是把索引放在 `.opennote/` 的一个附带好处。
- 删除 `.opennote/` 只损失去重能力与来源展示，**不损失任何正文**（00 号简报事实基线第 12 条的承诺仍然成立）。

#### 4.3.2 损坏与缺失

| 情形 | 行为 |
| --- | --- |
| 文件不存在 | 视为空索引；首次导入后创建 |
| JSON 解析失败 | 备份为 `import-index.json.corrupt-<ts>`（沿用 `backupCorruptState()` 的模式，`src/data/library.ts:217`），以空索引继续，并在 UI 上给一次提示 |
| `version` 大于当前支持 | 保守处理：只读不改，去重退化为「只用 importId 在内存里比对」 |
| 索引与磁盘不一致（索引说 `a.md`，文件已不在） | 以磁盘为准：`exists(path)` 为假则删除该条目并继续查找下一个候选 |

#### 4.3.3 索引缺失时的降级路径

索引丢了但 front-matter 还在，所以契约规定一条降级路径（**必须实现，这是「把惰性键写进文件」的回报**）：

```text
1. 打开工作区时，scanWorkspace 会通读每个 .md 的全文（src/data/library.ts:275）
2. 在这一次读取里顺手抽取 front-matter 的 opennote_import_id 与 source
3. 建立会话级 Map<importId, path> 与 Map<sourceHash, path>
4. 第一条新导入落盘时，把会话级 Map 的内容整体写回 import-index.json
```

抽取是极廉价的字符串操作（`splitFrontMatter()` + 两行正则），不额外读盘。代价只有一次扫描时多跑一个正则——相对于 `scanWorkspace` 已经付出的「读全文」成本可以忽略。

### 4.4 三种并发/重试场景的期望结果

#### 场景 1：重复投递（串行）

```text
t0  插件 POST importId=A (标题「测试」，正文 P)  → 201 { path: "测试.md", action: "created" }
t1  插件 POST importId=A (同一信封)              → 200 { path: "测试.md", deduped: true }
t2  插件 POST importId=B (同一信封，新 id)       → 200 { path: "测试.md", deduped: true, dedupedBy: "contentHash" }
```

磁盘结果：只有 `测试.md` 一个文件，内容只写了一次。UI 只提示一次（t1/t2 的 `deduped: true` 不应触发 toast，见第 8 章）。

#### 场景 2：并发投递（同一 importId 同时到达）

```text
t0  请求 1 与请求 2 同时到达（同一 importId=A）
    桥维护 inFlight: Map<importId, Promise<ImportResult>>
    请求 2 发现 A 在途 → await 请求 1 的 Promise（上限 10s）→ 返回同一结果
```

- 两个请求**都**返回 `201 { path: "测试.md" }`（或都返回 200，取决于谁先进入索引写入——契约规定：**后到者返回 `deduped: true`**，因为它是复用了在途结果）。
- 磁盘结果：一个文件。
- 超过 10s 仍未完成 → 请求 2 返回 `IMP-4020`（`409`，`retryable: true`），不阻塞客户端。

#### 场景 3：并发投递（不同 importId，同一标题）

这是最容易出错的场景：两个请求都要写 `测试.md`。

```text
t0  请求 1 (importId=A, 标题「测试」) 与 请求 2 (importId=B, 标题「测试」) 并发
    若各自独立跑 resolveAvailablePath：
      两者都看到「测试.md 不存在」→ 都选 "测试.md" → 后写者覆盖先写者  ← 数据丢失
```

**契约要求：所有提交串行化。** 主进程维护一个全局提交队列（单并发）：

```text
commitQueue = Promise.resolve()
function enqueue(fn): commitQueue = commitQueue.then(fn, fn); return commitQueue
```

- 期望结果：`测试.md` 与 `测试 2.md`，两份内容都在。
- 串行化的代价：单次导入的吞吐上限 ≈ 1 / 平均写盘耗时（本地 SSD 上通常 < 20 ms）。对本应用的真实负载（人手剪藏、AI 单篇导入）完全够用；不做并行化。
- 串行化还顺带消除了「同一批次的附件与正文互相竞争 `taken`」的问题（3.3.2）。

#### 场景 4：部分成功后的重试

```text
t0  POST importId=A（含 3 个附件，第 3 个过大）→ 400 IMP-4012
    partial: { assets: ["assets/3f9a1c02-a.png", "assets/7b2e91d4-b.png"] }
    磁盘：2 个附件已写入，正文未写
t1  插件修正第 3 个附件后，用同一 importId=A 重试
    → 附件 a/b 用同样的内容哈希命名 → 命中同一路径 → 覆盖写入（字节相同，无害）
    → 只新增 assets/<hash>-c.png
    → 201 { path: "测试.md", assets: [a, b, c] }
```

磁盘结果：`assets/` 下恰好 3 个文件，**没有** `a 2.png` 之类的垃圾。这正是 3.4 节「内容哈希前缀」的设计意图。

若客户端不重试而是换新 `importId`，结果也一样（内容哈希与 id 无关）；只是会多留下 2 条索引记录，无害。

### 4.5 响应字段与幂等的可观测性

`API-02`（创建导入）的响应必须携带足够字段，让客户端不必猜：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `status` | `"created"` \| `"appended"` \| `"deduped"` \| `"duplicate"` \| `"pending"` \| `"skipped"` | 本次调用实际做了什么（取值含义见 4.1 的判定链表与 00 号 §6.8⑦）。`duplicate` = 同 url 同内容；`pending` = 整页二次剪藏已投进收件箱；`skipped` = 命中 `conflict: "skip"` |
| `importId` | string | 回声，便于客户端对账 |
| `path` | string \| null | 目标笔记的工作区相对路径；`deduped` / `duplicate` 时给**首次/既有**落点；`pending` 时为 `null` |
| `inboxId` | string \| null | 仅 `status: "pending"` 时给出收件箱条目 id（5.8.2 的目录名） |
| `deduped` | boolean | 是否是「无写入」的命中（`deduped` 与 `duplicate` 皆为 `true`） |
| `dedupedBy` | `"importId"` \| `"contentHash"` \| `"sourceUrl"` \| null | 命中原因，用于排障 |
| **`revertible`** | boolean | **本次操作是否可逐字节回退**（00 号 §6.7④ 的推论）。`created` 恒为 `true`（新建文件，删掉即可）；`appended` / `overwrite` 仅在成功写下前像时为 `true`；`deduped` / `duplicate` / `skipped` 无写入，语义为 `true` |
| **`preimage`** | object \| null | `{ path: ".opennote/import-preimages/<importId>.md", bytes: 12345, sha256: "…" }`；`revertible: false` 时为 `null` |
| `assets` | string[] | **实际写入**的附件路径（不是请求里的 `name`） |
| `tags` | string[] | **最终生效**的标签集合（含正文 `#tag` 扫描结果，3.8） |
| `warnings` | string[] | 形如 `["IMP-W002 有未声明的本地附件引用"]` |

**提示口径（`deduped` 与 `duplicate` 不同，不要合并）**：

| 回执 | 提示方式 | 文案 |
| --- | --- | --- |
| `deduped: true` / `dedupedBy: "importId"` | **一律静默**（不 toast、不内联、不计入「最近导入」的失败感） | — |
| `status: "duplicate"`（同 url 同内容） | **客户端内联**：插件 popup / CLI stderr / 收件箱条目内联；**不是应用内 toast**（00 号 §6.12①） | **规范文案（唯一写法）：`已在笔记中（未重复入库）。`** 并提供「打开那条笔记」（`opennote://open?path=…`，`API-12`）。该事件同时进「最近导入」与导入日志，可事后追溯 |
| `status: "skipped"` | 静默（用户自己设的策略） | — |

「deduped 静默」这条是产品要求（00 号简报 6.4 的「零摩擦」），也是契约要求：重复投递不该在 UI 上产生第二个 toast。

**`revertible` 必须出现在回执里**（不能只写进日志）：客户端与 UI 要能立刻知道「这次点撤销能不能逐字节还原」。`revertible: false` 时 UI 的撤销入口必须换成降级文案（「移入回收站 / 查看历史快照」），**不得**承诺「撤销后恢复原样」（00 号 §6.7④）。

### 5.2 本地桥（HTTP，`127.0.0.1`）

本地桥是桌面版主进程内的一个极小 HTTP 服务。**默认关闭**（00 号简报 6.6 明确的非目标：不做默认开启的本地桥），必须由用户在设置里显式开启。

> **新增依赖与攻击面（如实评估）**：全仓当前**没有任何 HTTP 服务端能力**（无 `http.createServer`、无 express/fastify、无 WebSocket）。本地桥是全新引入。实现约束：
> - **必须**用 Node 内置的 `node:http`，**不得**引入 express / fastify / koa / hono 等框架。理由：桌面端要控制打包体积与攻击面；本契约的接口只有 4 个方法 + 8 条路径，内置模块足够；新增零运行时依赖。
> - 不得引入 WebSocket（`ws` 包）——`API-03` 的轮询已足够，收件箱用 IPC 通知（第 8 章）。
> - 不得新增任何 npm 依赖。若实现时发现确实需要，必须先改本契约并说明体积/锁文件影响。
> - 监听 socket 只存在两种形态之一：`server.listen(port, "127.0.0.1")` 或 `server.listen(0, "127.0.0.1")`。**禁止** `listen(port)`（不传 host 时 Node 会绑到 `::`/`0.0.0.0`，等于把写入口暴露给局域网）。
> - 开启本地桥会触发**操作系统防火墙的「允许应用访问网络」提示**（Windows Defender 防火墙在首次 `listen` 时弹窗）。这一点必须在设置面板的开启确认里预先告知用户，否则用户会以为应用在偷偷联网。虽然绑定 `127.0.0.1` 的回环监听在多数 Windows 配置下不触发弹窗，但**不能保证**（取决于第三方安全软件），所以按「会弹窗」准备文案。

#### 5.2.1 绑地址、端口与发现

| 项 | 规定 |
| --- | --- |
| 绑地址 | **只绑 `127.0.0.1`**（IPv4 回环）。不绑 `::1`、不绑 `localhost`（避免解析到 ::1 导致连不上）、绝不绑 `0.0.0.0` |
| 默认端口 | **8787** |
| 端口范围 | `8787`–`8796`（共 10 个）。默认从 8787 起顺序尝试，第一个可用者生效 |
| 可配置 | 设置里可改「起始端口」（8787–8796 之外的自定义值允许，但必须落在 1024–65535 且不能是 0） |
| 端口 0 | **不使用**（端口 0 = 让系统随机分配，客户端无法预知，会让插件必须扫描 65536 个端口） |
| 客户端发现 | 插件/CLI 依次尝试 `8787..8796` 的 `GET /v1/health`，每次 300 ms 超时，命中即停。10 次回环请求的耗时通常在 20 ms 内 |
| 展示 | 设置面板必须**显式显示**实际监听地址 `http://127.0.0.1:8787`，并提供一键复制。用户把这一行贴给任何客户端都能跑通 |

**为什么不做「固定单一端口」**：端口冲突（另一个应用、另一个 Opennote 实例、开发服务器）会让桥完全不可用。**为什么不做「让系统随机分配」**：客户端将必须扫描全部端口，且重启后端口变化会让所有客户端配置失效。折中方案 = 小范围固定 + 客户端扫描 + 界面显式展示。

#### 5.2.2 运行状态机（界面必须呈现的枚举，逐字使用）

```text
  未开启(disabled)
      │ 用户在设置里点击「开启本地接口」并确认
      ▼
  正在启动(starting)
      │
      ├── 成功 ─────────────► 运行中(running) ──用户关闭──► 已停止(stopped) ──► 未开启
      ├── 8787..8796 全被占用 ─► 端口被占用(port-busy) ──用户改端口/关掉占用者──► 正在启动
      └── 其它错误(EACCES 等) ─► 启动失败(failed) ──用户点「重试」──► 正在启动
```

| 枚举值 | 中文（UI 逐字） | 触发 | 设置面板应展示 |
| --- | --- | --- | --- |
| `disabled` | 未开启 | 默认状态 / 用户关闭后 | 「开启本地接口」按钮 + 一句话说明（仅本机、需令牌） |
| `stopped` | 已停止 | 用户本次会话中关闭 | 同 `disabled`，另加「本次会话已关闭」的次要说明 |
| `starting` | 正在启动 | 点击开启后的 ≤ 2 s 窗口 | 禁用按钮 + 进度指示 |
| `running` | 运行中 | `listen` 成功 | 地址 + 复制按钮 + 令牌状态 + 「最近导入」列表 + 「关闭」 |
| `port-busy` | 端口被占用 | 10 个端口全部 `EADDRINUSE` | 「8787–8796 都被占用」+ 端口输入框 + 「换端口重试」 |
| `failed` | 启动失败 | `EACCES` / `EPERM` / 未知异常 | 具体原因（中文）+ 「重试」+ 「查看日志」 |

**关掉本地桥 = 立刻 `server.close()` + 关闭全部 keep-alive 连接**，不是「停止接受新请求但保留 socket」。状态从 `running` 直接回到 `stopped`。

> **`opennote:bridge:status` 的字段不止 `state` 一个**：完整字段清单（含 `address` / `error` / `lastRejectedOrigin` / `startPort` / `portRange` 等）见 **5.2.11**——那份清单是「桥状态该有哪些字段」的唯一契约出处。

#### 5.2.3 令牌（token）生命周期

| 项 | 规定 |
| --- | --- |
| 生成 | `crypto.randomBytes(32)` → base64url → 43 字符；加前缀 `opn_`，**总长 47 字符** |
| 展示 | **按 00 号 §6.15㊴ 裁定（㊲ 的「绝不落盘 / 本会话内可复制」口径已被推翻，作废）**：明文与 `sha256`、`last4` **一并存在 `bridge.json`**，因此**任何时候都能复制**——不需要重新生成，也**没有**「重启后不可见」这一态。面板状态句逐字见本节末（`C27` / `C28` / `C29`） |
| 存储 | `userData/bridge.json` 里存 `sha256(token)` 的十六进制、`last4` **与明文**（三者并列）。**00 号 §6.15㊴ 明确推翻 ㊲ 的「明文绝不落盘」**——这是用户在知情取舍下选定的方案。**代价如实记录**：任何能读到该文件、剪贴板或扩展存储的程序都能拿到令牌并获得**导入**能力（导入能力**不等于**读笔记能力：桥只提供导入，不提供读取与删除）。面板必须逐字显示 §7.7 的令牌区披露句，**不得**再写「绝不落盘」这类与事实不符的话 |
| **有效期** | **长期有效**——只在用户点「重新生成令牌」时失效（00 号 §6.15㉞）。不设过期时间、没有使用次数限制；令牌是 0.3.1 起唯一的凭据 |
| 校验 | 收到的 `Authorization: Bearer <t>` 或 `X-Opennote-Token: <t>` → `sha256` → 与存储值**定时比较**（`crypto.timingSafeEqual`）|
| 传递方式 | `Authorization: Bearer` 优先；`X-Opennote-Token` 为兼容某些不方便设 header 的客户端保留。**禁止**放在 URL query（会进日志、进 Referer） |
| 轮换 | 设置里「重新生成令牌」→ 生成新令牌、旧令牌**立即失效**（哈希被替换）、`tokenVersion += 1`。UI 必须警告：「所有已配置的客户端都需要重新配置」。**「重新生成」= 立刻换新明文并作废旧令牌，面板同时更新可复制内容**（00 号 §6.15㊲） |
| 撤销 | 只有一把令牌，因此「撤销」=「轮换」。不实现「多把命名令牌」（P2 再议） |
| 未设置令牌时 | 桥**不允许开启**。开启流程 = 生成令牌 → 展示（**任何时候都能复制**，明文已存 `bridge.json`，00 号 §6.15㊴） → 启动服务。避免出现「无鉴权的写入端口」 |
| 客户端配置方式（0.3.1 起） | **「复制令牌 → 粘贴到客户端」**：设置面板的「复制令牌」区块（原 R4b「配对新客户端」区块，00 号 §6.15㊱）点一下复制，客户端把 47 字符令牌粘贴进自己的配置或输入框。**原「6 位配对码 + `API-06` 换令牌」的设计已被 00 号 §6.15㉞ 取代（0.3.1 起删除配对），不再有配对码、不再有「配对成功即轮换令牌」** |
| 日志 | **任何日志都不得包含令牌**。响应也不回显令牌 |

**设置面板令牌区的状态句（逐字，`03` 号 `C27`–`C29` 同源；00 号 §6.15㊴）**：

- `C27`（有令牌）：`明文保存在本机，任何时候都能复制。`
- `C28`（还没生成）：`还没有访问令牌。点「重新生成」生成一个，再复制到客户端。`
- `C29`（旧版文件，**必需的第三态**——升级前的 `bridge.json` 只有 `sha256`，长不出明文）：`这个令牌是旧版本生成的，明文没有保存在本机。需要明文请点「重新生成」拿一串新的。`

#### 5.2.4 四道请求前校验（顺序固定）

```text
1. Host 校验（防 DNS rebinding）
2. Origin 校验（防恶意网页 CSRF-to-localhost）
3. Content-Type 校验（防「简单请求」绕过预检）
4. 令牌校验（防本机其它用户/进程）
```

**第 1 道：Host**

```text
allowedHosts = { `127.0.0.1:${port}`, `127.0.0.1`, `localhost:${port}`, `localhost` }
missing Host header              → 400 IMP-1005
Host 不在 allowedHosts           → 403 IMP-1005
```

原理：恶意站点 `evil.com` 把 DNS 记录改成 `127.0.0.1`（DNS rebinding），页面即可向 `http://evil.com:8787/` 发请求——TCP 层连的确实是本机，但 HTTP 的 `Host` 头是 `evil.com:8787`，不在白名单里，直接拒绝。**请求头里的 `Host` 由浏览器按 URL 生成，页面脚本无法伪造**，所以这道校验对 DNS rebinding 有效。

**第 2 道：Origin（0.3.1 起**按类型**判定，00 号 §6.15㉞）**

```text
无 Origin 头（curl / CLI / MCP / 原生程序）→ 放行（继续第 3 道）
Origin == "null"（sandbox iframe / data: URL）→ 403 IMP-3001
Origin 是扩展来源  chrome-extension://<id> / moz-extension://<id> → 放行，并在响应里回显 CORS 头
Origin 是本机应用来源  http://127.0.0.1:<port> / file://          → 放行，并在响应里回显 CORS 头
其它一切来源（普通网页 http(s)://…）                            → 403 IMP-3001，不返回任何 CORS 头
```

- **判据是「来源类型」，不是「信任列表」**：不再有「配对成功才把该 `Origin` 加入 `allowedOrigins`」这一步（00 号 §6.15㉞ 删除配对）。`bridge.json` 的 `allowedOrigins` 只作为**历史遗留条目**保留（`removeOrigin()` 保留，用于删除遗留条目），**不再参与放行判定**。
- **普通网页来源一律拒绝**——这是防「任意网页驱动本机接口」的关键：去掉配对后令牌是唯一凭据，若再放行普通网页来源，任何被访问的网页都能借用户浏览器向本机写入。不能因为去掉配对而放宽。
- 本机 dev server（`http://127.0.0.1:5173`）属于本机应用来源，按类型即可放行；**不得**放行任何非 `127.0.0.1` 的 `http://` 来源。
- 为什么「无 Origin 就放行」不危险：浏览器发的跨源请求**一定**带 `Origin`（`fetch`、`XHR`、表单提交都带）。能不带 `Origin` 的只有非浏览器进程，而它们要么已经在用户机器上执行代码（此时令牌才是真正的防线），要么就是用户的 CLI。所以「无 Origin 放行」= 不与本地自动化工具为敌，同时不给网页留口子。

**第 3 道：Content-Type**

```text
POST 请求必须是 application/json 或 application/opennote+json（可带 charset 参数）
其它一切（text/plain、application/x-www-form-urlencoded、multipart/form-data、缺失）→ 415 IMP-3004
GET / OPTIONS 不校验
```

原理：HTML 表单只能发出 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain` 三种 Content-Type，且这三种都是 CORS **简单请求**——不发预检，直接到达服务器。如果桥接受 `text/plain`，任何网页都能用

```html
<form action="http://127.0.0.1:8787/v1/import" method="POST" enctype="text/plain">
```

向本机写入内容（经典的 CSRF-to-localhost，见 13 章的参考资料）。`application/json` **不在** CORS 简单请求的 Content-Type 白名单里，浏览器必须先发 `OPTIONS` 预检；而预检会被第 2 道的 Origin 校验拦下。**所以「拒绝 `text/plain`」这一步不是可选的加固，而是整条防线的一环。**

注：`multipart/form-data` 也不能接受——它同样是简单请求，且能携带文件（附件）。

**第 4 道：令牌**

```text
Authorization: Bearer <t> 或 X-Opennote-Token: <t>；两者都缺 → 401 IMP-2001
格式不对（不含 opn_ 前缀 / 长度不符）→ 401 IMP-2002
哈希不匹配 → 401 IMP-2002
允许失败 10 次 / 分钟 / 进程；超过 → 429 IMP-2003（避免本机暴力尝试）
```

`GET /v1/health` **不需要**令牌（第 5.2.6 节给出原因与信息暴露边界）。

#### 5.2.5 CORS 精确策略

只在**第 2 道校验通过**时返回 CORS 头，且**精确回显**来源（不使用 `*`）：

```http
Access-Control-Allow-Origin: chrome-extension://abcdefghijklmnopabcdefghijklmnop
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type, X-Opennote-Token
Access-Control-Max-Age: 600
Vary: Origin
Cache-Control: no-store
```

- **绝不**返回 `Access-Control-Allow-Origin: *`（`*` 配合 `Authorization` 会被浏览器拒绝，但更重要的是它表达了错误的意图）。
- **绝不**返回 `Access-Control-Allow-Credentials: true`（本桥不用 cookie，任何 `credentials: "include"` 的请求都应失败）。
- `Vary: Origin` 必须存在，否则中间缓存（某些企业代理会拦回环流量）可能把 A 来源的响应喂给 B 来源。
- 预检 `OPTIONS` 的响应体为空、状态 204，且**不校验令牌**（预检不携带 Authorization）。

**`API-06 POST /v1/pair` —— 本节被 00 号 §6.15㉞ 取代（0.3.1 起删除配对）**

原设计整段删除：`POST /v1/pair`、6 位配对码（`crypto.randomInt(100000, 999999)`）、120 秒有效期、一次性使用、失败 5 次作废、`pairingCode` / `newPairCode()` / `pendingPlaintext`，以及「配对成功即把该 `Origin` 写入 `allowedOrigins` 并轮换令牌」——全部移除。桥不再提供任何「无令牌状态下会改变服务端状态」的接口。

**取而代之的客户端配置流程（0.3.1 起）**：

```text
1. 用户在 Opennote 的「设置 · 文件 · 导入与接口」里点「复制令牌」（47 字符，形如 opn_…）
2. 粘贴到客户端：扩展 popup 的令牌输入框 / CLI 的 --token 或 OPENNOTE_TOKEN / MCP 客户端的 env
3. 客户端此后一律用 Authorization: Bearer <令牌> 调用（X-Opennote-Token 仍兼容）
```

令牌**长期有效**，仅在用户「重新生成令牌」时失效（5.2.3）。**明文就保存在本机 Opennote 数据目录的 `bridge.json` 里**（00 号 §6.15㊴ **推翻** ㊲ 的「绝不落盘」），因此**任何时候都能复制**，不需要重新生成、也没有「重启后不可见」这一态。**安全代价如实记录**（用户知情选择，00 号 §6.15㊴）：令牌是唯一凭据且长期有效，任何能读到 `bridge.json`、剪贴板或扩展 storage 的程序都能拿到明文并因此获得**导入**能力——注意导入能力**不等于**读笔记能力（桥只提供导入，不提供读取与删除）。这条必须写进设置面板的说明句（§7.7 令牌区披露句，逐字）。

#### 5.2.7 单实例

- 主进程调用 `app.requestSingleInstanceLock()`；拿不到锁的进程立即退出，并把命令行参数通过 `second-instance` 事件转交给已运行的实例（`opennote://` / CLI 参数都靠这条）。
- 桥的 `start()` 必须幂等：重复调用返回当前状态，不重复 `listen`。
- 若同一台机器上跑着**两个不同安装位置**的 Opennote，两者都拿不到对方的锁（Electron 的锁按 userData 目录），此时端口范围会自然分流（8787 与 8788）——这是预期的，不是错误。
- **桥的生命周期跟随窗口**（8.1 的后果）：最后一个窗口关闭时停止监听（macOS 上应用可能仍在运行）；重新创建窗口时，若用户上次已开启，则自动恢复监听。这条保证了「桥可用 ⇒ 渲染层在场」，从而让 `IMP-4006` 只在竞态窗口里出现。

#### 5.2.9 缺陷影响与规避（D20 / D29 / D31）

> 前提：按 8.1 的架构决定，**桥不在主进程写盘**——主进程只做传输与安全校验，落点决策与写入转交渲染层，由既有的 `FileSystemBackend` + 数据层完成（唯一例外是收件箱队列元数据，见 8.1.1）。下表的「规避」都建立在这条前提上。

| 缺陷 | 与桥的关系 | 规避方式 |
| --- | --- | --- |
| **D20**（渲染层可对宿主机任意读/写/删） | 若桥在主进程自建写盘路径，就会成为**第二条不受 `opennote:fs:authorizeRoot` 授权集合约束的写盘通道** | 桥**不在主进程写盘**（8.1）；转交渲染层后自动复用既有的 root 授权、`assertSafeRelative()` 与原子写。桥**绝不**接受来自信封的绝对路径，只接受工作区相对路径；桥**不提供** delete / move / 任意 mkdir 能力 |
| **D29**（`fs:remove(root, ".")` 可删整个库） | 桥**不需要**任何删除能力 | 契约层面禁止桥暴露任何 `remove`/`delete` 接口。撤销走 UI 的「移到回收站」（`trashNote`），不通过 HTTP |
| **D31**（junction / 符号链接绕过边界） | 若工作区里有指向外部的 junction，桥的写入会落到工作区之外 | 写入前对**最终目标**（写入类操作检查父目录）做 realpath 校验，与 IPC 的 `assertRealPathInsideRoot()` 同一函数。**这是硬前置**：在 D31 修复前，桥不允许开启（见 7.6 的门禁条款） |
| **D03**（导入不预检同名、静默清空） | 桥的每一次落点分配都可能撞上「外部新建的同名文件」 | 必须走 `resolveAvailablePath()`（磁盘 `exists()` 探测 + 内存 `taken`），见 3.3.2。**未提交的工作区改动**已经把 `importIntoWorkspace()` 改成这个写法（`src/lib/import.ts:84`），桥必须复用同一函数 |
| **D08**（外部改动被下次自动保存覆盖） | 桥写入一个**用户正在编辑器里打开**的笔记时，渲染层的自动保存可能在几百毫秒后覆盖桥写的内容 | ①`append` 前 `stat()` 比对（3.3.3）；②写入成功后立即发通知（第 8 章），让渲染层重载该笔记；③若目标笔记当前处于「有未落盘改动」状态（`dirty`），降级为新文件并返回 `warning` |
| **D12**（OPFS 导入覆盖同名） | 桥**不用于**浏览器后端（5.1 矩阵第 1 行：仅桌面版） | 桥与 D12 无关；D12 只影响页面内桥与手动导入（5.7.6） |

#### 5.2.10 降级路径

本地桥不可用时（未开启、装的是网页版、端口全被占用），按以下顺序降级：

1. **CLI 离线写收件箱** `opennote clip --to <工作区> --inbox`（5.3.5）——需要一个已知的工作区路径，且应用下次启动时扫到。
2. **`opennote://` URL scheme**（5.6）——把信封压缩成短载荷交给应用，应用用自己已经打开的会话完成落盘。适合「点一下就进来」的单条剪藏。
3. **手动搬运**：客户端导出 `.md`（+ 图片目录），用户拖进窗口（对应既有能力 `importIntoWorkspace()`，`src/lib/import.ts:40`）。这是**永远可用的兜底**，也是网页版与移动端的唯一路径。

#### 5.2.11 桥状态字段清单（`opennote:bridge:status` 的返回 = `BridgeStatus`）

**为什么单列一节**：这份清单曾经**只存在于代码里**（`src/desktop/bridge.ts` 的 `BridgeStatus`，`02` 里 0 处出处）。后果是真实发生过的：`bridgeStatusPayload()` 一度**逐字段重建**桥状态，把 `address` / `error` / `lastRejectedOrigin` / `startPort` / `portRange` **静默截断**，让「`UI-04`/`R8` 拒绝记录行」「8787–8796 全被占用」的提示变成**死代码**，而当时没有任何检查能发现它。契约因此必须自己持有这份清单。

**字段（与 `src/desktop/bridge.ts` 的 `BridgeStatus` 逐字一致，含可选标记 `?`）**

| 字段 | 类型 | 必现 | 一句话语义 | 产地 |
| --- | --- | --- | --- | --- |
| `state` | `BridgeState` | 是 | 当前运行态；取值 = 5.2.2 的 6 个枚举，逐字 | `bridge.cjs` 的 `status()`；桥模块加载失败（`!controller`）时由 `main.cjs` 固定给 `"failed"` |
| `port` | `number \| null` | 是 | 实际监听端口；未运行 `null` | `bridge.cjs`（`!controller` 时 `main.cjs` 给 `null`） |
| `endpoint` | `string \| null` | 是 | 客户端应使用的基址 `http://127.0.0.1:<port>`；未运行 `null` | 同上 |
| `tokenLast4` | `string \| null` | 是 | 令牌后 4 位，用于识别是哪一把（**不含明文**） | 同上 |
| `tokenSet` | `boolean` | 是 | 有没有令牌（哈希存在） | 同上 |
| `origins` | `string[]` | 是 | **历史遗留**来源条目；0.3.1 起不参与放行判定（5.2.4） | 同上 |

| `tokenPersisted?` | `boolean` | 可选 | 令牌（哈希）是否已落到 `bridge.json`；**没有 dataDir 时纯内存、重启会丢令牌**，UI 必须如实告知 | `bridge.cjs`（`!controller` 时 `main.cjs` 给 `false`） |
| `tokenVisible?` | `boolean` | 可选 | **当前是否握有可用明文**——`C27` 的「复制」能不能用；**只报在不在，绝不回显明文本身**。与 `tokenSet` 唯一不等的场景 = 旧版 `bridge.json`（只有 `sha256` + `last4`，长不出明文，即 `C29`）或外部塞入的哈希 | `bridge.cjs`（`!controller` 时 `main.cjs` 给 `false`） |

| `portRange?` | `[number, number] \| null` | 可选 | 端口探测范围（闭区间 `[起, 止]`），与 `bridge.cjs` 的 `status()` 逐字一致 | 同上 |

**硬约束（`bridgeStatusPayload()` 必须遵守；`scripts/bridge-hooks-check.cjs` 已有断言守）**

1. **必须先 `...raw` 展开底层 `status()`，再在下面覆盖显式字段**；**严禁逐字段重建**。`...raw` 放在最前面，显式覆盖照样赢——所以那串显式字段只用来**把类型收紧**，**不得**用来筛字段。
2. 桥模块加载失败（`!controller`）时，主进程**必须返回上表全部字段**（可选字段给 `null` / `false` / `[]`），**不得省略**——省略会让渲染层的 `undefined` 与 `false` 混在一起，面板被迫写第二套分支。
3. 渲染层遇到可选字段缺失，**必须按 `false` / 空降级，绝不假装可用**：`tokenVisible` 缺失 ⇒ 不显示可点的「复制」；`portRange` 缺失 ⇒ 不显示端口范围。
4. 这份清单只读；设置面板的写操作走 8.2 的独立频道（`start` / `stop` / `newToken` / `removeOrigin`），不通过状态字段回写。

> **附注（不属于 `BridgeStatus`，渲染层不得依赖）**：`bridge.cjs` 的 `status()` 对象里还带着 `stateLabel` / `addressText` / `running` / `allowedOrigins` / `spec` 等键，它们会随 `...raw` 一起到达渲染层。**契约不保证这些键**；需要文案时请用上表字段自行派生（`state` → 5.2.2 的中文名）。

### 5.3 CLI `opennote clip` / `opennote import`

#### 5.3.1 形态与分发（含一个必须如实说明的平台限制）

CLI 是 **Node 脚本**（`opennote.cjs` + `opennote.cmd` / `opennote.sh` 包装），随桌面版分发，**不是 Electron 二进制本身**。原因：Windows 上的 Electron 应用是 GUI 子系统程序，从终端启动时默认**没有附加控制台**，输出不会出现在用户终端里，也无法被 shell 捕获。因此：

- `opennote` = Node 脚本，**通过 HTTP 与本地桥通信**（不依赖 Electron 的 stdout）；
- CLI 不实现业务逻辑：校验完参数后把信封 `POST /v1/import` 给桥。**落点决策、去重、写盘全部在 L2 完成**。
- 无桥可用时走 `--to` 离线模式（5.3.5），该模式**只写收件箱文件**，不直接写笔记。

前置要求：系统有 Node ≥ 20。桌面版**不承诺「零依赖可运行 CLI」**；若产品要求零依赖，需另做静态二进制（P2 再议，见第 12 章）。

#### 5.3.2 参数表

| 命令 | 说明 |
| --- | --- |

| `opennote settings` | 打印接口地址与「导入与接口」设置的位置提示 |

| 参数 | 说明 | 默认 |
| --- | --- | --- |
| `--title <t>` | 标题；缺省时从正文首个标题行推导 | — |
| `--url <u>` | 来源 URL（→ front-matter 的 `source`） | — |
| `--site <s>` / `--author <a>` / `--published <iso>` | 来源信息补充 | — |
| `--selection` | 标记为「用户选中的片段」 | 整页 |

#### 5.3.4 退出码

| 退出码 | 含义 | 对应错误码 | Skill/AI 应如何处理 |
| --- | --- | --- | --- |
| `0` | 成功（含 `deduped`、`skipped`） | — | 继续 |
| `2` | 字段校验失败 | `IMP-4001`…`IMP-4014` | **不要重试**，修正参数 |
| `3` | 连不上本地桥 | `IMP-1001` / `IMP-1004` | 提示开启本地接口；或改用 `--to` |
| `3` | 桥在运行但桌面版窗口不在场 | `IMP-4006` | **Opennote 桌面版没运行（或窗口已关）时本地桥不存在**（00 号 §6.8①：桥生命周期跟随窗口）。文案（逐字，00 号 §6.14㉗）：「Opennote 没有在运行。请先打开 Opennote，再试一次。」；或用 `--to` 离线投递 |
| `4` | 鉴权失败 | `IMP-2001` / `IMP-2002` | **不要重试**，需在 Opennote 的「导入与接口」里复制令牌并粘贴到客户端（或让用户重新生成令牌后重新粘贴）；0.3.1 起没有配对流程 |
| `5` | 工作区未打开 | `IMP-4007` | 文案（逐字，00 号 §6.14㉗）：「Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。」 |
| `6` | 被冲突策略跳过 | `IMP-4011` | 视为成功（用户要求跳过） |
| `7` | 限流 | `IMP-4015` | 读 `Retry-After` 后重试 |
| `8` | 用法错误（缺参数、未知选项） | — | 修正命令行 |
| `9` | 内部错误（写盘/索引失败） | `IMP-5001` | 可重试一次；仍失败则把错误原文告诉用户 |

`--json` 模式下 stdout **只有一行 JSON**，人类可读信息走 stderr。这是给 AI 用的硬约束。

#### 5.3.5 离线模式与桥的关系

```text
有桥（应用在运行）     → POST /v1/import       → 立刻入库，响应确定
无桥 + --to <工作区>  → 写 .opennote/inbox/…  → 状态 pending，等应用确认
无桥 + 无 --to        → 退出码 3，提示开启本地接口
```

意义：AI 在沙箱/CI 里跑 Skill 时桌面应用可能没开；`.opennote/inbox/` 是**纯文件协议**，任何语言、任何进程都能投递。代价是它**收不到 `workspace-changed` 通知**（主进程显式跳过 `.opennote/**`），必须配合 5.8.4 的「投递即重扫」。

### 5.4 MCP Server

**形态**：一个 **stdio 进程**（`opennote-mcp.cjs`），由 AI 客户端作为子进程拉起；自身不写盘，只把工具调用翻译成 `API-02` 的 HTTP 请求。选 stdio 而不是 HTTP/SSE 的理由：桌面应用已在用 8787，再开一个端口意味着第二份「绑地址 + 鉴权 + 限流」的重复实现；stdio 由宿主管道生命周期，无网络面。协议版本 MCP [`2025-06-18`](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

**运行前提（00 号 §6.8①，必须在工具的 description 里写明）**：MCP 自身不写盘，它依赖桌面版本地桥。因此「AI 想导入」的完整前提是：**Opennote 桌面版正在运行 + 已打开一个笔记本文件夹 + 用户已在设置里开启本地接口 + 该客户端已配置令牌**。四条缺任何一条都会失败：

| 缺失项 | 机器码 | `content[0].text`（中文，模型与用户都能读） |
| --- | --- | --- |
| 桌面版没运行 / 窗口已关（桥不存在） | `IMP-1001` / `IMP-4006` | 「Opennote 没有在运行。请先打开 Opennote，再试一次。」（逐字，00 号 §6.14㉗） |
| 没开启本地接口 | `IMP-1001` | 「Opennote 的本地接口未开启。请到 设置 · 文件 · 导入与接口 里开启。」 |
| 笔记本文件夹没打开 | `IMP-4007` | 「Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。」（逐字，00 号 §6.14㉗） |
| 没配置令牌 / 令牌失效 | `IMP-2001` / `IMP-2002` | 「这个客户端还没有配置访问令牌。请在 Opennote 的「导入与接口」里复制令牌，粘贴到客户端。」 |

**0.3.1 起没有「配对」这个前置项**：MCP 与 CLI / Skill 一样只用令牌——用户在 Opennote 里「复制令牌」→ 粘贴进 MCP 客户端的配置（env），此后一律以 `Authorization: Bearer <令牌>` 调用；不再有配对码或配对流程（00 号 §6.15㉟）。

这条前提直接决定 P1 的可用性描述：**MCP 不是「随时随地可用」的导入能力，它要求桌面版在场**（00 号 §6.8① 明确要求不得含糊）。工具 description 里必须出现「需要 Opennote 桌面版正在运行」这句。

**能力边界（明确取舍）**：MCP **只提供「写入 + 查询写入结果」**，**不提供**读取笔记正文、全文搜索、目录遍历、删除、移动、重命名。

- 读取会让「一个 AI 工具能不能看你整个笔记本」变成需要单独设计授权的问题（哪本？全部？），远超「方便导入」的原始诉求；
- 写入是**追加性**的，读是**泄露性**的，风险等级不同，本阶段只承担前者；
- 用户在 AI 里想要的是「帮我把这篇记录一下」，只需要写；需要的读操作（「刚才那条进去了吗」）由 `opennote_import_status` 覆盖。

| 工具名 | 作用 | 注解 |
| --- | --- | --- |
| `opennote_import` | 提交一个导入信封 | `destructiveHint: false`、`idempotentHint: true`、`openWorldHint: false` |
| `opennote_import_status` | 查某次导入的结果 | `readOnlyHint: true` |
| `opennote_recent_imports` | 最近 N 次导入（不含正文） | `readOnlyHint: true` |
| `opennote_workspace_info` | 工作区名称 / 是否打开 / 默认落点 / 已有标签 | `readOnlyHint: true` |

`opennote_import` 的 `inputSchema`（`additionalProperties: false`，`required: ["title","body"]`）：

```json

  "name": "opennote_import",
  "title": "导入内容到 Opennote 笔记本",
  "description": "把一段 Markdown 正文写进用户本机的 Opennote 笔记本。绝不覆盖既有笔记；同一 importId 重复调用是幂等的。",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["title", "body"],
    "properties": {
      "title": { "type": "string", "minLength": 1, "maxLength": 200, "description": "笔记标题，写入正文首个一级标题，并用于生成文件名" },

      "sourceUrl": { "type": ["string", "null"], "description": "原始网页地址；本地文件/口述内容传 null" },
      "sourceTitle": { "type": ["string", "null"] },

```

返回：`content[0].text` 为人类可读中文，`structuredContent` 为机器可读（字段同 4.5 的 `ImportResult`）。失败时 `isError: true`，`text` 用第 6 章中文文案，`structuredContent.error.code` 给机器码。**工具层不抛 JSON-RPC 异常**——宿主对 `isError` 的处理比协议错误更友好，模型能读到文案并自行决定是否重试。

**与 Skill 的分工**：MCP 由宿主按工具协议调用（结构化、有 schema）；Skill 由模型读文档后自行执行命令。MCP 需 Node + **桌面版 Opennote 正在运行且已打开笔记本文件夹**；Skill 还需要 CLI 在 PATH 里。两者**共用同一个 `API-02`**，字段语义、错误码、幂等行为完全一致，也**共用同一条运行前提**（桌面版不在场就都不可用，只有 CLI 的 `--to` 离线投递例外）。

```markdown
# 把内容导入 Opennote

## 何时使用
（触发词：记录一下 / 存进笔记 / 剪藏 / 导入 Opennote / 帮我留个档）

## 前置检查
1. `opennote status --json` 确认本地接口在运行、且已打开笔记本文件夹
2. 桌面版没运行 / 窗口已关 → 告诉用户「Opennote 没有在运行。请先打开 Opennote，再试一次。」
   工作区没打开 → 告诉用户「Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。」
   接口没开 → 告诉用户「Opennote 的本地接口未开启。请到 设置 · 文件 · 导入与接口 里开启。」；
   **不要**替用户改配置，**不要**声称已导入
3. 确认不了（无 CLI）→ 请用户手动把内容存成 .md，或用 --to 离线投递

## 做什么
1. 取得正文：网页 → 抓原文并保留 Markdown；用户粘贴的内容 → 原样使用
2. 写入临时文件（不要用 shell 转义拼长字符串）
3. opennote clip <临时文件> --title <标题> --url <来源> --folder <目录> --tags <标签> --json
4. 读 JSON：status ∈ created/appended/deduped/skipped；按 code 决定是否重试
5. 把 path 告诉用户

## 硬性约束（不许违反）
- 不得改写用户原文：只允许（a）去掉导航/广告等明显噪声，（b）Markdown 语法规范化
- 必须带来源：--url 尽量提供；确实没有来源时在 --tags 里加「无来源」
- 不得编造：不要补写原文没有的段落、结论、摘要
- 不得覆盖：不要传破坏性选项；new 是默认值，保持它
- 一次一件事：用户给了多篇就逐篇导入，不要合并成一篇

## 失败处理
- 退出码 3（IMP-1001/1004/4006）→ 桌面版不在场或接口没开：提示用户先打开 Opennote（`IMP-4006` 逐字文案「Opennote 没有在运行。请先打开 Opennote，再试一次。」），
  或用 --to <工作区> 离线投递
- 退出码 5（IMP-4007）→ 逐字文案「Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。」
- 退出码 4 → 提示在 Opennote 的「设置 · 文件 · 导入与接口」里点「复制令牌」→ 粘贴到客户端（令牌**长期有效**，仅在用户重新生成时失效；0.3.1 起没有配对流程，00 号 §6.15㉟/㊱）
- 退出码 2 → 修正参数后重试一次，仍失败就把错误原文告诉用户
```

**运行前提（00 号 §6.8①）**：Skill 的成败取决于**桌面版 Opennote 正在运行且已打开笔记本文件夹**——桥的生命周期跟随窗口，没有窗口就没有桥。因此 Skill 的可用性描述必须是「需要用户先把 Opennote 打开」，**不得**宣传为「随时可用」；前置检查失败时的正确行为是**如实告诉用户**并给出离线方案（`--to` 或手动存文件），而不是重试或声称成功。

**为什么 Skill 优选 CLI 而不是 MCP**：Skill 是文档，模型按文档执行 shell 命令，CLI 的 `--json` 对它最直接；MCP 需要用户先改客户端配置并重启宿主，门槛更高。两条路可并存（前置检查里先探测 MCP 工具是否存在），属实现细节，不写进契约。

**「不许改写用户原文」「必须带来源」是契约的一部分，不是建议**：由接口层兜底——信封里没有 `source.url` 时响应带 `warning`（2.3），设置面板的「最近导入」对无来源条目做标记。**约束不靠模型自觉，靠可观测的痕迹。**

### 5.6 `opennote://` URL scheme

| 编号 | 形态 | 用途 | 分期 |
| --- | --- | --- | --- |
| `API-09` | `opennote://clip?d=<base64url(gzip(envelope))>` | 短载荷直传（≤ 4 KiB 二进制） | P1 |
| `API-10` | `opennote://clip?inbox=<条目目录名>` | 凭证领取：生产者已写好收件箱条目，应用读它并入库 | P1 |
| `API-11` | `opennote://settings/import` | 打开「设置 · 文件 · 导入与接口」 | **P0**（插件引导用，实现极简） |
| `API-12` | `opennote://open?path=<工作区相对路径>` | 打开一篇笔记（「已导入，点这里查看」） | P1 |

**0.3.0 实现范围（00 号 §6.14㉛）**：本次实现 **`API-11`**（`opennote://settings/import`，分期列 P0）与 **`API-12`**（`opennote://open?path=…`，分期列 P1，本次一并落地）——`app.setAsDefaultProtocolClient("opennote")` + `requestSingleInstanceLock()` + `second-instance` 转发（Windows/Linux）+ `open-url`（macOS）；0.2.0 里应用侧 **0 处** `setAsDefaultProtocolClient`，「打开 Opennote 设置」是死按钮。**`API-09`（`opennote://clip?d=…`）本次明确不实现**：剪藏主路径仍是本地桥，且它到达后必须先在应用内确认（见本节末段），属独立工作量。**未实现的路由必须明确报「暂不支持」，不得静默无反应。**代价如实记录：应用没运行时无法从浏览器剪藏，只能用插件内离线暂存（S11）等应用恢复后补投。

`API-11` 必须有：它补上「桥没开 → 用户不知道去哪开」这个断层。

| 长度上限 | 值 | 依据 |
| --- | --- | --- |
| 完整 URL | **8192 字符** | Windows `ShellExecute` / 注册表 / 多数 shell 的实际上限；超出时系统可能**静默截断**，应用会收到损坏的信封——比明确报错更糟 |
| `d=` 载荷（base64url 后） | 4096 字符 | 留出 scheme / 参数 / 转义余量 |
| 解压后 JSON | 256 KiB | 防 zip bomb：解压时限制输出字节 |

超限行为：**拒绝并提示**「链接过长，请改用剪贴板或插件重新剪藏」，不做部分解析。载荷格式 `d = base64url(gzip(utf8(JSON(envelope))))`，**`assets[]` 必须为空**（图片走不了 URL，带附件的剪藏只能用桥或收件箱）。

**为什么不把正文放进 URL**：URL 会进入 shell 历史、浏览器历史、剪贴板管理器、聊天软件的链接预览、企业代理日志，而用户剪藏的可能是一篇私人文章。**为什么不传 URL 让应用抓取**：这与 00 号简报 6.6 锁定非目标「不代用户爬取网页；正文由客户端在用户浏览器里取」直接冲突，且会引入 SSRF 面（内网地址、`file://`、重定向到本地服务）。**因此 `opennote://clip?url=…&fetch=1` 这类形态不予实现**，契约明确禁止。

| 平台 | `opennote://` |
| --- | --- |
| Windows 桌面版 | 支持：安装时写 `HKCU\Software\Classes\opennote`（**不写 HKLM**，避免要求管理员权限） |
| macOS 桌面版 | 支持：`electron-builder.yml` 的 `protocols` → `CFBundleURLTypes` |
| Linux 桌面版 | 支持：`.desktop` 的 `MimeType=x-scheme-handler/opennote` |
| 移动端 | **不支持**：移动浏览器不注册自定义协议，PWA 也无法接管；走 PWA Share Target（P1） |
| 网页版（非桌面） | **不支持**：没有进程可注册协议；`registerProtocolHandler` 只能注册 `web+` 前缀 |

**协议到达时必须先在应用内确认**（URL 可能来自任意网站）：弹窗显示标题、来源站点、目标目录，用户点「导入」才落盘。`API-09` / `API-10` **永远不做静默入库**——这是与「本地桥 + 令牌」不同的信任级别：令牌证明「这是用户配置过的客户端」，URL scheme 只能证明「有个东西调起了应用」。

**深链不涉及令牌，也不适用 Origin 类型判据**（00 号 §6.15㉟/㉛）：`opennote://` 是只读入口 + 一律弹窗确认，因此不携带 `Authorization`；5.2.4 第 2 道的 Origin 判据只作用于本地桥的 HTTP 请求。

### 5.7 页面内桥（postMessage）

**为什么需要它，以及它只在哪里用**：桌面版不需要（有本地桥）。但网页版（FSA / OPFS）**没有任何外部入口**——没有本地进程，也没有可被外部程序访问的目录。此时唯一可能的通道是剪藏扩展的 content script 与「正在浏览器里打开着笔记本的页面」直接对话。

前提条件（三者同时满足）：① 用户用 FSA 打开了真实文件夹，或用任意浏览器打开了 OPFS 笔记本；② 该页面**正开在某个标签页里**；③ 用户装了扩展。**只在 FSA/OPFS 用**的理由就是这些前提本身：桌面版有更可靠、无需页面在场的桥；FSA/OPFS 场景没有别的选择。

**分期（00 号 §6.11①）：两条后端的交付节奏不同，不得合并描述。**

| 后端 | 分期 | 门槛 |
| --- | --- | --- |
| **FSA**（Chrome / Edge 网页版，页面在场 + 真实文件夹句柄） | **P0** | 属于 00 号 §6.5 的 P0 判定标准（「Chrome/Edge 网页版**且页面在场**」）；落点走 `resolveAvailablePath()`（第 3 章）即可 |
| **OPFS**（其它浏览器的私有存储） | **P1，且绑定 D12 门禁** | 必须在 D12 的修复**提交并有测试覆盖**之后才允许启用（理由：OPFS 的「导入文件夹覆盖同名」与页面内桥的写入语义同源，D12 未修时启用等于把覆盖风险放大到自动化通道）。见 5.7.6 与 7.6 |

**网页版页面内的 Opennote 无法 `fetch` 本地桥**（00 号 §6.8⑤）：两套 CSP 都不含 `127.0.0.1`——网页版是 `contentSecurityPolicyPlugin()` 生成的 `default-src 'self'`（`vite.config.ts:147`，指令见 `:158`）＋ `connect-src 'self'`（`:166`）；桌面版是 `cspPolicy()`（`electron/main.cjs:51`，截至撰写时）生成的 `default-src 'none'`（`:53`）＋ `connect-src 'self' file:`（`:58`）。（行号为截至撰写时。）所以页面内桥**只能走 `postMessage`**，不能用 HTTP 去问「桥开没开」——网页版上根本没有桥。这条也决定了插件的连接状态文案：**在 FSA/OPFS 场景下不要显示「本地接口未开启」，那是桌面版才有的概念**（03 号设计稿据此区分两套状态文案）。

| 方向 | `type` | 说明 |
| --- | --- | --- |
| 扩展 → 页面 | `opennote:inpage:hello` | 握手：扩展声明自己与版本 |
| 页面 → 扩展 | `opennote:inpage:ready` | 页面回应：声明能力与工作区状态 |
| 扩展 → 页面 | `opennote:inpage:import` | 提交信封 |
| 页面 → 扩展 | `opennote:inpage:result` | 返回结果（形状同 `API-02`） |
| 页面 → 扩展 | `opennote:inpage:event` | 入库后的异步通知（如「已撤销」） |

```js
// 扩展 → 页面
window.postMessage({
  type: "opennote:inpage:import", v: 1,
  reqId: "3f9a1c02-7e41-4b90-8a35-1d2c4f6a8b90",   // 请求标识，用于匹配请求与回复（与已删除的「配对」无关）
  envelope: { /* opennote.import/v1 */ }
}, targetOrigin);                                  // 显式 origin，绝不用 "*"

// 页面 → 扩展
window.postMessage({
  type: "opennote:inpage:result", v: 1,
  reqId: "3f9a1c02-7e41-4b90-8a35-1d2c4f6a8b90",
  ok: true,
  result: { status: "created", path: "剪藏/…md", deduped: false, tags: [], warnings: [] }
}, event.origin);
```

**双向校验（缺一不可）**

```text
页面侧：
1. event.source === window        （必须是自己所在窗口，拒绝 iframe 转发）
2. event.origin 是扩展来源        （chrome-extension://<id> / moz-extension://<id>；普通网页来源一律拒绝，00 号 §6.15㉞）
3. data.type 以 "opennote:inpage:" 开头，且 v === 1
4. reqId 是字符串且 ≤ 64 字符
5. 信封通过第 2 章全部校验
任一失败 → 不回复、不入库、console.warn 一条脱敏记录

扩展侧：
1. event.source === window
2. event.origin === 目标页面的 origin（精确匹配，不能用通配）
3. data.reqId === 自己发出的 reqId（防止回复串台）
4. 5 秒超时 → 视为「页面无响应」
```

**绝不使用 `postMessage(data, "*")`**，必须显式给 `targetOrigin`。硬性红线。

**页面不在场时**：扩展先用 `chrome.tabs.query` 找有没有 Opennote 标签页（按扩展自己的 host 白名单匹配 URL）；有 → 发 `hello`，等 `ready`（300 ms），发 `import`；没有 → content script 无法凭空创建页面，只能 `chrome.tabs.create({url: <笔记本地址>})` 打开新标签页，等 `ready` 后导入——**需要用户在 popup 里点一次确认**（新开标签页是可见行为）。用户用 FSA 且句柄权限过期时，页面在 `ready` 里返回 `needsPermission: true`，页面自己弹权限请求（`requestPermission` 必须在用户手势里调用，`src/fs/fsa.ts:27`）；扩展侧文案「请在 Opennote 标签页里点一下授权」。

| 项 | 规定 |
| --- | --- |
| 单条消息上限 | 1 MiB（`postMessage` 会复制对象，大对象会卡住两个页面；超过则改走本地桥） |
| 超时 | 5 s（页面可能正在渲染大文档） |
| 失败文案 | 「Opennote 的页面没有响应。请确认笔记本标签页还开着，或改用桌面版本地接口。」 |
| 离线 | 不适用（页面必须在场，「离线」等于页面不在） |

**缺陷影响与规避**

| 缺陷 | 关系 | 规避 |
| --- | --- | --- |
| **D12**（OPFS 导入覆盖同名） | **直接相关，且只作用于 OPFS 桥**（FSA 桥为 P0，与 D12 无关）：页面内桥最终落到 `FileSystemBackend`。HEAD `7ea0661` 的 `importFilesIntoOpfs()`（`src/fs/opfs.ts:51`）的 `taken` 从不按磁盘种子化、`getFileHandle(name,{create:true})` 直接覆盖；**未提交的工作区改动已修**（撰写时观察到 `src/fs/opfs.ts` 现在按目录维护「完整相对路径」集合、用目录内真实文件名种子化、写入前再探测一次；该文件正被并发修改） | **硬前置（门禁作用于 OPFS 页面内桥，00 号 §6.11①）**：OPFS 桥**不得**依赖旧的「basename-only `taken`」形态，必须走「读目录 → 以完整相对路径为键的 `taken` → `resolveAvailablePath`」的落点分配（第 3 章）；D12 的修复必须**提交**并有测试覆盖后才能启用 OPFS 桥。**FSA 桥不受此门禁影响**（P0，与 D12 无关） |
| **D20** | 页面内桥在**渲染层**执行，与手动导入同一条路径，不扩大 IPC 攻击面 | 无额外要求；但**必须**校验 `event.origin`，否则任何页面都能向笔记本页面发写入指令 |
| **D31** | Windows 上 FSA 也能选到含 junction 的目录；realpath 检查只在 Node 后端可用 | 记录为已知限制：FSA/OPFS 后端在含连接点的目录上可能越界 |

#### 5.7.7 扩展侧的状态枚举与错误码映射（04 号评审 RV-04 的落点）

剪藏扩展在 popup 里要显示的状态比「成功/失败」细。为避免它在 UI 里自造一套不可追溯的文案，**扩展侧的每个状态都必须映射到本契约的某个 `code` 或某个已定义语义**——这就是 6.4「每种提示都要能追溯到 `code`」在扩展侧的具体化：

| 扩展侧状态（03 号 UI 用名） | 归类 | 映射到 | HTTP | 中文文案 | `retryable` | 客户端应如何反应 |
| --- | --- | --- | --- | --- | --- | --- |
| `unsupported_platform` | **错误码** | **`IMP-1006`**（本契约新增；00 号 §6.9① 称其为「一等状态」） | 409 | 「当前浏览器或平台不支持这种导入方式。可以复制正文手动粘贴，或安装 Opennote 桌面版。」 | `false` | **先探测再置灰**，不要让用户点了才报错；同时给出降级路径 |
| `no_window` | **通道级状态**（语义等同错误码） | **`IMP-4006`**（桌面版窗口不在场）；页面内桥场景下 = 「没有 Opennote 标签页」，走 5.7.4 的 `chrome.tabs.create` 流程 | 409 | 「Opennote 没有在运行。请先打开 Opennote，再试一次。」（逐字，00 号 §6.14㉗） | `true` | 桌面版：提示打开应用；页面内桥：按 5.7.4 开新标签页（需用户确认） |
| `queued_offline` | **通道级状态，不是错误** | 无错误码——它是**本地产物**（扩展暂存到自己的 `chrome.storage`，或经 CLI `--to` 落 `.opennote/inbox/`），对应 5.8.3 的 `pending` | — | 「Opennote 没有在运行，内容已暂存在插件里，打开 Opennote 后会自动补投。」（逐字，00 号 §6.14㉗） | 不适用（幂等，可重复） | **按成功对待**，不要显示成失败；显示「待入库」角标，Opennote 上线后靠 `opennote:inbox:changed` / `API-03` 确认 |
| `write_failed` | **错误码** | **`IMP-5001`**（**唯一文案源**是 6.2 的 `userMessage`；03 号不得另写一套，04 号评审 RV-05） | 500 | 「写入笔记失败，磁盘可能已满或没有权限。原内容没有丢失。」 | `true` | 重试一次；响应里的 `partial.assets` 列出已落盘附件（3.6） |

规则：

1. `unsupported_platform` 与 `write_failed` **是错误码**，必须走 6.1 的统一错误响应形状，`code` 出现在 `error.code` 里。
2. `no_window` 与 `queued_offline` **是通道级状态**（扩展/页面内桥的本地概念），但各自映射到已定义的契约语义（`IMP-4006` / 收件箱 `pending`）——**不允许出现既无 `code` 又无映射的第五种说法**。
3. 03 号 UI 文案表的每一行都应带「对应 02 号 code」列（RV-04 的建议改法），这样 §6.4 的自洽性才闭合。

### 5.8 收件箱目录 `.opennote/inbox/`

**定位**：待确认的导入暂存区（00 号简报术语表：与「回收站」并列）。服务两件事：① 用户选了「先进入收件箱等待确认」（00 号简报 6.4）；② 客户端在应用未运行时投递（`--to` 离线模式）。

```text
└── 20260929T131522-c41d9f77/
    └── …
```

条目目录名 = `YYYYMMDDTHHMMSS`（**UTC**，秒级）+ `-` + `importId` 前 8 字符。用 UTC 是为了跨时区稳定排序；人看时间读 `entry.json.capturedAt`（本地时区）。

`entry.json` 就是 `opennote.import/v1` 信封，**外加两个契约扩展字段**（只允许这两个）：

```json
{
  "spec": "opennote.import/v1",
  "importId": "8c2f1e40-1b77-4a0e-9c53-6d1a2b3c4d5e",
  "title": "离线剪藏",
  "body": null,
  "bodyFile": "body.md",
  "assets": [{ "name": "diagram.png", "mime": "image/png", "file": "assets/3f9a1c02-diagram.png" }],
  "source": { "url": "https://example.com/a", "capturedAt": "2026-09-29T21:10:11+08:00" },
  "target": { "folder": "剪藏", "notePath": null },
  "conflict": "new",
  "tags": ["剪藏"],
  "client": { "name": "cli", "version": "0.3.0" },
  "enqueuedAt": "2026-09-29T21:10:11+08:00"
}
```

扩展字段只有 **`bodyFile`**（正文外置，`body` 置 `null`）与 **`assets[].file`**（附件外置，省略 `dataBase64`）。理由：收件箱是给人看、给别的程序读的文件，base64 塞在 JSON 里既不可读又浪费一倍体积。

**它们是「通道级扩展」，不是收件箱专属**（00 号 §6.8③）：`spec` 仍是 `opennote.import/v1`，遵循「未知字段忽略」语义；**本地桥与 CLI 路径必须同时支持内联（`body` / `dataBase64`）与外置（`bodyFile` / `file`）两种形态**，否则同一个信封换个通道就失效（例如 CLI 收到一个 `bodyFile` 信封后转投桥，桥不能拒收）。读入时归一：`bodyFile` → 读文件填 `body`；`assets[].file` → 读文件后走 3.4 的落盘流程。**幂等**：目录名里的 `importId` 前缀 + `entry.json` 里的完整 `importId` 共同去重；读到两个同 id 条目 → 只处理第一个，第二个标 `failed` 并记 `IMP-4017`。

#### 5.8.3 状态机

```text
                  应用发现条目
                       │
                    pending ──────────────┐ 用户点「丢弃」
                       │                   ▼
         应用开始校验/落盘            discarded（条目与内容直接清理，不进回收站）
               ┌───────┴────────┐
         成功  ▼                ▼ 失败
         committed             failed
```

`state.json`：`{ "status": "pending", "attempts": 0, "lastError": null, "committedPath": null, "updatedAt": "…" }`

| 状态 | 含义 | 条目目录保留 |
| --- | --- | --- |
| `pending` | 已投递，等确认或等应用扫到 | 保留（**不设期限**，用户的待确认内容） |
| `committing` | 正在处理（防重复处理的锁） | 保留 |
| `committed` | 已写入工作区 | **24 小时**后删除（队列保留期，留时间给用户「撤销」） |
| `failed` | 校验或写入失败，`lastError` 记错误码 | **7 天**，UI 提供「重试」「丢弃」「查看原因」 |
| `discarded` | 用户主动丢弃 | **立即清理条目目录与内容，不进回收站**（00 号 §6.12②） |

**`discarded` 的语义必须写死**（00 号 §6.12②，取代本文 v2 的「移入 `.opennote/trash/`」写法）：

1. 「丢弃」是用户的**主动销毁意图**，实现上就是 `rm -r` 掉 `.opennote/inbox/<条目名>/`（含 `entry.json` / `body.md` / `assets/` / `state.json`），**不写任何回收站记录**，`.opennote/trash/` 里不会出现 `inbox-*` 目录。
2. 理由：①尊重用户意图与 `01` FR-29 的确认文案；②`committed 24h` / `failed 7d` 是**队列保留期**，与「回收站」是两回事，不得混用；③想要保险的正确路径是「**先入库、再删除**」——删除走既有回收站（`trashNote`），那才是可恢复的路径。
3. 确认框文案必须**如实**说明「丢弃后不会进入回收站」，**不得**暗示可恢复。
4. 因此 `.opennote/inbox/` 下的内容**只有两种结局**：入库（`committed`）或被丢弃（`discarded`）；任何「进回收站」的说法都是错的。

#### 5.8.4 **核心矛盾：收件箱在 `.opennote/**` 里，收不到变更通知**

**问题**：主进程的工作区监听刻意跳过 `.opennote/**`（避免「应用自己写元数据 → 触发重扫 → 又写元数据」的循环）。因此外部程序往 `.opennote/inbox/` 投递时，**`opennote:fs:workspace-changed` 不会触发**，应用不会知道有新条目——「投递成功但界面看不到」。

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| A. 放宽过滤规则 | 在 `.opennote/**` 跳过规则里给 `inbox/` 开例外 | 会把「应用自己写 inbox 状态」也算成外部变更；改的是既有、被注释明确解释过的行为，风险扩散到 `state.json`/`history/`/`trash/` |
| B. 另加专用监听 | 对 `.opennote/inbox` 单独 `watch(dir, {recursive:true})`，走**独立频道** `opennote:inbox:changed` | 需新增 watcher 与频道；但**完全不动既有规则**，语义清晰 |
| C. 打开/聚焦时轮询 | 不做监听，工作区打开时、窗口聚焦时、每 30 s 各扫一次 | 无需监听，但「投递后 30 秒才出现」——对「AI 说已导入、用户盯着屏幕看不到」是硬伤 |

**选定：B 为主 + C 兜底。**

```text
1. 打开工作区（或开启收件箱模式）时：
   watch(joinPath(workspaceRoot, ".opennote/inbox"), { recursive: true, persistent: false })
   目录变化后去抖 450 ms（与既有 WATCH_DEBOUNCE_MS 同值），广播
     opennote:inbox:changed   payload = { root: <绝对路径>, pending: <数量> }
2. inbox 目录不存在 → 先 mkdir 再 watch（目录必须存在才能 watch）
3. watch 失败（平台限制/权限）→ 静默降级到方案 C，并在设置面板显示
   「收件箱变更检测：轮询（每 30 秒）」，让用户知道为什么慢
4. 兜底轮询：窗口可见时每 30 s 扫一次；窗口重新获得焦点时立即扫一次
5. 应用自己写 state.json 也会触发该 watcher → 写 state.json 前设 500 ms 静默窗口
   （推荐，实现最简单），或由应用侧做「内容无变化就不通知」的判断
```

**为什么不在既有 `workspace-changed` 频道上加语义**：那个频道的语义是「工作区内容变了，去重扫」。收件箱不是「工作区内容」，它是**待处理队列**，需要的是「有新条目」这个事件，而且是**计数**（UI 徽标）。语义混用会让渲染层必须反推「这次广播是不是 inbox 引起的」。所以独立频道，但复用同一套 watch / 去抖 / 授权门控的实现模式。

**桥与收件箱的分工**（回答「既然有桥为什么还要收件箱」）：

| 场景 | 走哪条 | 为什么 |
| --- | --- | --- |
| 应用在运行，客户端能连上桥 | **桥**（`API-02`） | 同步、确定、有响应 |
| 设置里开了「先进入收件箱」 | **桥**（`API-02`）+ 服务端进收件箱 | 客户端不需要知道收件箱存在；`API-03` 可轮询确认 |
| 应用没在运行（AI 在 CI/沙箱里跑） | **收件箱**（`--to`） | 桥不存在，只有文件系统可用 |
| 用户手动把 `.md` 拖进 inbox 目录 | **收件箱** | 幂等键由应用生成（内容哈希），视为一次手动导入 |

#### 5.8.5 清理策略

| 项 | 规则 |
| --- | --- |
| `committed` 条目 | 24 小时后删除目录 |
| `failed` 条目 | 7 天后删除；UI 显示剩余天数 |
| `pending` 条目 | **永不自动删除**（用户的待确认内容） |
| `discarded` 条目 | **用户点「丢弃」时立即清理**（条目目录与内容一并删除，**不进回收站**、不可恢复）。这不是「保留期」问题，是销毁动作（00 号 §6.12②） |
| 总量上限 | 500 个条目；超出时拒绝新投递（`IMP-4013`）并提示用户清理 |
| 清除时机 | 工作区打开时扫一遍 + 每 6 小时一次（跟随兜底轮询） |
| 目录被删 | 下次启动重建（`mkdir`）——与 `.opennote/` 既有语义一致：删掉它不影响正文 |
| 与 git 的关系 | 工作区若是 git 仓库，`inbox/` 里的临时条目可能被提交。建议保证 `.opennote/` 已在 `.gitignore` 中——**记入第 12 章开放问题**，因为它会修改用户仓库的文件 |

## 6. 错误模型

### 6.1 统一错误响应

所有通道（本地桥 / CLI / MCP / 页面内桥 / 收件箱）使用**同一套错误码**，只在承载形式上不同。

```json
{
  "ok": false,
  "error": {
    "code": "IMP-4008",
    "message": "target.folder 含非法路径段",
    "userMessage": "导入被拒绝：「..」不能出现在目标目录里。",
    "http": 422,
    "retryable": false,
    "detail": { "field": "target.folder", "segment": "..", "value": "剪藏/../.." }
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | `IMP-xxxx`，**稳定不变**。客户端按它分支，不按文案分支 |
| `message` | string | 面向开发者的英文/中文短描述（可含字段名），**可能随版本微调** |
| `userMessage` | string | **面向用户的中文文案**，可直接显示。UI 应优先用它（UI 也可按 `code` 覆盖成更贴合场景的说法） |
| `http` | number | HTTP 状态码（非 HTTP 通道省略） |
| `retryable` | boolean | 客户端是否可以原样重试。`false` 时重试只是浪费 |
| `detail` | object | 结构化补充（字段名、附件下标、`Retry-After` 秒数等）。**不得包含宿主机绝对路径、用户名、令牌** |

非 HTTP 通道的映射：CLI → 退出码（5.3.4）+ stderr 上的同一份 JSON；MCP → `isError: true` + `structuredContent.error`；页面内桥 → `{ ok: false, error: {…} }`；收件箱 → `state.json.lastError` 存 `code`。

### 6.2 错误码总表

**分组**：`IMP-1xxx` 桥/传输、`IMP-2xxx` 鉴权与来源、`IMP-3xxx` 请求形态与来源、`IMP-4xxx` 信封与落点、`IMP-5xxx` 服务端内部。`IMP-Wxxx` 是非致命警告（`warnings[]` 里出现，不改变 HTTP 状态）。

#### IMP-1xxx 桥与传输

| code | 触发条件 | HTTP | 中文用户文案 | 客户端应如何反应 |
| --- | --- | --- | --- | --- |
| `IMP-1001` | 客户端连不上 `127.0.0.1:8787..8796` 任一端口（`ECONNREFUSED` / 超时） | — | 本地接口未开启。请在 Opennote 的「设置 · 文件 · 导入与接口」里开启，然后重试。 | **不要循环重试**。提示用户，并给出打开设置的入口（`opennote://settings/import`） |
| `IMP-1002` | 桥启动失败（`EACCES`/`EPERM`/未知异常） | — | 本地接口启动失败，端口可能被安全软件占用。可在设置里换一个端口，或查看日志。 | 显示失败状态；不做自动重试 |
| `IMP-1003` | 8787–8796 全部 `EADDRINUSE` | — | 8787 到 8796 端口都被占用了。请关闭占用端口的程序，或在设置里指定其它端口。 | 引导用户在设置里改端口 |
| `IMP-1004` | 请求超时（客户端侧 5 s 未收到响应） | 504 | 本地接口没有及时响应。请确认 Opennote 正在运行。 | 重试一次；仍失败则按 `IMP-1001` 处理 |
| `IMP-1005` | `Host` 头缺失或不在白名单（DNS rebinding 防护） | 403 | （不显示给用户——这是攻击特征或误配置）请求被本地接口拒绝。 | **不要重试**。若是自研客户端，检查是否用了 `127.0.0.1` 而不是自定义域名 |
| `IMP-1006` | **当前平台/后端不支持该导入形态**（00 号 §6.9① 称为「一等状态」）：例如在移动端或仅 OPFS 的浏览器里请求本地桥；或在浏览器里请求桌面版专有通道；或 OPFS 桥在 D12 门禁未解除时被调用（5.1 矩阵 6b） | 409 | 中文文案由调用方按平台覆盖：桌面版专有通道 → 「这个导入方式需要 Opennote 桌面版」；移动端/OPFS → 「当前浏览器里只能用『复制正文 → 手动粘贴』，或装桌面版」 | **不要重试**（换平台前重试必然失败）。客户端应**先用 `API-01` / 环境探测**判断可用性，把入口置灰并给出降级路径，而不是让用户点了才报错 |

#### IMP-2xxx 鉴权与来源

| code | 触发条件 | HTTP | 中文用户文案 | 客户端应如何反应 |
| --- | --- | --- | --- | --- |
| `IMP-2001` | 缺少 `Authorization` / `X-Opennote-Token` | 401 | 这个客户端还没有配置访问令牌。请在 Opennote 的「导入与接口」里复制令牌，粘贴到客户端。 | **不要重试**。引导用户「复制令牌 → 粘贴到客户端」（00 号 §6.15㉞：不再有配对流程与 `API-06`） |
| `IMP-2002` | 令牌格式错误或哈希不匹配 | 401 | 访问令牌不正确或已失效。重新生成令牌后，请在客户端里更新。 | **不要重试**。清掉本地缓存的令牌，提示用户在 Opennote 里复制当前令牌（或重新生成后复制）并重新粘贴到客户端 |
| `IMP-2003` | 鉴权失败超过 10 次/分钟 | 429 | 尝试次数过多，请稍后再试。 | 等 `Retry-After` 后重试；若持续失败提示用户检查令牌 |
| `IMP-2004` | ~~配对码错误、过期或已使用~~（配对功能已被 00 号 §6.15㉞ 取代） | 401 | 配对码不正确或已过期，请在 Opennote 里重新生成。 | **码号保留、0.3.1 起不再产出**：桥不再有配对码，因此这条不会出现；**不得复用该号**（00 号 §6.15㉞） |

#### IMP-3xxx 请求形态与来源

| code | 触发条件 | HTTP | 中文用户文案 | 客户端应如何反应 |
| --- | --- | --- | --- | --- |
| `IMP-3001` | `Origin` 不是扩展来源或本机应用来源（普通网页来源，或为 `null`） | 403 | 来源未被允许。本地接口只接受浏览器扩展与本机程序发来的请求。 | **不要重试**。本机接口只接受**扩展来源**（`chrome-extension://` / `moz-extension://`）与**本机应用来源**（`http://127.0.0.1:<port>` / `file://`），普通网页来源一律拒绝（00 号 §6.15㉞） |
| `IMP-3002` | JSON 解析失败 | 400 | 导入内容不是有效的 JSON，请重试。 | **不要重试**；修正序列化（常见原因：手写 JSON 有语法错、把 `body` 里的引号转义错） |
| `IMP-3003` | 请求体为空 | 400 | 导入内容为空。 | 检查是否真的发出了 body |
| `IMP-3004` | `Content-Type` 不是 `application/json` / `application/opennote+json` | 415 | （不显示给用户）请求格式不被接受。 | 设置正确的 `Content-Type`；**不要**降级成 `text/plain` |
| `IMP-3005` | 方法或路径不存在（含 `/v1/import` 上用了 GET） | 404 | （不显示给用户）接口地址或方法不对。 | 检查 endpoint 拼写与 HTTP 方法 |

> **`IMP-3001` 的展示口径**（04 号评审 RV-06）：**不进 toast、不进插件气泡**，但**要进设置面板的「被拒绝的来源」日志**（用户可见、可据此添加来源）——它是用户可自行解决的安全事件，不是纯内部错误。与此对照，`IMP-1005`（Host 校验失败）**完全不可见**（那是攻击特征或误配置，用户无从处置）。

#### IMP-4xxx 信封与落点

| code | 触发条件 | HTTP | 中文用户文案 | 客户端应如何反应 |
| --- | --- | --- | --- | --- |
| `IMP-4001` | 请求体不是 JSON 对象（数组 / 字符串 / null） | 400 | 导入内容格式不正确。 | 修客户端序列化 |
| `IMP-4002` | `spec` 缺失或不是 `opennote.import/v1` | 422 | 这个客户端版本太旧（或太新），请更新后再试。 | 提示升级插件/CLI；不要改字段名重试 |
| `IMP-4003` | 必填字段缺失或类型/取值非法（`title` 空、`source.capturedAt` 缺失或不可解析、`source.url` 协议非 http(s) 等） | 422 | 导入内容缺少必要信息（标题、来源时间或地址），请重试。 | 按 `detail.field` 修正。AI 场景：把 `detail.field` 读给自己，别猜 |
| `IMP-4004` | `body` > 8 MiB | 413 | 正文太长了（超过 8 MB），请分次导入。 | 拆分后分多次导入，**不要**截断用户原文 |
| `IMP-4005` | 请求体 > 16 MiB | 413 | 这次剪藏的内容太大（超过 16 MB），请分次导入或去掉图片。 | **不要原样重试**；缩小载荷或改走收件箱 |
| `IMP-4006` | 应用窗口不在场（窗口已关闭 / 渲染层无响应），无法转交落盘 | 409 | Opennote 没有在运行。请先打开 Opennote，再试一次。 | `retryable: true`。提示用户；若桥在窗口关闭时应已停止监听（8.1），此错误主要出现在「窗口正在关闭/卡住」的竞态里，重试一次即可 |
| `IMP-4007` | 工作区未打开（没有打开的笔记本文件夹） | 409 | Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。 | 提示用户；可用 `API-07` 先探测 `workspace.open` |
| `IMP-4008` | `target.folder` 非法（绝对路径、`..`、`\0`、`: `、超深、超长） | 422 | 目标目录不合法：不能使用 `..`、绝对路径或系统保留字符。 | 修正目录；**不要**自动「清洗」成别的目录（会写到用户没预期的地方） |
| `IMP-4009` | `target.notePath` 指向的文件不存在，或目录创建被拒（只读/权限） | 404 / 403 | 找不到要追加的那篇笔记，或目标目录无法创建（可能没有写入权限）。 | `404` 时改用 `conflict: new` 重发；`403` 时提示用户检查文件夹权限 |
| `IMP-4010` | 无法分配文件名（重试 500 次仍冲突） | 409 | 这个目录里同名文件太多了，请换一个目录或改标题。 | 换 `target.folder` 或改标题；不要空转重试 |
| `IMP-4011` | `conflict` 为 `append` 但找不到可追加的目标（来源索引与 `notePath` 都空）；或 `conflict: "overwrite"` 的四条件未全部满足（非桌面桥通道 / 设置未开启 / 未显式传 / 前像不可得）；或 `conflict: "skip"` 命中既有笔记 | 409 / 200 | 「追加」的目标不存在，已改为新建一篇。（`overwrite` 降级与 `skip` 情形不提示，靠回执 `status` 区分） | `409`：改用 `new` 重发；`200 + status: "skipped"`：视为成功；`200 + status: "created"` 且原本请求 `overwrite`：按降级处理（**不要把这次当覆盖成功**） |

| `IMP-4013` | 附件数量 > 32、附件合计 > 24 MiB、收件箱条目 > 500 | 413 | 附件太多或太大，请减少后用重新剪藏。 | 分批：先导入正文，再单独导入部分图片（P2 提供附件追加接口） |
| `IMP-4014` | 内部一致性错误（索引损坏无法解析、内容哈希计算失败等） | 500 | 导入时出现了内部错误，已记录日志。请重试一次。 | 重试一次；仍失败则提示用户查看「最近导入」的详情与日志 |

| `IMP-4017` | `API-03` 查询的 `importId` 不存在；或收件箱里出现重复 `importId` 的第二个条目 | 404 / — | 没有找到这条导入记录。 | 检查 `importId` 是否拼错；若刚提交，等 1 s 再查 |
| `IMP-4020` | 同一 `importId` 的在途提交超过 10 s 未完成 | 409 | 上一次导入还在进行中，请稍候重试。 | 等 2 s 后重试同一个 `importId`（幂等，安全） |

> **关于 `IMP-4006` 的措辞（已知并已裁定，不是缺陷）**：冻结文案是「Opennote 没有在运行。请先打开 Opennote，再试一次。」，而触发条件是「应用窗口不在场（窗口已关闭 / 渲染层无响应）」——macOS 上应用可能仍在运行但窗口已关闭。**对客户端而言这两种情况的结果相同**：桥的生命周期跟随窗口（8.1），窗口不在场时本地接口不可用，因此从客户端视角一律按「Opennote 没有在运行（对剪藏不可用）」呈现。**触发条件列保留事实描述不改**（它是内部语义），文案列按 00 号 §6.14㉗ 冻结。

### 6.3 错误码必须满足的三条性质

1. **稳定**：`code` 一旦发布不再改动含义、不再复用。新增错误用新号段，不复用已废弃的。
2. **可分支**：客户端只需要 `code` + `retryable` 就能决定行为，不需要读 `userMessage` 的中文。
3. **可解释**：每条都有 `userMessage`，且**不含**宿主机路径/用户名/令牌（主进程既有的脱敏实践：`scrubAbsolutePaths()`，`electron/main.cjs`）。

### 6.4 错误码→UI 文案的归属

`userMessage` 是**兜底文案**，UI 可以按 `code` 覆盖得更贴合场景（例如设置面板里说「本地接口未开启」而不是「本地接口未开启…然后重试」）。**但必须一一对应**：UI 里出现的每一种失败提示都要能追溯到某个 `code`，不允许出现「未知错误」这类兜底文案——真有未覆盖的情况，说明缺一个错误码，应该补号而不是加兜底文案。（03 号 UI 文档里的错误提示表应与 6.2 逐行对应。）

**这条自洽性包括通道侧的本地状态**：扩展 popup 里的 `unsupported_platform` / `no_window` / `queued_offline` / `write_failed` 四个原因码，各自映射到 `IMP-1006` / `IMP-4006` / 收件箱 `pending` / `IMP-5001`，映射表见 **5.7.7**。也就是说，`03` 号里不存在「映射不到 02 号」的用户可见提示。（04 号评审 RV-04 的关闭条件。）

## 7. 安全模型

导入接口的本质是：**给外部世界一个往用户磁盘写文件的入口**。在纯前端应用里，这是第一个这样的入口。因此本章按「威胁 → 对策 → 残留风险」逐条写，并在 7.6 给出**上线门禁**。

### 7.1 威胁清单与对策

| # | 威胁 | 触发场景 | 对策 | 残留风险 |
| --- | --- | --- | --- | --- |
| **T-01** | **恶意网页 CSRF-to-localhost** | 用户访问的任意网页用 `fetch`/表单向 `127.0.0.1:8787` 发写入请求 | ①`Content-Type` 必须是 `application/json`（非简单请求 → 触发预检）；②预检 `OPTIONS` 会走到 `Origin` 校验并被拒；③`Origin` **按类型判定：普通网页来源一律拒绝**（00 号 §6.15㉞）；④令牌（网页拿不到） | 无（普通网页来源在 Origin 这道就被拒；残留风险只剩「用户主动把令牌粘贴给某个程序」，见 T-10） |
| **T-02** | **DNS rebinding** | 恶意域名解析到 `127.0.0.1`，页面请求 `http://evil.com:8787/` | `Host` 头白名单（只认 `127.0.0.1[:port]` / `localhost[:port]`）；`Host` 由浏览器按 URL 生成、脚本无法伪造 | 无（只要白名单不含自定义域名） |
| **T-03** | **恶意剪藏内容**（正文或 SVG 附件里带脚本） | 剪藏一个含 `<script>`、`onerror=`、`javascript:` 的页面 | ①正文渲染走既有 DOMPurify（`src/lib/markdown.ts:12-26`）；②SVG 附件落盘前净化（拒 `<script`、`on*=`、`javascript:`、外部 `href`）；③正文里的原始 HTML 不额外放行 | 用户用外部编辑器打开该 `.md` 或直接在浏览器里打开本地 SVG 时，净化不生效（那是别的程序的信任边界） |
| **T-04** | **路径穿越与保留名** | `target.folder` 传 `..`、`C:\Windows`、`a.md:secret`（NTFS ADS）、`CON`/`NUL` | `assertSafeRelative()`（`src/fs/paths.ts:21`）+ 桌面侧 `resolveInsideRoot()` 的双层校验（拒绝对路径、`..`、`\0`、`:`）；保留设备名在 Node 与真实 OPFS 上都只是普通文件名（审计报告已核实） | 无已知缺口；后续新增任何「拼接路径」的代码都必须复用同一函数 |
| **T-05** | **junction / 符号链接越界**（D31） | 工作区里被植入指向工作区外的目录链接 | realpath 校验（`assertRealPathInsideRoot()`）；写入类操作检查**父目录** | **FSA/OPFS 后端没有 realpath 能力**，该场景下无对策 |
| **T-06** | **超大载荷 / zip bomb / 内存放大** | 16 MiB 的 JSON、400 MB 的 gzip URL 载荷、10 万个附件 | ①`Content-Length` 先于解析检查（16 MiB，超限不读 body）；②`body` ≤ 8 MiB、单附件 ≤ 8 MiB、附件合计 ≤ 24 MiB、数量 ≤ 32；③URL 载荷 gzip **解压时限流**（`maxOutputLength`），解压后 ≤ 256 KiB；④base64 解码前先按长度估算 | 16 MiB 的合法请求仍会驻留内存（JSON + base64 双份）→ 约 40–50 MB 峰值。可接受，但**不得**把上限调大而不重新评估 |
| **T-07** | **凭据泄漏（日志/URL/历史）** | 令牌被写进日志、查询串、错误消息 | ①`bridge.json` **之外**的任何地方都不得再复制明文（00 号 §6.15㊴ 允许该文件存明文，别处不行）；②日志与错误消息**绝不**含令牌；③禁止把令牌放 query；④`userMessage` 经脱敏检查 | 用户可能把令牌贴进聊天记录（这是用户行为，不是实现漏洞） |
| **T-08** | **本机其它进程读取凭据文件** | 同机另一个用户/程序读 `userData/bridge.json` | **明文与哈希同存**（00 号 §6.15㊴ 明确接受的取舍）：读到该文件即拿到令牌，因此 `userData` 与 `bridge.json` 的文件权限必须尽量收紧，且**不得**再宣称「只存哈希、读到也无用」 | 这就是 ㊴ 用「随时可复制」换来的代价：能读该文件的程序即获得**导入**能力（≠ 读笔记能力）；§7.7 的披露句必须如实写明 |
| **T-09** | **收件箱目录投毒** | 本机任意程序往 `.opennote/inbox/` 丢条目 | ①条目仍要过第 2 章全部校验；②落点仍由 L2 决定（信封不能指定绝对路径）；③`conflict: "overwrite"` 在收件箱通道**一律被忽略**（降级为 `new`，00 号 §6.7①：CLI / MCP / Skill / 扩展 / `opennote://` / 收件箱都不接受它）；④UI 明确显示「这条是外部投递的」 | 用户选「直接入库」模式时，本机程序可以静默往笔记本里加笔记——**这是本机信任边界的固有属性**（该程序本来就能直接写用户的 `.md` 文件），契约不试图解决，但**必须在设置面板写明**：开启收件箱/直接入库 = 本机上任何程序都能往笔记本投递 |
| **T-10** | **未配置令牌的客户端 / 恶意扩展** | 别的浏览器扩展尝试调用 | 令牌 + `Origin` **按类型判定**（只接受扩展来源与本机应用来源）；鉴权失败 10 次/分钟限流（`IMP-2003`） | 用户主动把令牌粘贴给某个扩展 = 授权（设置面板必须显示「谁在用」：客户端名 + 来源类型，让用户看见自己放进了谁）。0.3.1 起令牌即唯一凭据且长期有效（00 号 §6.15㉞） |
| **T-11** | **覆盖用户既有内容**（D03 / D08 / D12） | 导入撞上同名文件；导入用户正在编辑的笔记；OPFS 覆盖 | ①落点一律走 `resolveAvailablePath()`（磁盘探测）；②永不默认 `overwrite`，且**只有桌面版本地桥**能接受它（00 号 §6.7①：CLI / MCP / Skill / 扩展 / `opennote://` / 收件箱一律拒绝或降级）；③`append` / `overwrite` 写入前必须留下**逐字节前像**（3.3.3、`IMP-W008`），前像不可得时 `overwrite` 直接降级为 `new`；④`append` 前 `stat()` 比对；⑤浏览器后端按完整相对路径 + 磁盘实际文件名种子化去重（D12 的正确形态） | `overwrite` 一旦四条件齐备就有真实的覆盖能力——UI 必须给出不可忽略的警示文案；且因历史快照有约 3 分钟节流（`src/data/library.ts:98-99`，截至撰写时），**不得**用「有历史快照」代替前像来承诺可回退 |
| **T-12** | **静默数据损坏**（非原子写） | 写盘中途崩溃 | 桌面端 `writeFileAtomic()`（tmp + rename）；正文写入失败不留半截文件（3.6） | FSA/OPFS 的 `createWritable()` 语义由浏览器负责（审计 D37：失败路径不 `abort()` 不 `close()`，属既有缺陷） |
| **T-13** | **SSRF** | 若实现「应用去抓取 `source.url`」 | **不实现该能力**（5.6.3），从设计上消除 | 无 |
| **T-14** | **拒绝服务** | 刷 `/v1/import`；占满提交队列；端口抢占 | 令牌桶限流（60/分钟，突发 10）；单并发提交队列 + 10 s 排队上限（`IMP-4020`）；端口被占用时状态可见 | 持令牌的本机客户端可以把队列占满——同机信任边界内 |
| **T-15** | **隐私泄漏（剪藏历史）** | 索引/日志被同步到云端或提交进 git | ①日志放 `userData`，**不进工作区**；②索引只存标题/URL/哈希，**不存正文**；③`.opennote/` 建议已在 `.gitignore`（记入第 12 章） | 用户把工作区放进云盘时，索引里的 URL 会一起同步（内容本来就是明文 `.md`，故不增加泄漏面） |
| **T-16** | **跨源读取 `API-01` 的信息** | 任意网页探测本机是否有 Opennote | `API-01` 无鉴权但**不返回 CORS 头**，浏览器读不到响应体；返回字段压到最小（5.2.6） | 「是否存在一个本地服务」可被探测（端口是否有人监听），无法避免 |

### 7.2 为什么不给 `API-01` 加鉴权，也不给它加 CORS

- `API-01` 的价值是「未配置令牌的客户端也能判断桥开没开」——没有它，插件无法区分「桥没开」和「令牌错了」，用户只能看到一个笼统的失败。
- 它返回的信息是**用户自己的笔记本名称**与「有没有打开工作区」，不含路径、正文、统计。
- **不加 CORS 头**：跨源网页读不到响应体（浏览器强制），从而把「无鉴权端点」的信息暴露压到最小。
- 也不做 JSONP / `<script>` 兼容：那会主动绕过同源策略，等于把自己变成可被任意站点读取的接口。

### 7.3 输入校验的权威顺序（实现时必须按此顺序，且**不重复实现**）

```text
HTTP 层（5.2.4）       Host → Origin → Content-Type → 令牌
传输层（第 2 章）      spec → 必填字段 → 类型 → 长度/大小 → 枚举值
落点层（第 3 章）      sanitizeName() 逐段清洗 → assertSafeRelative() → 层级/长度上限
文件系统层（既有）      resolveInsideRoot() → assertRealPathInsideRoot()（Node 后端）
```

**任何一层都不得信任上一层的结论**（例如落点层仍要独立跑 `assertSafeRelative()`，因为收件箱的 `entry.json` 可能绕过 HTTP 层直接被读到）。

### 7.4 令牌与来源类型判据（0.3.1 起；原「令牌与配对码的对比」已被 00 号 §6.15㉞ 取代）

> **原表已作废**：「配对码」那一列（6 位数字、120 秒、一次性使用、5 次失败即作废、经请求体走 `API-06` 传递）随配对功能一并删除；`IMP-2004` 保留码号但不再产出。0.3.1 起桥的两道凭据是**长期令牌 + 按类型的 Origin 判据**：

| 维度 | 访问令牌 | Origin 类型判据（5.2.4 第 2 道） |
| --- | --- | --- |
| 长度 | 47 字符（`opn_` + 43） | 不适用（按来源类型判定，不比对白名单） |
| 有效期 | **长期有效**，直到用户在设置里「重新生成令牌」 | 每次请求都判定 |
| 一次性 | 否（长期使用） | 否 |
| 存储 | 服务端存 `sha256` + `last4` **+ 明文**（00 号 §6.15㊴，推翻 ㊲ 的「绝不落盘」） | 不需存储：扩展来源 / 本机应用来源按类型放行，遗留 `allowedOrigins` 条目不再参与判定 |
| 传递 | HTTP 头（`Authorization: Bearer` / `X-Opennote-Token`） | 请求头 `Origin`（无 `Origin` 的非浏览器进程放行，交由令牌这道把关） |
| 失败限流 | 10 次/分钟（`IMP-2003`） | 403 `IMP-3001`，且不返回任何 CORS 头 |
| 用户可见性 | **任何时候都能复制**（明文与 `sha256` / `last4` 一并存在本机 `bridge.json`，见 5.2.3 / 00 号 §6.15㊴）；配置方式 = **复制令牌 → 粘贴到客户端** | 用户不可见（按类型自动判定；普通网页来源一律拒绝） |

### 7.5 安全红线的可测断言（供实现阶段的自动化测试直接用）

```text
S-01  绑定地址必须是 127.0.0.1     → 断言 server.address().address === "127.0.0.1"
S-02  从不监听 0.0.0.0/::           → 断言任何情况下都不出现这两个地址
S-03  Host 为 evil.com:8787 → 403   → 断言不落盘
S-04  Origin 为 https://evil.com → 403 且响应无 Access-Control-Allow-Origin
S-05  Content-Type: text/plain → 415
S-06  无 Authorization → 401，且响应体不含 "opn_"
```

## 8. 与现有代码的接入点（只描述，不实现）

### 8.1 核心原则：桥不在主进程写盘

**决定**：本地桥在主进程只做「传输 + 安全校验」，**信封的落点决策与写盘一律转交渲染层**，由渲染层用既有的 `FileSystemBackend` + `resolveAvailablePath()` + 数据层函数完成。

理由（三条，任何一条都足以否定「主进程直接写盘」）：

1. **写盘必须与内存状态一致**。笔记身份是工作区相对路径，内存里有 `notes` / `dirty` / `knownStats` / 打开中的标签页 / 搜索缓存。主进程绕过数据层直接写文件，会造成「磁盘变了、内存不知道」——正是 D08 的形态。
2. **`rescanWorkspace()` 的第一步是 `flushAll()`**（`src/data/library.ts:405`）。若主进程刚追加写了一个**用户正打开且有未落盘改动**的笔记，紧接着触发的重扫会先把内存版本 flush 回磁盘，**把桥写的内容覆盖掉**。只有让写入发生在这套状态之内，才能避免这个覆盖。
3. **复用现有安全边界**。渲染层的 `FileSystemBackend` 已经走了 root 授权（D20）、`assertSafeRelative()`、原子写。主进程另写一套，等于多一份需要单独审计的写盘路径。

**后果（必须写清楚，避免实现时误解）**：

- 桥的可用性**依赖窗口在场**。窗口关闭（macOS 上）时桥应一并停止监听；下次创建窗口时按用户设置自动恢复。→ 新增错误码 `IMP-4006`。
- HTTP 响应的时延 = IPC 往返 + 落盘时间（本地通常 < 50 ms），仍在插件可接受的范围内。
- 收件箱的入库（5.8.3）走**同一条**「转交渲染层」的路：主进程只负责发现条目，入库动作由渲染层执行（唯一例外见 8.1.1）。

#### 8.1.1 唯一例外：主进程可写「收件箱队列元数据」（00 号 §6.10②）

「主进程不写盘」这条原则**针对的是笔记正文**（理由 2 就是 `flushAll()` 会覆盖它）。收件箱的**队列/状态元数据**不属于笔记正文，允许主进程写，但这是**唯一例外**，且必须同时满足四条约束：

| # | 约束 | 说明 |
| --- | --- | --- |
| ① | **只允许**写 `.opennote/inbox/` 下的队列/状态文件（`state.json`） | **绝不**触碰任何 `.md` 笔记与 `assets/`。写路径必须经 `assertSafeRelative()` + `resolveInsideRoot()`，且根必须来自主进程自己的「当前打开工作区」状态，**不来自请求体** |

### 8.5 为什么「入库后通知渲染层重扫」是不可省的一环

三个独立理由，缺任何一个都会出现「导入成功但界面看不到」或「看到了错的版本」：

1. **收件箱路径收不到任何通知**。主进程的 watcher 显式跳过 `.opennote/**`（避免自写循环）。没有新频道，外部投递的条目就只能等 30 s 轮询甚至下次启动——AI 说「已导入」，用户盯着一动不动的侧栏。
2. **桥的写入与渲染层内存状态是两份事实**。`rescanWorkspace()` 会重建 `notes`，但**已打开的标签页内容不会自动重载**（`reconcileTabs()` 只处理标签的有效性）。要让用户看到刚追加的段落，必须显式重载该笔记。
3. **`rescanWorkspace()` 会先 `flushAll()`**（`src/data/library.ts:405`）。这意味着「重扫」不是只读操作——它会把内存里的未落盘改动先写回磁盘。所以通知的**时机与顺序**很重要：必须在写入完成并更新了内存状态之后再触发重扫，否则重扫的 flush 会覆盖刚导入的内容（8.1 的理由 2）。

- `src/desktop/bridge.ts`：`OpennoteBridge` 接口同步扩展；`ImportEnvelope` / `ImportResult` / `ImportRecord` / `InboxEntry` / `BridgeStatus` 类型定义在同一文件里。
