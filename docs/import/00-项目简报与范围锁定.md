## 1. 想法来源（原始需求，未加工）

用户原话要点：

1. 在网站或其他地方看到**片段**，希望能「剪切过来」，剪到自己的 Opennote 里。
2. 网页场景 → 需要**浏览器插件**，通过**某个接口**导入 Opennote。
3. 在 Codex、Claude 等 AI 软件里工作，有时有文章需要记录 → 会**让 AI 执行某个 skill**，把这些需要记录的文件/内容导入 Opennote。
4. 核心诉求一句话：**Opennote 需要提供一些接口，方便外部把内容导进来。**
5. 团队分工：产品经理写需求文档，设计师设计 UI；**UI 要简洁美观，符合现在的应用**；本阶段只出文档。

因此本文档把「导入接口」视为一等公民：先定义**统一的导入信封（数据契约）**，再把插件、CLI、Skill、MCP、分享面板等视为**同一信封的不同传输通道**。这样可以避免「N 个客户端 × M 套导入逻辑」的碎片化。

## 2. 事实基线（全部来自当前代码，写文档时可直接引用）

> 以下每一条都已由 Lead 在读代码时确认。01/02/03 号文档若做相反假设，视为错误。

1. **Opennote 0.2.0 是纯前端应用，没有服务端、没有账号、没有遥测。** 笔记就是用户选定文件夹里的 `.md` 文件（`README.md` 开篇即此承诺，`package.json` 只有前端依赖，无 HTTP 框架）。
2. **三种文件系统后端共用一层接口** `FileSystemBackend`（`src/fs/types.ts:19`）：Electron 的 Node `fs`、Chromium 的 File System Access API、任意现代浏览器的 OPFS。**只有 Electron 桌面版拥有「无需页面在场即可写磁盘」的能力**；FSA 需要页面持有句柄授权，OPFS 是浏览器私有存储、外部进程无法访问。
3. **现有导入只有「用户手动搬文件」一条路**：`importIntoWorkspace(input: FileList | File[], targetFolder)`（`src/lib/import.ts:40`）——拖拽 / 文件选择器 → `.md` 变笔记、`.zip` 变整库、图片进 `assets/`；同名用 `uniquePath()` 自动加 ` 2` 后缀（`src/fs/paths.ts:89`），**不会覆盖**。入口在设置 · 文件：「导入文件或 zip」（`src/components/AppDialogs.tsx:241`）。
4. **笔记的身份是「工作区相对路径」**，不是 id 映射：`libraryStore.get().notes` 以 POSIX 相对路径为 key（`src/lib/import.ts:50`）。因此「导入到哪」= 目录 + 文件名，文件名由标题经 `sanitizeName()`（`src/fs/paths.ts:79`，CJK 友好、限 80 字）清洗后决定。
5. **front-matter 目前只被用于 tags**：`splitFrontMatter()`（`src/lib/utils.ts:54`）要求 `---` 位于文件**最开头**（允许 BOM），`deriveTags()`（同文件 `:132`）只解析 `tags: [a, b]` 或 `tags:` 块列表两种写法。**其他 front-matter 键（如 `title:`、`source:`）当前是惰性的**——会被 `deriveTitle()`/`stripMarkdown()` 当元数据跳过后忽略。这是本方案的关键可利用点（可安全承载来源信息），也是关键陷阱（**写了 `title:` 不会改变笔记标题**，标题必须来自正文 H1 或 state 里的 `titleOverride`）。
6. **标题推导规则**：`deriveTitle()` 取正文（去 front-matter 后）**第一个标题行**，否则第一行非空文本（`src/lib/utils.ts:61`）。所以「导入标题」的正确写法是写入 `# 标题`，而不是依赖文件名或 front-matter。
7. **桌面安全基线**：`contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`；渲染层只能通过 preload 的 `window.opennote` 说话；IPC 命名 `opennote:<group>:<op>`。

## 3. 设计张力（这是本需求真正的难点，文档必须正面回答）

| 张力 | 说明 | 必须回答的问题 |
| --- | --- | --- |
| **无服务端 × 要有接口** | 没有云端就意味着没有「一个 API 域名」，接口只能落在「本机进程 / 浏览器页面 / 文件系统」三种介质上 | 每种介质分别能提供什么？各自的适用平台与降级路径是什么？ |
| **三种后端能力不对等** | 只有桌面版能「外部直接落盘」；网页版要么页面在场，要么只能靠用户手动搬运 | 同一个「剪藏」动作在桌面 / Chrome网页 / 其他浏览器 / 移动端 分别是什么体验？差距要如实写明，不许糊过去 |
| **自动入库 × 不静默改文件** | D03/D08/D12 说明现有覆盖语义本身不可靠；而插件/AI 是「无人值守写入」 | 冲突（同名、同 URL 重复剪藏、用户正在编辑该文件）时的默认行为是什么？如何做到可撤销？ |
| **便利 × 本地接口安全** | 一个 `127.0.0.1` 的写入接口意味着**任何网页**都可能尝试 POST 到它（DNS rebinding / CSRF-to-localhost） | 绑定、鉴权、Origin 校验、token 生命周期、拒绝策略要写到可实现的粒度 |
| **来源信息 × 纯文本承诺** | 剪藏必须保留 URL/作者/时间，但正文必须是「换个编辑器也能看」的普通 Markdown | 元数据放哪？front-matter（Obsidian 兼容、但 `title:` 惰性）还是 `.opennote/`？重复剪藏如何识别？ |
| **新建面板 × 现有信息架构** | 应用已有侧栏四页签（文件/搜索/标签/星标）、命令面板、设置五类（外观/文件/编辑/视图/帮助）、状态栏 | 新增 UI 放在哪里最不打扰？是否需要新的侧栏页签？如何用现有命令注册表暴露入口？ |

## 4. 锁定的能力分层（所有文档用这一套分层说话）

```
L3  客户端       浏览器插件 · CLI · AI Skill · MCP Server · 分享面板 · 快捷指令
                        ↓ 都产出同一种东西
L0  导入信封     opennote.import/v1 —— 与传输无关的数据契约（标题/正文/来源/附件/冲突策略）
                        ↓ 通过某种介质送达
L1  传输通道     本地桥(HTTP 127.0.0.1) · 命令行 · URL scheme · 页面内桥(postMessage) · 收件箱目录 · 剪贴板
                        ↓ 交给应用
L2  应用内接收   落点决策（哪个笔记本/哪个目录）· 去重与冲突 · 收件箱/直接入库 · 提示与撤销 · 重扫刷新
```

**为什么先定 L0**：插件、CLI、Skill、MCP 四条路如果各自定义字段，就会出现「插件写的 `url` 和 CLI 写的 `source` 对不上」这种永久债。锁定信封 = 四条通道天然互通。

## 6. 锁定的选型与默认值（01/02/03 必须与此一致；如有异议，在文档里写「建议变更 + 理由」，但不得静默偏离）

### 6.1 导入信封字段名（JSON，`opennote.import/v1`）

```
{
  "spec": "opennote.import/v1",
  "importId": "<uuid，客户端生成，幂等键>",
  "title": "<笔记标题>",
  "body": "<Markdown 正文>",
  "source": {
    "url": "<原始 URL 或 null>",
    "title": "<网页标题或 null>",
    "site": "<站点名或 null>",
    "author": "<作者或 null>",
    "publishedAt": "<ISO8601 或 null>",
    "capturedAt": "<ISO8601，必填>",
    "selection": true
  },
  "target": { "folder": "<工作区相对目录，null = 根目录>", "notePath": "<追加时指向已有笔记，可为 null>" },
  "conflict": "new | append | skip | overwrite",
  "tags": ["<标签>"],
  "assets": [ { "name": "<文件名>", "mime": "<MIME>", "dataBase64": "<base64>" } ],
  "client": { "name": "chrome-extension | cli | mcp | share-target | manual | other", "version": "<语义化版本>" }
}
```

### 6.2 入库后的文件形态（锁定的 front-matter 键名）

写入 `.md` 时，正文第一行是 `# {title}`（因为 `deriveTitle()` 只认正文标题），来源信息以 YAML front-matter 置顶，**仅使用下列键**：

```
---
source: <url>
source_title: <网页标题>
source_site: <站点名>            ← v2 新增（采纳 02 号异议 2）
author: <作者>
published_at: <ISO8601>          ← v2 新增（采纳 02 号异议 2）
captured_at: <ISO8601>
tags: [标签1, 标签2]        ← 唯一被应用解析的键，写法必须能被 deriveTags() 认出
opennote_import_id: <importId>
---

# <title>

<正文>
```

约束：
- `tags:` 必须用 `[a, b]` 行内数组或块列表两种之一，且标签需通过 `normalizeTag()` 的字符规则（`src/lib/utils.ts:153` 附近）。
- front-matter 必须位于文件最开头（BOM 可），否则 `splitFrontMatter()` 不识别。
- **不得**依赖 front-matter 的 `title:` 改变笔记标题；`title` 只体现在 H1 与文件名上。
- 重复剪藏判定：优先 `opennote_import_id`，其次 `source` + `body` 内容哈希。
- 附件写进所在目录的 `assets/`，正文用 `./assets/xxx.png` 相对路径（与现有粘贴图片行为一致，`src/lib/import.ts:88`）。

### 6.3 冲突默认值

| 场景 | 默认 | 允许的其它策略 |
| --- | --- | --- |
| 同名文件已存在 | `new`：自动加序号（沿用 `uniquePath` 的 ` 2` 语义） | `append`（追加到该笔记）/ `skip` |
| 同一 URL 重复剪藏 | `append`：追加到已有同名来源笔记，带时间分隔 | `new` / `skip` |
| 用户正在编辑该笔记 | 不自动覆盖；走 `append` 或进入收件箱 | — |

### 6.4 默认入库模式（产品决策，已锁定）

**默认「直接入库 + 应用内可撤销提示」**：桌面版收到信封后写入工作区，应用内以现有 toast 机制提示「已从网页剪藏：xxx · 撤销」，并在状态栏/侧栏可见。**设置里提供「先进入收件箱等待确认」开关**，开启后所有外部导入先落 `.opennote/inbox/`，由用户在「收件箱」里逐条或批量确认。

理由：AI 场景（「帮我把这篇记录一下」）要求零摩擦；而误剪的可撤销性比事前确认更符合写作时的注意力经济学。此默认值如需推翻，01 号文档必须给出新默认 + 理由 + 对 AI 场景的影响分析。

### 6.13 修订 v7 —— Lead 在实现阶段对文档自身歧义与一处契约缺陷的裁定

实现阶段（2026-09-29）逐条蒸馏 `02` 号时暴露出若干文档内部不一致与一处**契约级缺陷**。以下裁定**效力高于 01/02/03 的既有文字**，实现与验收一律以此为准；契约字段名、错误码编号、front-matter 键名**均未改动**。

**① 契约级缺陷修补：`POST /v1/pair` 的 Origin 校验死锁。**
`02` §5.2.6 同时规定「配对需要 Host 校验与 Origin 校验都通过」与「配对成功自动把请求 `Origin` 加入 `allowedOrigins`（默认空）」。浏览器的扩展来源（`chrome-extension://<id>`）在配对前必然不在信任列表 → 第一次配对必被 403 `IMP-3001` → **配对流程不可达**，插件「需要配对」状态永远解不开。

裁定：`POST /v1/pair` 上，`Origin` 匹配 `chrome-extension://<id>` 或 `moz-extension://<id>`（`<id>` 为 `[a-z0-9]{8,64}`）时**视为通过第 2 道校验**，进入配对码校验；**仅当配对码正确时**才把该 Origin 写入 `allowedOrigins`；配对码错误时不写入。
边界：该放宽**只作用于 `/v1/pair`**。`/v1/import`、`/v1/imports*`、`/v1/tags`、`/v1/workspace` 对未受信 Origin 仍 **403 `IMP-3001` 且不返回任何 CORS 头**。「无 `Origin` 头放行」（curl/CLI/MCP/原生程序）保持不变——Chrome 扩展在 `host_permissions` 覆盖下发起 `fetch` 时可能不带 `Origin`，该分支正好覆盖。
取证要求：安全断言 S-04 之外补三条——①未受信扩展 Origin + 正确配对码 → 200 且 `allowedOrigins` 含该 origin；②同上 + 错误配对码 → 401 `IMP-2004` 且 `allowedOrigins` **不含**该 origin；③`https://evil.com` + 正确配对码 → 403 `IMP-3001`。

**② `warnings[]` 形状冲突**（§2.6 对象 `{code,message}` vs §4.5 `string[]`）：**裁定用 `string[]`**，形如 `["IMP-W002 有未声明的本地附件引用"]`。

**③ 落点序号上限的错误码冲突**（§3.3.2 写 `IMP-4014` vs §6.2 写 `IMP-4010`）：**裁定用 `IMP-4010`（409）**。「文件名重试 500 次仍冲突」是**落点问题**，不是内部一致性错误；`IMP-4014` 保留给索引损坏/哈希计算失败等真正的内部错误。

**④ 撤销窗口时长**：`02` 号完全未写毫秒值。**裁定 = 10000 ms**（冻结值来自 `01` FR-25 与 `03` O-4），且实现**必须显式传 duration**——`src/lib/toast.ts` 的 `notify()` 对带 action 的提示默认 **6000 ms**，不满足要求。撤销成功后提示停留 2600 ms（默认值）。

**⑤ 默认落点**（开放问题 Q-6）：**裁定 = 工作区根目录**。依据 `03` 号设计稿 popup 落点下拉的默认项即 `根目录`，且 `01` FR-15 的兜底链最后一级就是根目录。同时明确：**契约中不存在名为「收件箱」的落点目录**——「收件箱」只指队列目录 `.opennote/inbox/` 与设置开关「先进入收件箱等待确认」。

**⑥ `receiveEnvelope()` 的错误表达**：域错误（`IMP-4002/4003/4008/4012/5001` 等）**抛 `ImportRejection`**（字段 `code`/`message`/`userMessage`/`http`/`retryable`/`detail`，配 `isImportRejection()` 守卫），以对齐 §6.1 的统一错误响应。另**必须**提供**永不抛异常**的 `receiveEnvelopeOutcome()`（返回 `{ok:true,result}|{ok:false,error}`）供 IPC 转交使用——Electron `ipcMain.handle` 会把抛出的异常退化成字符串，结构化字段会丢失，桥就无法把 `IMP-4008` 映射成 422、`IMP-5001` 映射成 500。二者共用同一内部实现。

**⑦ preload 命名缺口**（§10 只授权新增 `import`/`bridge` 两个命名空间，却要求 `opennote:inbox:*` 三个 invoke 可用；两个订阅方法的挂载位置亦未写死）。裁定：
- 收件箱三个操作归入 `import` 命名空间：`opennote.import.inboxList()`（arity 0）、`opennote.import.inboxCommit({ id })`（1）、`opennote.import.inboxDiscard({ id })`（1）。
- 订阅方法挂**顶层**：`opennote.onImportNotice(callback)`（1）、`opennote.onInboxChanged(callback)`（1），均返回退订函数（与既有 `onMenu` 同构）。
- `bridge` 命名空间的 7 个方法 arity 逐字：`status()` 0、`start({ port? })` 1、`stop()` 0、`newToken({ origin? })` 1、`newPairCode()` 0、`removeOrigin({ origin })` 1、`openLog()` 0。
- 新增一律**只追加**；既有频道名与既有 preload 方法名/参数个数不得改动（`scripts/ipc-safety-check.cjs` 会冻结）。

**⑧ 通道上下文与 `overwrite` 四闸门的落地载体**：信封里没有通道信息，而闸门 2「仅桌面版本地桥」与闸门 3「用户显式开启的进阶开关」需要运行时上下文。裁定由 L2 接收端导出：
`setImportChannelContext({ channel: "in-app" | "local-bridge" | "inbox" | "inpage"; overwriteEnabled: boolean })` 与 `getImportChannelContext()`；默认 `{ channel: "in-app", overwriteEnabled: false }`。
`conflict: "overwrite"` 仅当「客户端显式请求 + `channel === "local-bridge"` + `overwriteEnabled === true` + 成功写下前像」四道同时满足才生效；否则**降级为 `new` + 警告**。本地桥转交前设 `"local-bridge"`，收件箱入库设 `"inbox"`，应用内保持 `"in-app"`。

**⑨ 收件箱变更检测**：`.opennote/**` 被既有工作区监听跳过，故采用「独立 watcher 为主 + 轮询兜底」：`watch(<workspace>/.opennote/inbox, { recursive: true, persistent: false })`，去抖 **450 ms**，广播 `opennote:inbox:changed`，payload `{ root, pending }`；watch 失败时静默降级为每 30 s 轮询（窗口可见时）+ 重新获得焦点时一次，并在设置面板如实显示降级状态。**不放宽** `.opennote/**` 的跳过规则。

**⑩ `committedAt` 与 `dedupedBy:"sourceUrl"`**：`committedAt` 出现在 §5.2.6/API-03 示例但不在 §4.5 规范字段表——**作为可选字段保留，不作为验收必查项**；`dedupedBy` 的 `"sourceUrl"` 枚举保留但判定链不产出该值，验收只看 `importId`/`contentHash`/`null`。

**⑪ 桥回执通道（实现缺口，`02` §10 未定义）。** §10 只授权新增 `import`/`bridge` 两个命名空间，但桥把信封转交渲染层后**必须**有一条回执路径，而 `ipcMain.handle` 的返回值语义不适用于「主进程主动发起、渲染层被动应答」。
裁定：新增两条**单向**通道——主→渲染 `opennote:import:receipt`（payload `{ reqId, envelope, client }`，`envelope` 为**原始 JSON 字符串**，解析由渲染层负责，避免主进程与渲染层两份解析器漂移）、渲染→主 `opennote:import:reply`（`(reqId, outcome)`，arity 2）。preload 侧为顶层订阅 `onImportReceipt(cb)`（1）与 `import.replyToImport(reqId, outcome)`（2）。
同构地，其余导入/收件箱操作走 `opennote:import:request`（主→渲染，payload `{ reqId, op, args }`，`op` ∈ `recent|undo|log|inboxList|inboxCommit|inboxDiscard`）与同一个 `replyToImport` 回执；preload 订阅 `onImportRequest(cb)`（1）。
**落地纪律**：这两条通道在主进程里**只是转发**，渲染层是唯一实现（`src/App.tsx` 的分发表）。主进程**不得**为它们复制任何工作区读写逻辑——否则就是「主进程写笔记正文」，违反核心原则。`replyToImport` 的回执形状对信 envelope 一路是 `ImportOutcome`（`result` 必为 `ImportResult`），其余操作用途不同（列表 / 撤销结果 / `void`），故类型上放宽为 `result: unknown`；这不放松任何契约字段。
渲染层 5 000 ms 不应答 → 主进程回 `IMP-4006`（409，`retryable`）；桥侧 10 000 ms 超时 → `IMP-1004`（504）。**两处都不得假成功。**

**⑫ `ImportUndoResult.mode` 增加 `"none"`。** 契约 §4.5 只列 `preimage|trash|snapshot`，但「既没有前像、回收站也失败」是真实可达状态。裁定：保留三个既有值并**追加 `"none"`**；`"none"` 时文案不得承诺任何可恢复性。

**⑬ `overwrite` 本轮无 UI 承载，一律降级。** §6.13⑧ 的第 3 道闸门是「用户显式开启的进阶开关」。本轮**不提供**该开关的界面，故实现里 `getAdvancedOverwrite()` **恒返回 `false`**，任何 `conflict: "overwrite"` 都走「降级为 `new` + 警告 `IMP-4011`」。这是**有意的保守选择，不是遗漏**：宁可不做，也不给一个没有 UI 依据的静默开启路径。CLI/扩展/MCP/Skill/URL scheme/inbox 六条通道**照旧永不接受** `overwrite`，与「四闸门」规则一致。

**⑭ 收件箱文件的单一写者。** `entry.json`/`body.md`/`assets/` 由**渲染层**经既有 `opennote:fs:*` 写入（同一授权根边界）；`state.json` 由**主进程**唯一的 `writeInboxStateAtomic()` 写入（`writeFileAtomic` + 500 ms 自写静音）。理由：桥需要把「已交付客户端」这类状态落盘，而那是主进程才知道的事实；同时避免渲染层与桥对同一个 `state.json` 竞写。桥的 `onInboxStateWrite(entryId, stateJson)` 挂钩形态是 **(entryId, stateJson)**（根路径由主进程用 `currentWorkspaceRoot` 补——该变量由 `opennote:fs:watchWorkspace` 成功时设置，即「用户打开了这个笔记本」的信号）。
另：`import.inboxList/inboxCommit/inboxDiscard` 三条 IPC **注册为转交渲染层**（见⑪），主进程不实现收件箱读写。

**⑮ 配对的令牌交付与轮换。** `02` §5.2.6 要求配对返回令牌，但服务端只存 sha256 → 已有的令牌明文无法回放，原实现会给客户端 `token: null`（**假成功**）。
裁定：`regenerateToken()` 把明文暂存**内存**（绝不持久化、绝不写日志）；配对时①有未交付的明文 → 直接交付且 `rotated:false`；②明文已交付过 → **轮换**出一把新的交付并带 `rotated:true`，旧令牌立即失效。**UI 必须在 `rotated:true` 时提示**「已为该客户端生成新令牌，其它已配置的客户端需要重新配置。」
边界：HTTP/1.1 缺 `Host` 时 Node 的解析层会先回 400 空体（应用层不可达）；应用层那条 `400 IMP-1005` 路径覆盖 HTTP/1.0 无 `Host`。两种都**不落盘**。

**⑯ `url: null` 的判定链读法。** §4.1 推论 5 只定义「两次都不带 URL 且正文相同 → 第 2 步判重复」。裁定：**`null` 不是可追加/可进收件箱的来源**——「两次都不带 URL + 正文不同」走第 6 步**新建**，绝不追加。理由：把两段互不相关的记录合并是**静默毁内容**，危害远大于多出一篇笔记。`lookupLatestBySourceUrl(null)` 返回 `null`。

**⑰ 设计令牌零新增的落地口径。** 本轮 UI 复用的令牌全部来自 `src/styles/tokens.css` 既有 55 个自定义属性；新增样式表规则**不得**引入任何新自定义属性。特别地：错误句、状态句、按钮文字**禁止**使用 `--ink-3`（素笺约 3.2:1、夜读约 4.1:1，均低于 4.5:1），一律用 `--fs-sm` + `--ink` 或 `--accent`。设计稿里 `--mono` 的写法是**笔误**，真实令牌名是 `--font-mono`。

**⑱ 新增的三个用户设置项（R1/R2/R8）。** 落入既有 `UiSettings`（`src/data/types.ts`），键名 `importConflict` / `importNotify` / `bridgeLog`，默认值 `"new"` / `true` / `true`；`load()` 走 `{ ...DEFAULT_UI, ...parsed }`，旧数据不含新键时自动取默认值，不破坏既有持久化格式。
`importConflict` 的枚举**只有** `"new" | "append" | "skip" | "inbox"`——**`overwrite` 不在其中**，且在 UI 里不得出现。

**⑲ 扩展的装配层。** `extension/src/manifest.json` 保留在 `src/` 层，由零依赖的 `extension/build.mjs` 输出到 **`extension/dist/`**（该目录根部直接有 `manifest.json`）。用户在 `chrome://extensions` 加载的是 **`extension/dist`**，README 必须逐字写明这一层。**canvas 之外不得有构建期网络访问**；`build.mjs` 只做复制、令牌注入与图标生成。

**⑳ `conflict` 键的缺省语义（跨线集成缺陷）。** 判定链第 3/4 步（同 URL 不同正文 → `appended` / `pending`）的**唯一触发条件是「客户端没有显式下发 `conflict`」**。
因此：**扩展在下发信封时默认不得包含 `conflict` 键**；`ENVELOPE_KEYS` 与 `envelopeProblems()` 对 `conflict` 的规则是「**缺省允许，有则校验**」——若存在必须是 `new|append|skip` 之一（`overwrite` 在插件通道上**照旧一律拒绝**）。
popup 里「直接入库」这一项的语义 = **不下发 `conflict`**，而不是下发 `"new"`。
依据：`src/lib/clip/envelope.ts` 专门用 `conflictExplicit` 区分「缺省」与「显式 `new`」，若客户端总是显式下发，收件箱在插件通道上**永远不可达**（5 态机、保留期、面板、commit/discard 全成死代码）。

**㉑ `IMP-5002` 补入 `02` 附录 A.3，且文案必须与 `IMP-1001` 区分。** `electron/bridge.cjs` 在 `state.status !== 'running'` 时发出 `IMP-5002`（HTTP 503，`retryable`），但该码未登记在附录 A.3，且其 `userMessage` 与 `IMP-1001` 逐字相同——两者对用户是**不同的下一步动作**（`IMP-1001` = 从没开过本地接口；`IMP-5002` = 开过但当前不在运行态），同文案即误导。
裁定：保留 `IMP-5002` 并登记，`userMessage` = `本地接口当前不在运行状态。请先在 Opennote 的「设置 · 文件 · 导入与接口」里开启接口，再重试。`

**㉒ `inboxId` 是收件箱目录名，不是 `importId`。** `02:719` 与 §5.8.2 已定死：`inboxId` = `YYYYMMDDTHHMMSS`(UTC) + `-` + `importId` 前 8 位。
裁定：回执中的 `inboxId` **一律返回磁盘目录名**。`InboxEntry.id`（条目身份，完整 `importId` 派生）与 `inboxId`（磁盘目录名）**不等价**，实现注释必须写明，避免后来者混用。同一份回执里已有 `importId` 字段，`inboxId` 再返回 `importId` 是冗余且会让客户端拼路径失败。

**㉓ `extension/src/manifest.json` 不得出现 `"default_locale": null`。** MV3 要求 `default_locale` 要么是字符串、要么**整个键不存在**；`null` 非法，可能导致加载被拒。`build.mjs` 加一条自检（存在时必须是字符串）。

**㉔ 收件箱标识双解析，且「查不到」一律报错、绝不静默。** `02:719` 把 `inboxId` 定义为**目录名**并作为客户端抓手，因此 `readInboxEntry` / `readInboxDetail` / `setInboxStatus` / `commitInbox` / `discardInbox` **五个入口必须同时接受「`importId`」与「目录名」两种写法**，解析只在一处（`findDir`），`importId` 精确匹配优先，目录名**精确**匹配（前缀/后缀不算命中）。
查不到时**一律抛 `IMP-4017`（`409`）**——`discardInbox` 原先「找不到就 `return`」是 §8 明令禁止的**静默成功**（客户端拿回执的 `inboxId` 去丢弃会「以为删了其实没删」）。
**语义拉伸备案**：`02:1706` 把 `IMP-4017` 定义为「查询的 `importId` 不存在 / 收件箱出现重复 `importId` 的第二条」，用它承载「丢弃目标不存在」是对该码场景清单的拉伸。**采纳此拉伸**，理由：它是唯一逐字冻结的「查不到」文案，明确报错远优于静默；且面板已有 catch → danger toast，界面会如实提示。
边界不变：`discarded` 仍是 `rm -r`、**不进回收站**、无「恢复」入口；`listInbox()` 与 `InboxEntry.id` 对外仍是 `importId`（本次为纯增量）。

## 6.14 · 0.3.0 追加裁定（收件箱为主入口 + Web Clipper 式剪藏）

> 优先级同上（**高于 01/02/03**）。用户原话需求：①「不用先打开」指的是**不用先打开某一篇笔记文件**，Opennote **应用本身需要打开**；②剪藏方式照 Obsidian Web Clipper（MIT 开源）；③内容**直接进收件箱**（默认）；④在收件箱里再决定保存到哪；⑤文案要改。Web Clipper 的四项能力（**高亮 / 按站点模板 / 属性面板 / 追加到指定笔记**）**全部要**。

**㉕ 「先进入收件箱」默认开启，且它就是 `UiSettings.importConflict`。**
`importConflict` 的默认值由 `"new"` 改为 **`"inbox"`**（`src/data/types.ts` 的 `DEFAULT_UI`）。语义（**本节核心规则**）：
- 当 `importConflict === "inbox"` **且通道不是 `"in-app"`**（即 `local-bridge` / CLI / MCP / Skill / URL scheme / 收件箱 / in-page）时：**该次导入强制 `pending`（进收件箱）**，跳过判定链第 2–6 步。
- **第 1 步（同 `importId` → `deduped`）依然优先**：重投同一个 `importId` 不得产生第二条收件箱条目（幂等）。
- 目录、文件名、信封校验、附件上限**全部照旧**（只是不改笔记文件）。
- 该设置是**应用侧用户的显式意愿，优先级高于客户端下发的 `conflict`**；但 `overwrite` 的四道闸门红线**不变**（仍只可能由本地桥在四条件齐备时触发）。
- `channel === "in-app"`（应用内自己发起）**不受影响**，仍是直接落盘 + 可撤销 toast。

**㉕.1 「外部通道」的准确范围（澄清，避免死循环）。** 强制 `pending` **只对 `channel === "local-bridge"` 与 `"inpage"` 生效**。
**必须排除 `channel === "inbox"`**：收件箱的「确认入库」走的是 `setImportChannelContext({ channel: "inbox" })` + 复投同一封信封（`src/data/inbox.ts` 的 `commitInboxResult`），若它也被强制 `pending`，用户点「确认入库」会被原样塞回收件箱——**死循环**。`inbox` 通道的语义是「用户正在确认这条已入队的条目」，不是「外部投递」。
（CLI / MCP / Skill 经由本地桥进来，仍是 `local-bridge`，已被覆盖；外部程序直接往 `.opennote/inbox/` 投递的文件本身就是 `pending`，无需再判。）

**㉕.2 「先进入收件箱」优先于客户端下发的 `conflict`（含 `overwrite`）。** 用户在应用里显式选择了「外部导入先进入收件箱」，这是**不可被客户端绕过**的意愿：`pref === "inbox"` 时判定链在第 1 步之后直接进收件箱，**根本走不到 `overwrite` 分支**。`overwrite` 的四道闸门代码**一行不动**（保留为纵深防御），只是在本偏好下不可达。
理由：`overwrite` 是本系统里**最不可逆的无审阅写入**，正是这个设置要拦的对象；若客户端能靠显式传值绕过它，这个设置就会变成又一个「假开关」。

**㉖ `importConflict` 必须真正接线。** 0.2.0 里它只被 `ImportApiPanel`（改 UI 值）与 `AppDialogs`（传值）引用，`src/lib/clip/receive.ts` **从不读它**——用户改了「先进入收件箱」而行为不变，是**假开关**。这是第 4 例同类缺陷（前 3 例：`bridgeStatusPayload` 截断字段、`getWorkspaceInfo` 漏传、`isLogEnabled` 未接线）。**根因是「UI 层的偏好没有通向行为层」，本节要求它必须是行为层的真输入。**

**㉗ 文案：区分「应用没运行」「工作区没打开」「某一篇笔记没打开」三件事。**
用户反馈 `IMP-4007`「Opennote 里还没有打开笔记本」会被读成「要先打开一篇笔记」。三条文案逐字冻结：
- `IMP-4007`（**应用在运行、但工作区没打开**）：`Opennote 里还没有打开笔记本文件夹。请在 Opennote 左侧选一个文件夹，或新建一个，再试一次。`
- `IMP-4006`（**应用没运行**，S12）：`Opennote 没有在运行。请先打开 Opennote，再试一次。`
- 扩展离线暂存（S11）：`Opennote 没有在运行，内容已暂存在插件里，打开 Opennote 后会自动补投。`
**禁止**再用「还没有打开笔记本」「请先打开一个文件夹（或新建浏览器笔记本）」这类措辞。

**㉘ UI-01 重构为 Web Clipper 模式。** 分段控件由「选中片段 / 整页正文」改为 **`正文` / `高亮` / `属性` 三区**；「选中片段」降级为正文区里的一个来源开关（页面有选区时默认取选区）。新增：**模板选择器**（按当前 URL 自动匹配、可手动切换）、**属性面板**（可视化编辑 `title` / `source.url` / `source.title` / `source.site` / `author` / `publishedAt` / `tags` / `target.folder`）、**追加到指定笔记**（选择器，写进信封的 `target.notePath`）。默认交付 = **收件箱**（由应用侧 ㉕ 决定，扩展只如实显示回执 `status`，`pending` 时用冻结文案 `已进入收件箱等待确认：{标题}。`）。

**㉙ 模板数据模型。** 存扩展侧 `chrome.storage.local`（键 `opennote.templates.v1`），支持导入/导出 JSON，**不新增任何运行时依赖**。
结构：`{ id, name, triggers: [{ type: "url" | "domain" | "path", value }], priority, folder, tags: [], noteNameFormat, properties: {}, appendTo, behavior: "new" | "append" | "inbox" }`。
匹配：`priority` 降序，第一个命中 `triggers` 的模板生效；无命中用内置默认模板。
变量：`{{title}}` `{{url}}` `{{site}}` `{{author}}` `{{publishedAt}}` `{{capturedAt}}` `{{selection}}` `{{highlights}}` `{{content}}` `{{wordCount}}`。
过滤：`|date:YYYY-MM-DD` `|upper` `|lower` `|trim` `|truncate:N`。
条件：极简 `{{#if 变量}}…{{/if}}`，**不做**完整解释器（不实现循环与嵌套表达式），超出范围的原样输出并由 `verify.mjs` 报错。
内置 3 个开箱模板：`默认` / `论文`（`arxiv.org`、`doi.org`）/ `视频`（`youtube.com`、`bilibili.com`）。

**㉚ 高亮数据模型。** 页面内 `content/highlight.js`：选中文字 → 浮标出现「高亮」→ 记录 `{ text, note?, color?, createdAt, selector }`；按 URL 分组存 `chrome.storage.local`（键 `opennote.highlights.v1`）。
写入正文的形态：正文末尾追加 `## 高亮` 小节，每条以 `> ` 引用摘录，若有批注则下一行 `— {批注}`。
**与 `source.selection` 的关系**：高亮**不**改变 `source.selection`（那是「本次取的是选区」的标志，影响判定链第 3/4 步，见 ㉕/⑳）；高亮内容作为 `body` 的一部分一起提交。高亮为空时**不生成** `## 高亮` 小节。

**㉛ `opennote://` 协议注册（0.2.0 的 P0 漏项）。** `02` §5.6 把 `API-11 opennote://settings/import` 定为 **P0**，扩展侧 `background.js` 早已调用它，但应用侧全仓 **0 处** `setAsDefaultProtocolClient`——那个「打开 Opennote 设置」按钮是**死按钮**。
本次实现：`app.setAsDefaultProtocolClient("opennote")` + `requestSingleInstanceLock()` + `second-instance` 转发（Windows/Linux）+ `open-url`（macOS）；路由 `opennote://settings/import`（API-11）与 `opennote://open?path=…`（API-12）。
**本次明确不做 `API-09 opennote://clip?d=…`**：用户已确认「Opennote 需要打开」，剪藏主路径仍是本地桥；且 `API-09` 到达必须先在应用内确认（§5.6），属独立工作量。未实现的路由必须**明确报「暂不支持」**，不得静默无反应。
不做 `API-09` 的代价如实记录：**应用没运行时无法从浏览器剪藏**，只能用插件内暂存（S11）等应用恢复后补投。

**㉜ 收件箱入库前可选落点（用户需求③④）。** `commitInboxResult(id, options?)` 增加可选 `{ folder?: string | null }` 覆盖参数：
- 不传 → 沿用信封的 `target.folder`（缺省为工作区根，§6.13⑤）；
- 传 `null` → 根目录；传字符串 → 该工作区相对目录；
- **必须走 `assertSafeRelative()` + 授权根校验**，信封不能指定绝对路径这条红线不变；
- `UI-03` 收件箱面板增加「保存到」选择器（复用既有文件夹树），入库时以选中值为准，并**在入库前**显示最终落点说明句。
`commitInbox(id)` 的既有签名保持不变（纯增量）。

## 6.15 · 0.3.1 追加裁定（元素选择剪藏 + 去配对）

> 优先级同上（**高于 01/02/03**）。用户原话：①「你知道 chrome 浏览器的选择元素吗？我期望 opennote 里面有这个功能，点击然后就能在网页上选择裁剪的部分」；②「原有的行为选中然后弹窗这种行为可以删除了」；③「我希望配对这个功能可以删除了，因为这是本地插件，用户知道安全性（后续也能使用 agent，如果 agent 也需要配对的话，那也太麻烦了）」；④「使用 url 以及令牌的形式，令牌长期存在」。

**㉝ 元素选择剪藏，替代「选中文字 → 浮标 → 弹窗」。**
扩展新增**元素选择模式**，交互对齐 Chrome DevTools 的 inspect element：
- 进入：popup 顶部一个「选择页面元素」入口（以及快捷键 `Alt+Shift+S`，语义由「剪藏选区」改为「进入元素选择模式」）。
- 页面内：鼠标移动时，**当前元素**加轮廓高亮（overlay 描边 + 轻量半透明遮罩），并浮出一个小标签显示元素信息（标签名 + 尺寸）。
- 点击一次：**取该元素及其子树**为正文，退出选择模式，**阻止该次点击的默认行为**（`preventDefault` + `stopPropagation`，避免点掉链接/提交表单），回到 popup 预览。
- `Esc` 取消、不改动页面。
- 选择模式**不得**改变页面：只允许新增一层覆盖层（Shadow DOM 内），不得改页面 DOM、不得注入持久样式。

**删除**（用户明说可删）：
- 页面内**浮标**（`content/float.js` 的「記 剪藏 / 整页」气泡）与它依赖的 `selectionchange` 逻辑；
- 右键菜单里的**选区剪藏**项（保留「剪藏整页」一项即可）；
- 「选区 / 整页」二分——正文来源改为三选一：**元素选择** / 整页正文 / 当前选区（仅当用户确实先选了文字时作为便捷项保留，**不再是主路径**）。

**与 `source.selection` 的关系**：元素选择走 `body`，`selection` 恒为 `false`（它不是文本选区），因此仍能命中判定链第 4 步（同 URL、不同正文 → 进收件箱，见 ㉕）。
**边界**：仅 `http(s)` 页面可用；`chrome://`、扩展商店、PDF 阅读器等受限页面 → 如实提示（沿用 `IMP-1006` 的口径），不得静默失败。

**㉞ 删除配对，改为「URL + 长期令牌」。**
- **扩展侧**：popup 的「配对码」输入块（`S6`）**删除**，改为**一次性粘贴令牌**的输入框（47 字符，形如 `opn_…`）。令牌存 `chrome.storage.local`，**长期有效**，除用户在 Opennote 里重新生成外不失效。
- **桥侧删除**：`POST /v1/pair` 与 6 位配对码、`pairingCode`、`newPairCode()`、`pendingPlaintext`、120 秒有效期、一次性、连续 5 次作废、以及「配对成功即轮换令牌」全部移除。
- **来源白名单机制调整**：不再有「配对成功才把该 Origin 加入 `allowedOrigins`」。四道前置校验里的 Origin 判据改为**按类型**：只接受**扩展来源**（`chrome-extension://<id>` / `moz-extension://<id>`）与本机应用来源（`http://127.0.0.1:<port>` / `file://`）；**普通网页来源一律拒绝**（这是防「任意网站驱动本机接口」的关键，不能因为去掉配对而放宽）。`removeOrigin()` 保留，用于删除历史遗留条目。
- **推翻既有条目**：本节取代 §6.13① 与 `02` §5 的配对设计（含 `IMP-2004` 配对码错误码）；`IMP-2001` 的语义改为「**这个客户端还没有配置访问令牌**」，逐字文案：`这个客户端还没有配置访问令牌。请在 Opennote 的「导入与接口」里复制令牌，粘贴到客户端。`；`IMP-2004` **保留码号但不再产出**（标记作废，不得复用该号）。
- **`IMP-3001` 的新逐字文案（本节冻结，两侧必须逐字一致）**：`来源未被允许。本地接口只接受浏览器扩展与本机程序发来的请求。`
  理由：去掉配对后，Origin 判据从「这个来源配对过吗」变成「这个来源**是不是一个浏览器扩展或本机程序**」，旧文案（「请在设置里添加来源，或用配对流程重新配对」）指向的下一步已经不存在了。新文案要如实说出**允许哪两类来源**，用户才知道该怎么办。
- **安全代价如实记录**（用户明确接受的取舍）：去掉配对后，**令牌是唯一凭据且长期有效**。`bridge.json` 仍只存 sha256 + 后 4 位，明文**绝不落盘**但在本进程内存保留到应用退出（§6.15㊲，原「只在生成时显示一次」口径已作废）；但**任何能读到扩展 storage 或用户剪贴板的程序都能拿到明文令牌**，并因此获得导入能力（注意：导入能力**不等于**读笔记能力——桥只提供导入，不提供读取与删除）。这条必须写进设置面板的说明句。

**㉟ Agent 通道同样不配对。** CLI / MCP / Skill 一律用**令牌**（既有 `Authorization: Bearer`），删除其文档与实现里一切「配对」前置步骤。`opennote://` 深链不涉及令牌（只读路由 + 一律弹确认，见 ㉛）。

**㊱ 文案清理。** 删除所有关于配对的用户可见文案（6 位配对码、120 秒、一次性、5 次作废、令牌轮换警告）；替换为「复制令牌 → 粘贴到客户端」的说明。设置面板的 R4b 区块（配对新客户端）改为「复制令牌」区块。

**㊲ 令牌明文在本会话内可重复复制（`O-15` 的裁定）。** `bridge.json` 仍**只存 `sha256` + 后 4 位**（这条不变，明文绝不落盘），但**生成后在本进程内存里保留明文**，直到应用退出或用户「重新生成」为止：
- 设置面板的「复制令牌」按钮**在本次会话内可反复点击**，始终复制到同一串明文；
- **应用重启后内存明文消失** → 面板此时必须**如实显示**「令牌已不可见，需要时请重新生成」，而不是留一个点了没反应的按钮（这正是 `00` 号一路在抓的「假开关」）；
- 「重新生成」= 立刻换新明文并作废旧令牌，面板同时更新可复制内容。
**理由**：令牌是长期有效的**唯一凭据**，用户唯一能拿到它的途径就是这串明文。若只允许「显示一次」，那么用户一旦误关弹窗、或换了客户端、或想给 agent 配一次，就只能重新生成——而每次重新生成都会**让此前所有已配置的客户端失效**。这会把「长期有效」变成一个自相矛盾的承诺。内存保留是「可用性」与「不落盘」之间唯一站得住的折中：**磁盘上没有明文，内存里有，退出即失**。
