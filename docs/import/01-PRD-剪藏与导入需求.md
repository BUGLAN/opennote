## 1. 背景与问题定义

### 1.1 用户原话诉求（未加工）

1. 在网站或其他地方看到**片段**，希望「剪切过来」，剪到自己的 Opennote 里。
2. 网页场景需要一个**浏览器插件**，通过**某个接口**把内容导入 Opennote。
3. 在 Codex、Claude 等 AI 软件里工作时，常有文章要记录，会**让 AI 执行某个 skill** 把内容导进 Opennote。
4. 一句话：**Opennote 要提供一些接口，方便外部把内容导进来。**

### 1.2 问题陈述

Opennote 的立身之本是「笔记就是你磁盘上的 Markdown 文件」——没有服务端、没有账号、没有遥测（`README.md:3`、00 号第 2 节第 1 条）。这个承诺带来了一个**结构性缺口**：应用只能从「用户已经打开的那个文件夹」里读内容，**没有任何入口能让应用之外的东西把内容送进来**。

缺口的后果，按用户能感知的顺序排列：

| 编号 | 缺口 | 用户侧后果 | 现状依据 |
| --- | --- | --- | --- |
| G1 | 网页内容进不来 | 看到好片段只能手动「复制 → 切到 Opennote → 新建笔记 → 粘贴 → 补 URL」，中断阅读 | 现有导入只接受文件选择器/拖拽的 `FileList`，`importIntoWorkspace(input: FileList \| File[], targetFolder)`（`src/lib/import.ts:40`） |
| G2 | AI 产出的内容进不来 | 在 Codex/Claude 里整理好的文章要人肉搬运；AI 无法让 Opennote 收下它 | 渲染层只能通过 preload 的 `window.opennote` 说话，而该桥只暴露 fs/dialog/shell/app/window 五组能力，**没有任何导入入口**（`src/desktop/bridge.ts:14-72`） |
| G3 | 导入没有「统一入口」概念 | 每加一个通道就要新增一套 UI 与一套文件命名/冲突逻辑，冲突语义会各自漂移 | 现有唯一入口是设置 · 文件里的「导入文件或 zip」（`src/components/AppDialogs.tsx:237-251`） |
| G4 | 批量导入不可见、不可撤销 | 导入 200 篇只有一个汇总 toast，用户不知道进了哪、也不知道怎么退回去 | `src/components/App.tsx:282` 只报「导入完成：X 篇笔记…，跳过 Y 项」 |
| G5 | 外部写入与界面所见不一致 | 外部改了文件，界面要等「切回窗口 / 手动同步」才更新 | HEAD 无文件监听（`README.md:185` 路线图第 1 条），手动同步入口是「立即保存」（`src/lib/appCommands.ts:302`） |

### 1.3 为什么现在做不到（逐条对应上面的缺口）

1. **没有服务端**，所以不存在「一个 API 域名」。接口只能落在三种介质上：本机进程、浏览器页面、文件系统（00 号第 3 节第一行张力）。
2. **三种文件系统后端能力不对等**（`FileSystemBackend`，`src/fs/types.ts:19`）。只有 Electron 桌面版的 Node `fs` 后端能做到「应用窗口不在场也能写磁盘」；Chrome/Edge 的 File System Access 需要页面持有句柄授权；OPFS 是浏览器私有存储，**外部进程在原理上无法访问**（`namespaceRoot()`（`src/fs/opfs.ts:14-22`，HEAD；工作区 `:15`；说明性注释在 `:4-8`） 的 `navigator.storage.getDirectory()`）。
3. **笔记的身份是工作区相对路径**（`libraryStore.get().notes` 以 POSIX 相对路径为 key，`src/lib/import.ts:50`），不是 id 映射。所以「导入到哪」必须落到「目录 + 文件名」，而文件名由标题经 `sanitizeName()` 清洗（`src/fs/paths.ts:79`，HEAD；工作区 `:85`，截至撰写时；CJK 友好、限 80 字）。
4. **标题只能从正文推**：`deriveTitle()` 取正文（去掉 front-matter 后）的第一个标题行，否则第一行非空文本（`src/lib/utils.ts:61`）。写 front-matter 的 `title:` **不会**改变笔记标题——这是设计 L0 信封时必须绕开的陷阱。
5. **front-matter 里只有 `tags:` 是被解析的键**（`splitFrontMatter()` `src/lib/utils.ts:54`；`deriveTags()` `:132`）。其余键是惰性的，可以安全承载来源信息，但不会产生任何行为。
6. **覆盖语义不可靠**：D03（`createNote`/导入不预检磁盘同名文件，可能静默清空既有文件）、D08（外部改动被下一次自动保存静默覆盖）、D12（浏览器笔记本导入覆盖同名文件），见 `docs/缺陷审计报告-2026-09-29.md`。而插件与 AI 恰恰是**无人值守写入**——把不可靠的覆盖语义暴露给自动通道，等于把丢数据风险放大。
7. **外部写入之后缺一环「让界面知道」**：HEAD 没有文件监听。**未提交的工作区（截至撰写时）**已有主进程侧管道：IPC `opennote:fs:watchWorkspace` / `opennote:fs:unwatchWorkspace`（注册函数 `registerFsWatchHandlers()`，`electron/main.cjs:652-705`），去抖后由 `notifyWorkspaceChanged()`（`:628-637`）向所有窗口广播 `opennote:fs:workspace-changed`，并**刻意跳过 `.opennote/**`**（`:671-676`，避免「自写 → 自读重扫」循环）。真正仍缺的是**渲染层的广播订阅**：`onWorkspaceChanged` 全仓只有 `src/desktop/bridge.ts:42` 的类型声明，`src/**` 没有任何调用点。即：**管道有了，消费端还没接**。

### 1.4 本需求的解决思路

沿用 00 号第 4 节的四层分层：先用 **L0 导入信封 `opennote.import/v1`** 锁死数据契约，再把浏览器插件、CLI、AI Skill、MCP、分享面板都视为**同一个信封的不同传输通道**（L1），最后由应用内统一完成落点、去重、冲突、收件箱/直接入库、提示与撤销、重扫刷新（L2）。这样避免「N 个客户端 × M 套导入逻辑」的碎片化。

## 2. 目标用户与典型场景

三类核心用户：

- **写作者/研究者（主）**：读写为主，网页剪藏是日常动作，在意「收进来之后好不好找、会不会写乱我的文件夹」。
- **AI 重度用户（主）**：在 Codex / Claude / Claude Code 里工作，希望「让 AI 记一下」是零摩擦的。
- **维护多笔记本的人（次）**：有工作/私人两个以上笔记本，需要选落点，并希望行为可预测。

下面 8 条端到端场景。每条写清「触发点 → 期望结果 → 失败时用户看到什么」。场景编号 `US-xx`。

### US-01 网页选片段剪藏（桌面版 + Chrome 扩展）

- **触发点**：用户在 Chrome 里读一篇长文，选中三段话，点扩展图标选「剪藏选中内容」。
- **期望结果**：扩展把选中内容转成 Markdown，带 `source.url`、`source.title`、`source.selection=true`、`capturedAt`，投给桌面版的本地桥；1 秒内在 Opennote 里出现 toast「已从网页剪藏：《文章标题》。」并带「撤销」按钮，侧栏出现新笔记（或在收件箱里，若用户开了收件箱模式）。
- **失败时用户看到什么**：桌面版没开本地接口 → 扩展气泡里显示「本地接口未开启。打开桌面版 Opennote 的「设置 · 文件 · 导入与接口」，开启本地接口后重试。」；端口被占 → 「本地接口无法启动：8787–8796 端口都被占用。请先释放一个端口，或在设置里改用其它端口。」；token 过期 → 「本地接口令牌不正确或已被撤销。请在 Opennote 设置里重新复制令牌，并更新剪藏工具的配置。」
- **关联需求**：FR-01、FR-40…FR-44、FR-50、FR-13、FR-25、FR-35。

### US-02 整页正文剪藏（桌面版 + Chrome 扩展）

- **触发点**：用户在同一篇文章里没选文字，直接点「剪藏整页正文」。
- **期望结果**：扩展抽取正文（P0 用保守策略：`document.body` 的可读化提取，宁可多带导航也不丢正文），标题取 `document.title``，写入一条标题为文章标题的笔记，front-matter 带 `source:` 与 `captured_at:`。
- **失败时用户看到什么**：正文抽取为空（例如纯 canvas 页面）→ 扩展侧「没有可导入的内容：标题和正文都是空的。」；正文超过体量上限 → Opennote 侧「正文超过 {上限}，未入库。可分段剪藏。」
- **关联需求**：FR-01、FR-51、FR-82。

### US-03 AI 里「帮我把这篇记录一下」（Codex / Claude Code + Skill/CLI）

- **触发点**：用户在 Codex 里读完一份整理好的文章，对 AI 说「帮我把这篇记录到 Opennote」。
- **期望结果**：AI 执行 Skill（P1）或直接调用 CLI `opennote clip --title … --file …`（P0），生成信封并投给本地桥；Opennote 入库后返回**确定性回执**（成功/失败 + 最终路径 + 最终标题），AI 能把结果告诉用户：「已记录到『剪藏/《标题》』。」
- **失败时用户看到什么**：Opennote 未打开笔记本 → CLI 退出码非 0 并打印「Opennote 还没有打开笔记本文件夹，这次剪藏没有入库。」；本地接口未开启 → 同上（US-01 的文案）；内容为空 → 「没有可导入的内容：标题和正文都是空的。」
- **关联需求**：FR-06、FR-45、FR-60、FR-40…FR-44、FR-13。

### US-04 批量导入多篇（CLI 或扩展的「全部标签页」）

- **触发点**：用户把 12 个标签页一起剪藏，或用 CLI 把一个目录下的 `.md` 批量投递。
- **期望结果**：12 条信封逐条入库；过程可见进度而不是一个汇总数字；结束时一条汇总提示「已入库 12 篇」，且这 12 篇作为**一次批量操作**可整体撤销（P1，FR-12、FR-28）。
- **失败时用户看到什么**：部分失败时明确列出失败条目与原因，不把失败混进成功计数；失败条目留在收件箱（若已开启收件箱模式）或写入 `.opennote/import-log.json` 供事后查看（FR-49）。
- **关联需求**：FR-11、FR-12、FR-20、FR-49。

### US-05 手机分享面板剪藏（PWA Share Target）

- **触发点**：用户在手机浏览器或 App 里点「分享」→ 选 Opennote。
- **期望结果**：设备支持 PWA Share Target 时，Opennote 被唤起并带着标题/URL/文本进入一个「确认剪藏」界面，用户确认后入库。
- **失败时用户看到什么**：**Safari / iOS 不支持 Share Target**（平台限制，见第 4 节矩阵）→ 该平台上不显示 Opennote；用户改用降级路径：把正文复制出来，在 Opennote 里新建笔记粘贴（FR-67）。
- **关联需求**：FR-65、FR-66、FR-67。
- **诚实说明**：这条链路的覆盖面比用户预期窄。凡不支持 Share Target 的移动平台，本需求**只能提供降级路径**，不承诺「手机一键剪藏」。

### US-06 只装了 Chrome 网页版的用户剪藏（FSA）

- **触发点**：用户是 Chrome 网页版用户，没装桌面版，装了扩展并点「剪藏选中内容」。
- **期望结果**：扩展通过 content script 把信封 `postMessage` 给**已经打开着的** Opennote 标签页；Opennote 页面把它当作一次普通入库处理，落进用户已授权的文件夹。
- **失败时用户看到什么**：没有已打开的 Opennote 标签页 → 扩展侧「没有找到已打开的 Opennote 窗口，请先打开 Opennote 网页版再重试。」；页面在后台且句柄授权已失效 → Opennote 侧「Opennote 需要重新授权这个文件夹，本次剪藏已暂存，授权后会自动入库。」
- **关联需求**：FR-39、FR-54、FR-56。

### US-07 其它浏览器（OPFS / Firefox）

- **触发点**：Firefox 用户点扩展剪藏。
- **期望结果**：扩展把信封送到页面内桥；页面在场时正常入库到 OPFS 笔记本。
- **失败时用户看到什么**：页面不在场 → 与 US-06 同样的兜底文案；OPFS 场景下**任何外部进程都无法写入**，因此不提供「后台静默入库」的承诺。
- **关联需求**：FR-39、FR-56、FR-83。

### US-08 首次开启本地接口（首次引导）

- **触发点**：桌面版用户第一次打开「设置 · 文件 · 导入与接口」并点「开启本地接口」。
- **期望结果**：面板明确告知风险与后果，用户确认后才写入设置；开启后显示绑定地址（`127.0.0.1`，端口在 8787–8796 中自动扫描选中）、**只显示一次的 token 明文**（可复制、可重置）、以及一个可复制的 `curl` 示例，让用户 30 秒内验证通路。
- **失败时用户看到什么**：端口被占用 → 「本地接口无法启动：8787–8796 端口都被占用。请先释放一个端口，或在设置里改用其它端口。」；用户拒绝风险说明 → 保持关闭且状态回落到「未开启」。
- **关联需求**：FR-40、FR-41、FR-42、FR-68、FR-70、FR-71。

矩阵的三条硬结论（评审请直接核对）：

1. **「外部直接落盘」只有桌面版有。** 因此 00 号 6.5 P0 里「插件 → 落盘」这条链路，**只在同时安装了桌面版 + 扩展的用户身上闭环**；只装网页版的用户走 FR-39 的页面内桥，且必须页面在场。这一点必须在产品文案里说清，不能用「都支持」糊过去。

## 5. 落点、去重与冲突规则

### 5.1 默认值（逐字沿用 00 号 6.3）

| 场景 | 默认行为 | 允许的其它策略 | 用户可见结果 |
| --- | --- | --- | --- |
| 同名文件已存在 | `new`：自动加序号（沿用 `uniquePath()` 的 ` 2` 语义，`src/fs/paths.ts:89`，HEAD；工作区 `:101`） | `append` / `skip` | 「已保存为《{最终标题}》（同名文件已存在，另存为新笔记）。」 |
| 同一 URL 重复剪藏 | `append`：追加到已有同名来源笔记，带时间分隔 | `new` / `skip` | 「已把新片段追加到《{标题}》。」 |
| 用户正在编辑该笔记 | 不自动覆盖；走 `append` 或进入收件箱 | — | 编辑器内容不被替换；提示说明改走了哪条路径 |

### 5.2 三个边界的期望行为（本节为 00 号 6.3 的补充，不改变其默认值）

**边界一：用户正在编辑同一笔记。**
判定口径必须可复现：**该笔记当前在编辑器中打开且 `activeId` 等于它**，或它的状态是「有未落盘改动（dirty）」——两者任一成立即视为「正在编辑」。此时：
- 信封为 `new` / `overwrite` → 不覆盖（`overwrite` 只在满足 FR-16 四道闸门时才可能到达此处；不满足时已在入口降级为 `new` + warning）。若收件箱模式已开启，进收件箱；否则按 `append` 处理并在 toast 里说明。
- 信封为 `append` → **允许追加**，但必须走「先落盘当前编辑内容，再追加」的顺序。D08 的现状按三段式表述（RV-07）：（a）**HEAD 缺失**——`flushNote()`（HEAD `src/data/library.ts:363` 一带）直接 `writeText`，无 mtime / size 校验；（b）**未提交的工作区已修**（截至撰写时）——`flushNote()`（工作区 `:624`）用 `knownStats`（`:107-108`）比对 `mtimeMs` / `size`（`:642-647`），命中即调 `preserveConflictCopy()`（`:612`）另存冲突副本；（c）**仍然缺的是广播订阅**——`onWorkspaceChanged` 全仓只有 `src/desktop/bridge.ts:42` 的类型声明，`src/**` 无任何调用点，主进程的 `opennote:fs:workspace-changed` 广播没有订阅者。因此本需求要做的是 (c)，**不要重复实现一层冲突保护**（会与 `preserveConflictCopy()` 打架）。
- 验收：编辑器中只敲一半未保存时投递一条 `overwrite`，编辑器里的文字逐字不变，且磁盘文件不是「半句」。

**边界二：同一 URL 二次剪藏。**
判定链按 00 号 6.8⑦（这是对 6.2 与 6.3 的消歧裁定，也是本文异议 3 的处理结果），四条分支互斥且有序：

1. **同一 `importId`** → 幂等：不入库，回执返回**首次**落点。提示按 `00` §6.9④ 与 §6.12①（本文 RV-01）：**应用内不弹 toast**；由客户端（插件 popup / CLI stderr / 收件箱条目）**内联**显示「已在笔记中（未重复入库）。」并给出「打开那条笔记」入口，重复事件同时进导入日志（文案见 §6.2）。
2. **同一 `source.url` 且正文内容哈希相同** → 判为重复，回执 `duplicate`，**不追加**（即使用户再点一次也不能污染已有笔记）。
3. **同一 `source.url`、内容哈希不同** → 按 `source.selection` 分流：选区剪藏（`selection=true`）默认 `append`，追加段落以「时间 + 来源行」开头便于看出边界；整页剪藏（`selection=false`）默认**进收件箱**，由用户选 `append` / `new` / `skip`，不静默追加。
4. **仅内容哈希相同但 URL 不同** → 视为两条独立笔记（拒绝误合并）：同一段话从两个站点剪来是两篇，不是重复。

验收：对同一 URL 先剪片段再剪**同一段**片段 → 第二次回执 `duplicate` 且文件未变；再剪**不同**片段 → 追加到同一文件；对同一 URL 连按两次「整页剪藏」→ 第二次在收件箱里等待确认；把同一段文字从两个不同 URL 各剪一次 → 产生两篇独立笔记。

**边界三：附件重名。**
- 落进笔记所在目录的 `assets/`（与现有粘贴图片行为一致，`src/lib/import.ts:88-98`）。
- 重名时沿用 `uniquePath` 加序号（`x.png` → `x 2.png`），并**同步改写本条正文里的相对引用**，不能出现「文件改名了但正文还指向旧名」。
- 若同一信封内两个附件重名，也必须各自唯一，且正文引用必须指向各自那一份。
- 验收：目录已有 `assets/x.png`，剪藏一条含 `x.png` 的内容后：新文件为 `assets/x 2.png`，正文引用为 `./assets/x 2.png`，图片在编辑器里能渲染出来。

## 7. 可撤销与可恢复性

三层机制分工明确，互不替代：

| 机制 | 存储位置 | 覆盖范围 | 时间尺度 | 谁来触发 | 解决什么问题 |
| --- | --- | --- | --- | --- | --- |
| **撤销** | 内存中的「本次入库操作记录」 | 一次入库操作（新建 / 追加 / 批量） | 10 秒（toast 生命周期） | 用户点 toast 上的「撤销」（FR-25） | 「我点错了 / 这不是我要的那段」——尚在注意力窗口内的即时反悔 |
| **回收站** | `.opennote/trash`（`TRASH_DIR`，`src/fs/paths.ts:72-76`，HEAD；工作区 `:78-82`） | 整篇笔记（文件级移动） | 直到用户清空 | 用户删笔记 / 撤销过期后的二次入口（FR-27） | 「那篇笔记我不要了」——文件级反悔，恢复即把文件移回原位（`restoreNote()`（`src/data/library.ts:809`，HEAD；工作区 `:996`）） |
| **历史快照** | `.opennote/history/<笔记路径>/` | 笔记内容（每次一段） | 每 3 分钟自动一份、最多保留 60 份（`SNAPSHOT_INTERVAL` / `SNAPSHOT_KEEP`（`src/data/library.ts:83-84`，HEAD；工作区 `:98-99`，截至撰写时）） | 自动 + 手动「记录当前版本」 | 「追加进来的内容把正文弄乱了，我要看之前长什么样」——内容级回看 |

三条边界的期望行为：

1. **撤销窗口（默认 10 秒）内的语义**：`new` → 删除本次新建的文件；`append` → 把笔记内容恢复到追加前（逐字节一致）；批量 → 整批回滚（FR-28，P1）。撤销后 toast 消失，不产生第二条提示。
2. **撤销过期后的分工**：整篇不要 → 回收站；只想退回内容 → 历史快照。二者都不能替代撤销窗口，因为快照有 3 分钟的节流间隔，**紧接着的两次追加可能不产生新快照**，无法保证「精确回退一步」。
3. **收件箱丢弃不产生恢复需求**：待确认条目从未进入正文，`discarded` 是**立即清理、不进回收站、不可恢复**（FR-29、`00` §6.12②），也不留快照；因此「丢弃」必须配确认框「丢弃后不会进入回收站」，想要保险的用户走「先入库，再删除」。

**前像（00 号 6.7④，锁定要求）**：凡改变既有笔记内容的操作（`append` / `overwrite`）**必须在入库前记录可回退的前像**。前像落 `.opennote/import-preimages/`（`00` §6.10①，**不放在 `history/` 之下**，与历史快照的保留策略无耦合）；操作类型与记录落 `.opennote/import-log.json`。原因是历史快照有约 3 分钟的节流（`SNAPSHOT_INTERVAL` / `SNAPSHOT_KEEP`（`src/data/library.ts:83-84`，HEAD；工作区 `:98-99`，截至撰写时）），不保证两次连续追加之间产生新快照——没有前像就无法做到「精确回退一步」。撤销的结果必须能被表达为两种之一，且 UI 如实呈现：

| 撤销结果 | 触发条件 | 用户看到什么 |
| --- | --- | --- |
| **可逐字节回退** | 前像存在且笔记未被他人改动 | 撤销后内容与入库前逐字节一致；toast 直接成功 |
| **降级为「回收站 / 看历史快照」** | 前像不可得（记录缺失、`.opennote/` 被删、前像与当前内容已不一致） | 撤销不假装改回，提示「撤销时间已过，可到回收站恢复《{标题}》。」，并给出快照入口 |

实现约束（写给 02 号）：撤销需要「本次入库操作记录」，而 `00` §2 第 12 条 要求新增元数据必须放进 `.opennote/`。建议记在 `.opennote/import-log.json`（FR-49）里并带操作类型与前像校验值，**且该记录必须可从正文恢复**（front-matter 的 `opennote_import_id` + `source` 即可重建去重索引），避免 `.opennote/` 被删除后去重与撤销能力变成单点依赖。推论：回执字段必须能表达「这次操作是否可逐字节回退」（见 00 号 6.7④的推论）。

## 8. 非功能需求

### 8.1 隐私

| 要求 | 可验证的验收 |
| --- | --- |
| 剪藏内容不出本机：正文、标题、来源信息只写入用户选定的工作区文件夹，不经过任何服务器 | 一次完整剪藏的抓包中，除用户显式开启的远程图片下载外**没有任何外部网络请求** |
| 零遥测：不加统计、不上报使用行为、不做崩溃上报 | 全量搜索产物与依赖中不存在遥测端点；关闭网络后所有功能行为不变（除远程图片） |
| 本地桥只在 `127.0.0.1` 监听，绝不监听 `0.0.0.0` | 开启后用外部设备访问本机 IP 的该端口，连接被拒 |
| 远程图片自动下载是唯一的外部请求，且必须可关闭、默认不开启（P1） | 关闭状态下剪藏一个含外链图片的页面：正文保留原 URL，不发起图片请求 |

### 8.2 安全

| 要求 | 可验证的验收 |
| --- | --- |
| 本地接口默认关闭；开启必须经过风险说明与二次确认 | 全新安装未开时端口不监听；首次开启必须先确认（FR-40、FR-70） |
| 用户可见后果直说：开启后**本机上的任何进程**都可以向你的笔记本写入内容 | 风险说明页逐字包含该句；关闭开关后端口立即停止监听 |
| token 鉴权 + `Origin` 校验 + 无效请求限流 | FR-42 / FR-43 / FR-44 的用例全部通过 |
| 桥的能力面最小：不提供读笔记 / 列目录 / 删除 | FR-47 的端点枚举检查 |
| 前置门禁：D20 / D29 / D31 未修复不得发布本地桥 | FR-48 的越权用例全部被拒（HEAD 现状：`electron/main.cjs:83` root 无白名单、`:286` 可 `remove(root,".")` 递归删根、`:82` 纯词法校验） |
| 导入内容不被当作可执行代码：正文里的 HTML/脚本按纯文本处理 | 剪藏一个带 `<script>` 的页面，编辑器与预览中均不执行脚本 |

### 8.3 性能

| 项 | 上限 | 依据 / 验收 |
| --- | --- | --- |
| 单个导入条目（正文或附件） | 32 MB | 沿用 `MAX_ENTRY_BYTES = 32 * 1024 * 1024`（`src/lib/import.ts:37`）；超限被拒并提示 |
| 批量导入条目数 | 5000 条 | 沿用 zip 导入的既有上限（`src/lib/import.ts:100-103`）；超限中止并提示 |
| `assets` 单件图片 | 32 MB | 与单条目一致 |
| 单次剪藏从投递到界面可见（P95） | ≤ 2 秒（不含用户等待 FSA 授权的交互时间） | 本机、笔记本 ≤ 2000 篇、单个附件 ≤ 5 MB 的条件下测量 |
| 大附件不得阻塞界面 | 导入 20 MB 图片期间编辑器可继续输入 | 手工复现：输入延迟无可感知变化 |

### 8.4 离线与降级

- 剪藏链路（扩展 → 桥 / 页面内桥 / 收件箱 → 入库）在**无网络**时全部可用；唯一例外是远程图片下载（P1，且默认可关）。
- 桥不可用时扩展进入暂存并补投（FR-53，P1）；不提供「假装成功」的路径——任何未真正入库的剪藏都必须让用户知道内容在哪（扩展本地 / 收件箱 / 已丢弃）。
- 浏览器版本地数据被清理（站点数据清空）会导致 OPFS 笔记本内容一并消失（`README.md:97`），本需求不改变这一事实，但收件箱与导入日志同属工作区，行为一致。
- Firefox 的 MV3 兼容性：扩展复用页面内桥时只依赖 `activeTab` + `scripting` + `storage` 与 `window.postMessage`，不使用 Chrome 专有 API；Safari 的扩展与 Share Target 限制已在第 4 节如实标注。

### 8.5 可访问性

- 收件箱面板、设置面板、toast 的「撤销」动作必须**仅用键盘可达**（Tab 顺序合理、Enter/Space 可激活、Esc 关闭）。
- 焦点可见：沿用现有界面的焦点样式，不新增「无轮廓」的按钮。
- 屏幕阅读器：toast 用 `role="status"`（现有实现即如此）并在入库/失败时读出结果；收件箱条目数变化要有可读提示。
- 对比度：新增界面沿用 `src/styles/tokens.css` 的既有令牌，不引入新的颜色体系；暗色主题（夜读 / 砚池）下同样达标。
- 动效尊重 `prefers-reduced-motion`：收件箱出现、toast 进出不做位移/缩放动画。

## 10. 非目标

照抄 00 号 6.6，并补充本阶段发现的边界：

**沿用 00 号 6.6**

- 不做云端账号、云端存储、云端同步（与「无服务端 / 无账号 / 无遥测」承诺冲突）。
- 不做服务端抓取（Opennote 不代用户爬取网页；正文由客户端在用户浏览器里取）。
- 不做专有格式或私有数据库（正文永远是普通 `.md`）。
- 不做默认开启的本地桥（必须用户显式开启）。
- 不做静默覆盖任何已存在的文件（D03 / D12 的教训）。
- 不做无人值守的全自动「抓取整个网站 / 定时订阅」（P2 之后另议）。
- 本阶段不改动 `src/**` 或 `electron/**` 的实现（只出文档）。

**本文补充**

- **不承诺跨端同步**：插件剪到桌面版笔记本，不会自动出现在手机的 OPFS 笔记本里——它们本来就是两个不同的文件夹。任何「插件会自动同步到手机」的表述都属越权承诺。
- **不承诺在移动端做「后台静默入库」**：移动端没有外部写入通道（第 4 节矩阵），只做 Share Target 与降级粘贴。
- **不做浏览器扩展的常驻全站读取**：不申请 `all_urls`，不做后台自动记录浏览历史（隐私承诺的一部分）。
- **不做剪藏内容的云端 HTML 快照**：只保留 Markdown 正文与来源信息，不存原始 HTML 归档（避免「专有格式」与体积膨胀）。
- **不做对既有笔记的自动化改写**：AI 通道不得读改用户已有笔记内容，只能新建或按冲突规则追加。
- **不做正文的自动翻译、自动摘要、自动打标签**（后者属 P2 的自动标签建议，本期不立 `FR`）。
- **不为 `.opennote/` 被删除做数据恢复**：元数据可丢，正文不可丢；这是 `00` §2 第 12 条 的既有承诺，本需求不改。

## 14. 对 00 号简报的异议

**异议 1（事实性）：00 号第 2 节第 7 条引用的 `opennote:fs:authorizeRoot` 在 HEAD `7ea0661` 不存在。**
HEAD 的 `resolveInsideRoot()`（`electron/main.cjs:82`）只做「相对路径不逃逸**调用方自己声明的** root」的校验，**没有任何授权白名单**，这正是 D20 的内容（审计报告 D20 位置栏即为 `electron/main.cjs:83`）。`opennote:fs:authorizeRoot`、`authorizedRoots`、realpath 检查都只存在于**未提交的工作区改动**里（截至撰写时）。建议 00 号把该条改写为「修复 D20/D31 的方案（工作区，未提交）」，并把 `:93-96`、`:382` 两个行号替换为符号名，否则 01/02/03/04 会引用一个不存在的接口。本文所有引用 HEAD 的行号可按 HEAD 复查，引用工作区代码处均已标注「截至撰写时」。

**异议 2（契约与原则冲突）：00 号 6.1 的 `"conflict": "new | append | skip | overwrite"` 与 6.6 的非目标「静默覆盖任何已存在的文件」直接冲突。**
原建议二选一：(a) 从对外 v1 契约中移除 `overwrite`；(b) 保留但在语义上限定为「仅当用户显式确认时才可生效，且必须存在可回滚的撤销记录」。
**裁定结果（00 号 6.7①）：** 采 (b) 并加四道闸门——①客户端显式请求（永不作为默认值）②只有桌面版本地桥接受，扩展 / CLI / Skill / MCP / `opennote://` / 收件箱一律拒收或降级 ③设置里显式开启的进阶开关（默认关闭）④写入前强制留可回退前像。6.6 的非目标精确表述为「永不默认覆盖、永不由自动化客户端覆盖、覆盖前必有可回退副本」。FR-16 已按此收敛，第 12 节 AC-6 与第 16 节自查表同步改齐。

**异议 3（需要消歧）：00 号 6.2 的「重复剪藏判定：优先 `opennote_import_id`，其次 `source` + `body` 内容哈希」与 6.3 的「同一 URL 重复剪藏 → `append`」在「同一 URL 但内容不同」时互相矛盾。**

**裁定结果（00 号 6.8⑦，比我原建议更精确）：** 同一 `importId` → 幂等并返回首次落点；**同一 `source.url` 且正文哈希相同 → 判为重复（回执 `duplicate`，不追加）**；同一 URL 但哈希不同 → 选区剪藏 `append`、整页剪藏进收件箱；仅哈希相同但 URL 不同 → 视为两条独立笔记（拒绝误合并）。本文第 5 节边界二与 FR-17 已按此逐字改齐。

**异议 4（判定标准缺前提）：00 号 6.5 P0 判定标准「一条『网页选一段 → 出现在笔记本里』的完整链路跑通」隐含了「用户同时装了桌面版」这一前提。**
按第 4 节矩阵，只装 Chrome 网页版的用户走的是页面内桥（页面必须在场），OPFS 与移动端则完全没有外部写入通道。建议在 6.5 的判定标准里补一句前提：「桌面版 + 扩展」「桌面版 + AI 通道」各跑通一条；网页版与移动端的链路另行标注为「页面在场」与「仅 Android 分享面板」。否则评审会以一句不含前提的标准去验收四条平台线，必然打架。

**另外一条不是异议、而是登记**：收件箱放在 `.opennote/inbox/` 与被监听跳过的 `.opennote/**` 相撞，00 号第 2 节第 9 条已给出结论（必须单独触发重扫）。本文把它落成 P0 的硬验收（FR-36、AC-5），不改 00 号的选型。
