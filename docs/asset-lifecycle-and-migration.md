## 0. 一句话结论

共享 `.assets/` + 内容派生 uuid 的**新**链路是通的（落点、命名、前缀重算、按引用删除都正确），
但有 **5 处实打实的缺口**：
① 「同一张图重复粘贴 → 复用同名」**不成立**（会退让成 ` 2` 副本）；
② 旧布局（`<笔记名>.assets/`、公共 `assets/`）在**重命名 / 移动笔记**时必然裂图（引用不改写、目录不跟走）；
③ 回收站里已出现 **3 个孤儿 `.assets/` 目录**（笔记早已改名/移动，图留在原地）；
④ 一批**注释与文档仍在描述旧行为**（`src/editor/media.ts:10-24` 等 9 处），用户读到会以为功能没做；
⑤ 迁移器要覆盖的写法比现有改写器多（`<img src>`、角括号、无 `./` 前缀、`${filenalme}` 这类脏路径、跨目录引用）。

用户已拍板的三个前提（本报告不再列为未决）：图片**不物理搬迁**、**要做迁移**（含回收站）、uuid **按内容复用**。

### 1.2 uuid 怎么算、扩展名从哪来

- **内容哈希，不是随机**：`contentUuid(bytes)` = `sha256(bytes)` 十六进制**前 32 字符**（16 字节），
  按 RFC 4122 摆成 `8-4-4-4-12`，**版本位写 5**、**变体位写 10xx** —— `src/lib/clip/hash.ts:68-73`。
- **扩展名来自「建议名」**：`assetFinalName(bytes, name)` 先 `sanitizeName`，再 `extName`，
  只接受 `/^\.[A-Za-z0-9]{1,6}$/` 并**小写化**，取不到就**不带扩展名**（绝不把怪字符带回路径）——
  `src/lib/clip/landing.ts:185-192`；`extName` 定义 `src/fs/paths.ts:51-55`。
- 编辑器路径上的「建议名」= 剪贴板文件的 `file.name`，取不到才退回 `imageNameForPaste(blob)`
  （`image-<YYYYMMDD-HHMMSS>.<ext>`）—— `src/editor/media.ts:57`，`src/data/assets.ts:252-257`。
  注意 `imageNameForPaste` 是**旧世界遗留**：它产出的名字只会被 `assetFinalName` 用来取扩展名。
- **验证（探针 A1/A2）**：`contentUuid(PNG)` 稳定且匹配 `^[0-9a-f]{8}-[0-9a-f]{4}-5[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`；
  `assetFinalName(PNG,"截图.PNG") === contentUuid(PNG) + ".png"`；原始名不进落盘名。

### 1.3 引用文本实际长什么样（`./` 差异的确认）

`saveImage` 的返回值是 `markdownRef(relativeAssetRef(notePath, path))`（`src/data/library.ts:2530`）：

- `relativeAssetRef` 按**笔记所在目录的层数**现算 `../`（`src/lib/clip/landing.ts:103-111`）；
- `markdownRef` 只在**路径含空格或 `()<>`** 时才包成 `<…>`（`src/lib/clip/landing.ts:293-295`）。

| 笔记位置 | 实际生成的引用 |
| --- | --- |
| 根目录 `a.md` | `.assets/<uuid>.png` ← **无 `./`** |
| `归档/a.md` | `../.assets/<uuid>.png` |
| `归档/子/a.md` | `../../.assets/<uuid>.png` |
| 回收站 `.opennote/trash/归档/a.md` | `../../../.assets/<uuid>.png` |

**验证（探针 B1/B3）**：根目录笔记得到 `.assets/<uuid>.png`，子目录得到 `../.assets/<uuid>.png`；
`relativeAssetRef` 四种层数全部与上表一致（同一组断言也在 `src/lib/clip/assets.test.ts:475-489`）。

**用户写的是 `./.assets/image.png`，程序写的是 `.assets/image.png`（少一个 `./`）。**
判定：**不要为这个差异改生成端**。理由（三条，都可查）：
1. 读取端对两种写法**等价**：`resolveWorkspacePath` 会先 `normalizePath` 把 `.` 段吃掉
   （`src/fs/paths.ts:7-19`，调用点 `src/data/assets.ts:50-68`）—— 探针 C1 证实 `./x` 与 `x` 解析到同一条工作区路径；
2. 改写器与扫描器都按「`.assets/` 前面的字符是路径起点」来认引用（`src/lib/clip/landing.ts:136-141`），
   两种写法都在射程内；
3. 真正的用户需求是「文件名不冲突 + 图片不裂」，与是否带 `./` 无关。
   唯一值得做的统一是**文档口径**：`src/data/welcome.ts:86` 的示例已经是 `.assets/…`（正确），
   所以把用户原话里的 `./` 理解成口语即可，不必改代码。

### 1.4 ⚠️ 「内容相同 → 同名」**不成立**（必须修正的认知）

两条路径的行为**不一致**，这是本次调研最反直觉的一处：

| 路径 | 同内容重复落盘的行为 | 依据 |
| --- | --- | --- |
| 剪藏接收端 `allocateAssetPath` | **复用同名**（存在 + 字节相同 → `reused:true`，不写） | `src/lib/clip/landing.ts:219-244`；测试 `src/lib/clip/assets.test.ts:277-283` |
| 编辑器粘贴/拖拽 `saveImage` | **另存** `X 2.png`（`uniquePath` 兜底） | `src/data/library.ts:2516, 2524`；`src/fs/paths.ts:101-127`；测试 `src/editor/media.test.ts:202-225` |

`saveImage` 的 `taken` 只来自**文件名清单**，从不比对字节（`src/data/library.ts:2515-2516`），
于是第二次粘贴同一张图时 `assetFinalName` 明明算出了同一个 uuid，却被 `uniquePath` 推成 `X 2.png`
—— 而 `uniquePath` 用的是**空格**序号（`${base} ${counter}${ext}`，`src/fs/paths.ts:121`），
所以引用还得退化成角括号形式（`src/data/library.ts:2530` + `landing.ts:293-295`）。

**验证（探针 B2）**：连续两次 `saveImage(同一字节)` → 路径分别是 `.assets/<uuid>.png` 与 `.assets/<uuid> 2.png`，
两个文件字节相同，第二处引用是 `<.assets/<uuid> 2.png>`。

**判定**：与用户「uuid 命名 = 复用」的决定**直接冲突**，属于必须修的实现缺陷（不在本任务范围内动手）。
修法很明确：`saveImage` 走 `allocateAssetPath`（或至少「存在 + 字节相同 → 复用」），
并把 `-2`（无空格）作为唯一的去重形态 —— `landing.ts:245-260` 已经把 `-2` 的理由写清楚了
（「这个名字会出现在正文的 Markdown 引用里，空格会截断链接目标」）。
顺带一处口径不一致：剪藏路径用 `-2`（`landing.ts:257-260`），编辑器路径用 ` 2`（`paths.ts:121`）。

## 3. 迁移方案（本次重点）

### 3.0 目标与硬约束

- 把**全部**旧附件目录（工作区 + `.opennote/trash/`）里的文件整理进**工作区根 `.assets/`**，改名为内容派生 uuid；
- 正文引用**同步改写**（含回收站里的笔记，这样恢复后仍然对）；
- **内容相同 → 同一个文件名**（用户裁定：uuid 复用）；**内容不同 → 绝不互相覆盖**；
- 图片文件本身「掉不掉」不看，只看**引用不断**（用户裁定甲）；
- **不碰** `.opennote/history/`（历史快照是只读历史，见 §3.6）；
- 迁移过程**可中断、可重复跑**，绝不因为「跑到一半」把数据搞坏。

### 3.1 分阶段流水线（顺序本身就是安全设计）

```
阶段 A（只读）  扫描 → 建映射 → 出报告            ← 不写任何字节
阶段 B（写）    复制到 .assets/ → 逐字节校验      ← 源文件一个字节都不删
阶段 C（写）    改写笔记引用 → 逐条反解校验        ← 仍不删源
阶段 D（写）    删旧目录（含空目录）→ 复扫 → 收敛  ← 只有 A~C 全部通过才走到这里
```

**为什么必须「先复制、后改写、最后删」**：任何中间状态下，
源文件都还在（阶段 B/C 不删），所以**最坏结果是「多一份冗余」而不是「丢图」**。
逐文件、逐笔记地「搬一个删一个」会在中断时留下「图已经不在原位、引用还没改」的最坏中间态。

#### 阶段 A：扫描与建映射（只读）

1. 用后端的 `list()` 递归扫描（不要用操作系统 API，网页版/OPFS 也要能用）：
   候选目录 = 名字等于 `assets` 的目录 + 名字以 `.assets` 结尾的目录
   （与 `src/data/library.ts:380-394` 的识别规则**保持同一份名单**；同一份名单还镜像在
   `electron/main.cjs:1245-1261`）。
2. 对每个候选文件算 `sha256(bytes)`，做**按内容**分组（同一哈希 → 同一最终名）。
3. **给每个内容组分配最终名**：
   - 若 `.assets/<contentUuid(bytes)><safeExt>` **已存在**：
     - 字节相同 → **复用该路径**（迁移后引用直接指向它）；
     - 字节不同（用户手放的同名 / 极端碰撞）→ 按 `-2`、`-3`… 让位（**绝不覆盖**）。
   - 否则 → 最终名 = `assetFinalName(bytes, 原文件名)`（复用现有唯一产地，不另抄公式）。
4. 产出**迁移清单**（JSON）：
   `{源路径, 最终路径, 内容哈希, 引用它的笔记清单, 无法解析的引用}`。
5. **验证**：清单里「源文件数 == 内容组文件数 + 已存在复用数」；打印
   「无法解析的引用」清单（不猜、不静默）。

> ⚠️ 阶段 A 必须**先把所有源文件读完并留住字节/哈希**，因为阶段 D 会删源。
> 中间状态若只存在内存里，中断重跑就必须**重算**（幂等，见 §3.4）。

#### 阶段 B：复制 + 校验（源不动）

1. 对清单里每个「需要新建」的项：`readBytes(源)` → `writeBytes(.assets/<最终名>)`。
2. **逐项校验**：重新 `readBytes` 目标，**逐字节比对**（复用 `landing.ts:200-205` 的 `sameBytes` 语义）。
   不一致 → 立刻停、把已复制项记进迁移日志、**不进入阶段 C**。
3. 已存在且字节相同的项 → 跳过（不重写、不改 mtime）。
4. **验证没裂图**：此阶段结束时，
   `.assets/` 里应当**已经**能读到清单里每一个最终名（`readBytes` 成功），而**旧目录仍在**。

#### 阶段 C：改写引用（仍不删源）

对**每一篇笔记**（含 `.opennote/trash/**/*.md`，**不含** `.opennote/history/**`）：

1. 用「引用解析 + 清单查表」改写（**不要**用现有 `rebaseSharedAssetRefs` —— 它按设计只认 `.assets/`，
   `src/lib/clip/landing.ts:154-171`，对旧布局一格不改；探针 C3 已证实）。
2. 改写规则表（**必须全覆盖**，每条都要有用例）：

| # | 输入写法（真实样例） | 解析 | 输出 |
| --- | --- | --- | --- |
| 1 | `](./foo.assets/a.png)` | 笔记目录 + `./foo.assets/a.png` | `](<新相对引用>)` |
| 2 | `](<./foo 2.assets/b.png>)` | 同上（**角括号**，空格名） | `](<…>)` |
| 3 | `](foo.assets/a.png)`（**无 `./`**，探针/回收站实测） | 笔记目录 + 值 | 同上 |
| 4 | `](assets/a.png)` / `](./assets/a.png)` | 笔记目录 + 值（公共目录与笔记同层） | 同上 |
| 5 | `](assets/操作系统概念/image.png)` | 笔记目录 + 值（**带笔记子目录**，83 处） | 同上 |
| 6 | `<img src="./foo.assets/a.png">` / `src="assets/a.png"` | 笔记目录 + 值 | 改写 `src`，**其余属性一字不动** |
| 7 | `](<QwenLM ….assets/63e80eb9-…>)`（超长名 + 空格） | 同上 | 同上（角括号形式必须保留） |
| 8 | `](E:\杂记\images\x.png)`、`](/Users/lan/…)`、`](./img/x.png)` | **解析不到任何已迁移文件** | **原样保留 + 记入报告**（死引用本来就死，绝不猜） |
| 9 | `![x](https://…)`、`data:`、`blob:`、`asset://` | 不是本地文件 | 一字不动 |
| 10 | `](assets/${filenalme}/image.png)`（**真实存在的脏路径**） | 按字面路径找不到 | 原样保留 + 报告（若其父目录里有同名文件，也**不要**自作聪明匹配） |

3. **前缀重算**：一律用 `relativeAssetRef(笔记路径, 最终路径)`（`src/lib/clip/landing.ts:103-111`）现算，
   **不要**手拼 `../`。回收站里的笔记路径是 `.opennote/trash/…`（**比工作区深两层**），
   所以回收站笔记的引用是 `../../../.assets/x.png`；恢复时由既有 `rebaseNoteAssets` 改回
   （`src/data/library.ts:1277-1299, 1358-1359`）。
4. **写回**：用笔记自己的写入路径（桌面端/OPFS/FSA 三种后端都要走同一层）。
   写入前**重新读一次正文**，比对「阶段 A 读到的版本」：不一致 = 用户/外部编辑器并发改了，
   **跳过这篇并报告**（`src/data/library.ts:505-509` 的 stamp 机制就是为这类判断存在的）。
5. **验证没裂图（逐条）**：
   - 对改写后的正文里**每一条**本地引用，调用 `resolveWorkspacePath(ref, parentPath(笔记路径))`
     （`src/data/assets.ts:50-68`），断言结果**等于**清单里的最终路径；
   - 再对该路径 `readBytes` 成功（文件真的在）——两步一起做才算「引用不断」；
   - 任一断言失败 → **整篇回滚到改写前**、记日志、继续下一篇（一篇坏不影响别人）。

#### 阶段 D：清理与收敛

1. 删除已迁移的源文件（清单里的每一项，且**阶段 B/C 校验都通过**的）。
2. 删除**空的**旧目录（`<笔记名>.assets/`、公共 `assets/`）。
   - 公共 `assets/` **只在真的空了才删**；删完顺手重建工作区根的空 `assets/`
     （`ensureWorkspaceScaffold` 每次开工作区都会建，`src/data/library.ts:609-612`，别留下「少了一个目录」的意外 diff）。
   - 有文件残留（死引用指向的、无归属的）→ 目录留下 + 报告。
3. **复扫**：重跑阶段 A。若清单里「需要新建」= 0 且「待改写引用」= 0 → **收敛**，结束；
   否则再跑一轮（上限 3 轮，超出即报错停下）。

### 3.2 引用改写的覆盖率分析（现有实现帮不上多少）

`rebaseSharedAssetRefs` 的射程（`src/lib/clip/landing.ts:154-171`）：
只匹配 `](…)`/`](<…>)` 里**字面以 `(../)*.assets/` 开头**的目标，以及 `<img src="…">` 里的同一形状。

| 迁移需要的写法 | 现有改写器覆盖？ |
| --- | --- |
| `](./foo.assets/a.png)` | ✗（不是 `.assets/`） |
| `](<./foo 2.assets/b.png>)` | ✗ |
| `](foo.assets/a.png)`（无 `./`） | ✗ |
| `](assets/a.png)`、`](assets/笔记名/a.png)` | ✗ |
| `<img src="…">` | ✅（但只对 `.assets/`） |
| 参考式链接 `![x][id]` + `[id]: ./foo.assets/a.png` | ✗（全仓库未发现使用，但迁移器应**识别并报告**，而不是漏改后静默裂图） |
| `<a href="assets/a.png">` | ✗（`sharedAssetFilesIn` 的边界字符集含引号，扫描侧能碰到；改写侧碰不到） |
| `](assets/a.png)` 的**裸名**写法（`](a.png)` 同目录） | ✗（`rewriteAssetRefs` 的 ② 分支只服务剪藏客户端写法，`landing.ts:331-335`） |

结论：迁移器需要**自己的解析器**（先解析成工作区路径 → 查清单 → 生成新引用），
而不是复用现有两个改写函数。可以复用的只有三件：`resolveWorkspacePath`（解析）、
`relativeAssetRef`（前缀）、`markdownRef`（角括号）。

### 3.3 去重与冲突（回答「多篇引用同一张图」与「同名不同内容」）

- **内容相同 → 同一个 uuid**：按**字节**分组，同组共用一个最终名（真实数据里 16 组、39 个文件 → 省 23 个文件）。
  注意：**不能按文件名分组**——真实数据里 `image.png` 与 `image 2.png` 各有一对同名不同内容的文件
  （回收站 `Agent 产出/无标题.assets` vs 工作区 `项目实战/system_panel/无标题.assets`）。
- **内容不同、最终名相同**（含用户手放同名文件、极端哈希碰撞）：按 `-2`、`-3`… 让位，
  **顺序必须确定**（按「源路径字典序」），否则重跑会得到不同结果、破坏幂等。
  参考 `src/lib/clip/landing.ts:245-260` 的 `-2` 形态与理由（空格会截断链接目标）。
- **多篇笔记引用同一张旧图**：迁移清单里记「最终路径 → 引用它的笔记集合」，
  逐篇改写时都指向同一个最终路径。用户笔记本当前**没有**这种例子
  （按解析后的绝对路径统计：0 例；`无标题 2/3/4.md` 与 `刷 B 站….md` 里那四条**看起来**同源的引用，
  其中只有 `刷 B 站….md` 一条真的能解析到 `.opennote/trash/刷 B 站….assets/35a62705-….png`，
  另外三条**没有 `./` 前缀**的写法指向的是 `.opennote/trash/` 下并不存在的路径 —— 属 §1.6b 的错位引用）。
  尽管如此，这条路径**必须**实现：剪藏/复制笔记（`src/data/library.ts:1246-1251` 的 `duplicateNote`）
  会天然产生「多篇引用同一文件」，而永久删除的判定也依赖它（`src/data/library.ts:1469-1489`）。

### 3.4 幂等性与中断恢复（回答「跑到一半失败/重复跑」）

设计要点：**任何一次运行都能从当前磁盘状态重算，且重算结果与上一次一致**。

1. **映射确定性**：内容哈希 → uuid 是纯函数（`hash.ts:68-73`）；
   冲突让位按固定顺序；已存在的同名文件按「字节相同则复用」判定。
   ⇒ 第二次运行得到与第一次**完全相同**的最终名。
2. **「已经迁过」的识别**（三种中间态都不出错）：
   - 源还在、目标已存在且字节相同 → 跳过复制，直接进改写；
   - 源还在、目标已存在且字节不同 → 让位成 `-2`（**不覆盖**）；
   - 源**已不在**、正文里已经没有旧引用 → 视为已完成（天然幂等，无需额外状态文件）。
3. **迁移日志**（唯一需要落盘的新文件，放 `.opennote/asset-migration-<时间戳>.json`）：
   记录每个源路径 → 最终路径、校验哈希、跳过原因。
   用途：① 失败后人工核对；② 回滚（把目标复制回源、把正文还原）。
   **不把它当幂等键** —— 幂等靠磁盘事实重算，日志只是证据。
4. **回滚**：阶段 D 之前的所有动作都可逆（源还在）。进入阶段 D 后，
   回滚需要从 `.assets/` 反向复制 + 用日志里的「改写前正文」还原。
   所以**改写前必须把原文写进日志**（或走 `.opennote/history` 快照机制）。
5. **上限**：收敛循环最多 3 轮；每轮都重出报告。超限 = 有东西在反复变化（外部编辑器/git 检出），
   停下报错，不猜。

### 3.5 回收站的处理（用户要求一并整理）

- **改写回收站笔记的引用**：必须做。否则「恢复」之后引用仍然指向旧布局的路径，恢复即裂图。
  回收站笔记路径深两层 ⇒ 前缀是 `../../../.assets/…`（探针 B3 已证实层数语义）。
- **搬回收站里的附件目录**：必须做（用户要求）。它们没有对应笔记（孤儿），
  所以**引用改写那一半不适用**，只做「搬 + 改名」。搬完必须**报告**，
  因为「无归属的图」是人工决策项（可能用户就是要它跟着回收站笔记）。
- **不要碰 `.opennote/history/`**：45 个快照里 5 个含旧引用，且快照本身没有正确的解析基准
  （见 §1.6c）。改它 = 篡改历史版本；不改 = 恢复旧快照时图片仍然是裂的（既成事实）。
  **判定：不改，写进报告与已知问题。** 若将来要修，应改「恢复快照」这条路径而不是快照文件本身。
- **`emptyTrash()` 会把整个 `.opennote/trash/` 递归删掉**（`src/data/library.ts:1515-1522`）——
  包括孤儿 `.assets/`。所以**迁移必须抢在用户清空回收站之前**，否则那 3 个孤儿目录里的图就永久没了。
  这条要写进用户可见的提示语。

### 3.6 每步「怎么验证没裂图」（汇总表）

| 阶段 | 怎么做 | 怎么验证 |
| --- | --- | --- |
| A 扫描 | 递归 list + 算哈希 + 建清单 | 打印清单与「无法解析的引用」；**不写任何字节**（后端调用轨迹里只有 `list/readBytes`） |
| B 复制 | `readBytes(源)` → `writeBytes(目标)` | 重新读目标并**逐字节比对**；`.assets/` 里每个最终名都可读 |
| C 改写 | 解析 → 查表 → `relativeAssetRef` → `markdownRef` → 写回 | 对**每一条**引用 `resolveWorkspacePath` 反解 == 最终路径，且 `readBytes` 成功；失败整篇回滚 |
| D 清理 | 删源、删空目录 | 复扫收敛；`git status`（笔记本是 git 仓库）逐条核对；旧引用计数 = 0 |
| 全程 | 迁移前整库备份（应用自带 zip 导出 / git 提交） | 迁移后 `git diff` 只应出现「正文引用改写」+「`.assets/` 新增」+「旧目录删除」三类 |

### 3.7 旧目录怎么清、空了要不要删

| 目录 | 处理 | 理由 |
| --- | --- | --- |
| `<笔记名>.assets/`（工作区） | 文件全部迁走后**删除目录** | 它按笔记名派生，笔记改名后就是孤儿；`library.ts:1444-1447` 的「彻底删除」也只认它 |
| `<笔记名>.assets/`（回收站，3 个） | 同上（孤儿，无笔记可归属） | 用户要求一并整理 |
| 公共 `assets/`（19 个） | 文件迁走后**目录空了就删**；有残留（死引用指向的）就留下并报告 | 它是旧布局的家，留着只会让 `rescan` 的排除名单继续背两套规则（`library.ts:380-394`） |
| 工作区根空 `assets/` | **保留**（或删掉后由 `ensureWorkspaceScaffold` 重建） | `src/data/library.ts:609-612` 每次开工作区都建它；删了会立刻回来，删不删只是 diff 噪音 |
| `.assets/`（共享） | **不删**，只往里加 | 新布局的家 |
