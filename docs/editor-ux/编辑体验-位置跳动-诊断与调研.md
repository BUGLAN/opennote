# Opennote 编辑时「位置变动」诊断与同类产品调研

> 问题（用户原话）：编辑的时候会感觉到很不好用 —— **不是产品形态有问题，而是我们没考虑到哪一点**，导致它难用。比如编辑时「这个位置经常性地变动」。

本文分两半：

- **第一半（§1–§8）诊断**：在 Opennote 源码里把「位置为什么变」逐条定位到 `文件:行`，能用真实浏览器/单测量到的都给真实数字。
- **第二半（§9）调研**：Typora 与同类产品（Obsidian Live Preview、Marktext、Milkdown、Bear/Craft/Notion）分别怎么处理，以及 CodeMirror 6 官方支持的做法。

---

## 0. 结论速览

**我们漏掉的那一点，不是某个 bug，而是一条贯穿整个 live preview 的设计约束：**

> **渲染态与源码态必须是同一个几何形状，并且必须在同一个时刻切换。**
> 只要「同一个位置」在不同时刻有不同的高度/宽度，或者「同一时刻」文档前后两段的渲染状态不同步，用户的眼睛就会看到位移。

Opennote 现在的 live preview 是「**按块在源码态 ↔ 渲染态之间来回换**」的模型，于是同时违反了这条约束的两半：

| # | 成因 | 位置 | 实测幅度 | 严重度 |
|---|---|---|---|---|
| 1 | **异步内容不预留空间**：mermaid / KaTeX / 图片渲染完成后才长高 —— **在你什么都没做的时候发生** | `widgets.ts:40-50, 107-111, 145-149` | **mermaid +225.29px**、公式 +53.58px、图片 −6.39px（§0.1 C） | 🔴 最高 |
| 2 | **装饰器追不上后台解析器**：语法树在后台推进后装饰器不重算，直到用户下一次点击/打字才一次性补上 → 文档当场重排 | `livePreview.ts:507-513` | 6309 字文档一次性新增 **880 条装饰**（§1） | 🔴 最高 |
| 3 | **长距离滚动被 CM 自己改写 `scrollTop`**：`HeightMapGap` 用字符比例猜行号，markdown 字符分布不均导致猜偏 24 行 | CM6 `view/dist/index.js:5768-5782`（触发路径见 §0.1 F） | **−708.63px**（一次 0→6000 的跳转） | 🔴 高 |
| 4 | **整块 widget ↔ 源码互换**：表格 / mermaid / 公式块 / 分隔线 / 块级图片，光标进出时整块换形态，高度任意突变 | `livePreview.ts:272-285, 298-312, 397-423`、`widgets.ts:269-306` | 表格 **−147.69px**、mermaid **−117.17px**（§0.1 A） | 🔴 高 |
| 5 | **整行 `display: none`**：Setext 下划线行、代码围栏行在「显示/隐藏」之间切换 | `src/styles/editor.css:113-115`、`livePreview.ts:178-183, 314-320` | 围栏 **+47px**、Setext +29.36px；未渲染时按 29.36px 估算、实测 0 ⇒ 文档高 **−38px**（§0.1 E） | 🔴 高 |
| 6 | **块级 widget 违反 CM6 官方约束**：5 个块 widget 都带垂直 margin/padding（官方明文「不应有垂直 margin」），且**没有一个实现 `estimatedHeight` / `coordsAt`** | `editor.css:346/363/373/384/389`、`widgets.ts`（全文） | 代码级确定（§3.1） | 🔴 高 |
| 7 | **行内标记显隐**：`# `、`> `、`**`、`` ` ``、链接 URL 在光标所在行露出，导致该行文字水平位移 | `livePreview.ts:164-186, 205-260, 355-368` | 链接 +64.47px、`# ` +24.11px、`**` +14.18px（§0.1 B）；Typora 同样未解决（§9.2） | 🟡 中 |
| 8 | **切笔记时视图与光标不一致**：光标恢复到记忆位置，视图却被显式滚到**文档开头** | `src/components/EditorPane.tsx:190-196` | 代码级确定（未实测） | 🟡 中 |

**最重要的一条横向结论**（§0.1 D）：CodeMirror **只有一个滚动锚点 —— 视口顶部那一行**。所以「变化发生在锚点处或下方」时（也就是**用户正盯着的内容**）**完全不补偿**。⇒ **「靠滚动锚定兜底」这条路走不通，唯一可靠的做法是不让高度变化发生。**

**调研中已排除的三个假设**（避免后续重复怀疑）：

- ❌ 「块级装饰来自 ViewPlugin 会抛 `RangeError`」 —— 我们**合规**：`livePreview.ts:514` 用的是 `StateField` + `EditorView.decorations.from(field, …)`。
- ❌ 「滚动容器是父级，撞上 CM6 的父级滚动 bug（issue #1673）」 —— 我们**不适用**：`.editor-host { overflow: hidden }` + `.cm-editor { height: 100% }` + `theme.ts` 的 `overflowY: auto` ⇒ 真正的滚动容器就是 `.cm-scroller`。
- ❌ 「`display:none` 破坏了点击定位 / 方向键 / heightMap」 —— **实测都不成立**（39 行 diff = 0、56 个采样点无偏移、方向键只是跳过隐藏行）；真正的问题是「未渲染的隐藏行按整行高估算」（见上表第 5 行）。

详见 §9.6 的逐条对照表。

### D. 视口滚动位置有没有被保住 → **只有「变化发生在锚点上方」时才补偿一半**

记录标记段落在**视口内的 y**（`rect.top − scrollerRect.top`，这才是用户看到的位移）：

| 场景 | 变化块相对锚点 | Δ`scrollTop` | 观察点在视口内的位移 | 被钉住了吗 |
|---|---|---:|---:|:--:|
| 表格整体滚到视口上方，观察 MARK6A | **锚点上方** | **−115** | **−32.69px** | ❌ |
| 表格贴视口顶部，观察 MARK4A | 锚点下方 | 0 | **−147.69px** | ❌ |
| 同 D2，但 `dispatch` 带 `scrollIntoView: true` | 锚点下方 | 0 | **−147.69px** | ❌ |
| 公式块贴顶，观察 MARK6A | 锚点下方 | 0 | **−13.66px** | ❌ |
| 光标离开围栏代码块，观察 MARK3A | 锚点下方 | 0 | **−47px** | ❌ |
| 表格跨视口上沿时点进表格，观察 MARK4A | 锚点上方 | **−115** | **−32.69px** | ❌ |

**实测结论（回答「CodeMirror 有没有自动补偿 `scrollTop`」）：有一半。**

CodeMirror **只有一个滚动锚点：视口顶部那一行**（`scrollAnchorAt()`，`view/dist/index.js:6682-6685`）：

- **变化发生在锚点上方** → 锚点行的 `top` 变了 → CM 补偿 `scrollTop`（Δ = −115，正好等于锚点 `top` 的变化量），内容**基本**被钉住，但仍有 **−32.69px** 残留。
- **变化发生在锚点处或锚点下方** → 锚点行 `top` 不变 → `diff ≈ 0` → **完全不补偿**（Δ`scrollTop` 全是 0），块下方内容按真实高度差**整块跳走**：−147.69px / −13.66px / −47px。
- **`scrollIntoView: true`（真实键入/方向键路径）不改变结论**：D3 与 D2 数字一模一样 —— 因为光标本来就在视口内，`scrollIntoView` 什么也不做。

> 也就是说：**用户眼睛正盯着的那块内容，恰恰是最不会被补偿的那块。** 补偿只对「已经在视口上方、你看不见的变化」生效。

### E. `.cm-line { display: none }` 的真实后果（§2）

**先说清楚实测推翻了我原本的源码级推断**（这正是要做实测的原因）：

| 我原本的推断 | 实测结果 |
|---|---|
| `display:none` 会让 `heightMap` 出错 | ❌ **不成立** —— 已渲染的 39 行，`lineBlockAt().top` 与真实 DOM 位置**逐行 diff = 0** |

### F. 长距离滚动会被 CodeMirror 自己改写 `scrollTop`（**−708.63px**）

用属性 setter 拦截 `scrollDOM.scrollTop`，抓到写入者的调用栈：

```
一次大跳转 0 → 6000：实际停在 5291（差 -709px）
   scrollTop 0 → 6000        由 at bigJump 写入
   scrollTop 6000 → 5291.37  由 at EditorView.measure (dist-*.js:6993:31) 写入
同样的距离分 100px 步进：漂移 0px，单步最大偏差 0px
同样的距离分 500px 步进：漂移 0px，单步最大偏差 0px
```

`EditorView.measure` 里那次补偿的完整算术：

```
#  0 scrollAnchorAt off=6000   → line=181 top=5993.32   ← 补偿前：锚点 top（估算值）
# 15 lineBlockAt   pos=1776    → line=181 top=5284.69   ← 补偿后：同一行的真实 top
diff = 5284.69 - 5993.32 = -708.63  →  scrollTop: 6000 → 5291.37
```

**为什么估算差了 708px（≈24 行）**：未渲染区域在高度表里是一个 `HeightMapGap` 节点，`HeightMapGap.blockAt()`（`view/dist/index.js:5768-5782`）用**字符数比例**猜行号。本文档是「长段落 + 空行」交替（markdown 的常态），字符分布极不均匀，`比例 × 字符数` 猜出来的行比真实行**晚了 24 行**，于是 `scrollAnchorHeight` 是个假值，`scrollTop += diff` 把它当成真实位移补偿掉了。

**触发条件（实测）**：一次跨度 **≥1000px** 的跳转（拖滚动条 / 点轨道 / 大纲跳转 / `Ctrl+End` / 恢复上次位置）会中招；100px / 500px 的**步进式滚动完全不中招**（漂移 0px）。

> **这解释了为什么「用滚轮翻很顺，一拖滚动条就跳」。**
> 也说明：`overflow-anchor: none` 与这件事无关（实测把 `overflow-anchor: none` 加到 `scrollDOM` 与 `contentDOM` 上，每一步的 delta 完全相同）—— 这是 CodeMirror 自己的补偿逻辑在改，不是浏览器原生滚动锚定。

## 1. 装饰器追不上后台解析器（已实测）

> 阅读顺序说明：**§0 / §0.1 按「跳动幅度」排序**，**§1–§6 按「机制」分组**，两边编号不对应，以各节标题为准。

### 1.1 机制

CodeMirror 的 Markdown 语法树是**增量、后台**解析的，不是一次解析完整篇：

- `LanguageState.init` 只解析前 **3000 字符**（`Work.InitViewport`）—— 见 `node_modules/@codemirror/language/dist/index.js:541`。
- 之后由一个 `ParseWorker` ViewPlugin 在**空闲回调**里继续解析（`requestIdleCallback`，最小延迟 100ms、最大 500ms 一拍），解析完再发一个**只有 effect 的事务**把新树交出去 —— 见 `node_modules/@codemirror/language/dist/index.js:621`：

  ```js
  this.view.dispatch({ effects: Language.setState.of(new LanguageState(field.context)) });
  ```

而 `livePreviewField.update()` 的守卫是：

```ts
// src/editor/livePreview.ts:507-513
update(value, tr) {
  const settingsChanged = tr.effects.some(
    (effect) => effect.is(setEditorSettings) || effect.is(refreshDecorations),
  );
  if (!tr.docChanged && !tr.selection && !settingsChanged) return value;   // ← 这里
  return updateDecorations(value, tr, settingsChanged);
}
```

`Language.setState` 这个 effect **不在白名单里**，而该事务既没有 `docChanged` 也没有 `selection` ⇒ **直接 `return value`，装饰器不重算。**

结果：`updateDecorations()` 里那段「后台解析器可能追上来了」的补算逻辑（`livePreview.ts:487-488`）

```ts
if (tree.length > value.parsedTo) dirty.push({ from: Math.max(0, value.parsedTo - 1), to: tree.length });
```

**在生产里几乎永远不会被触发** —— 它只在「用户恰好同时改选区/打字」时才顺带跑到。`parsedTo` 这套记账机制在真实使用中是死代码。

### 1.3 为什么用户感觉是「经常性」而不是「打开时一次」

- **打开长笔记**：尾部是原始 markdown，你往下滚也还是原始 markdown（滚动不产生事务）。**直到你点一下**才渲染 —— 这一下就是一次全文档重排。
- **正在打字**：每次敲键都会触发 `updateDecorations`，于是**后台解析推进到哪，文档就重排到哪**。你连续打字时，前方内容一段一段地从「源码」翻成「渲染」，看起来就是位置一直在动。
- 临界点只有 **3000 字符**（不是 `FULL_REBUILD_LENGTH` 的 20k）。一篇 3000 字的中文笔记就跨过去了 —— 这是「经常性」的原因。

### 1.4 修复方向（一行级）

守卫要把「语法树推进了」也算作需要重算的理由：

```ts
update(value, tr) {
  const settingsChanged = tr.effects.some(
    (effect) => effect.is(setEditorSettings) || effect.is(refreshDecorations),
  );
  // 后台解析器推进了树 ⇒ 也要重算，否则文档尾部会停留在原始 markdown
  if (!tr.docChanged && !tr.selection && !settingsChanged &&
      syntaxTree(tr.state).length === value.parsedTo) return value;
  return updateDecorations(value, tr, settingsChanged);
}
```

注意 `updateDecorations()` 里 `value.parsedTo` 的语义要跟着改：现在它只在「有 docChanged/selection」时才被消费，改成「树一推进就消费」之后，需要保证增量路径真的只重算新解析出来的那段（`livePreview.ts:488` 那条分支本来就是这个用途）。

## 2. 几何不一致之一：整行 `display: none`

```css
/* src/styles/editor.css:112-115 */
/* Lines CodeMirror keeps in the document but the reader should not see. */
.cm-content .cm-line.md-hide-line {
  display: none;
}
```

用它的地方：

| 位置 | 场景 |
|---|---|
| `livePreview.ts:178-183` | Setext 标题的 `====` 下划线行 |
| `livePreview.ts:314-320` | 围栏代码块的**首尾 ``` 行**（光标不在块内时） |

两个问题：

**(a) 切换即跳动。** 光标从代码块外移到块内，`showFences` 由 false 变 true ⇒ 两行 ``` 从 `display:none` 变回可见 ⇒ **代码块高度 +2 行**，其后所有内容整体下移。Setext 标题同理。

**(b) CodeMirror 是靠 `getBoundingClientRect()` 逐行量高度来维护行高表的**：

```js
// node_modules/@codemirror/view/dist/index.js:3318-3362
measureVisibleLineHeights(viewport) {
  ...
  let childRect = child.dom.getBoundingClientRect(), { height } = childRect;
  ...
  result.push(height + spaceAbove);
```

`display:none` 的行 `getBoundingClientRect()` 全为 0 ⇒ 它被记成**高度 0 的行**。行高表（`HeightMap`）、`posAtCoords()`（点击定位）、`lineBlockAtHeight()`（滚动定位）都建立在这张表上。这是**没有被官方支持的用法**（详见 §9 的 CodeMirror 官方结论），需要按官方支持的替代做法改写。

> **仓库内部其实已经写下了这条教训**：`DESIGN.md:1395` 讲专注模式时说「**不要**改成 `display: none`（那会让文档跳动）」—— 而 `.md-hide-line` 正是 `display: none`。同一份设计文档里，一条规则和一处实现互相矛盾。

**(c) 官方不支持这种用法，并给了替代做法。** CM6 的 `measureVisibleLineHeights()` 用 `getBoundingClientRect().height` 逐行实测高度写进 `heightMap`（`index.js:3318-3362`）；`display:none` 的行实测高度是 **0**。

**但实测把「这会带来什么后果」纠正得更精确了**（详见 §0.1 E）——原以为它会破坏点击定位和方向键，实测**都没有**：

| 后果 | 实测 |
|---|---|
| 已渲染行的 `heightMap` 出错 | ❌ 39 行逐行 diff = 0 |
| 点击定位偏移 | ❌ 56 个采样点无偏移 |
| 方向键跳行 | ❌ 光标只是**跳过**隐藏行 |
| **未渲染的隐藏行被估算成一整行高（29.36px），滚进视口后被实测为 0** | ✅ **真问题**：文档总高与滚动条高度 **−38px**，围栏以下内容**上移 37.73px** |

也就是说：**滚动本身会改变文档高度**，滚动条长度随滚动位置反复变化。changelog `6.43.1` 还专门修过一次「`display:none` 内容行导致的崩溃」（<https://github.com/codemirror/dev/issues/957>）。

官方给出的替代做法是**在 `StateField` 里用 `Decoration.replace({ widget })` 覆盖该行（含行尾换行符）** —— 也就是 CodeMirror 自己 folding 用的那套（<https://discuss.codemirror.net/t/hiding-replacing-lines-that-begin-with-a-certain-signifier/4473>）。

> 注意：**换成 `Decoration.replace({ block: true })` 只解决了「估算/实测不一致」这一半问题，不解决「切换即跳动」那一半**（§0.1 A 里的 +29.36px / +47px）。要同时解决后者，必须让隐藏形态与显示形态**占同样的高度**（或干脆不做整行显隐 —— 见 §9.2 与 §9.4）。

## 3. 几何不一致之二：整块 widget ↔ 源码互换

`livePreview.ts` 里所有块级元素都是「光标不在里面 ⇒ 换成 widget；光标进去 ⇒ 换回源码」：

| 块 | widget | 源码态 |
|---|---|---|
| 表格 | `TableWidget`（渲染后的 `<table>`） | 每行一条 markdown 竖线源码 |
| mermaid | `MermaidWidget`（SVG） | ``` 围栏 + 代码 |
| `$$` 公式块 | `MathWidget`（KaTeX，block） | `$$` + TeX 源码 |
| 分隔线 | `HrWidget`（三个圆点） | `---` |
| 独占一行的图片 | `ImageWidget` | `![alt](src)` |

两种形态的高度没有任何关系：

- **表格**：渲染态单元格 `padding: 0.42em 0.7em`（`prose.css` 的 `.table-widget th/td`）、`margin: 1.05em 0`，而且**单元格里的长文本会折行**；源码态是「一行一行不折行的竖线」。一张 3 行、单元格有长句的表格，两种形态高度可以差好几倍。
- **mermaid**：源码 5 行 ≈ 100px；渲染出来的图常常 300–600px。**点击图表准备编辑的那一刻，下方内容整体上移几百像素**，点击结束再弹回去。
- **公式块**：同理。

更糟的是 `TableWidget` 的交互设计就是「点一下换成源码」：

```ts
// src/editor/widgets.ts:285-299
host.title = "点击编辑表格源码";
host.addEventListener("mousedown", (event) => {
  ...
  view.dispatch({ selection: { anchor: view.posAtDOM(host) }, scrollIntoView: true });
```

`scrollIntoView: true` 还会让 CodeMirror 再滚一次视口 —— 于是「点一下表格」= 高度突变 + 强制滚动，两个位移叠加。

> 这正是 Typora 与 Opennote 最大的行为差异（见 §9.2）：**Typora 点进表格是在渲染出来的表格里原地编辑单元格，根本不切源码**，所以没有高度突变这回事。

### 3.1 而且这些块 widget 违反了 CodeMirror 的官方约束

CM6 官方文档（本机 `@codemirror/view@6.43.13` 的 `index.d.ts:140-144`）原文：

> "Note that **block-level decorations should not have vertical margins**, and if you dynamically change their height, you should make sure to call `requestMeasure`."

**我们的 5 个块级 widget 全部带垂直 padding/margin：**

| widget | 类 | 垂直间距 |
|---|---|---|
| `ImageWidget`（块级） | `.md-media--block` | `padding: 0.6em 0`（`editor.css:346`） |
| `HrWidget` | `.md-hr` | `padding: 1.35em 0`（`editor.css:363`） |
| `MathWidget`（block） | `.md-math.math-block` | `padding: 0.45em 0`（`editor.css:373`） |
| `TableWidget` | `.md-table` + `.table-widget` | `padding: 0.55em 0`（`editor.css:384`）+ `margin: 1.05em 0`（`prose.css`） |
| `MermaidWidget` | `.md-mermaid` | `padding: 0.8em`（`editor.css:389`） |

**并且没有任何一个 widget 实现 `estimatedHeight` 或 `coordsAt`** —— `src/editor/widgets.ts` 全文只实现了 `eq` / `toDOM` / `ignoreEvent`。而 `estimatedHeight` 的默认值是 `-1`（「我不知道」，`index.d.ts:229-234`）。

CM6 作者 Marijn 在官方论坛亲自答复过这一点；提问者实测的结论是：**估算值与实际高度偏差越大，跳动越剧烈 —— 5 行以内几乎无感，大表格则剧烈跳**（<https://discuss.codemirror.net/t/unwanted-programmatic-scrolling-with-large-widgets/9372>）。

⇒ 对**表格**和 **mermaid** 这两个大块 widget 来说，「不实现 `estimatedHeight` + 带垂直 margin」= 让 CM6 在高度未知的前提下布局，然后靠 `requestMeasure()` 事后纠正。**这正是「跳一下再稳」的机制来源。**

## 4. 几何不一致之三：行内标记显隐

`isActive(from, to)` 是**按行**判定的（`livePreview.ts:67-70` 的 `selectionSpans` 取整行），命中就把该行的标记全部露出来：

| 标记 | 非激活态 | 激活态 |
|---|---|---|
| `# ` 标题 | `hide()` 掉 | 显示 ⇒ 该行文字**整体右移** |
| `> ` 引用 | `hide()` 掉 | 显示 ⇒ 右移（且 `.md-quote` 还有 `padding-left: 14px`） |
| `**` `==` `~~` | `hide()` 掉 | 显示 ⇒ **同一行后半段右移** |
| `` ` `` 行内码 | `hide()` 掉 | 显示 |
| `[text](url)` | 括号与 URL 全隐藏 | 显示 ⇒ 该行剧烈右移 |

`hide()` 用的是 `Decoration.replace({})`（零宽替换），所以是「文本流里凭空多出几个字符的宽度」。光标在行间上下移动时，每一行都在「缩进」与「不缩进」之间反复横跳 —— 这是最容易被感知成「位置在变」的一类位移，因为它发生在**你眼睛正盯着的那一行**。

三个 widget 都是「先给一个一行高的占位（`公式渲染中…` / `图表绘制中…`），渲染完再换」。图片更极端：`<img>` 在 `src` 赋值前高度是 0，**没有任何 `width`/`height`/`aspect-ratio` 预留**。`view.requestMeasure()` 会重新量，但：

- **视口下方**的内容会被直接推下去（这是用户能看见的位移）；
- **视口上方**的内容是否被补偿，取决于 CodeMirror 自己的滚动锚定是否生效 —— 而它是**有条件**的（见下）。

**实测幅度（§0.1 C）**：

| 块 | 占位 → 渲染后 | 下方内容位移 |
|---|---|---:|
| KaTeX 公式 | 37.56px → 91.14px | **+53.58px** |
| mermaid 图 | 47.94px → **273.23px** | **+225.29px** |

> **这是本次实测里单次幅度最大的一类跳动，而且它发生在你什么都没做的时候** —— 打开一篇带图的笔记，图渲染完成的瞬间，图以下内容整体下跳 225px。它也是**唯一一类可以靠「渲染前预留高度」根治的**（§8.1 的 P0 项）。

### CodeMirror 的滚动锚定是有条件的（源码级）

CodeMirror **主动关掉了浏览器的原生滚动锚定**：

```js
// node_modules/@codemirror/view/dist/index.js:6864
".cm-scroller": { ..., overflowAnchor: "none" },
```

它自己实现了一套，但只在满足**全部**条件时才补偿 `scrollTop`（`index.js:8185-8281`）：

1. 高度变化必须是在**一次 measure 循环内**被发现的；
2. 该循环里**视口不能发生变化**（`if (!update.viewportChanged && this.measureRequests.length == 0)`，`index.js:8255`）；
3. **不能有待处理的 `scrollTarget`**（`index.js:8257-8261`：有 scrollTarget 就把锚定高度重置为 -1 并去滚目标）；
4. 用户在此前**没有滚动过**（`if (Math.abs(scrollOffset - this.viewState.scrollOffset) > 1) scrollAnchorHeight = -1;`，`index.js:8187`）；
5. 差值要大于 1px（`index.js:8267`）。

而 Opennote 的打字机模式**每次选区/文档变化都会主动派发一个 scrollTarget**：

```ts
// src/editor/setup.ts:59-63
this.frame = requestAnimationFrame(() => {
  ...
  update.view.dispatch({ effects: EditorView.scrollIntoView(head, { y: "center" }) });
});
```

⇒ 条件 3 被持续破坏，锚定补偿被反复重置。**打字机模式打开时，异步渲染造成的位移不会被自动补偿。**

### 但实测给出了一个比这 5 条更简洁、更致命的结论

CodeMirror **只有一个滚动锚点：视口顶部那一行**（`scrollAnchorAt()`，`view/dist/index.js:6682-6685`）：

```js
scrollAnchorAt(scrollOffset) {
  let block = this.lineBlockAtHeight(scrollOffset + 8);
  return block.from >= this.viewport.from || this.viewportLines[0].top - scrollOffset > 200 ? block : this.viewportLines[0];
}
```

⇒ **只有「发生在锚点（视口顶行）上方」的高度变化才会被补偿。**

实测（§0.1 D，6 个场景）：

| 变化位置 | Δ`scrollTop` | 用户看到的内容位移 |
|---|---:|---:|
| 锚点**上方** | **−115**（补偿了） | 仍有 **−32.69px** 残留 |
| 锚点处 / 锚点**下方** | **0**（完全不补偿） | **−147.69 / −13.66 / −47px** |

**也就是说：用户眼睛正盯着的那块内容，恰恰是最不会被补偿的那块。** 补偿只对「已经在视口上方、你看不见的变化」生效 —— 而那种变化本来就不该被看见。

这条结论比「4 个前提」更好用：**它意味着「靠 CodeMirror 的滚动锚定兜底」这条路走不通，唯一可靠的做法是不让高度变化发生**（预留高度 / 不切换形态）。

## 6. 切笔记：光标位置与视图位置不一致

```ts

## 7. 为什么测试没拦住：测试把「会跳」当成了基线

`src/editor/livePreview.test.ts` 有 32 条用例，其中一整个 describe 叫 **「装饰器基线：未改动的形态保持原样」**，逐条锁定了当前这套会跳的行为：

- `it("setext 标题：隐藏下划线行")`（:270）
- `it("围栏代码：非激活态隐藏围栏行，正文行带语言属性")`（:278）
- `it("表格：非激活态换成块级 TableWidget")`（:295）
- `it("标题：非激活态隐藏 \`## \` 并打上行类，激活态只留行类")`（:194）

也就是说：**任何修复都会先弄红这些用例**，而它们的存在理由是「保持原样」而不是「保证不跳」。修的时候要把这些断言从「形态断言」改成「**几何/时序断言**」（例如：切换激活态前后，块下方标记元素的 `rect.top` 变化必须为 0）。

更能说明问题的是 `livePreview.test.ts:76-93` 的 `settled()` 辅助函数，它的注释已经把这个生产缺陷当成测试环境的噪音写下来了：

> 「……而增量路径正是拿 `tree.length` 与 `value.parsedTo` 比，于是「增量 == 全量重建」这条断言会因「断言那一刻解析推进到哪」而分叉……
> 2. 补一个「只改选区」的事务 —— 字段的 `updateDecorations()` 会走 `tree.length > value.parsedTo` 那条分支，按完整的树重算一遍。」

```ts
function settled(state: EditorState): EditorState {
  ensureSyntaxTree(state, state.doc.length, 60_000);
  return state.update({ selection: state.selection }).state;   // ← 手动补一次「用户点了一下」
}
```

**测试里要手动补的那一次「只改选区的事务」，正是生产环境里用户必须手动点一下才能让文档渲染出来的那一次。** 作者当时把它归因为「测试不该测量解析时序」，实际上它测量到的就是一个真实缺陷。

## 9. 同类产品怎么做（调研）

> 本节由两路独立调研支撑，**逐条原始引文与 URL** 见：
> - [`R1-Typora-编辑稳定性机制.md`](R1-Typora-编辑稳定性机制.md)
> - [`R2-同侪产品与CodeMirror6技术手段.md`](R2-同侪产品与CodeMirror6技术手段.md)
>
> 可信度标签沿用两份调研的约定：【官方文档确证】/【官方开发者回复】/【官方源码或 issue】/【用户观察】/【未找到】。

### 9.1 先看清楚：只有一种编辑模型会跳

| 模型 | 代表 | 渲染态与光标的关系 | 会不会跳 |
|---|---|---|---|
| **A 块编辑器** | Notion / Craft / Bear | 块的类型是**持久属性**，不随光标改变 | **结构上不会** |
| **B 渲染 DOM 直接编辑** | Typora / MarkText | 整篇渲染成 DOM，直接编辑这个 DOM；源码模式是**整篇**显式切换 | 基本不会（只有行内标记） |
| **C 同文档 + 装饰器切换** | Obsidian Live Preview / **Opennote** | 同一份源码文档上，按行/按块在源码态 ↔ 渲染态之间换 | **只有这一种会跳** |

Notion 官方工程博客把块模型讲得很清楚：block 的 **Type 是持久属性**，「Turn into」是用户显式操作而不是光标的副作用 —— <https://www.notion.com/blog/data-model-behind-notion>【官方文档确证】。Craft 官方同样表述为「你创建的每个东西都是一个块，各自独立」 —— <https://support.craft.do/en/write-and-edit/blocks-and-pages>【官方文档确证】。

**Opennote 在模型 C，而模型 C 里「不跳」不是免费的**：编辑器不会替你做，必须自己保证三件事 —— **几何一致**（§2–§4）、**时序一致**（§1）、**滚动锚定**（§5）。下面看别人怎么补这三件事，以及谁补砸了。

### 9.2 Typora：不是「消除重排」，而是「认账 + 补偿」

**架构**：单一 hybrid view —— 把 Markdown 渲染成 DOM 之后**直接编辑这个 DOM**。作者 abnerlee 在官方 issue 仓库原话：

> "We implement the default hybrid view to save users from the traditional switching between source code and preview mode"

并明确拒绝分栏/双缓冲方案：「to make the hybrid view easy and good enough for users is our goal」 —— [typora-issues#1317](https://github.com/typora/typora-issues/issues/1317)、[#4215](https://github.com/typora/typora-issues/issues/4215)【官方开发者回复】

**行内标记**：光标进入即展开为源码，**这是官方设计**：

> "Moving the cursor to the middle of a span element will expand that element into the Markdown source"
> —— <https://support.typora.io/Markdown-Reference/>【官方文档确证】

**关键的反向发现：Typora 对由此产生的水平位移没有任何几何补偿，而且长期认账不修。**
官方 issue 标题就叫 "Links cause layout shifting"（标签 `hybrid editing`，**至今 open**）：长 URL 展开会把整段推走、光标列位置从 col 10 被重置到 col 22 —— [#5375](https://github.com/typora/typora-issues/issues/5375)、[#1313](https://github.com/typora/typora-issues/issues/1313)。另有 [#285](https://github.com/typora/typora-issues/issues/285)（**2018 年至今 open**）：标题显示 `###` 时不保持渲染样式，用户形容为 "disconcerting jumpy text"。【用户观察 + 官方已悉】

⇒ **§4 那条「行内标记显隐造成水平位移」不能靠「Typora 也这样」来豁免 —— 它是 Typora 自己都没解决的空白。**

**块级结构：这是 Typora 做对的那一件，也是 Opennote 最该抄的。** 表格/公式/图表一律**保持渲染态、原地编辑，绝不塌成源码**：

| 块 | Typora 的行为 | 来源 |
|---|---|---|
| 表格 | 聚焦表格时**弹出工具栏**，在渲染出来的表格里原地编辑；对齐信息写在 `<td>` 的 `style` 上 | <https://support.typora.io/Table-Editing/> |
| 公式 | 独立的 input mode（Up/Down 或 Ctrl+Enter 结束），**不替换**已渲染的公式 | <https://support.typora.io/Math/> |
| 图表 | 有 `.md-diagram-panel-preview` 预览面板，可右键另存 | <https://support.typora.io/Draw-Diagrams-With-Markdown/> |

【以上均为官方文档确证】对照 §3：Opennote 的表格是 `点击编辑表格源码`（`widgets.ts:285`）、mermaid 与公式块直接换成源码 —— **这正是 Typora 明确不走的那条路。**

**Typewriter Mode 是「补偿式」而不是「预防式」**：官方说它「在打字时滚动文章以保持光标固定」、「默认把光标保持在窗口正中」 —— <https://support.typora.io/Focus-and-Typewriter-Mode/>【官方文档确证】。也就是说 Typora 承认「打字过程中内容会移动」，只是**每次变更后主动把光标重新锚回屏幕中央**，用「光标不动」换掉「内容不动」。

**Focus Mode 官方定义是 fade out（淡化），不是隐藏** —— <https://support.typora.io/Change-Styles-in-Focus-Mode/>【官方文档确证】。它不改变布局。这一点 Opennote 做对了（`DESIGN.md:1395` 也写下了这条），但 `.md-hide-line` 是例外（§2）。

**Typora 自己的 3 处空白（不能照抄，必须我们自己解决）：**

1. **图片没有占位高度机制。** 官方只认 `width`/`height`/`zoom`，并明说其他 `style` 属性在编辑器内**被忽略**（即 `aspect-ratio` 不参与编辑态布局） —— <https://support.typora.io/Resize-Image/>【官方文档确证】。用户已报告远程图片异步加载把页面跳到顶部 —— [#3880](https://github.com/typora/typora-issues/issues/3880)【用户观察】。
2. **代码块行号「渲染迟到 → 推动页面」是跨 1.9.4 → 1.13.4 多年未修的 open 缺陷**："the line number gutter suddenly appears on the left side, causing the page to shift, flicker, or repaint" —— [#6548](https://github.com/typora/typora-issues/issues/6548)、[#6094](https://github.com/typora/typora-issues/issues/6094)【用户观察】。
3. **模式切换保持滚动位置是 1.13（2026-04）才补上的**："View switch between source code mode and hybrid editing mode will preserve scroll position" —— <https://support.typora.io/What's-New-1.13/>【官方文档确证】。

### 9.3 Obsidian Live Preview：同一条路上的前车之鉴

Obsidian Live Preview 与 Opennote **用的是同一个模型、同一个编辑器（CodeMirror 6）**，所以它是最直接的对照。

- 官方文档确证它采用「光标触达即显源码」："You can reveal the syntax for any Markdown-formatted text by moving the text cursor to it" —— <https://obsidian.md/help/edit-and-read>【官方文档确证】
- **但官方文档完全不提位置稳定性。**
- **它的滚动跳动是反复出现的版本回归**：1.12.5 复现（控制台直接出现 CM6 自己的 `Measure loop restarted more than 5 times` / `Viewport failed to stabilize`）→ 员工 WhiteNoise 确认复现并承诺 1.12.7 修复 → 用户 2026-05 报告 1.13.0 又回来了而且更糟。**触发源是 embeds / transclusions 的异步渲染。** —— <https://forum.obsidian.md/t/scrolling-unusable-when-document-has-transclusions-large-jumps-up-down-and-infinite-jump-loops-with-viewport-failed-to-stabilize-measure-loop-restarted-more-than-5-times/112103>【官方论坛员工回复 + 用户观察】

⇒ **结论很重要：模型 C 的跳动连 Obsidian 都没根治。** 不能指望「我们用 CM6 所以没事」；必须在 Opennote 里建立**自己的约束 + 回归测试**。Obsidian 那个报错（`Viewport failed to stabilize`）正是 `index.js:8208-8212` 的告警 —— 异步 widget 让 measure 循环无法收敛。

### 9.4 Bear / Zettlr：把标记显隐做成**全局开关**

Bear 官方 FAQ：Markdown 标记的显隐是 **Settings > General 里的 `Hide Markdown` 开关** —— <https://bear.app/faq/how-to-use-markdown-in-bear/>【官方文档确证】。Zettlr 同路线（全局 WYSIWYG/WYSIWYM 开关 + 逐类元素勾选）—— <https://docs.zettlr.com/en/editor/appearance.html>。

**这是一个成本极低、收益极高的对照**：全局开关只在切换的那一次改变布局；而 Opennote 的「按光标行显隐」是**每次移动光标都触发一次局部重排**。§4 那条位移，用「全局开关 + 只在光标行露标记」的折中就能大幅降低触发频率。

### 9.5 iA Writer：官方承认「光标居中」与「位置稳定」互相冲突

iA Writer 官方支持页的小节标题就叫 **"Jumping Screen When Editing?"**，原文：

> "A conflict between the area you will select to edit and Focus Mode's attempt to vertically center the cursor might result in the screen jumping vertically."

对策是**建议在编辑阶段关闭该模式** —— <https://ia.net/writer/support/editor/focus-mode>【官方文档确证】

⇒ **「位置绝对稳定」与「光标永远居中」是两个互相冲突的目标，必须显式取舍。** 这条直接解释了 §5 里 Opennote 打字机模式的问题：它无条件追求「光标居中」，代价就是持续破坏滚动锚定。

### 9.6 CodeMirror 6 官方怎么说（我们直接踩在它上面）

这一节是**可以立刻转成修复动作**的部分。逐条对照 Opennote 现状：

| # | 官方结论 | 来源 | Opennote 现状 |
|---|---|---|---|
| 1 | 块级装饰**只能由 `StateField` 提供**，由 ViewPlugin 提供会**直接抛 `RangeError`**（源码硬校验） | `view/dist/index.js:2770-2777`、<https://codemirror.net/docs/ref/#view.EditorView^decorations> | ✅ **合规** —— `livePreview.ts:514` 是 `StateField` + `EditorView.decorations.from(field, …)`；唯一的 ViewPlugin 是 `typewriterScroll`，不提供装饰。**此假设已排除** |
| 2 | 块级装饰**不应有垂直 margin**；高度动态变化时必须 `requestMeasure()` | `view/dist/index.d.ts:140-144`（本机 6.43.13 原文："block-level decorations should not have vertical margins"） | ❌ **5 个块 widget 全部违反**：`.md-media--block` 0.6em、`.md-hr` 1.35em、`.md-math.math-block` 0.45em、`.md-table` 0.55em、`.md-mermaid` 0.8em（`editor.css:346/363/373/384/389`），外加 `.table-widget { margin: 1.05em 0 }` |

### 9.7 一句话总结

> **在模型 C 里，「不跳」是使用方的责任，不是编辑器给的。**
> Typora 用「块级永不塌陷」换掉了大部分跳动、对行内位移公开认账；块编辑器用「渲染态持久」从结构上消灭了这个问题；Obsidian 证明了这条路会**反复回归**。
> Opennote 现在**两条都没做**：块级在源码态与渲染态之间来回换（§3），时序上装饰器又追不上解析器（§1）—— 所以它比这几个同类都更容易被感知到「位置在变」。

现在**没有任何测试能拦住「跳动」** —— 全部 32 条 livePreview 用例断言的都是「装饰器的形态」，而不是「几何是否稳定」。建议至少补两类：

2. **时序不变量**（纯 node 即可，成本极低）：只发 `Language.setState` 形状的 effect 事务后，装饰器必须已经追上语法树 —— 这正是 §1 那个缺陷的守门用例。

### 10.5 顺带发现（与本次主题无关，但值得单独开单）

1. **`scripts/cdp-eval.mjs --file` 有既有 bug**：`(await import("node:fs/promises")).readFile(...)` **没有 `await`**，页面收到的是字面量 `[object Promise]` → `SyntaxError`。本次**没有改这个共享脚本**，而是在探针目录里放了修好的 `cdp.mjs`（见 [`probe/README.md`](probe/README.md)）。
2. **`pnpm test` 有一个既有失败**：`src/lib/clip/webclip.e2e.test.ts:136` —— `bridge.start()` 之后 `getListeningPort()` 返回 0，`expect(port).toBeGreaterThan(0)` 失败（本机环境下桥接 HTTP 服务起不来）。**与本次改动无关**（`git status --porcelain -- src` 为空，`src/` 与 HEAD 逐字节一致），但会让「全绿」这个信号失真。其余 **1059 条用例全部通过**。
