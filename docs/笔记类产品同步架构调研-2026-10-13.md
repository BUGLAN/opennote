# 主流笔记产品的多端同步与服务端架构调研

> 全部结论来自一手来源（官方文档源码、官方设计文档/ADR、仓库源码）。GitHub 的 `raw.githubusercontent.com` 在本机不可达，正文中的 GitHub 引用均为等价可访问的官方路径（`github.com/.../blob/...`）。
> 每个产品按统一口径回答：数据真源 / 同步粒度 / 冲突策略 / E2EE / 服务端可自建 / 移动端后台策略。

## 1. Obsidian 生态

### 1.1 Obsidian Sync（官方，闭源）
- **数据真源**：本地 vault（每个设备一份）；remote vault 是集中副本，本地 vault 可直接连接它，不依赖网盘目录。
- **同步粒度**：**文件级**——"tracks changes at the file level and only transfers the files that have been modified"。服务端做**确定性文件哈希加密**以识别重复内容、避免重复上传/存储。
- **冲突**：Markdown 用 Google **diff-match-patch** 自动合并（1.9.7 起默认）；可改为生成冲突文件 `原名 (Conflicted copy 设备名 YYYYMMDDHHMM).md`，原文件保留远端版本；非 Markdown（含 canvas）= **last modified wins**；设置类 JSON 合并（本地键覆盖远端）。设置是**每设备**配置。
- **E2EE**：默认 E2EE，**scrypt** 派生 + **AES-256-GCM**；另有服务端持钥的 Standard 加密。服务端可见上传/删除者、时间与**加密路径 ↔ 加密内容的映射**（路由与版本历史需要）；确定性哈希带来确认攻击面。
- **版本历史**：Standard 1 个月 / Plus 12 个月，附件 2 周。**服务端不可自建**（DigitalOcean，SG/法兰克福/旧金山/悉尼）。
- **移动端**：应用内同步，天然规避移动文件系统/后台限制；离线改动排队，重连后同步；设置与插件需重启/强杀。

### 1.2 LiveSync（vrtmrz/obsidian-livesync，Self-hosted LiveSync 1.x）
- **真源**：本地 vault + 本地 PouchDB；远端为 CouchDB/Cloudant 或对象存储（S3/MinIO/R2）。
- **粒度**：文件 → **chunk**。Metadata（`children` 按序引用）＋内容寻址的 leaf chunk；`deleted:true` 是逻辑删除（可参与同步与冲突），`_deleted` 仅 CouchDB tombstone；命名空间 `i:`/`ix:`/`h:`(chunk)/`f:`(路径混淆)。控制文档 `syncinfo`、`_local/*sync_parameters`（协议版本 + PBKDF2 salt）、milestone、nodeinfo。
- **冲突**：CouchDB **revision tree**（PouchDB 选 winner，但 winner ≠ vault 当前显示版本）；每设备持久化 provenance `path -> {revision, observedStorageMtime?}`；自动合并 = 用双方都有的最近 `available` 共同祖先做**保守三方合并**；字节相同则折叠重复分支；祖先缺失/被压缩则**不猜**、保留独立分支让用户选；3+ 版本按 generation/mtime/revision id 两两审阅。"文件字节"才是内容身份，mtime/size/路径/哈希都不算。
- **E2EE**：支持；可叠加路径混淆（`f:` = SHA-256 派生），chunk id（`h:+`）可含加密材料；协议/加密配置不匹配时直接拒绝同步。
- **P2P**：WebRTC 直连；**Nostr 兼容 relay 仅做信令**（不传 vault 内容），TURN 可选（自建或 Cloudflare managed），传输本身由 WebRTC 加密；至少一台含数据的设备在线。`Announce/Follow changes` 只发"来拉"的通知。
- **服务端自建**：是（CouchDB/对象存储/自有 relay）。
- **移动端**：Obsidian 被系统挂起即停同步；"Keep replication active in the background" 明确**仅桌面**；移动靠 event-driven（save/open/startup）+ interval。移动 WebView 内存是硬约束，因此下载解密改成 Web Streams **按需流式**生成，避免 OOM。

### 1.3 obsidian-git / Remotely Save
- **obsidian-git**：真源 = **Git 仓库**；粒度 = 文件/commit；桌面用原生 git，移动（Android/iOS）只能用 **isomorphic-git**（无 SSH、无 rebase、性能受限）。冲突交给 Git：冲突标记 + 插件内 Keep ours/theirs/both → Mark resolved → 提交；"Other sync service (update HEAD only)" 模式下插件**不合并内容**。
- **Remotely Save**：真源 = 本地 vault，远端是"哑存储"（S3/WebDAV/Dropbox/OneDrive/…）。**0.4.1 起不再向远端写元数据**，改为本地保存上次成功同步状态，用 local/remote × unchanged/modified/deleted/created 决策表判断 push/pull/delete/conflict（明确吸收了 syncrclone/rsinc/rclone bisync 的思路，含 deletion 保护）。冲突：免费版 keep newer / keep larger；PRO「Smart Conflict」合并小 Markdown 或重命名保留两份。E2EE 用 **rclone crypt** 或 OpenSSL enc 格式。自动同步仅在 Obsidian 打开时有效，官方直言后台同步"技术上不可能"。
- **一手来源**：<https://github.com/obsidianmd/obsidian-help/blob/main/en/Obsidian%20Sync/Security%20and%20privacy.md>、<https://github.com/obsidianmd/obsidian-help/blob/main/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md>、<https://github.com/obsidianmd/obsidian-help/blob/main/en/Obsidian%20Sync/Local%20and%20remote%20vaults.md>、<https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/datastructure.md>、<https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/specs_conflict_resolution.md>、<https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/p2p.md>、<https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/settings.md>、<https://github.com/Vinzent03/obsidian-git/blob/master/docs/Conflict%20resolution.md>、<https://github.com/remotely-save/remotely-save/blob/master/docs/sync_algorithm/v3/design.md>、<https://github.com/remotely-save/remotely-save/blob/master/docs/minimal_intrusive_design.md>

## 2. Joplin
- **数据真源**：本地数据库（note/notebook/tag/resource 都是 `BaseItem`），sync target 只是复制目标。
- **目标模型**：文件系统 / WebDAV(Nextcloud 等) / Dropbox / OneDrive / S3 / **Joplin Server（可自建）** / Joplin Cloud；由 `FileApi` 抽象统一。
- **同步粒度**：**item**（序列化后的单个 note/notebook/tag/resource）。`sync_items` 表记录 `sync_time`、`sync_disabled`，并按 `sync_target` 作用域（同一 item 理论上可同步到多个目标）。`info.json` 保存目标级属性（version、e2ee、activeMasterKeyId、masterKeys、ppk），带 `updatedTime` 与启发式仲裁。
- **Joplin Server 增量**：`/api/files/delta?cursor=`，返回 create/update/delete 事件 + 新 cursor；事件会**压缩**（update+update→update；create+update→create；create+delete→NOOP；update+delete→delete），`limit` 只是建议值；cursor 失效 → `resyncRequired` 全量重来；旧 update 事件 180 天后压缩，create/delete 长期保留；`changes`/`changes_2` 双表迁移中。
- **冲突**：早期一律生成 **conflict 笔记**；现有 **auto-merge**：在"第二个同步的设备"上做行级三方合并（base 存 `sync_items.base_body/base_title`，`updated_time` 被推到远端时间之后以触发上传）。重叠/相邻行才真冲突；无 base、只读/锁定、解密失败、diff 超界（`maxEditLength` 5000、1000ms）则回退为冲突笔记。
- **E2EE**：**JED** 格式（`JED` + 版本 + 加密元数据 + 分块），仅同步序列化时加密；master key 由用户密码加密后随同步数据下发，另有 Data keys 与 PPK（共享笔记本走公钥交换密钥）。
- **移动端**：前台同步——改动几秒内上传，每几分钟轮询下载。
- **一手来源**：<https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/sync.md>、<https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/server_delta_sync.md>、<https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/conflict_auto_merge.md>、<https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/e2ee/index.md>、<https://github.com/laurent22/joplin/blob/dev/readme/dev/spec/server_items.md>

## 3. Logseq
- **两个世代要分开看**。**Markdown 世代**：真源是磁盘上的 `.md`，社区通行做法是用 `haydenull/logseq-plugin-git` 之类的插件 commit/pull/push 到远端 Git；本仓库无内置 git 同步，冲突由 Git 处理（与 obsidian-git 同源痛点：`logseq/` 元数据、journal、二进制附件都进同一仓库）。
- **DB 世代**：真源变成 **客户端 SQLite**（图不再是"一页一文件"）。ADR-0016 明确：DB 图不暴露可编辑的 per-page Markdown，Markdown 只能作为 **derived mirror**（`mirror/markdown/**`，单向、被 import/watcher 忽略）——这直接说明为什么"Git 当真源"在新架构下失效。
- **DB sync 协议**：`tx/batch` 传**有序 tx 条目列表**（每条带 `:tx` 与可选 `:outliner-op`），服务端按序应用并持久化到 `tx_log`/`pull/ok` 返回；客户端 `client_ops` + `sync_meta`(`local-tx`/`checksum`/`graph-uuid`) 存 SQLite；跨条目 tempid 复用被协议禁止。同步收敛以 **checksum** 校验（CLI 压测用 3 客户端 1 万 op + 离线窗口验证）。
- **冲突/一致性**：客户端 rebase（本地 pending tx 在临时连接上反演-应用-重放，成功才提交），服务端可 `tx/reject`，客户端回滚被拒 tx；服务端还有 consensus 与"缺失 block 修复"路径。
- **E2EE**：ADR-0003 定义**图级**开关 `Encrypt graph data`（默认开，创建后不可变，键存 `:logseq.kv/graph-rtc-e2ee?`）；关掉则同步载荷与附件走 TLS 明文。
- **服务端自建**：ADR-0001 提案增设 **Node.js adapter** 以脱离 Cloudflare（历史实现依赖 Cloudflare + D1/R2），配 PAT 鉴权；目前以官方托管为主。
- **移动端**：由前端 DB worker 驱动同步（websocket 长连 + 重连/重试），ADR 未承诺后台常驻同步。
- **一手来源**：<https://github.com/logseq/logseq/blob/master/docs/adr/0004-sync-tx-entry-outliner-op.md>、<https://github.com/logseq/logseq/blob/master/docs/adr/0015-client-ops-and-sync-meta-in-client-sqlite.md>、<https://github.com/logseq/logseq/blob/master/docs/adr/0003-optional-sync-graph-encryption.md>、<https://github.com/logseq/logseq/blob/master/docs/adr/0001-nodejs-db-sync-server-adapter.md>、<https://github.com/logseq/logseq/blob/master/docs/adr/0016-markdown-mirror.md>、<https://github.com/logseq/logseq/blob/master/docs/sync/failed-cases.md>、<https://github.com/haydenull/logseq-plugin-git>

## 4. 思源笔记 SiYuan（与 opennote 最接近的本地优先范式）
- **数据真源**：workspace 里的 `.sy` 文档 + assets；但**同步与快照都不直接同步文件**，而是先做一次"数据仓库（data repo）"提交，再同步 repo 对象。repo 由 `siyuan-note/dejavu` 实现，设计借鉴 ArtiVC/restic。
- **repo 结构**：`indexes/`、`objects/`、`refs/`（`latest` + `tags/*`），实体**全部 SHA-1 寻址**：`Index`(memo/created/files/count/size)、`File`(path/size/updated/chunks)、`Chunk`、`Ref`、`Repo`（`DataPath` 与 `Path` 分离，repo 不放在数据目录内）。
- **同步粒度**：**文件 → chunk，内容寻址去重**。每次索引生成新 `Index`；上传/下载以 **tag index** 为单位（`UploadTagIndex`/`DownloadTagIndex` 返回 file/chunk/bytes 统计），**只传缺失 chunk** → 天然增量 + 天然去重。
- **冲突**：既有同步侧冲突文档开关（`SetSyncGenerateConflictDoc`），也有快照语义：**回滚快照前自动暂停同步**，避免"刚恢复的数据又被覆盖"，并为回滚前的当前数据自动建一个快照。索引可增量重建（`incReindex`/`upsertIndexes`/`removeIndexes`）。
- **加密**：仓库支持"通过密码生成密钥"（AES）与**加密笔记本**——加密笔记本的快照数据是密文，回滚前需先解密/挂载。
- **服务端**：官方云 + **S3 + WebDAV**（`conf.Provider*`）三类远端，S3/WebDAV 完全可自建；另有**局域网同步**（`lan_sync.go`：mDNS 式 discovery、peer 列表、把 LAN 当作 chunk 来源），以及"同步感知"（`completeSyncPerception`）在云端发布新版本后通知其他设备来拉。
- **移动端**：Go kernel 常驻进程，按 interval 自动同步 + perception 通知触发；不是逐键实时。
- **一手来源**：<https://github.com/siyuan-note/dejavu>、<https://github.com/siyuan-note/siyuan/blob/master/kernel/model/repository.go>、<https://github.com/siyuan-note/siyuan/blob/master/kernel/model/sync.go>、<https://github.com/siyuan-note/siyuan/blob/master/kernel/model/lan_sync.go>、<https://github.com/siyuan-note/siyuan/blob/master/kernel/model/sync_path.go>

## 5. AppFlowy / AnyType / Notesnook / Standard Notes
- **AppFlowy**：真源 = 本地（**yrs/Yjs CRDT**）；`AppFlowy-Collab` 的 `collab` crate 是"collab 数据层"，`Collab` 把每次领域操作记为一次 **yrs transaction**，再由 plugin 持久化（`RocksdbDiskPlugin`）并可选同步远端（`SupabaseDBPlugin`、自定义 websocket 后端）——粒度 = CRDT update/transaction，多端最终一致，天然无文本冲突。**服务端**：`AppFlowy-Cloud` 已归档，自托管改走 **AppFlowy-SelfHost-Commercial**（闭源商业镜像 + docker compose，Free tier 1 seat）——即 open-core、服务端不再完全开源。移动端随 Flutter 客户端在线即同步。
- **AnyType**：真源 = 本地对象库；协议 **any-sync** 只把数据存成**加密 DAG**，用 **CRDT**（"每个设备独立应用并密码学校验 CRDT 更新"，无共识协议）保证最终一致，E2EE 内置、provider 可切换。**自建**：`any-sync-dockercompose` 提供一整套网络（coordinator + 3×sync-node + filenode + **consensusnode（冲突裁决）** + MongoDB/Garage），把 `client.yml` 导入客户端即可。官方文档站点提供 Self-host / Local-only 两条独立路径（GitBook 正文无法无头抓取，仅验证页面存在）。
- **Notesnook**：本地优先 + 自研 sync server；**全部内容（正文/标题/笔记本/标签/附件）在设备上用口令派生密钥加密后才上传**，服务端只见密文 blob。粒度 = item 级增量（`collector` 只取 `unsynced` 项，加密后分批推送；`merger` 处理下行）。**冲突**：两设备编辑间隔 **< 60s 或内容相同 → 取较新者，静默合并；> 60s → 标记 conflicted 交用户二选一**（官方明确"从不合并两版文本"）。移动端有实验性 `backgroundSync`：由 OS 决定，**最多每 15 分钟**唤醒一次做全量同步，且重启后恢复。
- **Standard Notes**：真源 = 本地加密库，服务端是"dumb data-store"。协议 004：口令经 **Argon2id** 派生 rootKey，前半 masterKey 永不出本地、后半作 serverPassword；masterKey 加密随机 **itemsKey**，itemsKey 再加密每条 item 的 `item_key`；算法 **XChaCha20+Poly1305**（192-bit nonce），加解密都在客户端。粒度 = item（可只重加密 itemsKey 完成换协议/改密码，避免全量重加密）。**自建**：官方 Docker 栈（server + MySQL + localstack SQS/SNS 等，见 `docker-compose.example.yml`），新版还提供桌面端内置 Home Server。
- **一手来源**：<https://github.com/AppFlowy-IO/AppFlowy-Collab>、<https://github.com/AppFlowy-IO/AppFlowy/blob/main/frontend/rust-lib/Cargo.toml>、<https://github.com/AppFlowy-IO/AppFlowy-Cloud>、<https://github.com/anyproto/any-sync>、<https://github.com/anyproto/any-sync-dockercompose>、<https://doc.anytype.io/anytype/data/sync-and-backup/self-host>、<https://github.com/streetwriters/notesnook/blob/main/docs/help/contents/sync/how-sync-works.md>、<https://standardnotes.com/help/security/encryption>、<https://standardnotes.com/help/47/can-i-self-host-standard-notes>、<https://github.com/standardnotes/server/blob/main/docker-compose.example.yml>

## 6. 范式归纳

| 范式 | 代表 | 同步粒度 | 冲突策略 | 实时性 | 实现成本 | 适用规模 |
|---|---|---|---|---|---|---|
| **a. 文件级 + 外部工具/网盘** | 网盘、obsidian-git、Remotely Save | 文件/commit | Git 标记 / keep newer-larger / 重命名保留 | 无（前台触发） | **最低**（复用现成 plumber） | 个人、单写者、低频切换设备 |
| **b. 自研增量协议 + 服务端 blob 存储** | Joplin、Obsidian Sync | item / whole file | 服务端 delta + 客户端三方合并或冲突副本 | 秒级（上传即时 + 轮询/长连） | 中高（要协议、版本、迁移） | 中小团队、要移动端一致性 |
| **c. CRDT/操作日志 + 服务端中继** | AppFlowy、AnyType、Logseq DB、Notesnook(半) | CRDT update / tx / item | 结构上无冲突，或语义裁决 + checksum 校验 | **真实时** | 最高（CRDT 模型、rebase、压缩/GC、快照） | 协作、并发写、多端同开 |
| **d. 内容寻址仓库（Git-like）+ 快照** | **SiYuan/dejavu**、LiveSync(rev tree) | 文件→chunk（去重） | 快照/分支比较，或 revision tree 三方合并 | 准实时（interval + perception） | 中（chunk store + index + ref），无 CRDT 复杂度 | 本地优先、要大附件去重与版本回溯 |

**给 opennote 的直接启示**：opennote 的"文件即真源 + 无服务器 + `.opennote/` 旁路目录"最贴近**范式 a 与 d 的交集**。若坚持不做服务端，可借鉴 Remotely Save 的"本地同步历史 + 三方决策表"（零远端元数据、对哑存储友好）；若要做真正的增量与历史，SiYuan/dejavu 的 `Index/File/Chunk/Ref` 四元组是成本最低的成熟模型——**chunk 内容寻址**同时解决增量上传、去重与快照回滚，且不需要引入 CRDT 的收敛复杂度。LiveSync 关于"**文件字节才是内容身份，mtime/size 不算**"以及"**provenance: path → revision**"的结论，正是 opennote 当前 `FileRecord{stat,content}` 模型可以对齐的下一步。
