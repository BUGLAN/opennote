## 0. 一句话结论与收窄后的方案骨架

**现状不是「重命名坏了」，而是「正文标题 → 磁盘文件名」这条通道从未存在**：全仓 14 个 `target.move(` 调用点里没有一处的输入是正文标题（`docs/title-source-of-truth.md` §5；**【实测】** A1a/A1b/A1c 全程 `moves() === []`，`.tmp-title/test-output.txt:7,14,17`）。

**收窄后的方案骨架**（用户裁定，不可再放宽）：

```
磁盘文件名 = ①「用户显式重命名」定下的名字（pin，永久）
           ?? ② 正文标题自动命名 —— 仅当磁盘文件名是「占位名」时启用
           ?? ③ 保持现状（其余 476 篇笔记一律不动）

显示名    = ① 有 pin 时 = pin 的值（现状不动）
           ?? ② 无 pin 时 = deriveTitle(正文, 文件名 stem)（现状不动）

落盘动作  = 一次 target.move（同名冲突让位；只差大小写走 moveCaseOnly）
           —— 与 renameNote 同一条顺序，但【不写 titleOverride / 不写 titlePinnedAt】
```

**一句话边界**：`文件名 ∈ {无标题, 无标题 N, 未命名, 未命名 N, untitled, untitled N}` **且** 正文里有真标题 → 才改名；**其他笔记的正文标题怎么改都不动文件名**。

## 1. 收窄后的范围界定（含「为什么下列风险不再触发」）

### 1.1 触发范围（唯一入口条件）

```ts
const PLACEHOLDER_NAME = /^(无标题|未命名|untitled)(\s\d+)?$/i;

function isPlaceholderNote(note: Note): boolean {
  return PLACEHOLDER_NAME.test(stripExtension(baseName(note.id)));
}
```

**【读码】** `stripExtension` / `baseName` 见 `src/fs/paths.ts`；占位名的三个产地：
- 新建笔记 `src/data/library.ts:988-989`：`options.title ?? "无标题"` → `sanitizeName(title, "无标题")`；
- 导入落点 `src/lib/import.ts:82`：fallback 是 `未命名`；
- 剪藏落点 `src/lib/clip/landing.ts:27`：fallback 也是 `未命名`。
（t2 §5 已指出「fallback 不是唯一产地」，收窄方案必须**三个都认**，否则会漏掉导入/剪藏产生的占位文件。）

## 2. 推荐语义（核心）

### 2.1 优先级次序与生命周期

| 档 | 名字 | 何时写入 | 生命周期 | 与正文标题的关系 |
|---|---|---|---|---|
| ① 显式命名 | `titleOverrides[path] = sanitizeName(用户输入)` + `titlePinnedAt[path] = Date.now()` | 用户右键「重命名」→ `renameNote`（`src/data/library.ts:1147-1180`） | **永久**（`state.json` 持久化，键随笔记走） | 正文标题再怎么变都不动 |
| ② 正文标题自动命名 | 只改**磁盘文件名**；**不写** `titleOverrides`、**不写** `titlePinnedAt` | 停笔 5 秒 + §2.3 全部条件通过 | 跟随：下一次标题变化会再改名 | 正文标题是唯一依据 |
| ③ 兜底 | 不动 | —— | —— | 无真标题时**什么都不做** |

**三条不变量（当判据写进测试）**：

1. **`titleOverride` 只由用户显式重命名写入**（`src/data/library.ts:1169-1173` 保持为唯一写入点之一；自动改名走另一条不碰它的路）。
2. **有 `titleOverride` 的笔记，自动命名对该笔记永久停用**。**【实测】** A7b：不判就会顶掉用户手改的名字（`.tmp-title/test-output.txt:64-69`）。本机受影响 **1 篇**（`项目实战/system_panel/系统设计ABC.md`，队长实测）。
3. **自动改名不触碰正文**。**【实测】** A3a：`renameNote` 前后正文逐字节相同（`.tmp-title/test-output.txt:25-28`）——「正文里的一级标题不会被改写」这条承诺**继续成立**。

**为什么自动改名不写 `titleOverride`**（t2 §7 阻断级发现的处置）：`renameNote` 会写 `titleOverride = clean`（`src/data/library.ts:1169-1173`），而 `refresh()` 是 `titleOverride ?? deriveTitle(...)`（`:223`）。若复用 `renameNote`，**第一次自动改名就把该笔记的「正文标题 → 文件名」通道永久锁死**，用户第二次改标题时文件名不再跟随——现象与本次修复前完全一样。**【实测】** A7b 已确认这条链路（`.tmp-title/test-output.txt:64-69`）。

### 2.3 ⭐ 收窄后的标题判定规则（队长要求的「明确、可测」）

**规则（唯一一条，不做分档）**：

```
derivePlaceholderTitle(md): string | null

1. { body } = splitFrontMatter(md)                        // src/lib/utils.ts:54-58
2. 逐行扫 body，维护围栏状态（照抄 deriveTitle 的 :63-73）：
   3. 跳过围栏行、围栏内所有行、空行、引用/表格/分隔线行（/^(>|\||-{3,}|\*{3,}|_{3,})/）
   4. 遇到 /^(#{1,6})\s+(.*)$/  →  text = cleanInline($2)
         · text 非空 → return text.slice(0, 90)          // ★ 唯一命中路径
         · text 为空（`#` 后无内容 / `# ** **`）→ continue
   5. 遇到任何其他非空行 → 【不返回】continue             // ★ 与 deriveTitle 的关键差别
6. 扫完 → return null                                     // 没有真标题行 = 不改名
```

**四条设计决定与理由**：

| 决定 | 理由 | 依据 |
|---|---|---|
| **认 H1–H6 全部**（不只是 H1） | 用户 5 篇占位笔记里 H1 为 **0** 篇（3 篇 h2 + 1 篇普通行 + 1 篇空文件）→ 只认 H1 等于**功能没做** | **【实测】** `.tmp-title/scan-output.txt:16-17,124-139`（t3 E9） |
| **绝不把「正文首行」当标题** | 49 篇的「标题」其实只是首个非空行；极端案例 `E:\repo\notes\无标题.md` 全文只有一行图片，`cleanInline` 把图片语法洗成 alt 文本，会产出 `3f1c9589f284944860bef0e22aecc5b0_720.png.md` 这种垃圾文件名 | **【实测】** `.tmp-title/scan-output.txt:34-64`（t3 §4.3） |
| **复用 `cleanInline` 与 `splitFrontMatter`** | 否则 `# **重点**` 会带 `**` 进文件名；front matter 里的 `title:` 会被误当标题 | `src/lib/utils.ts:89-101`、`:54-58` |
| **扫描范围从「正文开头」而非「正文全部」** | 与 `deriveTitle` 的既有语义保持一致（都取第一个可用标题行）；「全文找第一个标题」会跨过正文首段，语义漂移 | `src/lib/utils.ts:64-84` |

**为什么可以放宽到 H1–H6 而不危险**：入口条件（条件 0）已经把候选集压到**只有占位名的笔记**。在收窄后的候选集里，「认到哪一级」只影响**命中率**，不再影响**爆炸半径**——这正是队长裁定的直接推论。

**为什么不再提供「首个非空行」兜底**：唯一能被它救的是 `E:\repo\notes\无标题.md`（全文一行图片），而它会产出垃圾名；剩下 1 篇是空文件，任何规则都无解。**代价 1 篇、收益 0 风险** → 不做。

### 2.4 防抖窗口与「打字过程中不耍文件系统」

**窗口 = 5000ms，策略 = 取消 + 重排**（不是固定 5 秒，不是排队）。

- 挂点：`updateNoteContent()`（`src/data/library.ts:1037-1053`）**`:1051` 的 `persistNoteSoon(id)` 与 `:1052` 的 `maybeSnapshot` 之间**（即队长指定的 `:1048-1051` 区间；`refresh()` 已在 `:1044` 拿到新标题）。
- `scheduleAutoRename(id)`：**每次内容变化都 `clearTimeout` 重排**——连续打字永远不会触发改名。
- 定时器回调里**重新读取**最新状态（`libraryStore.get().notes[id]`），**不要**闭包捕获 `note` 对象。
- **改名途中又敲字**：复用 `renameNote` 的既有顺序——`remapIds` 会把改名期间敲进来的正文、`dirty`、`writeTimers` 一起搬到新 id（`src/data/library.ts:1860-1882`），已有 D01 回归测试（`src/data/library.regression.test.ts:294-312`）。**必须补一条新判据**「自动改名在途时继续打字」。
- **`options.immediate`（快照恢复，`src/data/library.ts:2483`）**：只排一次定时器，**不立即执行**。**【待验证】** t1 §9.2 V5 未实测「恢复快照要不要顺手改名」。

**「光标还在标题行」的判据 —— 队长明确要求加 `cursorRef`**：

- 现状：`cursor` 是 React state（`src/App.tsx:119` `const [cursor, setCursor] = useState<CursorInfo>(...)`；`:1303` `onCursor={setCursor}`），数据层拿不到；任何 5 秒定时器回调里读 `cursor.line` 都是**过期闭包值**（t2 §3.1）。
- 方案（推荐，两层一起做）：
  1. **`src/App.tsx:119` 旁新增 `const cursorRef = useRef(cursor)`**，在 `:1303` 的 `onCursor` 里同时 `cursorRef.current = value` 与 `setCursor(value)`；**用 `cursorRef.current.line` 判定**「光标是否还在第一个真标题行上」。
  2. 数据层不直接读 React 值，而是通过新增的 `setEditorCursorLine(id, line)` 把行号下推（与 `updateNoteContent` 同一层，便于单测注入）。
- 判定语义：**若光标所在行 == 第一个真标题行的行号 → 跳过本次改名**（用户可能还在改这一行）。光标离开该行后，下一次内容变化会重新排定时器。

> 理由：定时器读的是数据层的 `editorCursorLine`（`autoRenameContext()` 每次现取），比读 React ref
> 更可靠；`cursorRef` 只写不读 ⇒ 死代码。复核 R3 也认定「`cursorRef` 被定时器读取」这条判据
> **本身写错了**，并裁定「要么删掉、要么注释说明为何保留」。实现选择删掉，并在
> `src/App.tsx` 的 `onCursor` 旁留了注释说明「行号经 `setEditorCursorLine` 下推，因此不需要 ref」。

### 2.6 改名动作的精确形状（`autoRenameFromPlaceholder`）

```
autoRenameFromPlaceholder(id)          // 新增，紧邻 renameNote（src/data/library.ts:1147 之前）
  1. note = notes[id]；不存在 / 在 trash / 有 override / 非占位名 → return
  2. name = sanitizeName(derivePlaceholderTitle(note.content), "无标题")   // §2.3
  3. requested = joinPath(parentPath(id), `${name}${extName(id) || ".md"}`)
  4. requested === id → return（同名空操作）
  5. caseOnly = requested.toLowerCase() === id.toLowerCase()
  6. await flushNote(id)                       // 复用 renameNote 第一步（:1161）
  7. nextPath = caseOnly ? requested
                : await resolveAvailablePath(target, requested, taken, id)   // :822-838
  8. caseOnly ? await moveCaseOnly(...) : await target.move(id, nextPath)    // :1056-1066 / :1164
  9. remapIds(id, nextPath)                    // :1840-1903，dirty/writeTimers/tabs/override 全跟着走
 10. await moveHistory(target, id, nextPath)   // :1077-1095

                 titleOverride: null, updatedAt: Date.now())               // ★ 不写 override

**与 `renameNote` 的唯一差别就是第 11 步**（不写 `titleOverride`、不调 `setTitleOverride`、不 `flushMeta`）。`state.json` 的写入交给既有的 700ms `scheduleMeta`（`src/data/library.ts:920-923`）——自动改名**没有**「必须立刻落盘」的理由（不像用户显式改名会被下一次重扫读回）。

## 6. 迁移方案

### 6.1 规模收敛：真正该修的只有 3 篇（其中 1 篇要等附件迁移），另有 2 篇永远无解

| 方案 | 会动多少篇 | 判定 |
|---|---|---|
| 全库「文件名跟随正文标题」 | **364 篇（75.7%）**，撞名 5 组、17 篇被洗名 | ❌ 用户已否决 |
| 「有 H1 就跟随」 | **104 篇**（含 `index.md`/`README.md`/`docker.md`） | ❌ 用户已否决 |
| **「只救占位名」+ 首个真标题行（H1–H6）** | **5 篇占位里能算出新名的 3 篇；立即能改 2 篇，等附件迁移后 +1 篇** | ✅ **采纳**（§3 逐篇表） |
| 空文件 + 只有一行图片的 2 篇 | 0 | 无解，不给建议，如实告知 |

**【实测】依据**：`.tmp-title/scan-output.txt:12-19`（5 篇占位、4 篇有真标题、H1 命中 0）、`:124-139`（5 篇明细）、`:31`（目标名被占 = 0）。

### 6.2 建议的迁移形态：只读体检 + 逐条确认 + 复用既有入口

1. **不做启动时批量脚本**。新增一个只读「命名体检」结果（状态栏或命令面板给一条可点提示）：
   - 只报「`isPlaceholderName(文件名)` **且** `derivePlaceholderTitle(正文) !== null`」的笔记 —— 本机 **3 条**（§3 的第 3/4/5 篇）；
   - 每条给出「现文件名 / 建议名（`sanitizeName(标题)`）/ 冲突提示（**本机 0 冲突**）/ 旧布局附件引用警告（第 3 篇有）」；
   - 空文件与「只有图片行」的 2 篇**不给建议**。
2. 用户逐条点「改名」→ 复用 `renameNote(id, 建议名)`，**不要另写批量 move**（它会走 `flushNote → resolveAvailablePath → move/moveCaseOnly → remapIds → moveHistory → setTitleOverride → flushMeta` 全套，`src/data/library.ts:1160-1176`）。
3. **改名前列一遍「该笔记正文里有没有 `<旧文件名 stem>.assets/` 或 `](旧名.md)` 这类按旧名写死的引用」**；有就**跳过并如实告知**。本机第 3 篇命中（5 处 `./无标题.assets/…`）→ **必须先跑附件迁移**。
4. 迁移必须**在应用内、逐条、可撤销**（回收站与 `.opennote/history/` 都在），不要写跑在启动时的批量脚本。

> ❌ **本节的应用内入口：未做（队长裁定，2026-10-09 repair round 2）**
>
> 复核 R8 指出「附件迁移先于自动改名」这条硬顺序只在文档/注释里表达，应用内没有入口。
> **队长的裁定是：不需要代码机制，也不做应用内提示。** 理由（已确认，逐条）：
>
> 1. **顺序由流程保证，不靠代码**：附件迁移是一次性 CLI（`scripts/migrate-assets.mjs`），
>    由用户显式运行；执行顺序被排成 t13（迁移）在 t12（复验）之后，且要求**先关掉 Opennote**
>    再跑。这不是一个会在运行期反复发生的竞态，而是一次性的人工步骤。
> 2. **数据安全底线已经有代码机制**：条件 12 会拦住「正文里有旧布局附件引用」的笔记 ——
>    它们**不会被改名**，所以**不会裂图**。也就是说：即使顺序被搞错，代价是「这篇没被改名」，
>    而不是「图丢了」。真正需要代码兜的那一半已经兜住了。
> 3. **可点提示的收益与成本不成比例**：本机命中的只有 1 篇（§3 第 3 篇）。为 1 篇一次性操作
>    造一条常驻广播 API + 一条常驻 toast + 去重逻辑 + 用例，而迁移器自己的 dry-run 报告
>    已经把「哪些笔记有旧布局引用」逐条打出来了（`node scripts/migrate-assets.mjs --workspace <路径> --dry-run`）。
>
> **残留的 UX 缺口（如实记录）**：用户看不到「为什么这一篇没被改名」。若将来要补，最便宜的形态是
> 在 `autoRenameFromPlaceholder()` 的 skip 分支上挂一条 `notify`（数据层已有现成读数
> `AutoRenameOutcome.reason === "正文里有按旧文件名写死的附件引用"`），大约 15 行；**本轮不做**。

     └ 此时条件 12 已天然满足（不再有旧布局引用），第 3 篇也能自动修好
③ 只读体检 → 用户逐条确认（针对「②上线前就已存在」的 2~3 篇，做一次性收尾）
④ 顺手修 #23（saveImage 内容复用）/ #24（改名搬附件目录）/ #25（import-index 路径）
```

**为什么 ① 必须在 ② 之前**：自动改名会改文件名，而旧布局的目录名与文件名绑定；**【实测】** 探针 D2 已证明「改名 → 目录不改名 → 裂图」，本机第 3 篇就是活样本。**这条不能靠提示语兜**。
