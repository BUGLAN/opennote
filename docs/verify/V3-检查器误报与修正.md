# V3 · 检查器误报与修正（含验证者自身的错误与更正）

> **为什么单列这一节**：一个「全绿」的检查器可能是**被校准过的**，也可能只是**碰巧全绿**。本节把每一处误报的原因、修正方式、以及**我自己犯的错**全部摊开 —— 这比隐藏它们更能说明结论可信。
>
> 本节共 4 条**检查器误报** + 2 条**验证者自身的错误**。凡是「产品代码没错、是我的判据错了」的，我一律**改我自己的检查器**，绝不去改产品代码来迁就检查器。

---

## 一、检查器误报（5 条）

### 误报 1 · `BR-4` 把测试夹具的 `listen(0)` 当成产品违规

| 项 | 内容 |
|---|---|
| **原始判据** | 「产品代码不得使用端口 0」→ 全仓 grep `listen(0)` |
| **误报现象** | `extension/tests/bridge.test.mjs:60` 的 `server.listen(0, "127.0.0.1", resolve)` 被判违规 |
| **误报原因** | 那是**测试夹具**主动用「端口 0 = 让内核分配空闲端口」的常规写法，**不在产品代码里**。契约约束的是产品行为，不是测试脚手架 |
| **修正方式** | 新增 `isTestPath()`（匹配 `tests?/`、`__tests__/`、`*.test.*`、`*.spec.*`、`*.bench.*`），`BR-4` 只扫 `productFiles`；被排除的命中另记 `info("BR-4b", …)` |
| **修正后** | `PASS [BR-4] 产品代码不使用端口 0（契约禁止） — 0 处（产品代码 16 个文件）` + `SKIP [BR-4b] 测试夹具里出现 listen(0)（不算违规）` |

### 误报 2 · `IN-3` 把「读 `note.trashed`」当成「写回收站」

| 项 | 内容 |
|---|---|
| **原始判据** | 「`discarded` 不进回收站」→ 在收件箱相关文件里 grep `trash` |
| **误报现象** | `src/components/InboxPanel.tsx:118`、`:123` 命中 |
| **误报原因** | 那两行是 `findPreviousCapture(notes, url)` **只读地**看 `note.trashed`（判断某条笔记是否已被回收，用来不给用户提供死链），**没有任何写入动作**。判据把「出现 trash 一词」等同于「写回收站」 |
| **修正方式** | 改为只匹配**写入形态**：`TRASH_WRITE_RE = /trashNote\s*\(|trashDir\s*\(|moveToTrash\s*\(|toTrash\s*\(|["'`]\.opennote\/trash|TRASH_DIR\b|trashPath\s*\(/`；只读命中另记 `info("IN-3b", …)` |
| **修正后** | `PASS [IN-3] discarded 不进回收站（收件箱代码无 trash 写入调用） — 0 处写入调用` + `SKIP [IN-3b] 收件箱代码里 trash 的出现（读/写/文案） — 2 处` |

### 误报 3 · `U-8` 把代码注释里的排版符号当成用户可见 emoji

| 项 | 内容 |
|---|---|
| **原始判据** | 「产品代码无 emoji」→ 对产品文件逐行扫 emoji 码点 |
| **误报现象** | `src/lib/clip/envelope.ts:247` 命中 `⚠️` |
| **误报原因** | 该字符在**代码注释**里（内容是给开发者的文档标记，正是在记录 `D-07` 这个缺陷），**不会出现在界面上**。契约的「无 emoji」是 `03` 号 UI 规范对**用户可见文案**的要求 |
| **修正方式** | `U-8` 改为**先 `stripComments()` 再扫**；注释里确实存在的 emoji 记 `info("U-8c", …)`（**不隐藏事实**） |
| **修正后** | `PASS [U-8] … 0 处（剥注释后扫描 91 个源码文件）` + `SKIP [U-8c] …` |
| **边界与旁证** | Lead 已批准此收窄，并指出边界是「**渲染产物 / dist 产物 / 用户可见文案**零 emoji」；`extension/verify.mjs` 独立确认 **dist 里零 emoji**（且它也是剥注释后扫的）—— 两条线互相印证 |

### 误报 4 · `U-8` 把 `src/` 下的**开发者文档**当成界面文案

| 项 | 内容 |
|---|---|
| **误报现象** | `FAIL [U-8] … src/lib/clip/RECIPE-手工信封验证.md:131 ⚠️ 这条路是**实现者自证**，不是独立验证 …` |
| **误报原因** | C1 按 Lead 要求新增了一份 167 行「手工信封验证配方」（`src/lib/clip/` 下的 **Markdown 文档**）。我的 `productFiles` 是按目录（`src/**`）而不是按**文件类型**定义的，于是 `.md` 也被当成「产品代码」扫了 emoji；而 `stripComments()` 对 Markdown 无效（Markdown 没有注释语法），所以第 131 行的 `⚠️`**没能被剥掉** |
| **关键判断** | 这份文件**不被任何模块 `import`、不进构建产物**（我 grep 了 `src`/`electron`/`extension` 全部代码：**0 处引用**）。它里面的 `⚠️` 是给开发者的警示标记，**不在应用界面、不在扩展 dist 里** —— 与「代码注释里的 `⚠️`」（误报 3）是**同一类** |
| **修正方式（Lead 裁定，逐条落实）** | `U-8` 的扫描范围改为对准「**会不会出现在界面上**」：<br>· **严格扫**：`.ts/.tsx/.js/.cjs/.mjs/.html/.css`（剥注释后）+ **`extension/dist/**`**（**产物**是严格面，装进浏览器的东西必须零 emoji → 新增 `U-8e`）<br>· **不扫**：`*.md` / `*.txt`、`tests/`、自测脚本<br>· **被排除的命中记 `U-8c` INFO**，`[文档]`/`[注释]` 明确标注来源，**仍然打印出来**（不隐藏） |
| **修正后** | `PASS [U-8] 界面文案无 emoji（扫产品源码的 .ts/.tsx/.js/.html/.css，剥注释；不含 tests/ 与 *.md） — 0 处（剥注释后扫描 91 个源码文件）`<br>`PASS [U-8e] 扩展产物 extension/dist/** 零 emoji（产物是严格面，不是文档） — 0 处（扫描 16 个产物文件）`<br>`SKIP [U-8c] 开发文档（*.md）与代码注释里的 emoji（非用户可见，不计失败） — 3 处：[文档] src/lib/clip/RECIPE-手工信封验证.md:131 ⚠️ … \| [注释] src/lib/clip/envelope.ts:250 ⚠️ …` |
| **为什么这是「能一直绿下去的护栏」** | 加上 `U-8e` 后，这条检查**同时**保住了两头：界面文案与 dist 产物**严格零 emoji**，而**每新增一篇开发文档不会把检查器自己绊倒**。这是本节的第 5 次「范围修正」，也是 4 次修正里唯一一次由 Lead 直接裁定范围的 |

### 误报 5 · `U-6b` 把**非导入**的撤销 toast 纳入「导入撤销窗口」范围

| 项 | 内容 |
|---|---|
| **原始判据** | 「带 `action` 的 `notify()` 必须显式传 `duration`」→ 扫**全部** `.ts/.tsx` 产品文件 |
| **误报现象** | `src/App.tsx:501`（新建笔记的撤销）、`src/components/Sidebar.tsx:588`（移入回收站的撤销）被判违规 |
| **误报原因** | 契约 §6.13④ 的 **10000 ms 只约束「导入撤销」窗口**（`src/lib/clip/receive.ts` 的 `announce()`，那里确实显式传了 `UNDO_WINDOW_MS`，我的 E2E `S4.9` 也动态捕获到 `setTimeout(…, 10000)`）。上述两处是**应用自身的**撤销 toast，且**逐字来自基线 `5a98f59`、本次一行未动** |
| **修正方式** | 范围收窄为显式清单：`src/lib/clip/**`、`src/data/inbox.ts`、`src/data/importLog.ts`、`src/components/{InboxPanel,ConflictDialog,ImportApiPanel}.tsx`，外加 `src/App.tsx` 里**含「导入 / 入库 / 已在笔记中」**的 notify；范围外的命中记 `info("U-6c", …)` |
| **修正后** | `PASS [U-6b] 导入/收件箱范围内带 action 的 notify 显式传 duration…` + `SKIP [U-6c] 范围外带 action 的 notify 未显式传 duration（基线已有、非导入范围，不计失败） — src/App.tsx:501 \| src/components/Sidebar.tsx:588` |

**这 5 条的共性**：**判据的「范围」划错了** —— 把测试夹具当产品（1）、把读当写（2）、把注释当界面（3）、把开发者文档当界面文案（4）、把全局当导入（5）。**没有一条是放宽判据本身**，全部只是把范围对准契约真正约束的对象，并且把被排除的命中**记成 INFO/SKIP 保留在输出里**（可审计，不是静默丢弃）。

## 二、验证者自身的错误与更正（2 条）

> 一个验证者的价值不在「从不出错」，而在**出错时自己抓出来并撤回**。以下两条我都主动向 Lead 更正过。

### 自错 1 · 我发过一个**假的 P0**（`portRange` 形状「三处互相打架」）

| 项 | 内容 |
|---|---|
| **我做了什么** | 我先后读了 `electron/bridge.cjs`、`src/desktop/bridge.ts`、`src/components/ImportApiPanel.tsx` 三处对 `portRange` 的形状，发现元组/对象不一致，且 `pnpm typecheck` 当时**确实红了**（4 条 `TS2339`），于是我向 Lead 发了一条**紧急 P0** |
| **错在哪** | ① 我看到 `TS6133` 从「有」到「无」，**已经说明作者正在写这个文件**，此刻任何结论都是**中间态**；正确动作是**等 30 秒重跑**，而不是升级成 P0。② 我用的是「隔几分钟读两次代码」，而不是「同一次命令的完整输出」 |
| **实际结果** | 几分钟后三处形状自然一致，`pnpm typecheck` → **exit 0**。Lead 实证后指出：那是我两次读取之间的**编辑中间态**，不是两个并存矛盾的真值 |
| **更正方式** | 接受 Lead 的方法论并要求自己：**①** 每条结论绑定「一条命令 + 完整输出 + 退出码」；**②** 读到可疑内容**紧接着再跑一次**确认它还在，**只在两次跑命令都红时才定级 P0**；**③** 报「互相打架」前先确认是不是同一文件在同一分钟内被改 |
| **代价说明** | Lead 明确指出：**一个假的 P0 会把作者从正确的工作上拉下来**。这条教训写在这里，是为了让后来者知道这个检查器是**被校准过的** |

### 自错 2 · 我报过一个**我没实际观察到的退出码**

| 项 | 内容 |
|---|---|
| **我做了什么** | 我在一条消息里写「`verify-contract` → **PASS 64 / FAIL 0 / SKIP 1 / INFO 8，exit 0**」 |
| **错在哪** | 那个「FAIL 0 / exit 0」是我从**散文修正之前的中间态输出**推断的，**我没有复跑就报了数字**。这比自错 1 更严重：我报的是一个**从未存在过的退出码** |
| **实际结果** | 复跑后真相是 `PASS 64 / FAIL 1 / SKIP 1 / INFO 11`，**exit 1**；那一条 FAIL 恰恰是我新加的 `C-6c` 抓到的**真缺陷 `D-08`**（文案漂移）。如果我当时没更正，Lead 的最终报告里就会引用一个假数字，而且 **`D-08` 会被漏掉** |
| **更正方式** | 我主动发消息**撤回**该数字，附上现场复跑的真实输出，并写明「如果我这条数字进了你的最终报告，请以下面这条为准」；同时给出替代动作：**每个真缺陷都列全仓出现点、逐点对比**（这才产出了 `D-08` 那张「六处里只有 bridge 少尾句」的可执行修复单） |
| **我给自己定的规矩** | **任何数字必须现场跑出来，不许从「上一次的输出 + 我的推理」拼接。** |

## 三、由误报教训反推出来的两条新护栏（正向收益）

这两条不是「修 bug」，而是把误报的教训**升级成能防回归的判据**：

### 护栏 1 · `C-6` 从「硬编码白名单」改为「以 `02` 附录 A.3 为唯一真源」

* **动机**：`D-03`（`IMP-5002` 未登记）说明「代码加了码、文档没登记」会**静默发生**，而原始判据是一份写死在脚本里的 33 个码的清单 —— 脚本自己也会漂移，且**无法发现文档与实现不一致**。
* **做法**：
  * `C-6`：解析 `docs/import/02` 附录 A.3 的表格得到号段，代码引用必须**全部已登记**（文档驱动，非硬编码）；
  * `C-6b`：**本脚本硬编码清单必须是文档号段的子集**（防止脚本自己漂移）；
  * `C-6c`：**`electron/bridge.cjs` 的 `ERROR_TABLE` 与附录 A.3 的 `http` / `userMessage` 逐字比对** —— 双向护栏，`D-08` 就是它抓到的；
  * `C-6d` / `C-6e`：文案列是**说明性散文**或**多情形复合说明**的码不参与逐字比对，记 INFO（`IMP-1006`、`IMP-4011`）。
* **口径（Lead 裁定）**：`C-6c` **只**严格比对桥的**兜底表**，**不要求**渲染层按场景写的更贴切文案等于文档那一行（例如「收件箱满 500」就该说收件箱满，而不是复用「附件太多」那句）。

### 护栏 2 · `verify-contract.cjs` 自身的两处 `hit.lines.slice()` 崩溃

* **现象**：`TypeError: Cannot read properties of undefined (reading 'slice')` at `verify-contract.cjs:843`，**检查器直接崩掉**（`U-6b` 之后的检查根本没跑）。
* **根因**：`grepFiles()` 返回 `{file, line, text, match}`，**没有 `lines` 字段**；我在 `U-6b` 与 `BR-2` 两处假设它带整份文件。`BR-2` 那处因命中集为空**从未触发**，属**潜伏崩溃**。
* **修正**：新增 `lineWindow(hit, before, after)` 按需重读文件并切片；两处调用点改齐。
* **为什么值得单列**：**崩溃比失败更危险** —— 失败会打印失败清单，崩溃只会留一行 `TypeError`，很容易被当成「跑过了」。**验证脚本本身也需要被验证。**
