## 一、验证方法

### 1.1 为什么不是「再跑一遍作者的脚本」

作者自测（`scripts/bridge-smoke.cjs`、`scripts/gate-defects.cjs`、`scripts/ipc-safety-check.cjs`、`extension/verify.mjs`）**我都独立复跑过**，数字与作者自报一致（见 §三）。但自测脚本有一个结构性盲区：**它只检查它想到的地方**。所以本报告的主力是两个我**自己写的**脚本，它们的取径与作者脚本不同：

| 脚本 | 取径 | 与作者脚本的差别 |
|---|---|---|
| `scripts/verify-contract.cjs` | 以 `docs/import/02` 附录 A.3 为**唯一真源**做静态比对 | 号段/文案漂移能被抓出来（见 D-V08） |
| `scripts/verify-e2e.cjs` | **真跑**：Vite Node API 载入真 TS 源码 + 真 HTTP + 真磁盘（仅打桩 Electron IPC 边界），并**加载真实 `electron/main.cjs`** | 覆盖「两边各自单测绿、缝里断掉」的跨界缝（见 V4） |

### 1.2 动态执行方式（无 esbuild/tsx 的前提下）

仓库没装 esbuild / vite-node / tsx，所以真跑 TS 源码用 Vite 的 Node API：

```js
vite.createServer({ configFile:false, root:ROOT, logLevel:"error",
                    server:{ middlewareMode:true }, appType:"custom",
                    optimizeDeps:{ noDiscovery:true } })
  .then(server => server.ssrLoadModule("/src/lib/clip/receive.ts"))
```

`electron/bridge.cjs` 只依赖 Node 内建模块（`node:http` / `node:crypto` / `node:fs` / `node:path`）并导出 `createBridge`，所以它能在纯 Node 里用挂钩注入真跑。
`electron/main.cjs` 则通过**替换 `Module._load` 里的 `electron` 请求**来打桩 IPC 边界，其余（handler 注册、`relayToRenderer`、`bridgeStatusPayload`、`settleImportRelay`）**全是真代码**。

### 1.3 两个脚本的退出码约定

* `node scripts/verify-contract.cjs` → 退出码 **0 = FAIL 数为 0**；非 0 时打印失败清单。
* `node scripts/verify-e2e.cjs` → 退出码 **0 = FAIL 数为 0**；非 0 时打印失败清单、`UNVERIFIED` 清单、`INFO` 观测清单。
* `SKIP` / `UNVERIFIED` / `INFO` **永不**计入通过数，也不拉高退出码（`DYN-0` 这类「未传参数」明确归 `SKIP`）。
