# V4 · 「单测绿、端到端死」—— 三个缝里断掉的模式

> **本节是本次验证最有价值的发现。** 三个缺陷有**完全相同的形态**：**边界两侧各自的单测都是全绿的**，断的是**两者之间的那条缝** —— 而缝不属于任何一侧的测试范围。
>
> 这类缺陷用「再跑一遍单测」永远抓不到。它们是本报告的 `verify-e2e.cjs`（**真跑跨界链路**）与 `verify-contract.cjs`（**逐字比对文档真源**）抓到的。

---

## 模式总览

| # | 缺陷 | 谁写的（A） | 谁吃掉的（B） | 吃掉的方式 | 单测为何全绿 |
|---|---|---|---|---|---|
| 1 | `bridgeStatusPayload` 截断 6 字段 | `electron/bridge.cjs` 的 `status()` | `electron/main.cjs` 的 `bridgeStatusPayload()` | **逐字段重建**：B 用白名单重新拼一个对象，A 的额外字段被丢掉 | 桥的 smoke **有** `lastPairing` 断言且 PASS；主进程的单测根本没断言这 6 个字段 |
| 2 | `InboxError` 被降级为 `IMP-5001` | `src/data/inbox.ts` 抛 `InboxError("IMP-4013", …)` | `src/lib/clip/envelope.ts` 的 `isImportRejection()` | **类型守卫**：B 只认 `name === "ImportRejection"`，A 的错误对象被判定为「不认识」→ 被包成通用错误 | 收件箱单测断言「满了抛 IMP-4013」**全绿**；接收端单测没造过「收件箱满」的场景 |
| 3 | `discardInbox` 静默成功 | `src/data/inbox.ts` 的 `commitInbox` 抛 `IMP-4017` | 同一个文件的 `discardInbox` | **静默 return**：找不到就当作「已经不在了」，**既不删也不报错** | 各自单测都绿：commit 测了抛错、discard 测了幂等，**没人测「同一个错 id 喂给两个 API」** |

## 模式 1 · 写者 B 的**重建逻辑**吃掉写者 A 的字段

### 现象

`electron/main.cjs` 的 `bridgeStatusPayload()` 原本用「逐字段重建」返回桥状态：

```js
const raw = controller.status() || {}
return {
  state: raw.state,
  port: typeof raw.port === 'number' ? raw.port : null,
  // …白名单里没有 address / error / lastRejectedOrigin / startPort / portRange / lastPairing
}
```

**桥返回了这 6 个字段，主进程一个都没往外传。**

### 为什么两侧单测都是绿的

* **A 侧（桥）**：`scripts/bridge-smoke.cjs` 里 `lastPairing` **有断言且 PASS**（`PASS 72 · FAIL 0 · SKIP 3`）—— 桥确实返回了它。
* **B 侧（主进程）**：单测断言的是 `state` / `port` / `tokenSet` 这些**白名单内的**字段，**从未断言过那 6 个**。
* **缝**：没有任何测试从 `controller.status()` 一路走到 IPC payload。

### 后果（不是「少几个字段」，而是三条 UI 要求成了死代码）

| UI 要求 | 依赖字段 | 修前后果 |
|---|---|---|
| R4b 配对轮换警告 | `lastPairing` | 永不出现 |
| R8「已拒绝一个来源不明的请求：{origin}。」 | `lastRejectedOrigin` | 永不显示 |
| S4/S5「8787 到 8796 端口都被占用了…」 | `startPort` / `portRange` | 这句可执行的下一步永不渲染 |

### 我是怎么抓到的（可复现）

`node scripts/verify-e2e.cjs` → 场景 7B：用 **Electron 桩**加载**真实 `electron/main.cjs`**，走真实 `opennote:bridge:status` handler：

```
PASS  [S7B.1] 真实桥：`bridgeStatusPayload()` 带着 6 个可选字段
            键数=23；address="http://127.0.0.1:8788" startPort=8787 portRange=[8787,8796] lastPairing=null
```

并且用**哨兵桥**证明这条断言**红得起来**（不是碰巧绿）：

```
PASS  [S7B.3] (1) 哨兵桥的 6 个字段**逐值透传**（去掉 `...raw` 此断言必红）
            lastPairing={"at":12345,"origin":"https://pairing.example","rotated":true}
            lastRejectedOrigin="https://sentinel.example" portRange=[9999,10008]
```

> **敏感性自证**：哨兵桥伪造 `createBridge()`，返回带唯一哨兵值的 `status()`。若把 `...raw,` 移除，6 个值会全部变成 `undefined`/`null` → **断言必然变红**。注入靠 `Module._load` 拦截 `require`，**产品代码一行未改**。
>
> 另外两条边界也一并验了：`S7B.4`（桥给布尔 `true` 时主进程必须覆盖成 `'watch'`，**布尔绝不透传到渲染层**）、`S7B.6`（`!controller` 早退分支 `state="failed"` + 可执行 error 文案 + 6 键仍在，键数=15）。

### 教训

> **「重建白名单」是跨边界传对象的反模式。** 正确写法是 `...raw,` 打底 + 显式字段收紧类型（修复采用的正是这个形态）。**任何一次「我只要这几个字段」的重建，都在悄悄裁剪上游的契约。**

## 模式 2 · 写者 B 的**类型守卫**吃掉写者 A 的错误对象

### 现象

```js
// src/data/inbox.ts:771 —— A：码和文案都对
throw new InboxError("IMP-4013", INBOX_FULL_MESSAGE);

// src/lib/clip/receive.ts:694 —— B：本意是「域错误原样透传」
if (isImportRejection(error)) throw error;
// 否则 ↓
throw new ImportRejection(importProblem("IMP-5001", { reason: "inbox-enqueue-failed", message: errorMessage(error) }));

// src/lib/clip/envelope.ts:244 —— 守卫只认自己那一种
export function isImportRejection(value) {
  return value instanceof ImportRejection
      || (value?.name === "ImportRejection" && typeof value.code === "string");
}
```

`InboxError.name === "InboxError"` → 守卫判 false → `IMP-4013` **被包成 `IMP-5001`**。

### 实测输出

```
FAIL  [S8.2] 收件箱满 500 应拒 IMP-4013 —— 实际被降级成 `IMP-5001`
     基线投递=created；计数=501；第 501 条 code=IMP-5001
     ；对外 userMessage="写入笔记失败，磁盘可能已满或没有权限。原内容没有丢失。"
     ；真实原因藏在 detail.reason="inbox-enqueue-failed" message="收件箱已满（500 条），请先处理一些条目。"
```

**用户被告知「磁盘可能已满或没有权限」，而正确动作是「去收件箱处理几条」。原因和下一步都指错。**

### 为什么两侧单测都是绿的

* **A 侧**：收件箱单测断言「满 500 抛 `IMP-4013`」—— **全绿**，因为 A 抛的确实是对的。
* **B 侧**：接收端单测从未构造「收件箱满」的场景，它测的是自己的域错误。
* **缝**：没有任何测试断言「A 抛的域错误穿过 B 的守卫后**仍然是同一个码**」。

### 影响面（不止 4013）

`enqueueInbox` 内**所有**域错误都会被吞：`IMP-4010`（目录名 50 次耗尽，`inbox.ts:779`）、`IMP-4007`（无后端，`:744`）、`IMP-4003/4002/4001`（信封复校）。

### 修复与验证

Lead 裁定改为**结构化判定**（`IMP-####` 码 + 非空 `userMessage` 即认，`http` 缺失时按码从 `ERROR_MAP` 补），并要求补三条**能独立红**的断言：①满 500 → `IMP-4013` 逐字；②`IMP-4007` 原样透传；③普通 `Error` **仍然**归 `IMP-5001`。

我复跑：

```
PASS  [S8.2] 收件箱满 500 → 第 501 条被拒 `IMP-4013`（有码、不静默丢）
            基线投递=created；当前计数=501；第 501 条 → code=IMP-4013 userMessage="收件箱已满（500 条），请先处理一些条目。"
```

### 教训

> **「按类判」的守卫无法跨模块工作。** 跨模块传错误对象时，判据必须是**结构**（`code` + `userMessage`），而不是 `instanceof` / `name`。而且**「原样透传」这个意图必须被测试钉住** —— 否则它只是注释里的一句意愿。

## 模式 3 · 静默成功（既不做事、也不报错）

### 现象

同一个文件里两个 API 对同一个「找不到」的处理**不一致**：

```js
// commitInbox —— 明确报错
const found = await findDir(target, id);
if (!found) throw new InboxError("IMP-4017", inboxFailureMessage("IMP-4017"));

// discardInbox —— 静默 return
const found = await findDir(target, id);
if (!found) return; // 幂等：已经不在了
```

而 `findDir()` 当时**只按 `entry.id`（完整 `importId`）匹配**，可是回执里的 `inboxId` 是**目录名** —— 两者**不相等**（见 `V1` D-04）。于是客户端若拿 `receipt.inboxId` 去 `discardInbox()`：**不抛错、什么都没删，调用方以为删掉了。**

更糟的是 `inbox.ts:825` 的**文档注释**还写着「`id` 可以是 `entry.id` 或条目目录名（见 `findDir`）」—— **文档承诺与实现不符**。

### 实测输出（修前的探针形态）

```
commitInbox(目录名) → 抛错「没有找到这条导入记录。」
discardInbox(目录名) → **静默返回、无任何信号**
目录仍在=true
```

### 为什么两侧单测都是绿的

* `commitInbox` 的测试：测了「找不到就抛 `IMP-4017`」—— 绿。
* `discardInbox` 的测试：测了「重复丢弃是幂等的」—— 绿（**幂等本身是正确需求**）。
* **缝**：没人测「**同一个错误的 id 喂给这两个 API**」。而「幂等」与「静默吞掉错误 id」在测试上长得一模一样。

### 我的探针改造（Lead 指出第一版措辞会误导人）

第一版探针写的是「**没抛错** → 打印『静默返回、无任何信号』」。缺陷修好后**丢弃成功当然也不抛错** → 这行会**恒打印「静默失败」**，读起来像缺陷还在，而真正的信号是「目录仍在=false」。按 Lead 的要求改成**四条分支**：

| 情形 | 判定 | 文案 |
|---|---|---|
| `未抛错 && 目录已删` | **PASS** | 丢弃生效（目录已删除） |
| `未抛错 && 目录仍在` | **FAIL** | 静默无效：未抛错但目录仍在 |
| `抛错 && 目录仍在` | **PASS** | 明确报错（可诊断，不是静默） |
| `抛错 && 目录已删` | INFO | 状态矛盾 |

### 修复与验证

C2 修了 `findDir()` 双解析（`entry.id` 精确匹配优先 + 目录名解析）并让查不到**抛 `IMP-4017`**，零静默。我复跑：

```
PASS  [S5.8b] 丢弃（目录名写法）生效：未抛错且目录已删
            投递=pending；目录 20260929T134142-verify-p 投递后存在=true → 丢弃后存在=false
PASS  [S5.8c] `importId` 与「目录名」两种写法都能入库（行为一致）
            目录名写法：S5.8 已证；importId 写法：notes 2 → 3、inboxCount=0；
            回执 inboxId=20260929T134142-verify-d ≠ importId=verify-dualid-4697b890-945
            （两者确实不等价，但两种写法都认）
```

### 教训

> **「幂等」必须与「静默无效」区分开。** 幂等的正确形态是**能证明目标已处于期望状态**（这里：目录确实不存在），而不是**查不到就 return**。凡是「找不到就当作已完成」的代码，都在把**调用方的错误**伪装成**成功**。

## 三条模式的共同处方

| 处方 | 具体做法 |
|---|---|
| **1. 跨边界不要「重建」** | 传对象用 `...raw,` 打底 + 显式收紧类型；不要用白名单挑选字段 |
| **2. 跨边界不要「按类判」** | 用**结构**判定（`code` + `userMessage` 存在即可认），不要 `instanceof` / `name` |
| **3. 幂等要「证明状态」** | 「查不到」必须与「已完成」区分；查不到要报错或至少给出可观测信号 |
| **4. 每条缝都要有一条端到端断言** | 单测覆盖两侧、E2E 覆盖缝。**没有 E2E 的缝等于没人测** |
| **5. 断言必须「红得起来」** | 用哨兵值 / 反向还原证明断言有敏感性（本报告 `S7B.3` 的哨兵桥、C2 的三次反向还原都是这个做法） |
