## 1. 现场与根因（逐像素量出来的，不是估的）

用户截图 2528×1659、DPR 2 → **视口 1264×829 CSS px**。把截图行内亮像素投影成列（阈值 + 游程）得到每项的真实宽度：

| 项 | 宽（CSS px） |
| --- | --- |
| 笔记存放位置（`本机磁盘 · E:\repo\notes`） | ~194（`--path` 上限 300） |
| 510 个文件 | ~63 |
| 当前文件夹（`Agent 产出`） | ~72 |
| 保存状态（`● 已写入磁盘 · 7 分钟前`） | ~121 |
| 字数统计 | ~183 |
| 行列 | ~76 |
| 7 颗按钮（带文字） | ~342 |

**可用宽 = 视口 1264 − 侧栏 293 − 把手列 6 ≈ 971px；内容需要 ≈ 1170px → 溢出约 200px**，而 `overflow: hidden` 把溢出全部丢在右侧：截图里「收件箱」被切成「收件」，其后的「历史 / 夜读 / 设置」整颗消失。

三条根因（全在 `src/styles/app.css`，修前）：

1. `.statusbar` 是 `flex-wrap: nowrap` + `overflow: hidden`，`.statusbar__item` 一律 `flex: none` —— 溢出只能往右推，被裁的正好是最右边的**按钮**。
2. 唯一的降级规则是 `@media (max-width: 1180px)`，判的是**视口**；可底栏住在 `.main` 里，宽度 = 视口 − 侧栏（`SIDEBAR_WIDTH` 200–520，可拖）− 大纲（232）。视口 1264 > 1180 → **不降级** → 裁切。窗口最小 900、侧栏拖满 520 时底栏只有 **380px（内容盒 356px）**。
3. `.statusbar__item--compact` 还挂在「收件箱」「GitHub」「清除令牌」三个**按钮**上：一降级连能力入口一起消失，与 DESIGN.md「降级后必须仍然可用」冲突。

## 2. 改法（两条腿）

1. **结构**（硬保证，与阈值标定准不准无关）：底栏拆成信息段 `.statusbar__info`（`flex: 1 1 auto` + `min-width: 0` + `overflow: hidden`，唯一会被压缩、可被压到 0）与按钮段 `.statusbar__actions`（`flex: none`，永不收缩）。于是**按钮在任何宽度下都完整可见**；万一某档标定错了，被牺牲的只会是信息。
2. **分档**（避免「半截字」）：`@container statusbar (max-width: …)` 按**底栏自身宽度**整项隐藏信息。`--compact` 从此只给信息项（文件数、字数统计）用；按钮文字单独包一层 `.statusbar__label`（窄窗只丢文字，图标 + `title` + `aria-label` 都还在）；两段长文本（存放位置、当前文件夹）的文字包进 `.statusbar__ellipsis`，是唯一允许省略号收缩的两项；每个按钮补 `aria-label`（`Icon` 是 `aria-hidden="true"`，文字一没按钮就没有可访问名）。
3. 附带两处小改：`savedLabel` / `savedAgo` 分成两个 prop（窄窗能只丢「· N 分钟前」）；GitHub 的「清除令牌」补一枚**既有**图标 `trash`（否则它没有图标，窄窗只能整颗消失）。

| 档（底栏内容盒宽 ≤） | 隐藏 | 实测需求（用户那组内容） |
| --- | --- | --- |
| 1180 | 文件数 + 字数统计 | 全量约 1147–1213px |
| 900 | 加上当前文件夹 | −72px |
| 860 | 加上按钮文字（7 颗带字 342 ↔ 纯图标 247；GitHub 再多 74） | ~137px |
| 720 | 加上行列、保存状态里的「· N 分钟前」 | ~112px |
| 420 | 加上存放位置 | |
| 400 | 保存状态只留圆点（`title` 说全文），两组间距收到 `--s2` | 9 颗图标 + 圆点约 320px ↔ 底栏 356px |

## 3. 源码契约单测（`src/components/statusbarLayout.test.ts`，6 个用例）

口径与 `src/data/shellLayout.test.ts` 一致：读 `app.css` 源码文本、**先剥注释**。

```
npx vitest run src/components/statusbarLayout.test.ts src/data/shellLayout.test.ts
  → 10 passed（新增 6 + 既有外壳契约 4）
```

断言清单：

1. `.statusbar` 声明 `container: statusbar / inline-size`，且**任何 `@media` 块里都不再出现 `statusbar`**（降级不再按视口判）。
2. 结构保险：`.statusbar__actions` 是 `flex: none`；`.statusbar__info` 是 `flex: 1 1 auto` + `min-width: 0` + `overflow: hidden`；`.statusbar__item` 是 `flex: none`；`.statusbar__item--path` / `--folder` 是 `flex: 0 1 auto`；`.statusbar__ellipsis` 有 `text-overflow: ellipsis`。
3. 分档共 6 个、阈值严格递减、最窄 ≤440px、最宽 ≤1180px。
4. **逐个分档断言：不许隐藏任何 `--button`、不许隐藏 `.statusbar__dot`，且被隐藏的选择器必须落在 DROPPABLE 白名单里**（这是「必要项永远在」的机器判据）。
5. 被隐藏的项并集恰好是那 7 样（宽窗下全部照常显示）。
6. 按钮文字是单独一段、且确实会在某一档被丢。

## 6. 诚实声明（哪些证了、哪些没证）

**真跑了的**：真实的 Electron 窗口 + 真实 CSS 布局引擎（`Emulation.setDeviceMetricsOverride` 改视口、真 `--sidebar-w`、真点击大纲/侧栏按钮、`elementFromPoint` 命中测试、`Page.captureScreenshot` 像素）；真实 `app.css`（探针不注入任何 CSS，只换文字与补两颗克隆按钮）。

**没证 / 有偏差的地方**，逐条写明：

1. 探针跑在**临时 `--user-data-dir`**（没有工作区、没有 GitHub 远端），所以「真实内容」那一遍偏窄；覆盖它的是 ②③④ 三遍注入内容 —— ② 逐字复刻用户截图那组，③ 严格宽于任何真实笔记本（路径顶到 300px 上限、长文件夹名、六位数计数）。
2. GitHub 那一遍的两颗按钮是**克隆现成按钮**（同一套 class → 同一套 CSS，宽度等价），不是真连了 GitHub 远端；探针里带 `data-probe-github` 标记，产品代码里没有这个东西。
3. 「· 7 分钟前」那一段在临时 profile 下不存在（从没落过盘），探针补了一颗同 class 的空 span 再填文字；虽然宽度等价，但它不是产品真实渲染出来的（用户那台机器上有真实的落盘时间）。
4. **没有**在用户真实笔记本（484 篇、真实长路径）的窗口里跑探针：那要占用用户的 `user-data-dir`，还会把 UI 设置持久化进去。改用「严格更宽的内容」覆盖该情形。
5. 未在 macOS / Linux / 移动真机上目视核对。容器查询是标准 CSS（Chrome 105+），本项目已经在用 `:has()`（同档），`vite` 的 `cssTarget: chrome110` 也不会降级它；Electron 44 = Chromium，Android 走 WebView（与 `:has()` 同档）。
6. 未做 DPR≠1 之外的缩放观感核对；几何按 CSS px，与 DPR 无关（实测里已含 dpr=2 的用户那组）。
7. 分档阈值是**按上面那组内容标定**的：换一种语言/字体或用户把字体调大，档位触发点会整体平移（这是静态阈值的固有属性，不是缺陷）；但「按钮不被裁」与阈值无关（结构保证）。
8. 本轮**没有**引入「⋯ 溢出菜单」：用户选的是「图标常显，只收文字」，6 个档位已经能在 356px 下界兜住（含 GitHub 的两颗）。
