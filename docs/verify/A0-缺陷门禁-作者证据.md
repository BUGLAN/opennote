| `safePath(root, relPath, mode)` 的 `write` 分支 | `electron/main.cjs`（写入路径**同时**校验父目录与目标自身——只查父目录会漏掉「文件名本身是符号链接」） |

| `src/fs/handleBackend.ts` / `src/fs/opfs.ts` | **不含任何 `realpath` 调用**（静态断言，见下） |

**复现命令**：`node scripts/gate-defects.cjs`（其中 `D31 junction / 符号链接越界` 分组来自 `node scripts/ipc-safety-check.cjs --verbose`，会在临时工作区里真实创建 junction）

**期望输出（实测）**

```
静态：全部 fs handler 走 realpath 越界校验（target / parent / write 三模式） — 写入路径同时校验父目录与目标自身
行为：junction 读 / 写 / list / stat / exists / remove 全部被拒 — 7 PASS / 2 SKIP
行为：绝对路径 / UNC / NUL 等 8 种写法全部拒绝 — 3 PASS / 0 SKIP
已知限制：浏览器后端没有 realpath 可用，只能文档化（不声称等价） — 浏览器端限制已在 A0 证据文档中登记
行为：静态取证（handleBackend.gate.test.ts） — 2 个用例全绿
行为：词法边界（paths.gate.test.ts：链接名与普通目录名在词法上不可区分） — 1 个用例全绿
变异：把 assertRealPathInsideRoot 变成空操作后护栏变红 — 退出码 1，FAIL 5
WARN D31 有 2 项 SKIP（本机无法创建文件级符号链接）：文件符号链接指向工作区外：读/写/exists 全部被拒；文件符号链接指向工作区内：写链接 = 写它指向的文件（语义保持）
```

- 目录 junction 全绿：`readText` / `writeText` / `list` / `stat` / `exists` / `remove` 经 junction 一律「路径越界：链接指向工作区之外」，工作区外不产生任何文件（含 `.tmp` 残骸）；`remove(junction 本身)` 只删链接、不动链接目标。
- 2 项 SKIP 是**本机环境**限制（Windows 创建文件级符号链接需开发者模式/管理员），不是代码问题。**这意味着「文件名为符号链接」这一子场景在本机没有被真跑验证**，只被 `write` 模式的父目录+目标双检覆盖在代码层面。

**已知限制（必须明确，不许声称等价）**

- **桌面端（node 后端）**：三道校验齐全——`resolveInsideRoot()` 词法、`assertRealPathInsideRoot()` 对父目录与目标各做一次 `realpath`、写入走同目录临时文件 + `rename`。判定：**已修复且已验证**。
- **浏览器端（FSA / OPFS）**：`FileSystemDirectoryHandle` 契约里**没有 `realpath` 等价物**（`resolve()` 在 Chromium 中对 OPFS/FSA 条目不可用），因此浏览器后端**无法**判断某个条目是不是指向工作区外的链接。`src/fs/handleBackend.ts` 与 `src/fs/opfs.ts` 全文不含 `realpath`（`src/fs/handleBackend.gate.test.ts` 用静态断言钉住这一点，防止有人写出「已做 realpath 校验」的假注释）。
- 浏览器端的实际暴露面受限：FSA 的根是用户经系统选择器显式授权的目录，OPFS 是 origin 私有文件系统（页面无法在其中创建指向宿主机路径的链接）。**但这不等于等价**：浏览器端没有做、也做不到链接越界校验，这是一条**已登记的风险**，不是「已修复」。
- 判定口径：D31 在桌面端 PASS；浏览器端记为**已知限制**，不计入「已修复」。

**变异灵敏度**：把 `assertRealPathInsideRoot` 变成空操作 → 退出码 1、**FAIL 5**（junction 读、写、list/stat/exists、写入目标自身、remove 目标保护全部变红）。

## 3. 变异灵敏度（护栏不能只是「碰巧全绿」）

门禁脚本在**编译期**把 `electron/main.cjs` 的源码改回**修复前**的写法（`Module.prototype._compile` 钩子，**不落任何 main.cjs 副本**），再用同一套 `ipc-safety-check` 断言「护栏必须变红」。护栏对回归不敏感 = 证据无效，所以这一步失败同样计入 FAIL。

**变异运行的判定是四态，措辞刻意不同：**

| 状态 | 含义 | 是否 FAIL |
| --- | --- | --- |
| `DETECTED` | 有 PASS/FAIL 摘要、退出码非 0、FAIL > 0、且命中该缺陷的预期失败文案 | 否（期望结果） |
| `MISSED` | 跑完了但没红 —— **确认对该回归不敏感** | 是 |
| `CRASHED` | 没有任何 PASS/FAIL 摘要（加载期崩溃 / 锚点未命中 / 超时）—— **无法判定** | 是 |
| `NO_EFFECT` | 有摘要，但钩子从未真正改写 main.cjs（跑的是未变异代码）—— **无法判定** | 是 |

另有 **M0 零变异对照**：用与变异**完全相同的接线**、零变异跑一遍，结果必须与基线逐字一致（`PASS 62 / FAIL 0 / SKIP 2`）。它是「变异接线可用」的证据。

**为什么要有 M0 与 `NO_EFFECT`（0.3.1 真实事故，2026-09-29）**：Lead 现场跑出 `M1/M2/M3 全部 MISSED，FAIL ?`。独立核查确认根因**不是**当时怀疑的 Electron 打桩缺口（`requestSingleInstanceLock` / `setAsDefaultProtocolClient` 两个桩已经在位，基线本身是绿的），而是：0.3.1 给 `main.cjs:32` 加了 `require('./deeplink.cjs')`，而当时 harness 的做法是**把 main.cjs 复制到临时目录再改**——CJS 的相对 require 按**文件真实路径**解析，副本一离开 `electron/`，这条 require 立刻 `MODULE_NOT_FOUND`，harness 在**加载阶段**就崩：退出码 1、但没有任何 `PASS/FAIL` 行，于是被判成 MISSED。修法：改为**编译期注入**，main.cjs 始终从自己的目录加载，`__dirname`、相对 require、preload 路径全部保持真实。

**为什么这条最危险**：`MISSED` 与「harness 根本没跑起来」在输出上几乎一样，但含义相反——前者是「确认检不出来」，后者是「我们什么都不知道」。把后者说成前者是**静默减少覆盖**，比直接报错更容易骗过 reviewer。

**自证**：`node scripts/gate-defects.cjs --self-test` → **PASS 5 / FAIL 0，退出码 0**，三个对照全部实测通过：

```
WIRING   M0 零变异对照 — PASS 62 / FAIL 0 / SKIP 2，退出码 0
PASS 零变异对照可用（status=VERDICT 且退出码 0）
CRASHED  X1（故意打断兄弟模块 require）— 退出码 1：自测脚本自身异常： Error: Cannot find module './__gate_self_test_missing__.cjs'
PASS 崩溃被判定为 CRASHED（而不是 VERDICT/MISSED） — 退出码 1
PASS 报错措辞写明「无法判定」，且不使用 MISSED 的说法 — 变异 harness 崩溃：**无法判定**是否检出（不是「护栏对该回归不敏感」）…
NO_EFFECT X2（声明变异、零注入）— 退出码 0，FAIL 0：变异从未被应用到 main.cjs（runner 接线断了，跑的是未变异代码）
PASS 零注入被判定为 NO_EFFECT（而不是 MISSED / VERDICT） — 退出码 0，FAIL 0
PASS 零注入的报错写成「变异从未被应用」，且不使用 MISSED 的说法 — 变异从未被应用：**无法判定**是否检出…
```

对照 2（X1）复刻的正是 0.3.1 的崩溃形态；对照 3（X2）复刻的是「声明了变异却零注入」。**注意 M0 零变异对照发现不了 X2 那一类**（接线本身是对的），只有「变异是否真的落地」的**正向证据**能发现——所以钩子每次真正改写源码都会打印 `[gate-mutation] applied <id> to main.cjs`，判定时把它当作「变异已生效」的必要条件。

**同样的崩溃路径在真实门禁上的端到端复现**（临时把 `runIpcCheck` 的变异接线摘掉再跑，随后已还原、`TEMP-BREAK` 残留为 0）：

```

WARN 有 3 个变异运行**没有产出可信判定**（harness 崩溃 / 变异未生效）——这不是「检不出来」，而是「无法判定」，已按 FAIL 上报
FAIL 变异：注回「无授权判定」的 main.cjs 后护栏变红 — 变异从未被应用：**无法判定**是否检出（不是「护栏对该回归不敏感」）
```

## 4. 未覆盖项 / 未解决项（诚实清单）

1. **D31 文件级符号链接在本机 SKIP（2 项）**：Windows 创建文件符号链接需要开发者模式或管理员权限，`ipc-safety-check` 的两条用例被跳过。目录 junction 用例（7 项）正常执行并通过。「文件名本身是符号链接」这一子场景目前只有代码层面的 `write` 模式双检（父目录 + 目标各做一次 `realpath`），**本机没有真跑验证**。要补这一项，需要在开启开发者模式的机器或管理员会话里重跑 `node scripts/ipc-safety-check.cjs --verbose`。
2. **D31 浏览器端无法修复**：FSA / OPFS 没有 `realpath`，只能文档化（见 §2.3）。任何「浏览器端与桌面端等价」的表述都是错的。
3. **D08 的 mtime/size 启发式**：极端情况下（同毫秒 + 同大小 + 内容不同）依赖第二次 `readText` 内容比对兜底；没有构造出真实漏判复现，属**未验证的边界**，不是已证实的缺陷。
4. **本机为 Windows**：`node scripts/gate-defects.cjs` 的 D20/D29/D31 行为证据来自 Windows 主进程路径；macOS / Linux 未实测（代码里 `pathIdentity()` 只在 win32 折叠大小写）。
5. **全量 `pnpm test` 的状态变化（记录实况，不含粉饰）**：本线核查过程中，全量套件曾出现 2 条失败，全部在 `src/lib/clip/`（**A 线写入范围之外，且 `src/lib/**` 对本线是明令禁止修改的目录**）：
   ```
   FAIL src/lib/clip/envelope.test.ts > 信封校验（契约 §2 / §10.1） > target.folder 合法形态被清洗成 POSIX 段
        AssertionError: expected [Function] to throw error matching /路径不能包含冒号|目标目录不合法/ but got 'target 路径非法'
   FAIL src/lib/clip/frontmatter.test.ts > front-matter 字节级模板（契约 §3.2 / 附录 A.2） > tag 行是行内数组 `tags: [a, b]`
        AssertionError: expected [ '本地优先', '剪藏' ] to deeply equal [ '剪藏', '本地优先' ]
   ```
   这属于该线自己的新源码与新测试尚未对齐，**与 A 线 6 条缺陷无关**，A 线未代为修改。**该线随后自行修复**：本文件定稿前连跑两次全量均为 `30 passed / 1 skipped（31 文件）｜541 passed / 2 skipped（543 用例）`，退出码 0。上面记录的两次失败是**当时实况**，保留在此以免 reviewer 以为从没红过。
6. **工作区含其它线未提交改动**：本次门禁运行时 `git status` 除本线新增文件外，还包含 `electron/main.cjs`、`electron/preload.cjs`、`src/desktop/bridge.ts`、`src/styles/app.css`、`electron/bridge.cjs`、`extension/`、`src/lib/clip/`、`src/data/inbox.ts`、`scripts/bridge-smoke.cjs`、`scripts/verify-contract.cjs` 等其它线的在制品。本线只写自己独占范围内的文件；`ipc-safety-check`（含 preload 契约与窗口安全基线）在这些改动存在的情况下仍然 PASS 62 / FAIL 0，`electron/main.cjs` 被改动之后重跑门禁仍为 PASS 36 / FAIL 0——但这**不等于**对其它线改动的验收。
   **风险提示**：`scripts/gate-defects.cjs` 的静态锚点与变异锚点都指向 `electron/main.cjs` 的当前写法。若该文件后续被改动导致锚点漂移，门禁会以「锚点未命中（源码漂移）」FAIL 明确报错，而不是静默放行。
7. **`--no-mutants` 会降级证据**：该开关只用于快速迭代；正式门禁必须不带该开关运行，否则「护栏对回归敏感」这一层证据缺失（脚本会打印 WARN）。
8. **变异判定的残余依赖（记录在案，方向安全）**：`DETECTED` 除了要求「退出码非 0 且 FAIL > 0」，还要求命中该缺陷的**预期失败文案**（如 `/未授权的工作区目录/`、`/junction/`）。如果将来有人改了这些**用户可见文案**，变异运行会被判成 `MISSED`（FAIL）而不是 `DETECTED`——这是**误报**，会逼人来看一眼，方向是安全的（不会静默放过）；但如果只看「退出码非 0」就宣布检出，则可能把「harness 因别的原因崩溃」当成检出，所以这个偏严的判据是刻意的。
9. **变异机制依赖 Node 内部 API**：编译期注入用的是 `Module.prototype._compile`（`Module._extensions` 里没有 `.cjs`，实测确认）。该 API 属 Node 内部实现，跨大版本可能变动——但 `ipc-safety-check.cjs` 本身也用了 `Module._load`，同一套依赖；若将来失效，表现为 M0 零变异对照 `CRASHED`（明确的 FAIL），不会静默降级。
