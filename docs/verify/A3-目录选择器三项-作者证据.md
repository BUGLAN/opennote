## 2. 图 1/图 3：`FolderDialog`（移动到…）

### 2.1 几何：头部钉住，面板不跳

| 量（CSS px） | 搜索前（树模式，14 行） | 搜索「op」（14 条命中） | 列表滚到底（`scrollTop=52.5`） |
| --- | --- | --- | --- |
| `.dialog` 高度 | **598.59** | **598.59** | **598.59** |
| `.dialog` top | 65.7 | 65.7 | 65.7 |
| `.dialog__head` top | 66.7 | 66.7 | 66.7 |
| 搜索框 top | **172.52** | **172.52** | **172.52** |
| `.dialog__body.scrollTop` | 0 | 0 | 0 |
| `.folder-picker` | client 354 / scroll 399 | client 354 / scroll 407 | `scrollTop 52.5`（**只有它滚**） |

> 598.59 而不是 600：`.dialog` 带 `pop` 动画（`both` 填充），量的时候缩放还在 0.9977。三态一致才是判据。

**改前（同一脚本、同一笔记本）**

| 关键字 | 命中条数 | `.dialog` 高度 | 搜索框 top |
| --- | --- | --- | --- |
| `gopl` | 3 | **374.05** | 284.8（推算） |
| `op` | 14 | **578.62** | 182.51（实测） |

→ 打字过程中面板高度**跳 204.57px**；面板是居中定位的，高度一变 `top` 就跟着跑 —— 而搜索框恒在
面板 `top + 106.82`（这条和式在前后两轮都成立：定高版 65.7+106.82=172.52，旧版 75.69+106.82=182.51），
于是**两种命中的关键字之间，搜索框在屏幕上跑了约 112px**，正是用户说的「页面高度会变、（头部）不固定」。

### 2.2 行：压扁 → 自然高度

| 量 | 改前 | 改后 |
| --- | --- | --- |
| 结果行高（14 条，两行内容） | **27px**（`.tree__row` 的 `min-height` 地板） | **43.74px** |
| 行内容高度（`.tree__label`） | **33.74px** → 第二行（完整路径）被裁 6.74px，压到下一行的图标上 | 33.74px，**不再被裁** |
| `.folder-picker` | client 334 / scroll 405（滚动条在，但行已经被压扁） | client 354 / scroll 407 |
| 对照：只命中 3 条（不溢出）时 | 行高 **39.74px**（自然高度，不裁） | — |

根因：`.folder-picker` 就是 `<div class="folder-picker tree">` —— 它**既是列向 flex（`.tree`）又是滚动容器**。
定高之后默认的 `flex-shrink: 1` 会先压缩子项去「塞进」容器高度，而不是让它溢出滚动；
行的 `min-height: 27px` 是压缩的地板，于是两行内容被硬塞进 27px。
修法是一条：`.tree__row { flex: none }`（`app.css`）——**装不下是容器的事**。

### 2.3 搜索结果：顶格 + 命中上色

| 量 | 改前 | 改后 |
| --- | --- | --- |
| `paddingLeft` 的取值集合（14 行） | `19px / 32px / 45px`（照 `depth` 缩进 → 一串互不相干的目录看起来层层嵌套） | **`6px`**（唯一值，全部顶格） |
| `mark.hit` 个数（查「op」） | 0 | **16** |
| 每行的两段 | 名字 + 完整路径（`tree__note-snippet`） | 同左，但名字那行包了 `.tree__label-main`，两行**各自**截断 |

### 2.4 焦点

打开「移动到…」后 `document.activeElement` = `input.field.field--search.folder-picker__search`
（`placeholder="搜索文件夹…"`）—— 「打开就能直接打字」这条没有被我改动碰掉。

## 5. 没验证的部分（不许当 PASS 读）

- **Windows 桌面端（Electron）窗口本身**没有单独跑一遍：本轮核对全部在真实 Chrome + OPFS 笔记本上完成。
  弹窗/下拉都是渲染层的 DOM 与 CSS，两端同一份代码 —— 但「真机 Electron 里的像素」本轮**未量**。
- **`prefers-reduced-motion` / 键盘以外的无障碍**（读屏、`aria-activedescendant`）本轮未测。
  搜索框的 `aria-label`（`搜索文件夹`）、列表的 `role="listbox"` / `role="option"` 与原实现一致。
- **`看过的书/gopl` 这种「只在真路径上命中」的查询不高亮标签**（原因见 §3）是**当前口径**，
  不是「已解决」：要它高亮就得把标签与真路径做一次归一化映射（斜杠两侧的空格），本轮没做。
- **矮窗口（视口高 < 500px）没量**：本轮视口是 1238×730。定高取 `min(600px, 100vh - 96px)`，
  矮窗口下面板变矮、列表照样自己滚（`.dialog__body` 还有一层 `overflow-y: auto` 兜底）——
  这是**推断**，不是实测值。
