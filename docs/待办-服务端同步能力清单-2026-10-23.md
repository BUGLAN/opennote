## 这份文档回答什么

控制台界面早已做好，这轮把支撑它的服务端能力接通了（真实用量、同步活动记账、删账号编排、
设备登记、静态资源修复）。**但仍有若干功能没做或只做了一半。**

每条都标了：**当前状态**、**需要客户端配合吗**、**若需要，客户端要做什么**、**卡在哪**。

## 阅读顺序建议

按「不依赖客户端 → 依赖客户端」排。前半部分我自己就能做完；后半部分必须先改客户端或协议。

## 一、服务端自身可完成（不需要动客户端）

### 1. 设备名显示：用「设备类型 + 设备名」取代「未命名设备」

- **当前状态**：部分实现。服务端能存 `name` / `platform`，但展示层是 `d.name || "未命名设备"`，
  平台列只有「未知 / 桌面端 / Android / 网页端」四档，且平台为空时显示「未知」。
- **需要客户端支持**：**否**（有一个纯服务端兜底方案）。
- **服务端要做什么**：
  - `platformLabel()` 扩展成能识别 `windows` / `macos` / `linux`（即使现在还传不进来，先写好映射）；
  - 组合展示：`platform + name` → 「Windows 设备 · 我的台式机」；只有平台 → 「Windows 设备」；
    都没有 → 按 `deviceId` 稳定派生「设备 dc529c00」（比「未命名设备」有用，且不会随刷新变化）；
  - 改 `/panel` 的设备页与「我的设备」页两处。
- **卡在哪**：无。这是纯展示层改动。
- **注意**：真正的「Windows / Mac」必须由客户端上报，服务端猜不出来（见 4）。

### 2. `upsertDevice` 会用 `NULL` 覆盖已有字段（**这是一个真 bug**）

- **当前状态**：已实现但有缺陷。
  ```sql
  ON CONFLICT(id) DO UPDATE SET name = excluded.name, platform = excluded.platform, ...
  ```
  只要**某一次** checkpoint 不带 `name`，已存的名字就被冲成 `NULL`。
  客户端现在**每次都**不带，所以字段恒为 `NULL`；但一旦客户端开始上报，
  任何一次上报失败/降级（例如拿不到机器名）就会把已有名字擦掉。
- **需要客户端支持**：否。
- **服务端要做什么**：改成「只在传入非空时更新」：
  ```sql
  name = COALESCE(excluded.name, devices.name),
  platform = COALESCE(excluded.platform, devices.platform),
  ```
  并补一条用例：先带 `name` 登记，再不带 `name` 登记，断言名字还在。
- **卡在哪**：无。**建议优先做**，因为它是在给第 4 条铺路。

### 3. 长期不活跃设备的回收策略

- **当前状态**：未实现。控制台只会把 `lastSeenAt` 超过 30 天的标成「30 天未同步」，
  **从不清理**，`devices` 表只增不减。
- **需要客户端支持**：否。
- **服务端要做什么**：定一个保留期（例如 180 天），加一个清理入口（CLI 命令或控制台动作）。
- **卡在哪**：**需要你定策略**——多久算废弃？是否要保留最后一条以便审计？

### 4. `platform` 枚举粒度不足（协议层）

- **当前状态**：部分实现。`shared/contract.ts` 里是 `z.enum(["desktop","android","web"])`。
  `desktop` 无法区分 Windows / macOS / Linux，所以做不出「Windows 设备」。
- **需要客户端支持**：**是**（协议要变，见下一节第 4 条）。
- **服务端要做什么**：放宽为 `desktop | windows | macos | linux | android | web`，
  写一条迁移把历史 `desktop` 保留（不猜成具体系统）。
- **卡在哪**：**协议变更需要客户端同步改**，否则客户端传 `windows` 会被服务端丢弃并降级成 `null`
  （现有代码是白名单判断，非枚举值一律 `null`）。

### 5. `DELETE /v1/notebooks/:id/invites/:codeHash`（撤销笔记本邀请码）

- **当前状态**：**未实现**。§4.7 契约第 1217 行列了这个端点，`notebooks.ts` 里只有
  `POST /notebooks/:id/invites`（生成），**没有对应的撤销**。
  控制台能撤销注册邀请码（`DELETE /v1/admin/invites/:code`），但撤不了笔记本邀请码。
- **需要客户端支持**：**是**（客户端目前连生成笔记本邀请码的 UI 都没有）。
- **服务端要做什么**：补这个端点（校验 owner、幂等、记审计），约 40 行。
- **卡在哪**：补了暂时**没人调用**。要做成可用的功能，客户端需要新增邀请面板（见下一节第 1 条）。

### 6. 协议版本协商只在 `/v1/health` 报，不强制

- **当前状态**：部分实现。`/v1/health` 返回 `protocolVersion` 与 `minSupportedProtocolVersion`，
  但**没有任何一个业务端点校验请求方的版本**。老客户端会一直调到「行为不兼容」才暴露问题。
- **需要客户端支持**：**是**（客户端要在请求里带版本）。
- **服务端要做什么**：读 `X-Opennote-Protocol` 头，低于 `minSupportedProtocolVersion` 就回
  `400 { code: "protocol-unsupported" }`，并带上服务端支持的区间。
- **卡在哪**：**属于契约留白**，双方都没做。要先定「带在头里还是 query 里」。

### 7. 逐条文件级同步记录（**按设计不做**）

- **当前状态**：不做，且**不应做**。
- **原因**：E2EE 下服务端连明文路径都没有（红线 3），模式 B 连 `did` 都是密文标识。
  能记的只有「某账号在某库某天拉/推/冲突/错了几次」。
- **需要客户端支持**：否。
- **卡在哪**：这是红线，不是待办。列在这里是为了**下次不要再尝试**。

## 二、需要客户端给予支持

### 1. 笔记本邀请与成员管理的 UI（整块缺失）

- **服务端现状**：**已就绪**。`POST /v1/notebooks/:id/invites`、`GET /v1/notebooks/:id/members`、
  `POST /v1/notebooks/join` 都在，`cryptoMode != none` 时生成邀请码会按契约回 409。
  缺的只有撤销（上一节第 5 条）。
- **客户端现状**：`src/sync/accountApi.ts` 只暴露 `listNotebooks` / `createNotebook`；
  `SyncDialog.tsx` 只有「新建远端笔记本」一个动作。**没有加入、没有邀请、没有成员列表、没有删除**。
- **客户端要做什么**：
  1. `accountApi.ts` 补 4 个方法：`createInvite` / `revokeInvite` / `listMembers` / `joinNotebook`；
  2. `SyncDialog.tsx` 加一块「成员与邀请」：成员列表 + 生成邀请码（选角色/次数/有效期）+ 撤销；
  3. 生成的邀请码**只显示一次**（服务端只存哈希），要提醒用户当场复制。
- **卡在哪**：需要你确认「这一版要不要做多人协作」。不做的话服务端那几个端点就是给未来留的。

### 2. 设备上报 `platform` 与 `name`（**这是「Windows 设备」的唯一来源**）

- **服务端现状**：**已经能收**。`PUT /v1/checkpoint` 的请求体里读 `name`（截断 120 字）与
  `platform`（白名单三值）。**不需要任何服务端改动**（除第 4 条的枚举扩展）。
- **客户端现状**：`src/sync/providers/opennote.ts:296` 的请求体是
  ```ts
  JSON.stringify({ deviceId: this.deviceId, cursor })
  ```
  **只发这两个字段**。而且 `src/sync/` 下**完全没有平台判定代码**
  （grep 不到 `process.platform` / `navigator.platform`）。
- **客户端要做什么**（比看上去多，因为渲染进程在沙箱里）：

  ⚠️ **关键约束**：桌面端的渲染进程是 `contextIsolation: true` / `nodeIntegration: false` /
  `sandbox: true`（`electron/main.cjs:13`），**`src/sync/` 里读不到 `process.platform`**。
  而 `src/sync/` 是**三端共用**的同一份代码。所以必须走 IPC 桥，不能就地 `require('os')`。

  1. **主进程**：加一个 `opennote:app:deviceInfo` 处理器，返回
     `{ platform: process.platform, hostname: os.hostname() }`（拿不到 hostname 就 `null`，不要编）；
  2. **preload**：按现有 `opennote:<group>:<op>` 命名约定暴露一个 `getDeviceInfo()`；
  3. **渲染进程**：`src/sync/` 加 `describeThisDevice()`：
     - 桌面：调 preload 桥，`win32→windows` / `darwin→macos` / `linux→linux`；
     - Android（Capacitor）：固定 `android`；
     - 网页：固定 `web`；
     - **桥不可用时**（网页、或 preload 没接上）返回 `{ platform: null, name: null }`，**不要猜**；
  4. `checkpoint()` 的请求体带上这两个字段。

  **涉及文件**：`electron/main.cjs`、`electron/preload.cjs`、`src/sync/device.ts`（或新建）
  `src/sync/providers/opennote.ts`，外加 `electron/verify-contract.cjs` 的通道配对检查。
  工作量从「约 20 行」上调为 **半天左右**（主要是 IPC 与三端分支）。
- **卡在哪**：客户端改动。**如果你希望「不改客户端」，那就只能走第一节第 1 条的兜底显示**
  （显示「设备 dc529c00」而不是「Windows 设备」）。

### 3. `POST /v1/stats`（客户端上报按天计数）

- **服务端现状**：**已就绪，且已经不需要它了**。
  这轮新增了 `sync_activity`，服务端在 `/v1` 数据面上**自己数**拉/推/删/冲突/错，
  `/panel/api/stats` 会把两个来源按天取较大值合并。所以页面上现在有真实数据。
- **客户端现状**：从不调用。
- **客户端要做什么**：**建议不做**。理由：服务端的观测不会撒谎（它数的是自己收到的请求），
  客户端自述反而可能漏报或重复报。留着这个端点给「客户端才知道的信息」用即可（目前没有这种信息）。
- **卡在哪**：无。**建议明确决定「不做」并写进契约，避免以后有人以为漏了。**

### 4. `platform` 枚举扩展（协议变更，需两端同步）

见第一节第 4 条。**客户端要做什么**：
- 上报时按新枚举传值（`windows` / `macos` / `linux` / `android` / `web`）；
- 若有本地缓存了旧的 `desktop`，展示层要能同时识别新旧值。

**服务端要做什么**：放宽 `platformSchema`、加迁移、保留旧值兼容。

**卡在哪**：`shared/contract.ts` 是两端共享文件，**必须同时发版**，否则一端认不出另一端。

### 5. `POST /v1/devices` 独立登记端点

- **服务端现状**：已实现（`notebooks.ts`），但**实际没人调用**。
  设备现在是靠 `PUT /v1/checkpoint` 顺带登记的（客户端每次同步都会打它）。
- **客户端要做什么**：**不需要**。
- **卡在哪**：无。这个端点可以保留，不必要求客户端用。

## 四、建议的推进顺序

1. **先做**：第一节第 2 条（`upsertDevice` 的 `COALESCE`）—— 真 bug，且是设备上报的前置；
2. **再做**：第一节第 1 条（兜底显示）—— 纯服务端，能立刻改善截图里那台设备的观感；
3. **然后**：第二节第 2 条（客户端上报 `platform`/`name`）—— 这是「Windows 设备」的唯一来源。
   **注意它需要 IPC 桥**（渲染进程在 sandbox 里，读不到 `process.platform`），
   涉及 `electron/main.cjs` + `preload.cjs` + `src/sync/`，约半天；
4. 接着：第一节第 4 + 第二节第 4 条（枚举扩展，两端同步发版）；
5. 视需求：第一节第 5 条 + 第二节第 1 条（笔记本邀请与成员管理，整块功能）；
6. 最后：第一节第 6 条（协议版本强制）、第一节第 3 条（设备回收策略，需你先定规则）。

## 五、本轮明确没做的事（如实标注）

- 没有真机验证客户端上报（客户端目前根本不发 `platform`/`name`，无从验证）；
- 没有定设备回收策略（需要产品决策）；
- 没有做笔记本邀请的 UI 与撤销端点（取决于「这一版要不要多人协作」）；
- 没有强制协议版本（属于契约留白，需两端一起定）；
- 没有清理历史 `quota_usage` 列（已绕过，删它需要迁移，收益低）。
