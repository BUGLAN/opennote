## 0. 一页速览

### 0.1 架构一句话

> **出站隧道 → Node（唯一公网服务：密钥鉴权 + API + 控制台 + PWA）→ CouchDB（仅内网，一笔记本一库）。**
> **身份 = 一条客户端生成的密钥**；没有用户名、没有口令、没有登录。
> **客户端默认端到端加密**：服务端只存密文与「用密钥包起来的加密根」。
> 客户端保留「文件是唯一真源」：本地 `.opennote/` 存基线，用现有 `planPush` / `planPull` 纯函数做三方 diff。

### 0.2 组件与职责（**3 个容器**）

| 容器 | 角色 | 存什么 | 公网可达 |
| --- | --- | --- | --- |
| `tunnel` | 公网入口（出站连接，当前 cloudflared） | 无 | ——（它往外连） |
| `sync`（Node/TS） | **唯一公网服务**：密钥鉴权、`/v1/*`、`/panel` 控制台、PWA 静态、CouchDB 适配、SSE 中继、配额 | SQLite：`accounts`（**无口令、无用户名**）/`invites`/`devices`/`notebooks`/`memberships`/`quota`/`audit` | ✅ 经隧道 |
| `couchdb` | 数据面 | 一笔记本一库；一文件一文档 + 附件（**E2EE 时全是密文**） | ❌ **完全不发布端口** |
| **客户端**（`src/sync/*` 新增） | 收敛决策的唯一权威 + **密钥的唯一持有者** | 本地文件 + `.opennote/sync.json` 基线 + **账号密钥** | —— |

### 0.3 阶段与工作量

| 阶段 | 内容 | 估时 |
| --- | --- | --- |
| **P0** | 五条跨设备正确性前置（纯客户端） | 2–3 天 |
| **P1** | 抽 `SyncProvider` + `SyncEngine` + **忽略规则**（内置集 + `.gitignore`）；纯 diff 函数从 `src/lib/github/` 提到 `src/sync/diff.ts`；**建 `shared/`**（路径纯函数 + 契约类型 + 夹具）；新增 `sync.json` 账本 | 2–4 天 |
| **P2** | **建 `server/`** + 服务端骨架 + **密钥即身份**（账号/引导码/邀请码/设备登记/成员授权/配额）+ CouchDB 适配 + `/v1/*` + 控制台 + CLI + compose + 隧道 + 客户端 `opennote` provider + Onboarding + 自动同步 | **8–11 天** |
| **P3** | SSE 实时（Node 中继 + 可配心跳；桌面走主进程；移动回前台） | 3–4 天 |

> P2 比上一版**少了 2–3 天**：没有口令哈希、没有登录接口、没有会话表、没有撞库防护。
> P1 因为多了一条「忽略规则」而略增（+0.5–1 天），但**它同时消灭了 watcher 那条 P0 待办**（§3.11）。

### 0.4 八条不可违反的红线

1. **文件是唯一真源**（`docs/architecture-overview.md:16`）。不引入 CRDT，不引入「第二个真源」的本地数据库。
2. **不在 Node 里重造 CouchDB 的语义**——`_rev` CAS、leaf 冲突保留、`_local` 检查点、单调 cursor
   全部来自 CouchDB；Node 只做**鉴权 + 翻译 + 控制台**（§4.2 执行清单）。
3. **账号密钥与 `encRoot` 只由客户端生成，且永不发给服务端。**
   服务端只存 `sha256(authToken)` 与 `wrappedEncRoot`。（**这条一破，E2EE 就是假的**——§1.5）
4. **授权的唯一真源是服务端的成员表**（`memberships`）。**不要**把 ACL 镜像进 CouchDB `_security`（§4.4）。
5. **绝不静默覆盖**：两边都改 → 列出等裁决；内容已相同 → 不算冲突。
6. **CouchDB 不进公网**：不发布端口、不给它隧道 hostname。
7. **删除只能由「远端显式说它删了」触发**，不能由「我列的树里没有它」触发（§6.4）。
8. **同步范围只由忽略规则定义，且被忽略的路径双向不可见**——不 push、不 pull、不删、不参与 diff；
   **内置忽略集（`.git/`、`.opennote/` 等）不可被 `.gitignore` 取反**（§3.11）。

## 1. 决策

### 1.1 三个组件的存在理由

| 组件 | 只有它能做 | 依据 |
| --- | --- | --- |
| **CouchDB** | revision tree 冲突保留 · `_local` 检查点 · `_changes` 增量与推送 · 服务端 `validate_doc_update` | 上游结论「它一次解决了增量、检查点、实时推送、冲突四件事」（`多端实时同步技术栈调研.md:72`） |
| **Node** | **账号与授权** · 邀请码 · 配额 · **控制台** · SSE 心跳规范化 · 备份作业 | CouchDB 没有「账户」这一层，也不该有 |
| **出站隧道** | **零入站端口**拿到 HTTPS 公网入口 | 宿主机可在家宽/NAT 后。**当前是 CF 命名隧道，架构不依赖它**（§2.5） |

### 1.2 为什么「多用户」必须现在就做（不能后补）

**这是 v4 就定下的判断，本版继续沿用。** 后补多用户的代价不是「加一张表」：

| 如果先做单用户 | 现在做多用户 |
| --- | --- |
| 笔记本 id 用「用户自取的 slug」→ **改成分离的 `db_name` 要迁移全部库** | `db_name = nb-<uuid>`，**一开始就不透明** |
| 授权散落在「对不对得上硬编码的 owner」里 → 要逐个端点重写 | 授权集中在 `memberships` + 一个中间件 |
| 客户端「配对」流程要重做 | 一次设计到位 |
| 加密密钥没有归属概念 | `crypto_mode` 挂笔记本，`encRoot` 挂账号（§3.9） |

**结论：P2 直接做成多用户**，不做「先单用户再重构」的中间态。

### 1.3 入口不绑定 Cloudflare

你明确了「不绑定 cf」。落实为四条约束：

| 约束 | 做法 |
| --- | --- |
| **不使用 CF Access / Zero Trust** | 鉴权完全自持（密钥即身份，§1.5） |
| **心跳不写死 CF 的 125s** | `SSE_HEARTBEAT_MS` **配置项**，默认 25000 |
| **不硬编码 `CF-Connecting-IP`** | `TRUSTED_PROXY_HEADERS` **配置项**，默认**空**（谁都不信） |
| **隧道可替换** | compose 里 `tunnel` 只是一个容器；换 `frp` / `Tailscale Funnel` / 自建反向代理只改这一个服务 |

**顺带简化**：不用 Access 之后**只需要一个 hostname**——`/` 给 PWA、`/v1/*` 给客户端、`/panel` 给控制台，
全部同源 → **CORS 不用配、网页版 CSP 不用改**。

> **当前入口（CF 命名隧道）的已知限制**——**实现细节，不是架构约束**，换隧道即失效：
> - **Proxy Read Timeout = 125 秒**（[官方 524 文档](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)）→ 心跳必须远小于它 → 默认 25s。
> - **Proxy Write Timeout = 30 秒，不可调** → 单次上传（含 base64 附件）要在 30s 内推完 → 文件上限留余量（U18）。
> - **必须用命名隧道**：Quick Tunnel 会把 SSE **攒到连接关闭才发**。CF 维护者在
>   [cloudflared#1449](https://github.com/cloudflare/cloudflared/issues/1449) 明确：
>   *"It works as expected with **named tunnels** … quick-tunnels are only meant for demo purposes."*

### 1.4 E2EE 的工作量（**结论：做**，约 2.5–4 天）

| 块 | 内容 | 工作量 |
| --- | --- | --- |
| **A. 密钥派生** | `accountKey` → HKDF → `{authToken, wrapKey}`；`encRoot` 的包裹与解开 | **小（0.5 天）** |
| **B. 内容加解密** | AEAD（内容 + 附件）；AAD 绑定 `did`/`accountId` | **小（0.5 天）** |
| **C. 密文元数据** | `ehash = HMAC(macKey, sha256(plaintext))`；`esize` | **小（0.25 天）** |
| **D. 路径加密** | `did = "h:" + HMAC(idKey, NFC(path))` + **本地 `did↔path` 映射** | **小（0.5 天）** |
| **E. 列树改造** | 模式 B 用 `_all_docs?include_docs=true` | **小（0.25 天）** |
| **F. 密钥导入导出** | 复制 / `.key` 文件 / **二维码**；新设备导入 | **小（0.5 天）** |
| **G. 两种模式并存 + 测试** | 往返、错密钥、篡改、跨文档搬运密文、模式混用 | **中（1 天）** |

**总计 ≈ 2.5–4 天。而且比上一版更简单**——因为「加密根装进账号密钥」之后：

- **不再需要 Argon2id**（慢 KDF 只为对抗低熵口令；`accountKey` 是 256 位随机，不需要）。
- **不再需要单独的加密口令**，网页端也不再「每次刷新重输口令」（只要密钥在本机）。
- **Apple/Android 的密钥串行化问题消失**（不再有「口令」这个概念要保管）。

**我修正了上一版一个过高的估计**：v3 说模式 B「列树变贵」。实测不是：

| | 模式 A（明文路径） | 模式 B（加密路径） |
| --- | --- | --- |
| 列树方式 | view 查询 | `_all_docs?include_docs=true` |
| 每篇字节 | ~30 B | ~200 B |
| 3000 篇一次全树 | ~90 KB | **~600 KB** |

→ 差的是一次全树比对多传 **~0.5 MB**，且**增量同步完全不受影响**。这不是「变贵」，是「多传半兆」。

**明确排除在 v1 之外**：**共享笔记本的 E2EE**（要把同一笔记本的密钥安全发给多个账号 → 公钥体系 + 每成员密钥封装，
参考 Joplin 的 PPK，**约 1–2 周**）。
> **v1 规则：`crypto_mode != 'none'` 的笔记本不可共享**（服务端直接拒绝加成员，返回 409）。
> 要共享就建明文笔记本。**这条要写进 UI 文案，不能只写在文档里。**

### 1.5 身份模型：**密钥即身份**（本版核心）

#### 为什么这比 username + password 更适合这里

| | username + password | **密钥即身份** |
| --- | --- | --- |
| 弱口令 | 用户会设 `123456` | **不存在**（密钥是 256 位 CSPRNG） |
| 撞库 / 离线爆破 | 需要慢 KDF + 限流 + 加盐 | **不存在**（2²⁵⁶ 空间） |
| 用户名枚举 | 要小心统一文案与恒定响应时间 | **不存在**（没有用户名） |
| 服务端存什么 | 口令哈希（**一个必须保护的资产**） | `sha256(authToken)`（**泄露也无法反推**） |
| 口令重置 | 要设计邮件/工单 | **没有重置**（这正是 E2EE 的定义） |
| 代码量 | 哈希、登录、会话、限流、重置、枚举防护 | 生成、比对、轮换 |

#### 密钥层级（**必须这样分叉，否则 E2EE 是假的**）

```
账号密钥 accountKey    32B CSPRNG，★ 客户端生成，★ 永不发给服务端
   │                    （用户保存的唯一秘密）
   │ HKDF-SHA256(salt = accountId, info = "opennote/v1/…")
   ├── info="auth"  →  authToken   → 唯一发给服务端的东西
   │                                 （服务端只存 sha256(authToken)）
   └── info="wrap"  →  wrapKey     → ★ 永不外发，只用来解开 encRoot

encRoot   32B CSPRNG，注册时客户端生成一次，★ 永不外发
   └── AEAD(wrapKey, encRoot, aad = accountId)  =  wrappedEncRoot
                                                  → 存服务端（服务端解不开）

encRoot
   └── HKDF(info = "notebook/" + notebookId)  →  notebookKey（每笔记本一把）
          ├── info="enc" → 内容与附件
          ├── info="mac" → ehash（内容等价类）
          └── info="id"  → 路径 HMAC（did）
```

**为什么必须有 `auth` / `wrap` 这个分叉**：

> `authToken` 和 `wrapKey` 都由 `accountKey` 经 HKDF 导出，但**互相推不出来**（HKDF 的输出在计算上独立）。
> 所以服务端——**以及终结 TLS 的云边缘**——拿到 `authToken` 也拿不到 `wrapKey`，
> 解不开 `wrappedEncRoot`，拿不到 `encRoot`。**E2EE 成立。**
>
> **反例（一定要避免）**：如果直接把 `accountKey` 当令牌发出去，服务端就拿到了它 →
> 它同时是加密根 ⇒ **服务端能解开全部笔记，E2EE 名存实亡**。

**为什么不需要 Argon2id**：慢 KDF 的唯一目的是对抗**低熵输入**（人类口令）。
`accountKey` 是 256 位 CSPRNG，`sha256(authToken)` 无法离线爆破 →
`wrappedEncRoot` 安全 ⇒ **HKDF 足够，不需要慢 KDF**。这直接砍掉一个依赖（§4.9）。

#### 三个流程

**① 注册（客户端生成一切）**

```
客户端：
  1. 生成 accountId  (16B 随机，公开)      ← 客户端生成，所以可以当 HKDF salt / AAD
  2. 生成 accountKey (32B 随机，秘密)
  3. 生成 encRoot    (32B 随机，秘密)
  4. authToken  = HKDF(accountKey, salt=accountId, info="auth")
     wrapKey    = HKDF(accountKey, salt=accountId, info="wrap")
     wrappedEncRoot = AEAD(wrapKey, encRoot, aad=accountId)
  5. POST /v1/account
       { accountId, authToken, wrappedEncRoot, inviteCode }
服务端：
  6. 校验邀请码（未过期 / 未用尽 / 未作废）
  7. 存 accounts(accountId, auth_hash=sha256(authToken), wrapped_enc_root)
  8. 消耗邀请码
客户端：
  9. ★ 立刻把 accountKey 交给用户保存（复制 / 下载 .key / 二维码）
     —— 并强制「我已保存」确认，否则不给进下一步
```

**② 新设备（一个秘密搞定）**

```
用户导入 accountKey（粘贴 / 打开 .key / 扫二维码）
  → 客户端派生 authToken + wrapKey
  → POST /v1/account/unlock { }  （带 Bearer authToken）
  → 服务端返回 { accountId, wrappedEncRoot }
  → 客户端用 wrapKey 解开 → 得到 encRoot
  → 完成。不需要第二样东西。
```

**③ 轮换（你要的「旧密钥废弃、新密钥生成」）—— 零重加密**

```
客户端：
  1. 生成新的 accountKey'
  2. 派生 authToken' 与 wrapKey'
  3. wrappedEncRoot' = AEAD(wrapKey', encRoot, aad=accountId)   ← encRoot 不变！
  4. POST /v1/account/rotate          （用【旧 authToken】认证）
       { authToken', wrappedEncRoot' }
服务端：
  5. 一个事务里替换 auth_hash 与 wrapped_enc_root
  6. 旧 authToken 立即失效
```

**零重加密**：因为 `encRoot` 没变，只换了「包着它的壳」。
这是本设计最漂亮的一点——如果把加密根直接绑在密钥上，轮换就得**重新加密整个笔记本库**，
还要在多设备间协调，中途失败极难收拾。

#### 这条路线砍掉的东西（比预想的多）

| 砍掉 | 为什么 |
| --- | --- |
| `password_hash` + scrypt | 没有口令 |
| 登录接口、`sessions` 表 | **令牌本身就是身份** |
| 用户名 / 邮箱 / 枚举防护 | 没有用户名 |
| 撞库限流那一整套 | 2²⁵⁶ 空间无法爆破（只留全局限流防 DoS） |
| **Argon2id**（慢 KDF） | 不需要慢 KDF（`accountKey` 是 256 位随机）。**但仍引入 `@noble/hashes` 做 HKDF/HMAC**（§4.9） |
| 「登录口令 ≠ 加密口令」这条红线 | 升级成更彻底的 HKDF 分叉，同一目的 |
| 口令重置 / 找回流程 | 没有可重置的东西 |
| **离机备份能力**（服务端作业 + 客户端 GitHub 入口） | 已定：**不提供**，由用户自理（§4.10） |

#### 三条要接受的代价（**如实列出**）

1. **密钥丢失 = 账号与数据一起永久消失。** 没有找回、没有重置、**服务端也帮不了你**
   （它从来没存过密钥）。
   → UI 必须强制「已保存」确认，并提供**复制 / `.key` 文件 / 二维码**三种方式。
   → **控制台「我的账号」页必须明说：密钥只能从已有设备导出，服务端无法补发。**
2. **轮换会让其它设备立刻掉线**（它们手上还是旧 `authToken`）。
   这是「一个密钥 = 一个账号」的固有结果，不是缺陷。
   → 客户端收到 401 时要给明确文案：「此设备的密钥已被轮换，请导入新密钥」，
   而不是含糊的「登录失效」。
3. **无法单独吊销某一台设备**（没有每设备凭据）。
   → 唯一手段是**轮换账号密钥**。控制台的设备列表因此是**只读账本**，不带「踢掉」按钮。
   这一点要在控制台写清楚，不能让用户以为有个不存在的按钮。

#### 邀请码（注册始终只能靠管理员生成）

你说「始终只能靠管理员生成邀请码」。**这带来一个必须先解决的鸡生蛋问题**：

> **第一个管理员从哪来？** 而这里有个**很容易踩的坑**：
> **CLI 如果顺手生成了管理员的账号密钥，服务端就知道了它 → 管理员自己的笔记本 E2EE 直接失效**
> （恰恰是最该保护的那个账号）。

**正确做法：CLI 只发一次性引导码，密钥永远由客户端生成。**

```
首次部署（鸡生蛋的解法）：
  1. docker compose exec sync node dist/cli.js bootstrap-admin
     → 打印一个一次性「管理员引导码」（只在控制台标准输出出现一次，不写日志、不落盘）
  2. 用户在自己的客户端用它「创建管理员账号」
     → ★ 客户端生成 accountId / accountKey / encRoot（CLI 从不接触密钥）
     → 该账号被标记 is_admin
  3. 之后：注册入口【完全关闭】；所有新账号只能凭管理员在控制台生成的邀请码
  4. 管理员密钥若丢失 → 用同一个 CLI 再发一次引导码，创建新的管理员账号
     （旧的可以留着或删掉；★ 旧账号的数据不会因此可读）
```

**另外**：注册接口在**没有有效邀请码时一律拒绝**，与「有没有账号」无关——
即**不存在「首次注册自动成为管理员」这条路径**（那会被抢注）。

**笔记本共享也不需要用户名**：owner 生成**一次性笔记本邀请码** → 对方用自己的账号 + 该码加入。
（`crypto_mode != 'none'` 的笔记本直接 409，§1.4。）

### 1.6 仓库结构：**单仓**，服务端放 `server/`

> 已定：**单仓**。客户端与现有代码保持在 `E:\repo\opennote`；
> **服务端新建在该仓库的 `server/` 目录下**（目录名就叫 `server`）。

#### 为什么回到单仓（这条决定是被一次「试了分仓」反推出来的）

本文档曾短暂设计为分仓（客户端 `opennote` + 服务端 `opennote-service`）。
分仓能成立，但要靠**四件套**才达到同等保证：契约包 `@opennote/contract` + 精确版本钉死 +
两仓都跑共享夹具 + 运行期 `protocolVersion` 闸门。而它**同时引入了分仓独有的新问题**：

| 分仓带来的问题 | 单仓是否还有 |
| --- | --- |
| **跨仓类型漂移**（原来的「同仓」护栏没了，漂移变成需要显式防的头号风险） | ❌ 没有——**两端直接 import 同一份纯 TS** |
| **需要发布/维护一个契约包**（私有 registry 或 git tag 依赖 + 版本纪律） | ❌ 不需要 |
| **PWA 产物交接**：客户端打包带 sha256 的发布产物 → 服务端镜像下载并校验 | ❌ 不需要——**同仓构建时直接产出 `dist/`** |
| **产物与镜像版本错配** | ❌ 不存在 |
| **破坏性改动要跨仓协调两个 PR** | ❌ 一个 PR 原子改两端 |
| 契约夹具作为「唯一能自动发现漂移的机制」 | ⚠️ **仍然需要**，但用途收窄了（见下） |

**一句话**：分仓买到的是「物理隔离」，付出的是「一整套跨仓协调机制」。
对这个规模的项目，**目录规则 + 一条 CI 检查**比「两个仓库」便宜得多。

#### 目录结构

```
E:\repo\opennote\

├── server/               # ★ 服务端（新）
│   ├── src/
│   │   ├── index.ts  config.ts  db.ts  couch.ts  quota.ts  cli.ts
│   │   ├── auth/     key.ts  rotate.ts  invite.ts  guard.ts

│   └── Dockerfile
```

#### 三层边界规则（**这个替代了「物理分仓」**）

| 目录 | 可以 import 什么 | 不可以 |
| --- | --- | --- |
| `src/`（客户端） | `shared/` | ❌ **不可** import `server/` |
| `server/`（服务端） | `shared/` | ❌ **不可** import `src/` |
| `shared/` | 只依赖标准 ES | ❌ 谁都不 import（**没有 DOM、没有 Node 内建**） |

**四条把边界机械化的做法**（否则「目录规则」只是一句口头约定）：

1. **`shared/tsconfig.json` 用 `"lib": ["ES2022"]` 且不配 `types`**
   → 在 `shared/` 里写 `document`/`window`/`import fs from "node:fs"` **直接编译不过**。
   这是「共用代码必须是纯函数」的**强制保证**，不是靠自觉。
2. **`server/tsconfig.json` 用 `types: ["node"]` 且 `lib: ["ES2022"]`**（**没有 DOM**）
   → 服务端代码里用 `window` 编译不过。
3. **`server/` 不进前端构建**：客户端 `tsconfig.json` 的 `include` 是 `["src", …]`，
   Vite 入口是根 `index.html` → **`server/` 天然不会被收进去**（§5.6）。
4. **加一条 CI 检查**：`server/` 里不出现 `from "../src/`，`src/` 里不出现 `from "../server/`。
   这条是**唯一**需要人工维护的边界守卫，成本一行 grep。

#### 共享夹具仍然需要（但用途收窄了）

**为什么还需要**：CouchDB 的 `_design/opennote` 里的 `validate_doc_update` 与 `by_path`
是 **CouchDB 内部 JS 引擎**里的代码——**它既不能 import `shared/`，也不是 TS**。
所以路径规则**在服务端侧仍然必须写两份实现**（`shared/paths.ts` 的 TS 一份 + `_design` 的 JS 一份）：

| | v7（分仓） | **本版（单仓）** |
| --- | --- | --- |
| 路径规则实现份数 | **三份**（客户端 TS + 服务端 TS + `_design` JS） | **两份**（`shared/` 的 TS + `_design` JS） |
| 靠什么保证一致 | 契约包夹具，两仓 CI 都跑 | **`shared/fixtures/path-rules.cases.json`**，驱动两份实现各自的测试（§10.1 F） |
| 线上形状一致性 | 契约包夹具 + 版本钉死 | **同仓 import 就够**；夹具作为「行为样本」的补充 |

→ 夹具从「防跨仓漂移的基础设施」降级为「**防 TS ↔ CouchDB JS 这一个接缝**的工具」。
它仍然必须存在（`_design` 那份 JS 无法被类型系统覆盖），但**不再承担跨仓协调的职责**。

#### 仍然保留的两条纪律（与分仓无关，本来就该有）

1. **`PROTOCOL_VERSION` 运行期闸门**：`/v1/health` 与 `syncinfo` 都带它；
   客户端**不匹配就拒绝同步并提示升级**。
   原因不是「两仓版本错配」，而是**用户机器上装着旧客户端**——这跟仓库怎么分无关。
2. **契约类型只有一处定义**：`shared/contract.ts`。**`server/` 与 `src/` 都 import 它，不要复制**。

### 1.7 明确不引入的东西

CRDT · 纯 P2P · 内容寻址 chunk 仓库（SiYuan/dejavu 模型）· 第二个真源（PouchDB 本地库）·
自建反向代理（当前用出站隧道）· 自研复制协议（`/v1/*` 是**适配层契约**）· **用户名 / 口令 / 邮箱 / OAuth / SSO** ·
**共享笔记本的 E2EE**（§1.4）· 账号找回流程（§1.5）· **离机备份**（服务端与客户端都不提供，§4.10）。

### 2.2 一次「桌面改一篇 → 网页端出现」的完整时序（E2EE 开启时）

```
桌面端                                          网页端
  │ 用户编辑 notes/a.md（明文在磁盘上）
  │ flushNote() 落盘（450ms 防抖，现有逻辑）
  │
  │ ── Crypto 层（只有这里认识明文）──
  │ nk     = HKDF(encRoot, info="notebook/"+notebookId)
  │ ct     = AEAD(nk.enc, plaintext, aad = did)
  │ ehash  = HMAC(nk.mac, sha256(plaintext))     ← 不给服务端看「内容是否相同」
  │ did    = "h:" + HMAC(nk.id, NFC(path))       ← 不给服务端看路径
  │
  ├─(1) PUT /v1/file?nb=<notebookId>&did=<urienc did>    ← 只传 did，不传明文 path
  │      Header: Authorization: Bearer <authToken>
  │              If-Match: <ehash>
  │      body: <ct 原始字节>
  │      │
  │      └─ Node：查 sha256(authToken) → accountId
  │              → 查 memberships(notebookId, accountId) 角色够不够
  │              → 转成 CouchDB PUT /nb-<uuid>/<did>?rev=<baseRev>
  │      ← 200 {ehash, rev} | 409 | 412
  │
  ├─(2) 更新 .opennote/sync.json（每路径 ehash + rev + did）
  │
  └─(3) PUT /v1/checkpoint { nb, cursor }
                                                  │
                                                  │ (4) 网页端挂着 EventSource /v1/events?nb=...
                                                  │     Node 订阅 CouchDB _changes 并转成 SSE
                                                  │     心跳 ≤ SSE_HEARTBEAT_MS（默认 25s）
                                                  │◄── event: change
                                                  │    data: {"cursor":"7-...","dids":["h:..."]}
                                                  │
                                                  ├─(5) 收到信号 → dirty → 跑一次正常同步
                                                  ├─(6) GET /v1/changes?nb=..&since=<cursor>
                                                  ├─(7) GET /v1/file?nb=..&did=h:...   ← 密文字节
                                                  │
                                                  ├─(8) 解密 → 用本地 did↔path 映射写盘
                                                  └─(9) applyExternalPaths([...])
                                                        → UI 只刷新变化的篇
```

**注意三处容易忽略的地方**：

- **(1)(7) 客户端不传明文路径**，只传 `did` → **客户端必须自己维护 `did → path` 的本地映射**
  （存 `.opennote/`，**不跨端**；新设备通过全树解密重建）。这是 E2EE 的真实代价之一。
- **(9) UI 刷新必须显式驱动**：`electron/main.cjs:712` 的自写过滤会吞掉 watcher 事件
  （现有 GitHub 拉取就是靠 `rescanWorkspace()` 绕开的，`src/App.tsx:868,880`）。
- **服务端全程看不到**：明文路径、明文内容、甚至「两篇内容是否相同」。

### 2.3 数据面：客户端只说 `/v1/*`，永不接触 CouchDB

| | **已定：Node 做数据面** | 否决：客户端直连 CouchDB |
| --- | --- | --- |
| **多账号隔离** | ✅ 一个中间件统一强制 | ❌ 要靠 CouchDB `_security` 逐库配 |
| 鉴权 | 密钥即身份，**可轮换** | CouchDB 账号，无法自动过期 |
| 路径参数 | 走查询参数 → **`%2F` 问题根本不存在** | 路径进 `_id`，要处理 `%2F` |
| E2EE | ✅ 服务端只做密文搬运，天然不碰密钥 | ⚠️ 服务端策略无处落地 |
| 主要风险 | **在 Node 里重造 CouchDB**（红线 2） | 加固 + 多租户隔离都难做 |

### 2.4 只需一个 hostname

| 路径 | 谁用 | 鉴权 |
| --- | --- | --- |
| `/` | PWA 静态 | 无（页面公开，数据要密钥） |
| `/v1/*` | 三端客户端 | `Authorization: Bearer <authToken>` |
| `/panel` | 人（浏览器） | 同一个 `authToken`（HttpOnly cookie） |
| `/v1/events` | 三端客户端（SSE） | `authToken`（query 参数或 cookie） |

**同源带来三个免做项**：**不做 CORS**、**不改网页版 CSP**（`'self'` 已覆盖）、**不需要第二个 hostname**。

### 2.5 隧道配置（当前实现：CF 命名隧道）

```yaml
tunnel:
  image: cloudflare/cloudflared:latest
  restart: unless-stopped
  command: tunnel --no-autoupdate run
  environment:
    TUNNEL_TOKEN: ${TUNNEL_TOKEN:?}

```

| 配置项 | 值 |
| --- | --- |

但**域名与合规仍要你自行确认**。

## 3. 数据模型

> **为什么这一节重要**：上游调研写着「CouchDB 的详细设计另存 `设计-CouchDB同步-2026-10-13.md`」，
> 但该文件**三处被引用、实际不存在**（`三端同步…:352,425`、`选型…:180`）。
> 且两份支撑调研**完全没覆盖** `_changes`、版本约束、409 处理、附件存储、多租户隔离。
> 本节与 §4、§7、§8 一起补上。

### 3.1 库的划分：一笔记本一库，库名不透明

```
db_name = "nb-" + uuid_v4（去掉连字符）
例：nb-9f2c4a7e8b1d4c6fa3e5071b2d8c4e6f
```

- **不透明**：不能枚举或猜别人的库（多账号下基本要求）。
- **稳定**：改笔记本名不动库名。
- **不冲突**：跨账号天然唯一。
- 库名**不由用户输入**，只由服务端生成。

**容量提醒**：CouchDB 每个库有自己的分片文件与视图索引。
本地笔记量级（几十~几百笔记本）没问题，但**库数量是最需要早测的一项**（U22：100/500/1000 库下的内存、句柄、启动时间）。
退路是「一账号一库 + 笔记本作为文档属性」——但那会让 `_changes` 推全部笔记本的变更，**是明确降级**，不到万不得已不做。

### 3.2 每库的固定文档

| 文档 | 内容 | 作用 |
| --- | --- | --- |
| `_design/opennote` | `views.by_path`（**仅模式 A 可用**）、`validate_doc_update` | 列树投影 + **服务端第二道防线** |
| `_local/device-<deviceId>` | `{cursor, deviceId, at}` | 每设备检查点（**不参与复制、不进 `_changes`**） |
| `syncinfo` | `{protocolVersion, cryptoMode, createdAt}` | **协议与加密模式校验**：不匹配就拒绝同步 |
| `_security` | 只有 `sync` 的服务账号 | **纵深防御**（不是 ACL 真源，§4.4） |

> `protocolVersion` / `cryptoMode` **不匹配就拒绝同步**，而不是「尽力而为」（LiveSync 纪律）。

### 3.3 `_id` 方案：**每笔记本按 `crypto_mode` 选一种**

| | **模式 A（`crypto_mode='none'`）** | **模式 B（`crypto_mode='user-key'`，E2EE）** |
| --- | --- | --- |
| `_id` | `"f:" + base64url(NFC(path))` | `"h:" + hex(HMAC(idKey, NFC(path))).slice(0,32)` |
| 服务端能否看到路径 | ✅（文档 `path` 字段） | ❌ |
| 列树 | view `by_path`（~30 B/篇） | `_all_docs?include_docs=true`（~200 B/篇） |
| 可用于共享 | ✅ | ❌ **v1 不允许**（§1.4） |
| 客户端需不需要 `did↔path` 映射 | 不需要（`did` 可逆） | ✅ **需要**（HMAC 不可逆） |

**为什么模式 A 也用 base64url 而不是裸路径**：

| 问题 | 裸路径做 `_id` | **base64url** |
| --- | --- | --- |
| 路径里的 `/` | 要 `encodeURIComponent` 成 `%2F`，得赌中间层不还原 | ✅ **根本不存在** |
| `#`、`?`、`%`、空格 | 每个都要单独想 | ✅ 全部安全 |
| 超长路径 | 可能撞 URL 长度限制 | ✅ 定长膨胀 |
| 人类可读性 | ✅ 好 | ⚠️ 差 → **但 view 的 key 是 `path`**，列树照样给可读路径 |

**`id(path)` 与 `path(id)` 都是纯函数**，放在 **`shared/paths.ts`** 里（§1.6），
`src/` 与 `server/` **import 同一个文件**——不是「各自照规格实现一遍」。

### 3.4 文档形状

**模式 A：**

```jsonc
{
  "_id": "f:bm90ZXMv6K+75Lmm56yU6K6wLm1k",
  "_rev": "3-8a7f...",
  "path": "notes/读书笔记.md",   // NFC、'/' 分隔
  "hash": "sha256:9f2c...",      // 客户端算的 sha256
  "size": 4096,
  "kind": "file",
  "deleted": false, "deletedAt": null, "deletedBy": "device-<id>",
  "updatedAt": "2026-10-13T04:20:00Z",
  "_attachments": {
    "blob": { "content_type": "text/markdown", "length": 4096,
              "digest": "md5-...", "revpos": 3, "stub": true }
  }
}
```

**模式 B（E2EE）：**

```jsonc
{
  "_id": "h:3f0786e96b20b0102b77f1a49c041be6",   // HMAC(idKey, path)
  "epath": "base64(iv||ct)",                     // 加密后的路径（AAD = did）
  "ehash": "base64(HMAC(macKey, sha256(plaintext)))",
  "esize": 4096,
  "kind": "file",
  "deleted": false, "deletedAt": null, "deletedBy": "device-<id>",
  "updatedAt": "2026-10-13T04:20:00Z",
  "_attachments": {
    "blob": { "content_type": "application/octet-stream",   // 不泄露类型
              "length": 4108, "digest": "md5-...", "revpos": 3, "stub": true }
  }
}
```

**E2EE 下服务端仍能看到的（如实列出，不要宣称「什么都看不到」）**：
文档数量、**每篇密文大小**（≈ 明文大小，除非填充）、写入时间、写入设备、`_attachments.length`、
以及**「两个文档的密文是否逐字节相同」**（`ehash` 已防住「内容等价」这一层）。
**要抹掉大小信息需要填充（padding）**，代价是存储膨胀——**v1 不做**，只如实告知。

### 3.5 正文为什么走 `_attachments` 而不是 base64 进正文

- 写入时以 base64 提交（JSON 传输的固有开销，**无法避免**），但 CouchDB **落盘存解码后的二进制** → **存储不膨胀**。
- 读取用 `GET /{db}/{docid}/blob` → **原始字节，不经过 JSON/base64**。
- CouchDB 官方明确警告 `_changes?attachments=true` 会带来 33% 传输开销
  （[`_changes` 文档](https://docs.couchdb.com/en/stable/api/database/changes.html)），**所以我们永远不用那个参数**。
- 附件的 `digest`（`md5-<base64>`）可用于上传后校验；但它是 **MD5**，与客户端的 **HMAC/SHA-256** 不是一回事。
- ⚠️ **与 30 秒写超时联动**（§1.3）：base64 提交使体积 ×4/3 → 上限要留余量（U18）。

### 3.6 列树投影

```js
// _design/opennote —— 模式 A 用；模式 B 下无用（key 必须是明文 path）
{
  "views": {
    "by_path": {
      "map": "function (doc) { if (doc.path && !doc.deleted) emit(doc.path, { hash: doc.hash, size: doc.size }); }"
    }
  },
  "validate_doc_update": "function (newDoc, oldDoc, userCtx, secObj) { /* 见 §3.8 */ }"

```

| 用途 | 模式 A | 模式 B |
| --- | --- | --- |
| 全树 | `_design/opennote/_view/by_path` | `_all_docs?include_docs=true` |
| 增量 | `_changes?since=<cursor>&style=all_docs` | 同左（**不受影响**） |

**分页必须取完**，否则会把「没取到」误判成「被删除」——见 §6.4，这是**误删**的来源。

### 3.7 检查点：`_local/<deviceId>`

- **`_local` 文档不参与复制、不出现在 `_changes` 里**——正好是检查点该有的性质。
- 客户端通过 `PUT /v1/checkpoint` 提交，**由 Node 转写**。
- **不要**只放本地 `.opennote/sync.json`：它**不跨端**（G8），换设备/重装会丢。
- **本地基线仍然需要**：`_local` 记 cursor（「拉」的位置）；
  `.opennote/sync.json` 记**每路径的 hash/ehash + rev + did**（判断「我改没改」）。**职责不同。**
- `deviceId` 是客户端生成的 uuid，持久化在 `localStorage` / Capacitor Preferences
  （**绝不能放 `.opennote/`**，否则跨设备会撞）。

### 3.8 路径与命名规范

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| **Unicode 归一化** | macOS 给 **NFD**，Linux/Windows 多为 **NFC** → 「看起来一样、字节不一样」→ 同一篇笔记变成两个文档 | **全链路统一 NFC**：`id(path)` 内部先 NFC，**客户端与 Node 共用同一函数** |
| **大小写** | Windows/macOS 大小写不敏感，CouchDB `_id` **大小写敏感** → 永久分叉 | **不折叠**；Node 检测折叠冲突并**拒绝或告警**，不自动改名 |
| **路径分隔符** | Windows 反斜杠 | 已统一 `/`（`src/fs/paths.ts:7`） |
| **绝对路径 / `..` / NTFS ADS 冒号** | —— | 复用 `assertSafeRelative`（`src/fs/paths.ts:21`） |

**两道防线，职责不同**：

1. **Node（第一道）**：明文笔记本的每个写请求都过 `assertSafeRelative(path)` + 大小写折叠检测。
   **`assertSafeRelative` 与 NFC 归一化都在 `shared/paths.ts`**（§1.6），
   `src/` 与 `server/` import 同一个文件 → **同一份实现**。
   （客户端侧 `src/fs/paths.ts` 改为 re-export，既有 import 路径不变。）
   ⚠️ **模式 B 下 Node 看不到明文路径**，只能校验 `did` 的形状（前缀、长度、字符集）。
   **路径安全完全由客户端保证**——这是 E2EE 的固有代价，必须如实写进文档：
   **加密笔记本的路径安全等级低于明文笔记本。**
2. **CouchDB `validate_doc_update`（第二道，防绕过）**：防「拿到 `sync` 的 CouchDB 凭据直接写库」。
   ⚠️ 它在 CouchDB 内部 JS 引擎里，**既不是 TS、也不能 import `shared/`** → 规则**必然另写一份 JS**。
   → 靠**共享夹具**驱动：`shared/fixtures/path-rules.cases.json` 同时喂给
   `shared/paths.ts` 的测试、以及 `_design/opennote` 的 JS 测试（§1.6、§10.1 F2）。
   **这是单仓下唯一无法靠类型系统消除的接缝**，所以夹具是必须的。

```js
// _design/opennote 的 validate_doc_update（第二道防线）
function (newDoc, oldDoc, userCtx, secObj) {
  if (newDoc._deleted) return;                        // tombstone 放行
  if (newDoc._id.indexOf('_') === 0) return;          // 保留 id 放行（_design/_local）
  if (!/^[fh]:/.test(newDoc._id)) throw({ forbidden: 'bad id prefix' });
  if (newDoc.path !== undefined) {                    // 模式 A：有明文 path，严格校验
    if (typeof newDoc.path !== 'string' || !newDoc.path) throw({ forbidden: 'bad path' });
    // 按「路径段」匹配，不要用 indexOf('..') —— 会误伤 a..b.md
    if (/(^|\/)\.(opennote|git)(\/|$)/.test(newDoc.path)) throw({ forbidden: 'reserved path' });
    if (newDoc.path.charAt(0) === '/' || /(^|\/)\.\.(\/|$)/.test(newDoc.path)) {
      throw({ forbidden: 'unsafe path' });
    }
  } else if (typeof newDoc.epath !== 'string' || !newDoc.epath) {
    throw({ forbidden: 'missing path/epath' });       // 两者必有一个
  }
  if (typeof newDoc.hash !== 'string' && typeof newDoc.ehash !== 'string') {
    throw({ forbidden: 'missing hash/ehash' });
  }
  if ((newDoc.size || newDoc.esize || 0) > MAX_BYTES) throw({ forbidden: 'too large' });
}
```

### 3.9 E2EE 的密码学设计

**层级**（全部在客户端，服务端永不见密钥材料）：

```
accountId (公开, 16B 随机, 客户端生成)
accountKey (秘密, 32B CSPRNG, 客户端生成, 用户保存的唯一东西)
   │ HKDF-SHA256(salt = accountId, info = "opennote/v1/auth") → authToken   → 发给服务端
   │ HKDF-SHA256(salt = accountId, info = "opennote/v1/wrap") → wrapKey     → 永不外发
   ▼
encRoot (秘密, 32B CSPRNG, 客户端生成)  ──AEAD(wrapKey, aad=accountId)──►  wrappedEncRoot → 存服务端
   │ HKDF-SHA256(info = "opennote/v1/notebook/" + notebookId) → notebookKey
   ▼
notebookKey
   ├── HKDF(info="enc") → 内容与附件（AEAD）
   ├── HKDF(info="mac") → ehash（HMAC-SHA256）
   └── HKDF(info="id")  → 路径 HMAC（did）
```

**算法选择**：

| 用途 | 算法 | 理由 |
| --- | --- | --- |
| 内容与附件 | **XChaCha20-Poly1305**（`@noble/ciphers`） | **192-bit nonce → 随机 nonce 天然安全**（生日界 ~2⁹⁶），**不需要写入预算与计数器**；软件实现恒定时间，不依赖 AES-NI（部分 Android WebView / 老设备无硬件 AES） |
| `ehash` / `did` | **HMAC-SHA256**（`@noble/hashes`） | 只暴露「相等/不等」 |
| 密钥派生 | **HKDF-SHA256**（`@noble/hashes`） | 同步 API、四端同一条纯 JS 代码路径；**不需要慢 KDF**（§1.5） |
| 包裹 `encRoot` | 同 AEAD，**AAD = `accountId`** | 防跨账号替换 `wrappedEncRoot` |
| 随机数 | `crypto.getRandomValues` | 四端一致的系统 CSPRNG（noble 内部也用它） |

**六条必须做对的地方**：

1. **nonce 每次写入重新随机**（192-bit，`iv || ct` 存在密文里，不靠推导），
   且 **AAD 必须绑定 `did` 与 `notebookId`**——
   否则攻击者可以把 A 文档的密文搬到 B 文档上（**密文重排攻击**）。
   ✅ **不需要写入次数预算**：192-bit 随机 nonce 的碰撞概率在 2⁹⁶ 量级，笔记场景永远达不到。
2. **`ehash` 必须 HMAC**，不能直接送 `sha256(plaintext)`——否则服务端能判断「两篇内容是否相同」。
3. **`authToken` 与 `wrapKey` 必须分叉派生**（§1.5）——这是 E2EE 成立的前提。
4. **`accountKey` 必须客户端生成**。**服务端生成 = E2EE 直接不成立**。同理 **CLI 绝不接触密钥**（§1.5）。
5. **账号密钥丢失 = 数据不可恢复**。UI 用最强措辞，并建议离线保存（纸质/密码管理器/另一台设备）。
6. **加解密只在客户端**：**`server/` 里不应出现任何解密函数或密钥类型**（§4.2、§7.3）。

**密钥在本地的存放**：

| 宿主 | 存哪 | 说明 |
| --- | --- | --- |
| 桌面 Electron | **主进程**持有（可选 `safeStorage` 落盘） | 渲染层拿不到，与令牌处理一致（§5.5） |
| Android | Capacitor Preferences / Keychain | 可选「记住」 |
| 网页 | **`localStorage`**（已定） | ⚠️ **可被 XSS 读**——这是网页端 E2EE 的固有弱点，UI 必须写明；换来的是「刷新不用重新导入密钥」 |

### 3.10 `_revs_limit`、compaction 与容量

| 项 | 默认 | 建议 | 为什么 |
| --- | --- | --- | --- |
| `_revs_limit` | 1000 | **1000（保持默认）** | 决定 revision tree 保留多少祖先。**调小会让三方合并失去共同祖先** |
| compaction | 手动/自动 | 定期 `POST /{db}/_compact`（`sync` 定时任务） | 回收磁盘 |
| ⚠️ **compaction 副作用** | —— | **压缩后旧 revision 可能不可达** | 三方合并不再可能 → 保留独立分支交用户裁决 |
| 单文件上限 | —— | 默认 32 MB（可配，**受 30s 写超时约束**） | 三层约束 |
| **墓碑保留** | —— | **逻辑删除文档永不物理清除** | 见 §6.4 |
| 附件压缩 | —— | CouchDB 按 content_type 决定 | ⚠️ **E2EE 下统一 `application/octet-stream`** → 文本不再压缩 → **磁盘占用上升**（如实记一笔） |

**容量估算**：3000 篇 × 平均 4 KB ≈ 12 MB 正文；`_revs_limit=1000` 且每篇改过 20 次 →
约 **10–50 MB/账号**。**E2EE 后文本附件不再压缩，按 2–3× 估算。**

### 3.11 同步范围：忽略规则（**参考 `.gitignore`**）

> 已定：**`.git` 这类经常被修改的文件忽略掉就行**。本节把「同步范围」定义成一套明确、可测的规则。

#### 三个层次，优先级从高到低

| 层次 | 内容 | 能否被 `.gitignore` 取反 |
| --- | --- | --- |
| **① 内置忽略集**（硬编码） | `.git/`、`node_modules/`、`dist/`、`release/`、`.opennote/`、`.DS_Store`、`Thumbs.db`、常见编辑器临时文件（`*.swp`、`*~`、`.#*`、`*.tmp`） | ❌ **永远不能**（安全底线） |
| **② `.gitignore`**（工作区根目录） | **git 兼容语义** | —— |
| **③ 一切都同步** | 默认 | —— |

**① 为什么必须不可取反**：如果用户在 `.gitignore` 里写 `!/.git/`（想「把 git 目录也同步」），
**必须被拒绝**——同步 `.git/` 会跨设备搬 `objects`/`index`，**把仓库搞坏**。
同理 `.opennote/` 里有基线、密钥引用、历史，**绝不能跨端**。
→ 实现上：**先判内置集，命中就直接排除，不再看 `.gitignore`。**

#### 语义：用现成实现，不要自己写解析器

`.gitignore` 的语义比看起来复杂得多，**自己实现必错**：

- `!` 取反；`**` 跨目录匹配；目录尾斜杠 `/`；行首斜杠锚定根目录；
- **最反直觉的一条**：**被忽略的目录里，仍然可以用 `!` 重新包含文件**（但 git 有个前提：父目录本身没被排除）。

→ **用官方语义的现成实现**：npm 的 **`ignore` 包**（就是照着 git 的 `gitignore` 规则实现的）。
上一版的调研文档也给了同一条建议：

> 「要么用 git 官方语义的现成实现（如 `ignore` 包），要么**明确只支持一个子集并写进文档**。」
> —— `设计：服务端自动同步 与 GitHub 手动备份 如何共存.md:202-209`

#### 作用域决定：**只读工作区根目录的 `.gitignore`**（v1）

- git 原生支持**逐目录**的嵌套 `.gitignore`。v1 **只支持根目录那一个**，并在 UI/文档里写明。
  理由：嵌套要求遍历时逐目录解析，且用户很难预期「哪个规则在起作用」；根目录一个已经覆盖绝大多数实际用法。
  **若你以后要 git 完全兼容，那是一次独立的、有测试的改动**（列入 P4 备选）。
- `.gitignore` **本身不会同步**（它是隐藏文件，本来就被排除）。
  → **各设备可能有不同的 `.gitignore`** ⇒ 各设备同步范围可能不同。这是有意的，见下面「双向不可见」。

#### 最关键的一条规则：**忽略 = 该路径在同步引擎里双向不存在**

这条是防「忽略规则变化造成误删 / 反复拉取」的核心：

```
对每个候选路径：
  ignored(path) ?  →  完全跳过：不 push、不 pull、不删除、不参与三方 diff
                   →  它既不算「本地删了」，也不算「远端有而本地没有」
```

**为什么必须双向**：`.gitignore` 不同步 ⇒ 设备 A 可能忽略 `foo.md` 而设备 B 不忽略。
- 如果只做「不 push」：A 的本地扫描看不到 `foo.md`，但远端有 → A 会**判定「远端新增」并拉下来** →
  但 A 又忽略它 → 下次扫描还是看不到 → **再次拉取，死循环**。
- 双向跳过则没有这个问题：**A 彻底当它不存在**，B 照常同步它。✅

**这条规则的推论（要写进 UI）**：

1. **被忽略的文件不会同步到其它设备**——用户容易以为「忽略 = 不显示」，其实是「不参与同步」。
2. **忽略一个已有内容的文件，等于让它在其它设备上停更**（不是删掉，只是不再传播）。
3. **改 `.gitignore` 是「改变同步范围」的严肃操作**——表现为「一批文件从同步范围里消失」。
   删除保护（§6.3）能拦住**大批量**，**小批量会直接生效**，所以 UI 应该在保存 `.gitignore` 后提示
   「同步范围已变化：新增忽略 N 个路径 / 解除忽略 M 个路径」。

#### 一处实现，两处使用（**同一个判定函数**）

```
         ┌──────────────────────────────┐
         │ src/sync/ignore.ts           │
         │  shouldIgnore(relPath, isDir)│  ← 纯函数
         └───────┬──────────────┬───────┘
                 │              │
    ① 扫描（collectLocalFiles）  ② watcher（electron/main.cjs 的 onChange）
```

**这就是「已核对的事实」里那个待办的正解**：现在
`electron/main.cjs:797`（parcel-watcher 的 `ignore` 选项）**已经有** `.git/**`，
但 `electron/main.cjs:866-880`（`node:fs` 退路 `onChange`）**只过滤 `.opennote/` 与自写**。
→ **把判定收敛成 `src/sync/ignore.ts` 一个函数，两条路径都用它**，而不是各写一张过滤表。

⚠️ **注意 `.git/` 已经在扫描侧被排除了**：`collectLocalFiles` 用
`isHiddenPath(path)`（`src/lib/github/sync.ts:164`）跳过所有点开头的路径，
所以 `.git/`、`.gitignore`、`.DS_Store` **本来就不在扫描范围**。
本节的价值在于：**把「碰巧被隐藏规则排除」变成「显式的、有测试的、watcher 也遵守的规则」**。

#### 误伤与边界（必须测）

| 情况 | 期望 |
| --- | --- |
| `a..b.md`（文件名里有两个点） | **不忽略**（不要用 `indexOf('..')` 这种粗暴判断） |
| `notes/.opennote.md` | `.opennote/` 是**目录**，不是文件名前缀 → **不忽略** |
| `.gitignore` 写 `!/\.git/` 或 `!.opennote/` | **仍被忽略**（内置集不可取反） |

### 4.2 红线 2 的执行条款（**放进 PR 模板**）

> **Node 不得产出任何同步语义，也不得接触任何密钥材料。**

| 禁止在 Node 里实现 | 必须由 CouchDB 提供 |
| --- | --- |
| 版本号 / 版本自增 | `_rev` |
| 冲突检测与冲突版本保存 | revision tree（leaf 不丢） |
| 冲突裁决（谁赢） | **不由任何自动算法决定**——由用户裁决（§6.1） |
| 检查点存储 | `_local/device-<id>` |
| 变更游标生成 | `_changes` 的 `last_seq` |
| 批量收敛 / 复制协议 | `_revs_diff` + `_bulk_docs`（P4 若用） |

| 禁止在 Node 里出现 | 为什么 |
| --- | --- |
| 任何解密函数 / `encRoot` / `notebookKey` 类型 | 一旦服务端能解密，E2EE 就没了 |
| 任何从 `authToken` 反推 `wrapKey` 的尝试 | HKDF 保证做不到，但**代码里不该有这个企图** |
| 生成账号密钥 / `encRoot`（**包括 CLI**） | 只有客户端能生成它们（红线 3、§1.5） |

**Node 只做四件事**：① 身份与授权；② **参数与格式翻译**（`did`↔`_id`、字节↔base64 附件、CouchDB 流↔SSE）；
③ 控制台与配额；④ 定时作业。

### 4.3 SQLite 模式（**无口令、无用户名**）

```sql
-- 账号：一条密钥就是一个账号
CREATE TABLE accounts (
  id                TEXT PRIMARY KEY,       -- accountId（客户端生成的公开随机 id）
  auth_hash         TEXT NOT NULL UNIQUE,   -- sha256(authToken)  ★ 反推不出 authToken
  wrapped_enc_root  TEXT NOT NULL,          -- AEAD(wrapKey, encRoot, aad=accountId)  ★ 服务端解不开
  is_admin          INTEGER NOT NULL DEFAULT 0,
  status            TEXT NOT NULL DEFAULT 'active',   -- active | disabled
  label             TEXT,                   -- 可选备注名（★ 纯装饰，不参与鉴权、不唯一）
  created_at        INTEGER NOT NULL,
  last_seen_at      INTEGER
);
CREATE INDEX idx_accounts_hash ON accounts(auth_hash);

-- 引导码（首次创建管理员用；由 CLI 生成，一次性）
CREATE TABLE bootstrap_codes (
  code_hash  TEXT PRIMARY KEY,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  used_at    INTEGER
);

-- 邀请码（注册用；只能由管理员在控制台生成）
CREATE TABLE invites (
  code_hash  TEXT PRIMARY KEY,
  created_by TEXT NOT NULL REFERENCES accounts(id),
  created_at INTEGER NOT NULL,
  expires_at INTEGER,
  max_uses   INTEGER NOT NULL DEFAULT 1,
  uses       INTEGER NOT NULL DEFAULT 0,
  revoked_at INTEGER
);

-- 设备登记（★ 不是凭据：一个账号密钥所有设备共用，所以这里只是账本）
CREATE TABLE devices (
  id           TEXT PRIMARY KEY,            -- 客户端生成的 uuid（= 同步检查点用的 deviceId）
  account_id   TEXT NOT NULL REFERENCES accounts(id),
  name         TEXT,
  platform     TEXT,                        -- desktop | android | web
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER,
  last_ip      TEXT
);
CREATE INDEX idx_devices_account ON devices(account_id);

-- 笔记本
CREATE TABLE notebooks (
  id          TEXT PRIMARY KEY,             -- uuid（对外 notebookId）
  owner_id    TEXT NOT NULL REFERENCES accounts(id),
  name        TEXT NOT NULL,
  db_name     TEXT NOT NULL UNIQUE,         -- 'nb-' + uuid
  crypto_mode TEXT NOT NULL DEFAULT 'user-key',   -- 'none' | 'user-key'
  created_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

-- ★ 授权的唯一真源
CREATE TABLE memberships (
  notebook_id TEXT NOT NULL REFERENCES notebooks(id),
  account_id  TEXT NOT NULL REFERENCES accounts(id),
  role        TEXT NOT NULL,                -- owner | editor | viewer
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (notebook_id, account_id)
);
CREATE INDEX idx_memberships_account ON memberships(account_id);

-- 笔记本邀请码（共享用；不需要知道对方是谁）
CREATE TABLE notebook_invites (
  code_hash   TEXT PRIMARY KEY,
  notebook_id TEXT NOT NULL REFERENCES notebooks(id),
  role        TEXT NOT NULL,                -- editor | viewer
  created_by  TEXT NOT NULL REFERENCES accounts(id),
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER,
  used_at     INTEGER
);

-- 配额
CREATE TABLE quota_usage (
  account_id  TEXT PRIMARY KEY REFERENCES accounts(id),
  bytes_used  INTEGER NOT NULL DEFAULT 0,
  notebooks   INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL
);

-- 客户端上报（供控制台展示；★ 服务端看不到冲突内容，只有计数）
CREATE TABLE client_stats (
  account_id TEXT NOT NULL, notebook_id TEXT NOT NULL, day TEXT NOT NULL,
  conflicts INTEGER NOT NULL DEFAULT 0, errors INTEGER NOT NULL DEFAULT 0,
  pushes INTEGER NOT NULL DEFAULT 0, pulls INTEGER NOT NULL DEFAULT 0,
  deletes INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (account_id, notebook_id, day)
);

-- 审计（★ 永不包含正文或密钥材料）
CREATE TABLE audit (
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  at       INTEGER NOT NULL,
  actor_id TEXT,                            -- accountId 或 null
  action   TEXT NOT NULL,                   -- rotate_key / create_invite / revoke_invite / ...
  target   TEXT, ip TEXT, detail TEXT
);

CREATE TABLE schema_version (version INTEGER NOT NULL);
```

**迁移**：`db.ts` 里维护 `schema_version` + 顺序迁移函数。
**不要**用「启动时自动改表」的魔法 ORM——这是要长期跑的服务，迁移要可审计。

### 4.4 认证与授权

**认证（你是谁）：只有一条链路。**

```
Authorization: Bearer <authToken>
  1. 计算 h = sha256(authToken)
  2. SELECT id, is_admin, status FROM accounts WHERE auth_hash = h
     （直接走唯一索引；因为 authToken 有 2²⁵⁶ 空间，索引查找不泄露任何部分信息，
       不需要再做常量时间比较）
  3. 无行        → 401
  4. status != 'active' → 403
  5. → accountId
```

**没有独立的会话表**：控制台也直接用 `authToken`，登录时把它塞进
`HttpOnly; Secure; SameSite=Lax` cookie。**一个凭据贯穿所有入口**。
（轮换之后浏览器的 cookie 自然失效 → 回到导入密钥页，这正是期望行为。）

**授权（你能干什么）：单一中间件 + 单一真源。**

```
涉及笔记本的请求：
  1. 认证 → accountId
  2. 解析 notebookId
  3. SELECT role FROM memberships WHERE notebook_id=? AND account_id=?
     ├─ 无行                    → 404（★ 不是 403：不泄露「这个笔记本存在」）
     ├─ role == viewer          → 只允许 GET
     └─ role in (editor, owner) → 允许写
  4. 需要 owner 的操作（删笔记本、生成/撤销笔记本邀请码）→ 再查 role == 'owner'
```

**五条纪律**：

1. **CouchDB `_security` 不是 ACL 的第二份真相**，它只设成「只有 `sync` 的服务账号」。
   把每账号 ACL 也镜像进去会立刻产生两份真相。它的角色是**纵深防御**：
   万一 `sync` 的 CouchDB 凭据泄露，攻击者拿到的也不会比 `sync` 本来能拿的更多。
2. **越权返回 404，不是 403**（多账号下很重要）。
3. **服务端不存也不生成任何密钥材料**（红线 3、§4.2）。
4. **`sync` 运行时不使用 CouchDB admin**：用专用账号；建库/改 `_design` 用 admin 只在置备时（§4.5）。
5. **账号状态**：`disabled` 的账号，其所有请求立即 403；**数据保留**（管理员可以再启用）。

### 4.5 笔记本置备（幂等）

```text
创建笔记本（POST /v1/notebooks 或控制台）：
  1. 生成 notebookId = uuid, dbName = 'nb-' + uuid（去连字符）
  2. INSERT notebooks(...) + INSERT memberships(owner)
  3. CouchDB 置备（admin 凭据，仅此一次）：
     a. PUT /{dbName}                      建库（409 = 已存在则跳过）
     b. PUT /{dbName}/_security            只留 sync 服务账号
     c. PUT /{dbName}/_design/opennote     views.by_path + validate_doc_update
     d. PUT /{dbName}/_revs_limit          → 1000
     e. PUT /{dbName}/syncinfo             { protocolVersion, cryptoMode, createdAt }
  4. 回滚：第 3 步任一步失败 → 删库 + 删 notebooks 行（不留半个笔记本）
```

**验收**：置备后控制台显示「`_design` 已就位、`_revs_limit=1000`」；
手工删掉 `_design` 后控制台应能**发现不一致并提示**（**不自动重建**——会掩盖人为误删）。

### 4.6 控制台（`/panel`）

**定位**：一台多账号自托管同步服务的「账户 + 仪表盘 + 开关」，**不是产品的一部分**。
无构建步骤的静态页（原生 HTML + 少量 JS）。

**进入方式**：粘贴 / 导入账号密钥 → 客户端派生 `authToken` → 塞进 HttpOnly cookie。**没有登录表单。**

| 区块 | 普通账号 | 管理员 |
| --- | --- | --- |
| **我的账号**：账号 ID、**导出密钥**（从本机重新显示）、轮换密钥、删除账号 | ✅ | ✅ |
| **我的设备**：列出（名称/平台/上次同步/IP） | ✅ **只读**（§1.5 代价 3） | ✅（可看全部） |
| **我的笔记本**：新建（**选 `crypto_mode`**）、改名、删除、生成/撤销**笔记本邀请码** | ✅ | ✅ |
| **用量**：已用空间 / 配额 / 笔记本数 | ✅ | ✅ |
| **冲突与错误**：自己笔记本的按天计数 | ✅ | ✅ |
| **账号管理**：列出、禁用/启用、删除、**生成邀请码** | ❌ | ✅ |
| **服务器**：健康、CouchDB 版本、库数量/总大小 | ❌ | ✅ |
| **备份**：上次备份时间、**「立即备份」**（P4） | ❌ | ✅ |
| **危险操作**：触发 `_compact`、导出整库 | ❌ | ✅ |

**⚠️ 三条必须写在界面上的说明**（否则用户会以为有这些能力）：

1. **「服务端无法补发你的密钥。」** 你的账号密钥从来没到过服务端。
   所以「导出密钥」只能在**已经有密钥的设备**上做；新设备必须从旧设备导入。
2. **「要踢掉某台设备，只能轮换密钥。」** 没有每设备凭据 → 轮换会让**所有其它设备**也要重新导入。
3. **「管理员也无法重置任何人的密钥。」** 管理员能做的只有：禁用账号、删除账号、生成邀请码。

**访问控制（不用 CF Access，所以全靠自己）**：
- `authToken` 存 `HttpOnly; Secure; SameSite=Lax` cookie；**轮换即全端失效**（这是特性）
- **全局限流**（不是防爆破，而是防 DoS）：按 IP 与按账号两条
- 变更类请求要求自定义头 `X-Requested-With: opennote-panel`
  （跨源无法在不触发预检的情况下发送自定义头 → 天然防 CSRF，比 token 简单）
- 管理员页面的 API **默认拒绝**，只有 `is_admin` 能过

### 4.7 客户端 HTTP 契约 v1

```text
鉴权：Authorization: Bearer <authToken>      （由账号密钥在客户端派生）

# —— 账号（客户端生成一切密钥材料）——
POST   /v1/account              { accountId, authToken, wrappedEncRoot,
                                  inviteCode? | bootstrapCode? }
                                -> { accountId, isAdmin }        （★ 注册必须有码）
POST   /v1/account/unlock       （带 Bearer；用于新设备取回 wrappedEncRoot）
                                -> { accountId, wrappedEncRoot, quota: {...} }
POST   /v1/account/rotate       { newAuthToken, newWrappedEncRoot }
                                （用【旧 authToken】认证）        -> 204（旧令牌立即失效）
GET    /v1/account              -> { accountId, isAdmin, label, quota }
DELETE /v1/account              （删账号 + 其独占笔记本的库）      -> 204

# —— 设备登记（不是凭据，只是账本）——
POST   /v1/devices              { deviceId, name, platform }       -> 204
GET    /v1/devices              -> [{ deviceId, name, platform, lastSeenAt }]

# —— 笔记本 ——
GET    /v1/notebooks            -> [{ notebookId, name, role, cryptoMode, ... }]
POST   /v1/notebooks            { name, cryptoMode }               -> { notebookId, cryptoMode }
GET    /v1/notebooks/:id        -> { notebookId, name, role, cryptoMode, protocolVersion }
DELETE /v1/notebooks/:id        （仅 owner）
GET    /v1/notebooks/:id/members -> [{ accountId, label, role }]
POST   /v1/notebooks/:id/invites { role, expiresIn?, maxUses? }
                                -> { code }        ★ cryptoMode != 'none' 时 409
DELETE /v1/notebooks/:id/invites/:codeHash
POST   /v1/notebooks/join       { code }           -> { notebookId, role, cryptoMode }

# —— 同步数据面（nb = notebookId）——
GET    /v1/tree?nb=&limit=&startkey=
       -> { cursor, truncated, files: [{ did, hash?, ehash?, size?, esize?, rev }] }
          （紧凑投影，不含正文；truncated 为真时禁止推断删除，见 §6.4）

GET    /v1/changes?nb=&since=<cursor>
       -> { cursor, resync?: true, changes: [{ did, op: add|update|delete }] }

GET    /v1/file?nb=&did=<urienc>            -> 200 bytes / 404
PUT    /v1/file?nb=&did=<urienc>
       Header: If-Match: <hash 或 ehash>      （缺省 = 允许新建；对不上 = 409）
       body: 原始字节（E2EE 时是密文）
       -> 200/201 { hash?, ehash?, rev } | 409 { current: {...} } | 412

DELETE /v1/file?nb=&did=<urienc>             Header: If-Match
       -> 204 | 409 | 410

GET    /v1/events?nb=                        -> text/event-stream
       event: change      data: {"cursor":"...","dids":["h:..."]}
       event: heartbeat   data: {}            （≤ SSE_HEARTBEAT_MS）

PUT    /v1/checkpoint           { nb, cursor }                        -> 204
POST   /v1/stats                { nb, day, conflicts, errors, pushes, pulls, deletes }

# —— 管理（仅 is_admin）——
POST   /v1/admin/invites        { expiresIn?, maxUses? }              -> { code }
GET    /v1/admin/accounts       -> [{ accountId, label, status, quota, lastSeenAt }]
POST   /v1/admin/accounts/:id/disable | /enable                       -> 204
DELETE /v1/admin/accounts/:id                                          -> 204
GET    /v1/admin/server         -> { couchVersion, dbCount, totalBytes, ... }
```

**八个刻意的设计点**：

1. **`did` 走查询参数，不走 URL 路径段**——`did` 可能带 `:`；放 query 最稳，
   服务端仍要校验形状（模式 B）或 `assertSafeRelative`（模式 A）。
2. **客户端传 `did` 而不是 `path`** → **服务端在 E2EE 下根本不知道路径**。
   代价：客户端维护 `did → path` 本地映射（§2.2）。
3. **`If-Match` 用内容哈希（或 `ehash`），不用 ETag**——语义比自定 ETag 清楚；
   对不上返回 409 + 当前值。Node 内部转成 CouchDB 的 `?rev=<baseRev>`，
   所以**客户端仍要持有并回传 `rev`**（放在基线里）。
4. **`cursor` 是「不透明字符串」，不是数字**。CouchDB 2.0 起 update sequence 可以是任意 JSON。
5. **`_changes` 是「部分有序」的**：官方明确顺序不保证一致，并要求客户端**幂等**。
   → **客户端把「收到变更」当 idempotent 的 dirty 信号**，而不是「按顺序应用事件」。
   这是上游「SSE 只发『来拉了』」设计（`设计：同步服务接口…:103-104`）的**官方依据**。
6. **`truncated` 必须如实上报**——它是「禁止推断删除」的开关（§6.4）。
   现有 GitHub 通道已有这个纪律（`src/lib/github/importRepo.ts:53,101`；提示见 `src/App.tsx:789`）。
7. **`/v1/file` 传原始字节**（不是 JSON 包 base64）。Node 内部再转 base64 给附件 →
   客户端传输开销最小，base64 膨胀只发生在 Node↔CouchDB 这一段（内网，且落盘不膨胀）。
8. **越权返回 404 而不是 403**（§4.4 纪律 2）。

**⚠️ 没有「找回密钥」的端点，也不该有。** 契约里刻意留白——这是设计，不是遗漏。

### 4.8 SSE 中继

**为什么不直接透传 CouchDB 的 `_changes?feed=eventsource`**：

- CouchDB 默认心跳 **60000ms**；边缘读超时可能是 125s（CF）或别的值。
  **透传就把「心跳能否活过边缘超时」交给了一个我们控制不了的默认值。**
- Node 自己发可以：**心跳可配**、过滤事件、多设备扇出、把 `_id` 映射成 `did`。

**要点**：
- 订阅 `GET /{db}/_changes?feed=continuous&since=<cursor>&heartbeat=15000`，逐行解析。
- 按 200–500ms 窗口聚合成一个 `change` 事件。
- **每 ≤ `SSE_HEARTBEAT_MS`（默认 25000）发一次 `heartbeat`**，即使没有变更。
  **换入口时要重新核算这个值。**
- 响应头：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、
  `Connection: keep-alive`、`X-Accel-Buffering: no`。
- **背压与连接上限**：每账号/设备最多 N 条（默认 4），超了 429。
- **断线重连**：Node 把 cursor 放进 SSE 的 `id:` 字段 → 客户端带 `Last-Event-ID` 回来 →
  Node 用那个 cursor 续订。**客户端不需要为重连自己存 cursor。**
- **降级链**：SSE 不可用 → 每 15–30s 轮询 `/v1/changes` → `visibilitychange` 立即查一次。

⚠️ **验收（P3 第一号项）**：在**真实入口**上实测「另一端写入 → 本端收到」的延迟，
并故意空转 2× 心跳时间，确认心跳到达且连接未被断开。

### 4.9 加密依赖：**`@noble/ciphers` + `@noble/hashes`（已定）**

现状：仓库**没有任何加密相关依赖**（已核对 `package.json`）。**本版引入两个纯 JS 依赖**——
按你的决定「不省体积，哪个更好就用哪个」，选型的理由是**正确性与一致性**，不是大小。

| 用途 | 依赖与 API | 为什么是它 |
| --- | --- | --- |
| 内容 / 附件 / `wrappedEncRoot` | `@noble/ciphers` → **XChaCha20-Poly1305** | **192-bit nonce → 随机 nonce 天然安全，整套写入预算与计数器可以删掉**；软件恒定时间，不依赖 AES-NI |
| HKDF-SHA256 | `@noble/hashes/hkdf` | 同步 API |
| HMAC-SHA256 | `@noble/hashes/hmac` + `sha256` | 同步 API |
| 随机数 | `crypto.getRandomValues` | 系统 CSPRNG，四端一致（noble 内部也用它） |

**四条选它的理由**：

1. **删掉一整类设计负担**：XChaCha20 的 192-bit nonce 让「随机 nonce 会不会撞」这个问题**不存在**
   （生日界 ~2⁹⁶）。上一版为 AES-GCM 设计的**写入计数器与 2²⁴ 轮换阈值全部删掉**。
2. **不依赖硬件 AES**：部分 Android WebView / 老设备没有 AES-NI，纯软件 AES 既慢又有侧信道顾虑；
   ChaCha20 是 ARX 结构，软件实现天然恒定时间。
3. **同步 API + 一条代码路径**：WebCrypto 是异步的（`Promise`），且四个宿主在 HKDF/HMAC 的细节上
   有差异；noble 是纯 JS，**四端跑同一份字节码**，测试也就只需要一套。
4. **纯 JS、无原生依赖、可 tree-shake**：Electron / Capacitor WebView / 浏览器 / Node 全部能打包进去；
   仓库本来就无原生加密依赖，这条不会引入新的构建复杂度。

**代价（如实列）**：

| 代价 | 说明 |
| --- | --- |
| 多两个依赖 | 需要**锁版本**并纳入依赖审查；noble 系列经过第三方审计、被广泛使用，风险可控 |
| 包体积增加 | 你已明确**不把体积当约束**；实际只用 chacha/hkdf/hmac/sha256 四块，可 tree-shake |
| 纯 JS 性能低于原生 | 笔记量级（几百 KB 级文件）**无感**；大附件加密在移动端需实测（U16） |
| **不再有「零依赖」这个卖点** | 换来的是**更少的自研密码学风险和更简单的设计**，值得 |

**仍然保留的硬约束**（与算法选择无关）：

- **必须用 CSPRNG**（`crypto.getRandomValues`），**绝不**用 `Math.random`。
- **必须锁版本**（`package.json` 精确版本，不用 `^`）——密码学依赖的补丁升级要人工过一遍。
- **`server/` 不依赖 `@noble/*`**：服务端不做加解密（§4.2）。它们**只进客户端构建**。
  → 建议在 CI 加一条检查：`server/` 里**不允许出现 `@noble/`**（红线 3 的机械化）。

5. **mtime 判据必须换掉**（说清**准确的失效路径**）：
   - `I2` 规定「是不是外部改动 = **磁盘字节 ≠ record.content**，stat/mtime **只决定要不要读**」
     （`docs/设计-同步层与索引重构-2026-10-10.md:37`）。
   - **真正的 bug**：`src/data/library.ts:1060`

     ```ts
     const isForeign =
       !seen || (disk.content !== seen.content && (!stamp || stamp.mtimeMs > seen.stat.mtimeMs));
     ```

     它要求「**磁盘 mtime 比我们记录的新**」才认外部改动。**跨设备 / 网盘 / `git clone` 下 mtime 不可比**——
     来自另一台机器的远端写入可能带**更旧的 mtime** → 判「不是外部改动」→ 走 `keepLocal`
     → **本地旧 buffer 在下次 `flushNote` 时把远端新内容覆盖掉**。
   - `src/data/fileStates.ts:64,67` 有同一问题。
   - **正确修法**：换成**显式的本地写 epoch / 在途写集合**，
     然后**任何「内容不同且不在途」都判为外部改动**。
   - 依据：LiveSync「**文件字节才是内容身份，mtime/size/路径/哈希都不算**」；上游 `三端同步…:109`。

### 5.5 CSP、主进程代理与密钥保管

- **网页版**：`vite.config.ts:189` 的 `connect-src` 增加同步服务 origin（**同域时 `'self'` 已够**）。
- **桌面端**：`cspPolicy()`（`electron/main.cjs:75`）**不放任何 https**，所以远端请求**必须走主进程**：
  - **只允许「配置好的 base URL + 相对路径」**——不能做成通用 `fetch(url)`，否则**一次 XSS 就能借它把笔记外发**。
  - IPC 只接受 `{method, relPath, headers, body}`，`relPath` 经 `assertSafeRelative`，
    拼出的绝对 URL 再断言 `startsWith(syncBaseUrl)`。
  - **`authToken` 与 `encRoot` 都由主进程持有**（渲染层拿不到）→ XSS 收益被压到最低。
  - 参照物：`electron/bridge.cjs`、`electron/fetch-images.cjs`。
- **移动端**：Capacitor WebView 不受桌面 CSP 约束，仍走 `http.ts` 的统一退避与鉴权。
- **网页端（诚实说明）**：`accountKey` **存 `localStorage`（已定）**——
  可被 XSS 读，这是网页端 E2EE 的固有弱点，**UI 必须写明**；换来的是「刷新不用重新导入密钥」。

### 5.6 构建隔离与 Docker（**单仓版**）

单仓意味着 `server/` **和客户端代码住在同一个仓库里**，所以「构建隔离」重新变成一个要认真处理的问题；
但同时**没有 PWA 产物交接问题**了（同一个仓库，构建时直接产出 `dist/`）。

#### ① 三套 tsconfig，别互相污染

实测：客户端 `tsconfig.json` 的 `include` 是 `["src", "capacitor.config.ts", "vite.config.ts", "vitest.config.ts", "vite.clip.config.ts"]`，
Vite 入口是根 `index.html` → **`server/` 与 `shared/` 都不会被前端构建收进去**（这是好事），
但也意味着**它们不会被类型检查**。所以要各自有配置：

| 配置 | lib / types | 作用 |
| --- | --- | --- |
| `tsconfig.json`（现有，客户端） | `DOM` + `vite/client` | 客户端 |
| **`shared/tsconfig.json`** | **`lib: ["ES2022"]`，不配 `types`** | ★ **用不了 DOM、也用不了 `node:*`** → **机械保证 `shared/` 是纯函数** |
| **`server/tsconfig.json`** | **`lib: ["ES2022"]` + `types: ["node"]`，没有 DOM** | 服务端；照抄客户端已有的严格开关（`strict` / `noUnusedLocals` / `verbatimModuleSyntax` / `isolatedModules`），**别放松** |

客户端 `tsconfig.json` 的 `include` **加一项 `"shared"`**（这样客户端也会检查它，且能 import）。

#### ② 根 `package.json` 脚本

```jsonc
"typecheck": "tsc --noEmit",
"typecheck:shared": "tsc --noEmit -p shared/tsconfig.json",
"typecheck:server": "tsc --noEmit -p server/tsconfig.json",
"build:server": "tsc -p server/tsconfig.build.json",
"build": "pnpm typecheck && pnpm typecheck:shared && pnpm typecheck:server && vite build",
"test": "vitest run"                    // 单仓好处：一个 vitest.config.ts 覆盖 src/ + shared/ + server/
```

`vitest.config.ts` 的 `include` 扩成 `["src/**/*.test.ts", "src/clip-web/**/*.test.ts", "shared/**/*.test.ts", "server/**/*.test.ts"]`。

#### ③ Dockerfile：同一个仓库，一次构建

```dockerfile
# server/Dockerfile（多阶段，构建上下文是仓库根）
FROM node:22-slim AS build
WORKDIR /app
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN corepack enable && pnpm install --frozen-lockfile
COPY . .
RUN pnpm build                         # ← 同仓：直接产出客户端 dist/
RUN pnpm build:server

FROM node:22-slim AS runtime
WORKDIR /app
COPY --from=build /app/server/dist         ./server
COPY --from=build /app/shared              ./shared
COPY --from=build /app/dist                /app/pwa     # ← PWA 静态（Node 直接托管）
COPY server/package.json ./
RUN corepack enable && pnpm install --prod --frozen-lockfile
USER 1000:1000
CMD ["node", "server/index.js"]
```

**对比 v7（分仓）**：那时要先在客户端仓打包 `opennote-web-<ver>.tar.gz`、
再让服务端镜像**下载 + 校验 sha256**。现在**一次 `pnpm build` 就都有了**——这是单仓最直接的一个好处。
（好处：不存在「镜像里的 PWA 与 API 版本错配」这一类问题。）

#### ④ CI（**单仓，一个流水线**）

| Job | 做什么 |
| --- | --- |
| `check` | `pnpm typecheck`（含 `shared/` 与 `server/`）+ **边界 grep**（§1.6 第 4 条） |
| `test` | `pnpm test`（`src/` + `shared/` + `server/` 一次跑完）+ **夹具测试**（§10.1 F） |
| `build` | `pnpm build` + `build:server` + 构建镜像 |
| `smoke` | 起 compose → 跑一遍 `/v1/health` 与 `bootstrap-admin` 冒烟 |

**单仓的代价**：CI 会同时触及两端（改客户端也会跑服务端测试）。对这个规模**完全可以接受**；
换来的是**任何破坏性改动都是一个 PR、原子生效**。

#### ⑤ ⚠️ 一个与仓库结构无关、但必须说清的安全边界

> **网页端信任的是「服务端当天发给它的那份 JS」。**
> 桌面/移动端的应用是从可信渠道装上去的；**网页端每次打开都在从服务器下载代码**。
> 而 E2EE 的前提是「不信任服务器」。所以：
> **服务端如果某天下发一段改过的 JS，就能拿到网页端 `localStorage` 里的 `accountKey`。**

这不是设计缺陷，是**浏览器端 E2EE 的固有边界**（所有 Web 端 E2EE 都面对它，与单仓/分仓无关）。
三条务实的应对：

1. **把保证等级说清楚**：桌面/移动 = 强（应用已装、密钥在主进程/Keychain）；
   **网页端 = 弱（信任服务端下发的代码）**。写进文档与 UI。
2. **可核对**：`/v1/health` 报 `webBuildHash`（构建时注入的产物哈希），
   让在意的人能核对「今天服务器给我的 JS 和我本地那份是不是同一个」。
3. **不做「网页端更安全」的宣传**——**绝不**把网页端当作高保证客户端来承诺。

## 6. 冲突、删除、改名的完整语义

### 6.1 三层冲突模型

| 层 | 机制 | 位置 | 作用 |
| --- | --- | --- | --- |
| **L1 协议层** | CouchDB revision tree：并发写产生多个 leaf，**不丢弃** | CouchDB | **保证不丢版本**；`_rev` 对不上返回 409 |
| **L2 决策层** | 客户端基线三方 diff → 两边都改就**列出不覆盖** | 客户端 | **主机制**；决定「谁赢」的是**用户** |
| **L3 收尾层** | 用户裁决后写合并结果为新 revision，落败 leaf 标 `_deleted: true` | 客户端驱动 + CouchDB | 让 revision tree **真正收敛** |

**关键取舍（上游两份支撑调研互相矛盾，本文档显式裁决）**：

- **默认：只报不猜（列出不覆盖）**。与现有 GitHub 通道一致（`src/lib/github/sync.ts:83-85,118-136`）。
- **可选的自动合并**：仅对**纯文本**且**用户显式点击**时，做**行级三方合并**（需要共同祖先）。
  **绝不默认开启，绝不后台自动执行。**
- **共同祖先缺失就不猜**：§3.10 指出 compaction 会让旧 revision 不可达 → 保留独立分支交用户裁决。
- **不采用「阈值式取巧」**：Notesnook 是「60s 内静默取新者」，但它明确「**从不合并两版文本**」。我们不采用。
- **Node 不参与裁决，而且 E2EE 下它也做不到**（只有密文）。
  控制台只**展示**冲突计数（`client_stats`），**不提供「自动解决」**——这也符合红线 2。

### 6.2 判定表（三方 diff 的完整语义）

| 本地 | 远端 | 内容 | 动作 |
| --- | --- | --- | --- |
| 未改 | 未改 | 同 | 无操作 |
| 未改 | 改了 | 不同 | **下载覆盖**（设备落后，自动补齐） |
| 改了 | 未改 | 不同 | **上传** |
| 改了 | 改了 | **相同** | **判为已同步**（不写入）← 「false conflict」，**P1 必修** |
| 改了 | 改了 | 不同 | **列出，不覆盖** |
| 新增 | 不存在 | —— | 上传 |
| 不存在 | 有 | —— | 下载 |
| 已删 | 未改 | —— | 删除（**受删除保护约束**） |
| 已删 | 改了 | —— | **列出**（改 vs 删） |
| 改了 | 已删 | —— | **列出**（改 vs 删） |
| 已删 | 已删 | —— | 无操作 |

> 「改了 + 改了 + 内容相同 → 判为已同步」来自 rclone bisync 官方定义；
> 二次来源是 Unison 手册的 **"false conflict"**。
>
> ⚠️ **E2EE 下这条靠 `ehash` 比较实现**——所以 `ehash` 必须是 `HMAC(macKey, sha256(plaintext))`：
> 只发 `sha256(plaintext)` 会让服务端能做同样的比较（泄露内容等价关系，§3.9 第 3 条）。

### 6.3 删除语义与「删除复活」的防范

- **删除必须可区分于「没看见」**——WebDAV/裸 S3 方案的核心痛点。
  **CouchDB 的 `_changes` 带 `deleted: true`** → **我们天然能区分**。
- **绝不用「listing 快照差异」推断删除**：rclone bisync 的 `--resync` 会「复制而非同步」，
  **导致已删除文件复活**。删除来源只有两个：**远端 `_changes` 的 `deleted: true`**，或**本地基线里有、现在扫描不到**。
- **删除保护阈值**：一次同步计划删除数 > `max(20, 总量 × 25%)` → 停止并请用户确认（客户端 + 服务端各一遍）。
- **`trash/` 与 `history/` 不同步**，所以删除在本地仍有回收站兜底（`.opennote/trash/`）。

### 6.4 墓碑保留期 vs 游标过期（长期离线设备的关键）

| 事实 | 后果 |
| --- | --- |
| `_changes` 是**日志**，不是**状态快照** | 设备离线超过日志可回溯范围 → **永远看不到**中间那些删除 |
| **compaction 会回收旧 revision 与旧变更** | 离线越久，越可能拿不到自己「错过了什么」 |
| 客户端凭「基线里有、远端树里没有」**反推删除** | 一旦远端树是**分页**取来的，**没取到的部分会被误判成删除** → **误删** |

**三条规则定死**：

1. **删除只能由「远端显式说它删了」触发**。树**必须完整**才允许「树里没有 ⇒ 删除」的推断；
   **`truncated` 为真时，只做新增与更新，全部删除一律挂起待确认**。
   （现有 GitHub 通道已有这个纪律：`planImport` 如实带 `truncated`，`src/App.tsx:789` 据此提示。）
2. **游标过期要走全量重来**：`/v1/changes` 返回 `{ resync: true }` → 客户端退化成全树比对
   （`planPush`/`planPull` 本来就是全树比对）。这正是 Joplin 的 `resyncRequired` 语义。
3. **墓碑必须比 update 事件活得更久**：Joplin 的做法是**旧 update 事件 180 天后压缩，
   create/delete 长期保留**——因为**丢掉一个 update 只是慢一点，丢掉一个 delete 会让文件复活**。
   → **`deleted: true` 的逻辑删除文档永不物理清除**。

### 6.5 改名

- 改名 = 删除 + 新建（§3.7），**会重传一次字节**。
- ⚠️ **E2EE 下改名是「换 did」**（`did = HMAC(path)`）：路径变了 → `did` 变了 →
  在服务端看来就是「旧的没了、来了个新的」。**与明文模式行为一致**，只是必然如此。
- **不要**试图推断 rename（Syncthing 的结论是「纯改名/大小写冲突**只报错、不自动解决**」）。

## 7. 安全模型

### 7.1 威胁模型与边界

**两个必须知情同意的点**：

> ⚠️ **① 边缘可见明文（若该笔记本 `crypto_mode='none'`）**。隧道/边缘必须能看到 HTTP 才能转发。
> E2EE 笔记本不受此影响——**这正是默认加密的理由**。
> ⚠️ **② 多账号意味着服务端运维者（你）在技术上能看到未加密笔记本的全部内容**。
> 对「分发给其他用户」这件事，**必须把这句话写在注册页上**。

| 资产 | 威胁 | 缓解 |
| --- | --- | --- |
| 笔记内容 | 服务端/边缘被入侵或运维者窥看 | **默认 E2EE**；明文笔记本**知情同意** |
| **`encRoot`** | 服务端或边缘拿到 | **`authToken` 与 `wrapKey` 分叉派生**（§1.5）；`encRoot` 只用 `wrapKey` 包裹后存服务端 |
| **跨账号越权** | A 读/写 B 的笔记本 | `memberships` 单一真源 + **越权 404** + **隔离测试 M1–M14** |
| **账号密钥** | 从客户端存储被读走 | 主进程持有（桌面）；**可轮换**（旧令牌立即失效）；**没有「踢单台设备」**（§1.5 代价 3） |
| **服务端 SQLite 泄露** | 拿到 `auth_hash` + `wrapped_enc_root` | `auth_hash` 是 256 位随机令牌的哈希 → **无法离线爆破** → `wrappedEncRoot` 安全 |
| **CLI 泄露密钥** | 管理员账号被服务端知晓 | **CLI 只发一次性引导码，绝不接触密钥**（红线 3、§1.5） |
| **Node 服务** | 唯一公网单点 | 最小路由面（`/` + `/v1/*` + `/panel`）；默认拒绝；限流；配额 |
| **CouchDB** | 被直接访问 | ✅ **不发布端口、不给 hostname** |
| 渲染层 XSS | 借主进程代理外发笔记 | 主进程代理收窄；**`authToken`/`encRoot` 由主进程持有** |
| 路径穿越 | `../` 写到库外 | `assertSafeRelative`（**仅明文笔记本**）+ `validate_doc_update`（第二道） |
| 一次误操作删库 | 基线坏 / bug | 删除保护阈值 + `trash/` + 备份 |
| 邀请码泄露 | 陌生人拿到账号 | 一次性 / 有期限 / 可作废 / **控制台可见未用码** |
| **账号删除** | 数据残留 | 删账号 → **级联删其独占笔记本的库**；有共享成员的笔记本移交 owner；写进控制台确认文案 |

### 7.2 「三样东西」的分工（本版的密钥体系）

| 名称 | 是什么 | 谁持有 | 泄露/丢失后果 |
| --- | --- | --- | --- |
| **账号密钥 `accountKey`** | 32B CSPRNG，**用户保存的唯一秘密** | **只有用户的设备** | 泄露 → 轮换；**丢失 → 账号与数据永久消失** |
| `authToken` | `HKDF(accountKey,"auth")`，发给服务端 | 客户端 + 服务端（**只存 sha256**） | 泄露 → 能读写你的笔记本，**但解不开密文**（推不出 `wrapKey`）→ 轮换即可 |
| `encRoot` | 32B CSPRNG，**永不出设备** | 客户端内存 + `wrappedEncRoot`（服务端） | 泄露 = 全部密文可解 → **必须靠 `accountKey` 不泄** |

**关键安全性质**（值得单独说）：

> 即使云边缘（TLS 终结处）或服务端被完全攻破，攻击者拿到 `authToken` 后：
> - ✅ **不能解密任何笔记**（缺少 `wrapKey` → 解不开 `wrappedEncRoot` → 拿不到 `encRoot`）
> - ❌ **能冒充你读写笔记本**（在令牌有效期内）→ **处置方式：轮换密钥**
>
> 也就是说：**E2EE 保证的是机密性，不保证「账号不被冒用」**。后者靠轮换。
> 这是必须写清楚的边界，不能含糊成「端到端加密，服务端什么都做不了」。

### 7.3 加固清单（**逐条做完再上线**）

**CouchDB**：

```ini
[chttpd]
bind_address = 0.0.0.0          # 只在 compose 内网可达（不发布端口）
port = 5984
require_valid_user = true
max_http_request_size = 50331648   # 32MB × 4/3 + 余量
# 不需要 enable_cors：唯一访问者是 Node，没有浏览器直连
```

1. **Admin Party 必须关掉**；密码由密钥管理注入，**不进镜像、不进 git**。
2. **运行时用专用账号（不是 admin）**；只在建库/改 `_design` 时用 admin。→ 缩小影响面。
3. **`_utils`（Fauxton）不对外**（无 hostname；需要时 `docker compose exec` + curl）。

**Node**：

1. 只挂三个路由面：`/`、`/v1/*`、`/panel`。**默认拒绝一切其他路径**。
2. 安全响应头：`Strict-Transport-Security`、`X-Content-Type-Options: nosniff`、
   `Referrer-Policy`、`X-Frame-Options: DENY`，以及**控制台自己的 CSP**。
3. cookie：`HttpOnly; Secure; SameSite=Lax`；变更请求要求 `X-Requested-With`（防 CSRF）。
4. 请求体上限、速率限制、SSE 连接上限、全局限流（§4.10）。
5. **日志脱敏**：永不记录密钥、`authToken`、`Authorization` 头、正文。
6. 容器**只读根文件系统 + 非 root 用户**（`read_only: true`、`user: "1000:1000"`），数据目录单独挂 volume。
7. **代码层审查（针对 `server/`）**：**不应出现任何解密函数或密钥类型**。
   建议加两条 CI 检查（把红线 3 机械化）：
   - `server/` 里不出现 `decrypt`/`encrypt` 导出或 `encRoot`/`notebookKey` 类型；
   - **`server/` 里不出现 `@noble/`**（服务端不该有加解密能力）。

### 8.1 `docker-compose.yml`（3 个容器）

> **这个文件在仓库根目录** `E:\repo\opennote\docker-compose.yml`（单仓）。

```yaml
services:
  couchdb:
    image: couchdb:3.3
    restart: unless-stopped
```

### 8.2 首次部署的引导顺序（密钥即身份特有）

```text
1. docker compose up -d
2. docker compose exec sync node dist/cli.js bootstrap-admin
   → 打印一个一次性【管理员引导码】（只在 stdout 出现一次，不写日志、不落盘）
   ★ CLI 不生成任何密钥
3. 客户端打开 → 「用引导码创建管理员账号」
   → ★ 客户端生成 accountId / accountKey / encRoot，派生出 authToken
   → 提示保存账号密钥（复制 / 下载 .key / 二维码）→ 强制「我已保存」确认
4. 控制台 → 生成注册邀请码 → 发给要用的人
5. 其余设备：★ 不要重新注册 —— 导入同一个账号密钥即可（一个密钥所有设备共用）
```

**四条必须做进 UI 的说明**（否则用户会以为有这些能力）：

1. **服务端无法补发密钥**（它从来没存过）。
2. **导出密钥只能在已有密钥的设备上做。**
3. **要踢掉某台设备 → 只能轮换密钥**（会让所有其它设备也要重新导入）。
4. **管理员也无法重置任何人的密钥。**

**密钥丢失的唯一出路**：管理员用 CLI 再发一个引导码，**创建一个新的管理员账号**；
或者你自己**用另一台还留着密钥的设备**导出、再导入到新设备。**旧的密文数据在密钥丢失后不可恢复。**

### 8.3 备份与灾难恢复

> ⚠️ **CouchDB 的备份不是 `rsync` 数据目录**。这是选 CouchDB 相对 C4/C3 实际付出的运维代价。

| 备份对象 | 方式 | 频率 | 恢复代价 |
| --- | --- | --- | --- |
| **CouchDB 数据** | ① **`POST /_replicate` 到第二台 CouchDB**（推荐）；② `couchdb-dump` / `_all_docs` 导出；③ 停机后 `rsync` | 每日 replicate + 每周全量 | ① 最省 |
| **`sync` 的 SQLite** | `sqlite3 control.db ".backup out.db"`（在线备份） | 每日 | 低（**但账号的 `auth_hash`/`wrapped_enc_root` 必须保住**，否则所有账号失效） |
| **配置与密钥** | `.env`、`local.ini`、`TUNNEL_TOKEN` → **密钥管理，不进 git** | 变更时 | 低 |
| **用户自己的** | **账号密钥**（离线记牢）+ 定期导出 zip | —— | ⚠️ **丢了就是不可恢复** |

**灾难恢复矩阵**：

| 丢了什么 | 恢复方式 | 代价 |
| --- | --- | --- |
| 一台设备 | 在另一台设备导出密钥 → 导入新设备 → 全量拉 | 需还有一台留密钥的设备 |
| **所有设备的密钥** | ❌ **无解**（密文还在，但打不开） | **这是 E2EE 的真实代价** |
| **`sync` 容器 / SQLite** | 重建 + 恢复 SQLite；**若 SQLite 没备份 → `auth_hash` 丢失 → 所有账号失效**（数据仍在但没人能认证） | ⚠️ **所以 SQLite 备份和 CouchDB 备份一样重要** |
| **CouchDB** | 从第二台复制回来；或从导出恢复 | 丢失最后一次 replicate 之后的内容 |
| **CouchDB + 某设备** | 用另一台设备重建（此时**该设备是唯一真源**） | 需至少一台设备还在 |
| **全都没了** | 从导出恢复 + 从留存的账号密钥进入 | 最后一次备份之后的内容不可恢复 |

**关键结论**：
- **CouchDB**：笔记数据的真源，**必须认真备份**。
- **`sync` 的 SQLite**：看起来「可重建」，**但 `auth_hash` + `wrapped_enc_root` 丢了就没人能进**。
  → **必须和 CouchDB 同级对待**（这是本版相对上一版新增的一条，因为身份现在只在服务端存了个哈希）。
- **账号密钥**：**只有用户自己能保**。服务端无论如何都救不了。
- **离机备份不在本方案的范围内**（§4.10）——**上面这张表只保证「服务端自己不出事」，不保证
  「服务器和你所有设备同时出事」时还有一份**。那份额外的备份请你自理，并注意两件事：
  ① `crypto_mode='user-key'` 的笔记本备份出来是**密文**，**必须同时备份账号密钥**，否则打不开；
  ② **`.gitignore` 里被忽略的文件既不进同步、也不会被任何自动化备份**（§3.11）。

### 8.4 升级与回滚

- **CouchDB**：`3.3.x` 补丁内升级安全；**跨大版本前先全量 replicate 备份**，并核对 `_design` 与 `local.ini`。
- **`sync`**：无状态（除 SQLite）；**迁移脚本必须先跑通 dry-run**。
  多账号下**回滚 `sync` 版本可能不兼容新 schema** → 迁移设计成「只加不删」。
- **客户端**：靠 `protocolVersion` + `cryptoMode` 做兼容判断——**不匹配就拒绝同步并提示升级**。
- **回滚**：客户端与 `sync` 回滚安全；**CouchDB 回滚不安全**。

### 8.5 可观测性（控制台是主要入口）

| 问题 | 数据源 |
| --- | --- |
| 同步还在工作吗 | `/v1/health`；每设备「上次成功同步时间」；SSE 活跃连接数 |
| 同步有多慢 | Node 结构化日志里 `syncOnce` 耗时分布（p50/p95） |
| 是不是在疯狂冲突 | **`client_stats` 的按天趋势**（控制台展示）。**持续增长 = 有一端基线坏了** |
| 多账号是否健康 | 每账号用量 / 配额占比；库数量增长；**认证失败计数**（异常升高 = 有人在探测令牌） |
| 服务端健康 | `/v1/health` + CouchDB `/_stats`、`/_active_tasks`、`/_prometheus` |

### 10.2 场景矩阵

| 场景 | 期望 |
| --- | --- |
| 同一账号 A 设备改 → B 设备打开 | B 看到新版本（**不弹冲突**） |
| A 改 → B 改同一篇 → 同步 | **列出冲突**，两份内容都还能找到 |
| A 改 → B 改 → **两边内容恰好相同** | **不算冲突**，判为已同步（E2EE 下靠 `ehash`） |
| A 删 → B 未动 | B 同步后删除（受阈值约束） |
| A 删 → B 改了同一篇 | **列出**（改 vs 删） |
| 断网编辑 30 分钟 → 恢复 | 自动补齐，**不阻塞编辑** |
| A 改名 → B | B 表现为「旧的没了、新的来了」 |
| 一次性删 60% 的库 | **被删除保护拦住**（客户端与服务端两道） |
| 服务器停 3 天 → 恢复 | 增量补齐，或退化为全树比对 |
| **新设备导入账号密钥** | 成功解锁 `encRoot` 并全量拉；**`did↔path` 映射重建成功** |
| **轮换密钥后，另一台设备继续同步** | **立即 401**，并显示「此设备的密钥已被轮换，请导入新密钥」 |
| 网页端两个标签页同时开 | **只建一条 `/v1/events` 连接**（SharedWorker 广播） |
| 手机上从后台回前台 | **立刻增量拉取** |
| **设备离线很久后回来** | 走 `resync` 全量比对；**删除不会被误判、已删文件不复活** |
| **两个账号各自同步** | 互不可见；控制台用量分别统计 |
| **入口重启（隧道）** | 公网恢复后客户端自动重连（退避） |

### 10.3 必须钉住的回归断言

1. **`.git/` 不在同步范围**（`isHiddenPath` 已兜底，`src/lib/github/sync.ts:164`）——加测试钉住。
2. **`.opennote/` 不在同步范围**，且**账号密钥 / `encRoot` / `did↔path` 映射都不在**。
3. **非法路径被服务端拒**（C9）。
4. **同步路径不触发整库重扫**：断言 `rescanWorkspace` **没有**被调用。
5. **纯 diff 函数搬家后行为不变**（`src/lib/github/` → `src/sync/diff.ts`）——
   **用现有 GitHub 测试套件全绿来证明**（这是「搬家不是重写」的证据）。
6. **忽略规则**：内置集覆盖 `.git/`/`.opennote/`；`.gitignore` 的 `!` 不能取反内置集；
   **被忽略的路径双向不可见**（不 push / 不 pull / 不删 / 不进 diff）——见 §10.1 E。
6. **`truncated` 时不产生删除**（C12）。
7. **越权一定是 404**（M1–M3）——多账号核心断言。
8. **`server/` 里不出现解密能力**（E6 + 两条静态检查：无 `decrypt*`/无 `@noble/`）。
9. **轮换零重加密**（K6）——本设计的核心不变量。
10. **注册一定要有码**（K2）——不存在抢注管理员的路径。
11. **路径规则两份实现判定一致**（§10.1 F1）——单仓下唯一无法靠类型系统消除的接缝。
12. **边界 grep 通过**（§10.1 F5）——`src/` ↔ `server/` 不许互相 import。

### A.4 v5 相对 v4 的改动（保留为决策记录）

| 主题 | v4 | **v5** |
| --- | --- | --- |
| **身份** | `username` + `password`（scrypt）+ 邀请码 + 会话表 | **密钥即身份**：一条客户端生成的 32B 密钥 = 一个账号（§1.5） |
| 凭据形态 | 设备令牌（sha256）+ 用户会话（12h） | **一个 `authToken`**，贯穿所有入口 |
| 加密密钥来源 | 用户记得住的**加密口令** → Argon2id | **`encRoot` 由 `accountKey` 经 `wrapKey` 包裹**（一个秘密搞定） |
| **慢 KDF** | 需要 Argon2id（客户端） | ❌ **不需要**（256 位随机密钥，HKDF 足够） |
| 密钥轮换 | 未涉及 | **零重加密**（只换 `auth_hash` + `wrapped_enc_root`）（§1.5③） |
| 口令重置 | 有（管理员） | ❌ **没有，也不该有** |
| 撞库防护 | 需要（限流 + 枚举防护） | ❌ 不需要（2²⁵⁶ 空间）；只留全局限流防 DoS |
| 每设备吊销 | 有（删 `devices` 行） | ❌ **没有**（一个密钥所有设备共用）→ **只能轮换** |
| 管理员创建 | 未明确 | **CLI 发一次性引导码，密钥仍由客户端生成**（§8.2） |
| 注册门槛 | 曾考虑「首个账号自动成为管理员」 | **始终只能靠邀请码/引导码**；不存在抢注路径 |
| SQLite 备份重要性 | 「可重建」 | ⚠️ **提到与 CouchDB 同级**（`auth_hash` 丢了所有账号进不去） |
| 账号共享 | `username` | **笔记本邀请码**（不需要知道对方是谁） |

**v5→v6 保持不变的部分**：CouchDB 数据模型（库名、`_local`、`validate_doc_update`、附件走 `_attachments`）、
§6 冲突/删除语义、§5.4 的 P0 五条、`truncated` 纪律、密钥层级（`accountKey → {authToken, wrapKey}`、`encRoot`、`wrappedEncRoot`）、
隧道不绑定、附录 B/C/D。

## 附录 D：术语表

| 术语 | 含义 |
| --- | --- |
| **账号密钥 `accountKey`** | 32B CSPRNG，客户端生成，**用户保存的唯一秘密**。一条密钥 = 一个账号 |
| **`authToken`** | `HKDF(accountKey, "auth")`；唯一发给服务端的东西（服务端只存 `sha256`） |
| **`wrapKey`** | `HKDF(accountKey, "wrap")`；**永不外发**，用于解开 `wrappedEncRoot` |
| **`encRoot`** | 32B CSPRNG，**永不出设备**；按笔记本 HKDF 出 `notebookKey` |
| **`wrappedEncRoot`** | `AEAD(wrapKey, encRoot, aad=accountId)`；存服务端，**服务端解不开** |
| **轮换** | 换 `accountKey` → 换 `authToken`/`wrapKey` → 重包 `wrappedEncRoot`。**零重加密** |
| **引导码 / 邀请码** | 前者由 CLI 发（建管理员）；后者由管理员在控制台发（建普通账号）。**都必须用**才能注册 |
| **`crypto_mode`** | 每笔记本的加密模式：`none`（明文、可共享）/ `user-key`（E2EE、不可共享） |
| **`did`** | 文档标识：模式 A = `f:`+base64url(path)；模式 B = `h:`+HMAC(idKey, path) |
| **`ehash`** | HMAC 后的内容哈希：让「内容相同不算冲突」成立，又不泄露内容等价关系 |
| **T1 / T2** | T1 = 同步服务（自动收敛）。**T2（离机备份）本方案不提供**——已从设计中移除（§4.10） |
| **基线 / 检查点** | 前者 = `.opennote/sync.json`（每路径 hash + rev + did）；后者 = 远端 `_local`（cursor） |
| **内置忽略集** | 硬编码的忽略列表（`.git/`、`node_modules/`、`dist/`、`release/`、`.opennote/`、`.DS_Store`…），**不可被 `.gitignore` 取反**（§3.11） |
| **忽略路径双向不可见** | 被忽略的路径不 push / 不 pull / 不删 / 不进 diff——防「规则变化导致误删或反复拉取」（§3.11） |
| **AEAD** | `XChaCha20-Poly1305`（`@noble/ciphers`）；192-bit nonce → **无需写入预算**；支持 AAD（本文用它绑定 `did`/`notebookId`/`accountId`） |
| **`shared/`** | 两侧共用的纯 TS：路径纯函数（`id(path)`/`path(id)`/NFC/`assertSafeRelative`）+ 线上类型 + `PROTOCOL_VERSION` + **共享夹具**。**无 DOM、无 Node 内建**（由它自己的 tsconfig 强制）（§1.6） |
| **共享夹具（fixtures）** | `shared/fixtures/` 里的 JSON 样本与用例表。单仓下用途收窄为：保证**无法被类型系统覆盖的 `_design` JS** 与 TS 实现判定一致（§10.1 F） |
| **`PROTOCOL_VERSION`** | 线上协议版本整数；`/v1/health` 与 `syncinfo` 都报它；**不匹配就拒绝同步**（防的是用户机器上的旧客户端） |
| **边界 grep** | CI 检查 `server/` 里没有 `from "../src/`、`src/` 里没有 `from "../server/`（§1.6） |
| **false conflict** | 两边都改过、但当前内容相同——不算冲突（Unison 术语） |
| **truncated** | 远端树没取全；此时**禁止推断删除**（§6.4） |
| **命名隧道 / Quick Tunnel** | Named = 生产（**SSE 正常**）；Quick = 演示用（**SSE 被缓冲，禁用**） |
