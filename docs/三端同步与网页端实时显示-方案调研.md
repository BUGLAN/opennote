# 三端同步 + 网页端实时显示 · 方案调研

> 调研日期：2026-10-13 · 对照代码版本：`ae12f6e`（0.11.0）
> 范围：**桌面端 Electron / Android(Capacitor) / 网页端 PWA 三端同步**，以及**网页端实时显示**别的端刚改过的内容。
> 需求前提（用户确认）：**不需要协同编辑**；默认「同一个用户在不同时间段修改同一份笔记」——即写者时序错开，而不是并发。

---

## 一、结论先行

1. **这是「文件级同步」问题，不是协同编辑问题。不要引入 CRDT（Yjs / Automerge / Loro / 操作日志）。**
   本项目的第一条架构约束是「文件是唯一真相，内存只是镜像」（[architecture-overview.md](architecture-overview.md):16-18）。
   CRDT 会把真相搬到「内存里的文档对象」上，与这条约束正面冲突；而且它换来的是「并发协同」这个**我们不需要**的能力，
   代价却是要额外持久化一份 CRDT 状态、并处理 Markdown 文本与 CRDT 文本的往返失真
   （Yjs 官方绑定层明确：JSON 不能当主存储，必须另存 Y.Doc 二进制；Loro 官方专门列出「简单 C/S 同步就够」时不建议用 CRDT，
   见 §3.4）。而「同一个人的多端笔记」这一场景，成熟产品——Obsidian Sync、Joplin、Syncthing——**都走文件级/条目级同步**（见 §3）。

2. **推荐路线（2026-10-13 修订）：把已有的「基线 + 内容哈希 + 三方 diff」抽象成 `SyncProvider`，
   然后走 C —— 自建 CouchDB（或国内对象存储 + manifest）；GitHub 降级为开发期调试 driver。**
   修订原因是**国内可达性**：`api.github.com` 时通时不通，不能当持续同步通道；
   而云盘那三家在国内同样不可用，B 里不存在「三端 + 国内可达 + 零运维」的组合。见 §4.1 / §4.2。
   项目里已经有一台可用的同步发动机：`src/lib/github/sync.ts` 的 `planPush` / `planPull` / `collectLocalFiles`
   （`.opennote/github.json` 基线里存 `localHash` / `remoteSha`，用 SHA-256 判「谁改了」，两边都改就列出来**一个字节都不动**）。
   它缺的只是：① 远端抽象不通用；② 只能手动点按钮；③ 没有「远端变更」的推送通道。
   另外两条成熟替代（哑存储 + 本地历史、内容寻址仓库 + 快照）见 §5.6。

3. **网页端「实时显示」在 C 下是原生能力**：CouchDB 的 `_changes?feed=continuous` 本身就是长连接推送
   （[复制协议](https://docs.couchdb.org/en/stable/replication/protocol.html) 把它定义为
   「never stops… kept alive by periodic heartbeats」，默认心跳 60000ms）；
   浏览器还可以直接用 `feed=eventsource`，拿原生 `EventSource` 的断线重连与 `Last-Event-ID` 续传。
   亚秒~秒级可见，不需要为「实时」单独加一层。
   若哪天退回 A（GitHub）当备用出口，则用**条件请求轮询**兜底——`304` 不计入配额
   （[GitHub 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)），
   但那是分钟级近实时，不是实时。

4. **有三处跨设备的正确性问题必须先修，否则同步会丢数据**（详见 §五.5）：
   ① `fileStates` 是**进程级**内存表，且三态播种靠 `mtime`（`src/data/fileStates.ts:43,52-73`）——mtime 在不同机器/网盘间不可比；
   ② 现有设计文档 D2「同一篇笔记不会被并发写」在跨设备后不成立（[设计-同步层与索引重构](设计-同步层与索引重构-2026-10-10.md):19-21），
      D4 又据此**整体删掉了冲突概念**；
   ③ 远端拉下来的文件若通过同一个本地后端写盘，会被主进程的**自写过滤**吞掉，UI 不会刷新
      （现有 GitHub 拉取就是靠落盘后手动 `rescanWorkspace()` 绕开，见 `src/App.tsx:868,880`）。

## 三、成熟方案调研（附一手来源）

### 3.1 文件级同步：外部工具与协议

| 方案 | 变更检测 | 冲突策略 | 实时性 | 网页端能否用 |
| --- | --- | --- | --- | --- |
| **Syncthing** | 双侧扫描 + 块哈希（128 KiB–16 MiB，SHA-256）+ **version vector**（每设备一个自增 counter，key 是 Device ID 前 64 位；重连走 delta index exchange 只传增量索引） | 内容不同的并发修改 → 把较旧/来源较劣的一方改名成 `<名>.sync-conflict-<日期>-<时间>-<device>.<扩展名>`，**两份都保留并继续传播** | 有 watcher，但默认聚合 10s（`fsWatcherDelayS`），删除再延 1min；官方说「轻微延迟」→ 实际秒级到十几秒 | ❌ BEP 是长连接二进制协议 + 常驻进程，无浏览器实现，也不能塞进 Capacitor WebView |
| **rclone bisync** | 保留上一次的 **listing 快照**，与本次两侧 listing 做三方比较（`--compare size,modtime[,checksum]`） | 默认 `--conflict-resolve none`：两边新/改且内容不同 → `file.txt.conflict1` / `.conflict2`，**两份都留**；可配 `newer/older/larger/...` 或 `delete` | 按次运行（cron/手动），非实时 | ❌ 本机 CLI |
| **网盘同步客户端**（Dropbox / OneDrive / iCloud / Google Drive） | 服务端 `rev` / `eTag`+`cTag` / changes pageToken | 各厂商保留「冲突副本」（如 `文件 (conflicted copy).txt`）；iCloud 用 `NSFileVersion` 标记冲突版本 | 秒级~分钟级，厂商决定 | ⚠️ **厂商的文件夹同步客户端**只服务本机；但**云盘的开放 API 浏览器可直接用**（见下「第四条经验」） |
| **WebDAV**（RFC 4918 + RFC 6578） | `PROPFIND` + `getetag`；**RFC 6578 的 `sync-collection` REPORT + `sync-token` 只返回上次 token 之后的变更**；乐观锁用 `If-Match` / `If-None-Match` | 由客户端决定（Nextcloud 客户端生成冲突副本，并回读 `OC-Conflict*` 响应头） | **无任何推送机制**，只能轮询（Nextcloud 实测分钟级） | ✅ 纯 HTTP，浏览器可 fetch（需 CORS + CSP），服务端零开发 |
| **Git**（本项目已用） | 三方 diff（基线里存 `localHash`/`remoteSha`） | 非快进推送被拒绝 → **绝不强推**，让用户先拉；两边都改的逐条列出 | 无推送，靠轮询/手动 | ✅ 网页端可直接用（CSP 已放行） |
| **S3 兼容 + 自研** | `ListObjectsV2` 分页，但 **ETag 不能当内容指纹**（只有非 multipart 且未加密/SSE-S3 时才是 MD5）→ 必须把哈希写进 metadata，或自建 manifest | 条件写 = CAS：`If-None-Match`（不存在才写）/ `If-Match`（ETag 未变才覆盖），412/409，官方说明条件请求**不加价** | ❌ 服务端事件只能投递到 SNS/SQS/Lambda/EventBridge，要秒级必须自建转发 | ✅ 浏览器可用（SigV4 或 presigned URL；别在前端放长期密钥） |

**可直接抄的四条经验**：
① 判「谁改了」用**内容哈希**而不是 mtime（rclone 默认对比 size+modtime 会不够，Syncthing 用块哈希 + version vector）；
② 冲突**不要静默覆盖**，要么保留冲突副本（Syncthing/rclone），要么列出来让用户决定（本项目 GitHub 已经这么做）；
③ **对象存储的 ETag 不是内容指纹**，S3 上做增量必须自带 manifest 或 metadata 哈希；但它的条件写是现成的乐观锁
（这正是 §5.2 `put(path, bytes, baseRev)` 能成立的依据）；
④ **云盘开放 API 是「不自建服务端、却仍能拿到服务端推送」的唯一一条路**：OneDrive 有 `/delta` 的 `deltaLink`
+ change notification 订阅（webhook / Event Hubs / Event Grid），Google Drive 有 `changes.list` 的 pageToken + `changes.watch`
notification channel，Dropbox 有 `files_list_folder_longpoll`；Dropbox 官方 SDK 明确支持现代浏览器与 Web Worker（OAuth PKCE）。
代价是 OAuth、厂商锁定与配额。

### 3.2 笔记产品的同步架构：五种范式

| 范式 | 代表 | 真源 | 同步粒度 | 服务端 | 实时能力 |
| --- | --- | --- | --- | --- | --- |
| **A. 外部工具同步文件夹** | Obsidian / 本地 Markdown 用户 + Syncthing、网盘、Git | 磁盘文件 | 文件/块 | 无（或厂商网盘） | 取决于工具（Syncthing 有 watcher） |
| **B. 驱动式 SyncTarget** | **Joplin** | 本地数据库 + 远端 blob | 条目（note/资源） | 可换：Joplin Cloud / Nextcloud / S3 / WebDAV / Dropbox / OneDrive / 本地 FS | 内容变更后**自动后台同步**；无服务端推送 |
| **C. 复制协议 / 文档数据库** | **Obsidian Self-hosted LiveSync**、CouchDB 系 | 本地数据库，远端是同构数据库 | 文档 + chunk | CouchDB（自建）/ S3 兼容对象存储（MinIO/R2）；也支持 WebRTC P2P（但**仍需要信令中继**） | `_changes` 连续 feed = 长连接推送 |
| **D. 闭源托管同步** | **Obsidian Sync** | 磁盘文件（本地优先） | 文件/设置 | 官方托管（付费） | 后台常驻同步；共享库宣称实时 |
| **E. 内容寻址仓库 + 快照** | **思源笔记 SiYuan（dejavu）** | 本地 workspace；同步/快照都先提交成仓库对象 | 文件 → chunk（内容寻址去重） | 官方云 / **S3 / WebDAV 可自建**；还有局域网 chunk 来源 + 同步感知 | interval + 感知触发，准实时 |

**Joplin 的抽象几乎就是本项目该走的形状**——官方表述（[Joplin Synchronisation](https://joplinapp.org/help/apps/sync/)）：
「Most of the synchronisation process is done at an abstract level and access to external services … is done via lightweight drivers.
It is easy to support new services by creating simple drivers that provide a **filesystem-like interface**, i.e. the ability to
**read, write, delete and list items**.」并支持 Joplin Cloud / Nextcloud / S3 / WebDAV / Dropbox / OneDrive / 本地文件系统，
内容变更后自动后台同步。这就是 §五 的 `SyncProvider` 的业界同构物。

**Obsidian LiveSync 的关键取舍**（[仓库 README](https://github.com/vrtmrz/obsidian-livesync)）：CouchDB 或对象存储（MinIO/S3/R2）+ E2EE；
WebRTC P2P「no central data-storage server is required, but a **signalling relay is still required** for peer discovery」，
且「at least one device containing the required data **must be online** while another device synchronises」——
即 **P2P 省掉的是存储，不是服务器；而且它不能保证随时可用**。这解释了为什么「零后端 + 真实时」在工程上很贵。

**CouchDB 复制协议**（[v3 规格](https://docs.couchdb.org/en/stable/replication/protocol.html)）值得单独注意：它定义了
`GET /{db}/_changes`（`feed=continuous` + `heartbeat`）、`POST /{db}/_revs_diff`（只问「缺哪些 revision」）、
`_local/<replication-id>` 里的 **checkpoint**（上次同步到哪），以及 MVCC 的 `N-sig` revision / leaf revision 冲突模型。
**它同时解决了「增量」「检查点」「实时推送」「冲突」四件事，而且服务器是现成的开源软件。**
冲突不会丢：并发写会产生多个 leaf revision（构成 revision tree），CouchDB **不丢弃**冲突分支，只用确定性算法选 winner；
`GET /db/doc?conflicts=true` 取冲突列表、`?open_revs=all` 取全部分支，写回合并结果并对旧分支标 `_deleted:true` 才算解决。
PouchDB 完整实现该复制算法，`sync({live:true, retry:true})` 自带断线重试，官方注明适合移动设备
（[PouchDB replication](https://pouchdb.com/guides/replication.html)）。

**Obsidian Sync**（[官方页](https://obsidian.md/sync)）的公开信息：AES-256 端到端加密、后台自动同步、每篇笔记版本历史、
支持 Mac/Windows/Linux/iOS/Android **以及 headless 服务器**、离线编辑恢复联网后合并、可选择性同步附件；
闭源付费（$4/月）。它是「D 范式」的标杆，本项目不可能也不需要在能力上对齐它。

**范式 E（思源 SiYuan / dejavu）最值得本项目细看**（[dejavu](https://github.com/siyuan-note/dejavu) +
`kernel/model/repository.go`、`sync.go`）：同步与快照都**不直接同步文件**，而是先提交成一个「数据仓库」，
结构是 `indexes/ objects/ refs/`，`Index / File / Chunk / Ref` 全部 **SHA-1 内容寻址**；
上传/下载以 tag index 为单位、**只传缺失 chunk** → 天然增量 + 天然去重；快照 = 带 tag 的 index，
回滚前会**自动暂停同步并先为当前数据建快照**。远端支持官方云、**S3、WebDAV**（都可自建）。
这是「要增量 + 要版本回溯 + 要附件去重」时**比 CRDT 便宜得多**的成熟模型。

**另一个对「哑存储」极友好的做法是 Remotely Save**（[设计文档](https://github.com/remotely-save/remotely-save/blob/master/docs/sync_algorithm/v3/design.md)）：
自 0.4.1 起**不再向远端写任何元数据**，只在本地保存「上次成功同步的状态」，用
local/remote × unchanged/modified/deleted/created 的**决策表**决定 push/pull/delete/conflict（含删除保护），
远端可以是 S3 / WebDAV / Dropbox / OneDrive 这类「哑存储」。**这正好是本仓 `.opennote/github.json` 基线的泛化**——见 §5.6。

**LiveSync 有一条纪律可以直接抄**（[datastructure.md](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/datastructure.md) +
[specs_conflict_resolution.md](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/specs_conflict_resolution.md)）：
「**文件字节**才是内容身份，mtime / size / 路径 / 哈希都不算」，并且给每台设备持久化
`path → revision` 的 **provenance**；三方合并用「双方都有的最近共同祖先」，**祖先缺失就不猜、保留独立分支交给用户**。
这与本仓 `FileRecord{stat, content}` 的 I2 不变式同向，也再次说明 §5.5 第 5 条的 mtime 依赖必须改。

### 3.3 实时通道选型

| 通道 | 方向 | 浏览器支持 | 经 CDN / 穿透 | 移动端后台 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **SSE**（[HTML Living Standard](https://html.spec.whatwg.org/multipage/server-sent-events.html)） | 服务端→客户端单向 | 全支持，自动重连 | 好（就是 HTTP） | 后台会被挂起 | **网页端实时显示（推荐）** |
| WebSocket（[RFC 6455](https://datatracker.ietf.org/doc/html/rfc6455)） | 双向 | 全支持 | 需代理/CDN 支持 | 后台会被挂起 | 需要客户端上行时（本项目不需要） |
| WebRTC DataChannel（[RFC 8826](https://datatracker.ietf.org/doc/html/rfc8826)/[8827](https://datatracker.ietf.org/doc/html/rfc8827)） | 双向 P2P | 全支持 | 需 STUN/TURN + 信令 | 同样受限 | 想省服务端流量；但 LiveSync 的经验是「信令中继仍不可少」 |
| HTTP 轮询 / 长轮询 | 客户端→服务端 | 全支持 | 好 | 回前台才跑 | **零服务端方案（推荐先做）** |
| CouchDB `_changes?feed=continuous` | 服务端→客户端 | 全支持（就是 HTTP 流） | 好 | 回前台重连 | 已经选了 CouchDB 时**免费得到实时**（协议文档建议心跳 10000ms；`_changes` API 默认 60000ms） |

SSE 的两点工程注意：WHATWG 规格明确警告 HTTP/1.1 对单域名的**并发连接数限制**——同域多开标签页各挂一个 `EventSource`
会撞上限（官方建议用 SharedWorker 共享连接）；它自带断线重连与 `Last-Event-ID` 续传语义。
若要自托管 WebSocket，[Cloudflare Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
的 Hibernation API 可以让实例空闲休眠而不断开客户端，是目前最省运维的落点。

**移动端必须接受的现实**：这不是「最好别这么做」，而是平台强制——
WICG [Page Lifecycle](https://wicg.github.io/page-lifecycle/) 把 **Frozen** 定义为
「lifecycle state for **CPU suspension**」，并写明「Normally HIDDEN pages will be frozen to conserve resources」，
冻结期间 JS、定时器、网络回调全部停止；Apple 官方文档同样写明 App 进入后台后
「UIKit suspends it」、「Apps don't normally receive any extra execution time after they enter the background」；
Android 的 [Doze](https://developer.android.com/training/monitoring-device-state/doze-standby) 会推迟后台 CPU 与网络活动。
Capacitor 官方 App 插件提供 `appStateChange` / `pause` / `resume` 事件
（[@capacitor/app](https://capacitorjs.com/docs/apis/app)，Android 上由 Activity 的 `onResume`/`onStop` 触发，Web 端等价于 `visibilitychange`），
这是移动端**唯一可靠**的「回到前台」信号。
所以正确形态是「**前台事件（resume / appStateChange / visibilitychange）+ 增量拉取（since / checkpoint）**」，
而不是指望后台长连接——项目现在连这个兜底都还没有（缺口 G7）。
后台唤醒只能靠 APNs/FCM 系统推送，不能靠 JS 长连接。

**网页端「不花配额」的轮询**：GitHub 官方明确写了 `304` 条件请求在有 `Authorization` 头时**不计入** primary rate limit，
并点名「especially useful when you poll an endpoint」（[best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)）；
配额与退避规则见 [rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。
**但注意**：仓库自己的注释说 `raw.githubusercontent.com` 走 CDN、不占 API 那 60 次/小时的匿名配额
（`vite.config.ts:186`）——那是取**文件内容**的路径；要拿**「哪些文件变了」**仍需 `api.github.com` 的
tree/manifest 接口（或对该接口发条件请求）。

### 3.4 为什么明确不用 CRDT（一手依据）

- **必须多存一份二进制，直接违背「文件是唯一真源」**：Yjs 的变更编码为可交换、可幂等的 *document update*，
  同步靠 `encodeStateVector` 算差量；但官方绑定层写明
  *"Serializing and deserializing to JSON will not store collaboration history steps and as such should not be used as the
  primary storage. You will still need to store the Y.Doc binary update format."*
  （[y-prosemirror README](https://github.com/yjs/y-prosemirror)）——即磁盘上的 `.md` 之外必须再维护一份 Y.Doc 二进制。
- **粒度不适配**：一个 Markdown 文件 = 一个 `Y.Doc`、一个 room；文件数 = 连接数 = 持久化条目数。
- **官方自己说了不适用场景**：Loro 专门有一页
  [When not to use CRDT](https://loro.dev/docs/concepts/when_not_crdt)，列出的排除项包含「简单 C/S 同步就够」——
  本项目的需求正落在这一档。
- **状态只增不减**：CRDT 的历史/墓碑只增长，只能靠 GC 与格式优化缓解（Yjs V2、Loro 的 Document Size 都在专门优化这件事）。
- **附件不是它的强项**：Yjs 没有 blob 类型；Loro 把大二进制列为不适用场景。图片仍得走文件系统/对象存储。
- Automerge 也一样：`StorageAdapter` 落盘的是二进制 chunk，sync protocol 是 point-to-point
  （[automerge-repo](https://automerge.org/docs/reference/repositories/storage/)）。

**结论**：本项目「同一用户、时序错开」的语义下，CRDT 的合并收益≈0，代价是第二个真源 + 永久墓碑 + 包体/状态体积。

一手来源：[yjs](https://github.com/yjs/yjs)、[y-websocket](https://github.com/yjs/y-websocket)、
[y-indexeddb](https://github.com/yjs/y-indexeddb)、[y-prosemirror](https://github.com/yjs/y-prosemirror)、
[Hocuspocus](https://tiptap.dev/docs/hocuspocus/getting-started/overview)、
[Automerge](https://automerge.org/docs/reference/repositories/storage/)、[Loro](https://loro.dev/docs/concepts/when_not_crdt)。

### 3.5 非 CRDT 的「本地优先同步引擎」：都要求中心权威库

| 引擎 | 模型 | 能不能用在「无中心库、文件即真源」 |
| --- | --- | --- |
| Replicache / Zero | mutator 本地乐观执行 + push 重放，pull 按 cookie 算 patch；**poke** 只是「该 pull 了」的信号；官方口径是 *server authoritative* | ❌ 假定服务器持有 canonical 状态（示例放 Postgres） |
| ElectricSQL | 官方自称 *read-path sync engine for Postgres*，写路径由开发者自己的 API 负责 | ❌ 必须有 Postgres 中心库 |
| PowerSync | server-authoritative reconciliation；客户端写进 upload queue 顺序上传 | ❌ 需要源库 + 服务；冲突是字段级 LWW、delete 永远赢 |
| RxDB | `replicateRxCollection({pull, push})`，checkpoint 迭代 / stream 观察，断线重连发 `RESYNC` 回退 checkpoint；默认冲突处理是 master 赢 | ⚠️ 需中心存储，但**协议最薄**，后端可为任意 HTTP/WS |
| TinyBase | `MergeableStore` + `Synchronizer`，HLC 时间戳确定性合并 | ⚠️ 不是文件同步；适合当「元数据/设置」的合并层 |

**可抄的是「checkpoint / cursor」这个模式**，不是它们的服务端：`since`/`cursor` 记「上次同步到哪」，
断线重连只拉增量。这正是本项目缺口 G3（无设备 ID、无版本号）。

一手来源：[Replicache how-it-works](https://doc.replicache.dev/concepts/how-it-works)、
[Zero](https://zero.rocicorp.dev/docs/introduction)、[ElectricSQL](https://electric.ax/docs/intro)、
[PowerSync 冲突处理](https://docs.powersync.com/handling-writes/handling-update-conflicts)、
[RxDB replication](https://rxdb.info/replication.html)、[TinyBase Synchronizer](https://tinybase.org/api/the-essentials/synchronizing-stores/synchronizer/)。

## 四、三条候选路线对比

> 前提：三端 = 桌面 Electron + Android + 网页 PWA；非并发；网页端要「别处改了，这边自动看到」。

| 维度 | **路线 A：Git 仓库当同步枢纽**（私有 repo） | **路线 B：网盘/云盘**（Syncthing 同步文件夹，或云盘开放 API 当后端） | **路线 C：自建/托管同步服务**（CouchDB 或自研 SSE + 对象存储） |
| --- | --- | --- | --- |
| 三端一致性 | ✅ 三端都实现同一套 plan/diff | ⚠️ 文件夹同步只覆盖桌面/Android；**换成云盘 API 则三端都行** | ✅ |
| 网页端实时显示 | ✅ 条件请求轮询，秒~分钟级 | ⚠️ 文件夹同步 ❌；**云盘 API + 服务端变更订阅可做到秒级**（OneDrive/Drive） | ✅ SSE / continuous feed，亚秒~秒级 |
| 复用现有代码 | ⭐⭐⭐ 现有 GitHub 同步器直接改造 | ⭐ 只需读盘刷新（云盘 API 路线可复用 plan/diff） | ⭐⭐ 纯函数可复用、传输重写 |
| 运维成本 | 0（GitHub 托管） | 0~低（Syncthing 自托管 / 网盘付费） | 中（一个服务 + 备份 + 域名/TLS） |
| 新增依赖 | 0 | 各端装同步客户端 / 或各端接 OAuth SDK | 服务端组件 or 一小段自研服务 |
| CSP / 平台改动 | 免改（网页版已放行） | 云盘路线要把其域名加进网页版 CSP | 要改网页版 CSP；桌面端要走主进程代理 |
| 隐私 / E2EE | 仓库私有 + token；**无 E2EE**（GitHub 能看到明文） | 取决于网盘；Syncthing 可全 P2P | 可做 E2EE（参考 Joplin / LiveSync），但工作量大 |
| 大附件 / 图片 | ⚠️ 仓库有体积软上限，图片会进 git 历史；每次同步推 blob | ✅ 无所谓 | ✅（对象存储便宜） |
| 冲突安全 | ✅ 非快进拒推 + 逐条列出（已实现） | ✅ 冲突副本 | ✅ 可在协议层做（CouchDB leaf revision） |
| 离线优先 | ✅ 本地始终是完整副本 | ✅ | ✅ |

**选型结论**：
- 想**今天就能落地、0 运维**：选 **A**。
- 已经把笔记放在**网盘/NAS**：选 **B**。其中「Syncthing / 网盘同步文件夹」覆盖不到网页端；
  改用**云盘开放 API 当远端**（OneDrive / Google Drive / Dropbox）才能三端通吃并拿到服务端推送——代价是 OAuth 与厂商锁定。
- 要**真正的实时**、要 E2EE、要摆脱 GitHub：选 **C**，且优先**直接上 CouchDB**（协议现成、四件事一次解决），而不是自研协议。
- **A / B / C 不冲突**：把远端抽象成 `SyncProvider` 后，A 是第一个 driver；B（哑存储、云盘 API）与 C（CouchDB / SSE）
  只是后续的 provider 实现，核心的 `planPush`/`planPull` 纯函数不用改。这也是本文推荐的路径。

### 4.1 决断：先看「网络可达性」，再谈省不省

> **⚠️ 2026-10-13 修订**：本节初版结论是「A 最好」，前提是 **GitHub 可达**。
> 确认本项目实际面向**国内用户**后，这个前提不成立，结论**反转为 C**。
> 修订依据与 C 的后端选型见 §4.2；下面的 A 代价清单仍然有效，用于说明「A 即使在可达时也要付什么」。

**判断依据**（按本项目实际约束排序，不是通用排序）：

| 决定因素 | A. GitHub | B. 网盘/云盘 | C. 自建服务 |
| --- | --- | --- | --- |
| **国内可达性（一票否决）** | ❌ `api.github.com` / `raw.githubusercontent.com` 时通时不通，**作为持续同步通道不可靠** | ❌ Google Drive / Dropbox / OneDrive 同样不可用；iCloud 到不了网页与 Android | ✅ **唯一由自己完全控制的一条** |
| **网页端（硬需求）** | ✅ CSP 已放行，fetch 直用 | ⚠️ 文件夹同步到不了网页；云盘 API 可以但国内用不了 | ✅ 但要改 CSP + 主进程代理 |
| **复用现有代码** | ⭐⭐⭐ 发动机已在 `src/lib/github/sync.ts` | ⭐ 只剩「读盘刷新」能复用 | ⭐⭐ 纯函数可复用，传输重写 |
| **新增运维** | 0（托管） | 0~低 | **中**：一台要自己装的 CouchDB/服务 |
| **实时性** | 条件请求轮询，**秒~数十秒** | 云盘 webhook 可秒级 | 亚秒~秒级 |
| **平台改动面** | 桌面端要补一条主进程 HTTP（见下） | 三端各接一套 OAuth | 同左 + CSP + 服务端配置 |
| **大附件 / 隐私** | 图片进 git；无 E2EE | 取决于厂商 | 对象存储便宜；可做 E2EE |

**A 的真实代价（必须如实说清，不藏）**

1. **不是「实时」，是「分钟级近实时」。** 上限由两段延迟决定：保存后的推送防抖 + 网页端的轮询间隔。
   现实目标：**15~45 秒**。轮询用条件请求（`304` 不计配额）可以压到 5~10 秒，但 GitHub 有 secondary rate limit，
   不建议更激进。
2. **桌面端目前根本不能用 GitHub 功能。** README:195 写明桌面版 CSP **不放开** `api.github.com` / `raw.githubusercontent.com`，
   「对应功能也不开放」。所以要让 A 成为桌面端的同步后端，**必须补一条主进程 HTTP 通路**——
   这笔成本 A 和 C 都要付，不影响结论，但别漏算。
3. **提交噪音。** 自动同步若每次保存都推，会产生大量小 commit。缓解：推送防抖到「停笔 10~30 秒 / 切后台 / 关窗前」，
   并按「一次同步 = 一个提交」聚合（现有 `pushChanges` 本来就是一次一个提交）。
4. **图片/大文件进 git 历史。** 仓库有体积软上限，二进制会永久留在历史里。缓解：笔记正文与图片分开评估，
   真有大媒体需求时再考虑把 `assets/` 排除、只同步 `.md`。
5. **网页端的令牌在浏览器里。** 沿用现有 model（`localStorage`/`sessionStorage`、绝不进 `.opennote/`），
   但要承认「能读到站点存储的程序就能拿到它」。
6. **没有 E2EE，且依赖 GitHub 可用性。** 私仓 + token 对个人笔记通常够；GitHub 挂掉只影响同步，不影响编辑。

**为什么不选 B（在国内直接出局）**：Syncthing / 网盘同步文件夹**到不了网页端**；
而云盘开放 API 那三家（OneDrive / Google Drive / Dropbox）在国内同样不可用，iCloud 又到不了网页与 Android。
B 里不存在「三端 + 国内可达 + 零运维」的组合。

**为什么选 C**：
1. **可达性掌握在自己手里**——这是国内场景下唯一能真正解决的一条，也是它压过 A/B 的决定性理由；
2. **真秒级**：`_changes?feed=continuous` / SSE，不必在轮询间隔上做妥协；
3. **可 E2EE、可完全自托管**：数据与密钥都不经过第三方；
4. **一条通道收齐三端**：桌面、Android、网页端共用同一套 provider。
代价是三条路里工作量最大、并且**要多维护一台服务器**——这是明知且愿意付的成本，不是被忽略的。

**A 的新定位**：不再是「首选」，而是**开发期调试 driver / 备用出口**。
`SyncProvider` 抽出来之后，GitHub 作为 driver 之一留着，本地开发与 CI 用它做端到端验证（不受网络影响）；
国内用户默认走 C。这样将来可达性再变也不返工。

**落地顺序**：P0 五条正确性前置 → P1 抽 `SyncProvider`（GitHub 保留为调试 driver，不引入新依赖）
→ P2 CouchDB provider + 自动 pull/push + 冲突列表 → P3 `_changes` 实时（网页 SSE / 桌面主进程 / 移动回前台）。

### 4.2 选了 C 之后真正的分岔：服务器放哪、用哪种后端

「选 C」只定了一半；**决定成败的是下面这一层**，因为它直接决定国内可达性与运维量：

| 后端 | 实时性 | 国内可达性 | 运维 | 适合 |
| --- | --- | --- | --- | --- |
| **C1. 自建 CouchDB**（Docker，境外 VPS 或境内 VPS） | ✅ 秒级（`_changes`） | ✅ 自己选机房 | 一台 VPS + TLS | **要真秒级、要 E2EE，首选** |
| **C2. 国内对象存储**（阿里云 OSS / 腾讯云 COS，S3 兼容）+ manifest | ⚠️ 只能轮询 | ✅ 最快 | 免运维（只有 bucket + 规则） | 不想维护服务器，接受秒~分钟级 |
| **C3. 国内 WebDAV**（如坚果云）| ⚠️ 只能轮询 | ✅ | 零运维 | 想零成本起步、接受轮询 |
| **C4. 自研极小 SSE 服务** | ✅ 秒级 | ✅ | 一个服务 + 部署 | 不想背 CouchDB，但愿意自己写/维护 |

**部署选址的两个现实约束**（比选后端更容易被漏）：

1. **服务器离用户多远**：境外 VPS（香港 / 新加坡 / 日本）免备案、部署最快，但从国内访问的延迟与稳定性取决于线路；
   境内 VPS 速度快，但**网站对外提供服务通常需要 ICP 备案**。这是项目排期里必须提前算进去的一项。
2. **网页端本身也要有可达的托管地址**：现在 README 说「网页版还没有可访问的部署地址」。
   走 C 之后，**把 PWA 与同步服务放在同一个域名/机器上**最省事——一份运维、一处 TLS、一处 CSP `connect-src`。

**最终选定（2026-10-13）**：**C4 —— 自研服务端，技术栈 Node 22 + TypeScript（与客户端同仓、共享契约）**，
部署在自有小 VPS 上，并与 PWA 同机同域托管。
选它的决定性理由是**共享契约与路径规则**：协议是我们自己的，最大的风险是两端类型漂移，
而同仓 TS 能直接复用 `src/fs/paths.ts` 的 `assertSafeRelative` 与一份共享 contract
（仓库已有先例 `src/clip-web/contract.ts`）。接口与改动清单见
[设计-同步服务接口与客户端改动清单-2026-10-13.md](设计-同步服务接口与客户端改动清单-2026-10-13.md)，
完整对比见 [选型-自托管同步后端-C1-C4-2026-10-13.md](选型-自托管同步后端-C1-C4-2026-10-13.md)。
**C1（CouchDB）保留为备选**：服务端一行代码都不用写（Docker 起、配 CORS/TLS/专用用户），
代价是服务端数据变成数据库形态、内存占用最高；它的详细设计另存
[设计-CouchDB同步-2026-10-13.md](设计-CouchDB同步-2026-10-13.md)。
三条路的共同点不变：`planPush`/`planPull` 一行不改。

## 五、推荐方案与落地路径

### 5.1 目标架构

```
        ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
        │ Electron 桌面 │   │ Android 端   │   │ 网页端 PWA   │
        │ node backend │   │ capacitor    │   │ fsa / opfs   │
```

### 5.2 `SyncProvider` 接口草案（对齐 Joplin 的 SyncTarget 与本仓的 `FileSystemBackend`）

```ts
export interface RemoteEntry { path: string; rev: string; bytes: number }
export interface RemoteChangeSet { paths: string[]; cursor: string }

export interface SyncProvider {
  readonly kind: "github" | "couchdb" | "webdav" | "s3";
  /** 整棵远端树（首次 / 兜底用）。成本 ∝ 文件数。 */
  list(): Promise<RemoteEntry[]>;
  read(path: string): Promise<Uint8Array>;
  /** 乐观锁：baseRev 不匹配必须失败，绝不静默覆盖。 */
  put(path: string, bytes: Uint8Array, baseRev: string | null): Promise<{ rev: string }>;
  remove(path: string, baseRev: string): Promise<void>;
  /** 只取「相对 cursor 变了什么」。有服务端时实现为长连接/SSE；GitHub 实现为条件请求。 */
  changes(cursor: string | null): Promise<RemoteChangeSet>;
  /** 可选：服务端主动推送（SSE / CouchDB continuous feed）。 */
  subscribe?(onChange: (paths: string[]) => void): () => void;
}
```

- GitHub 实现：`list()` = `git/trees?recursive=1`；`changes()` = 带 `If-None-Match` 的 tree 请求，`304` 直接返回空；
  `put()` = blob→tree→commit→updateRef（现有 `pushChanges`），`rev` = blob sha；`subscribe` 不实现 → 退化为轮询。
- CouchDB 实现：`list()` = `_all_docs`；`changes()` = `_changes?since=cursor`（continuous 时即 `subscribe`）；`rev` = `_rev`。

### 5.3 网页端实时机制

| 档位 | 机制 | 预期延迟 | 代价 |
| --- | --- | --- | --- |
| **主路径** | CouchDB `_changes` 长连接（浏览器用 `feed=eventsource`，或用 `fetch` 读 `feed=continuous` 的流）。**事件只当「来拉了」的信号，不携带内容** → 触发一次正常同步 | 亚秒~秒 | CSP + CORS + 认证（桌面端走主进程、不需要 CORS） |
| 降级 | 长连接不可用 → `feed=longpoll`（配 `since=now`，最省）→ `feed=normal` 每 15–30s 轮询 → `visibilitychange` 立即查一次 | 秒~分钟 | 0 |
| 移动端 | `@capacitor/app` 的 `appStateChange`/`resume` → 立即增量拉取；**不在后台保持连接** | 回前台即同步 | 一个依赖 + 一个监听 |
| 备用出口（A） | 走 GitHub 时只能条件请求轮询：对 tree 发 `If-None-Match`，`304` 不计配额 | 分钟级 | 0 服务端 |

### 5.5 必须同时修的跨设备正确性问题

1. **`refreshPaths` 要能被远端复用**：目前是模块私有（`src/data/library.ts:935`）。要么导出，要么新增
   `applyExternalPaths(paths)`；远端落地后必须显式调用（原因见 G5，自写过滤会吞掉 watcher 事件）。
2. **不要依赖 watcher 感知远端写入**：现有 GitHub 拉取落盘后直接 `rescanWorkspace()`（`src/App.tsx:868,880`），
   简单正确但成本是 O(库)；P3 起改成按路径。
3. **冲突策略从「磁盘赢」升级为「列出来」**：`reconcileExternalChange`（`library.ts:1195`）现在是 D3「磁盘赢」——
   会自动采纳磁盘、把内存改动塞进隐藏前像。单机没问题；跨设备时用户会「看到自己的改动消失」。
   建议：本地 dirty 且远端也变 → 不自动采纳，走 GitHub 那套 `conflicts` 列表。
4. **`.opennote/` 的同步边界要重新划**（当前是「一律不推」，README:130）：
   - **要同步**：`titleOverrides`（但它的键是**路径**，两端各自改名会漂，需改成内容/稳定 ID 关联）；
   - **不要同步**：`expanded` / `lastOpened` / `ui.*`（重扫时本来就会被本地 UI 覆盖）、`trash/`、`history/`、`inbox/`、`import-log.json`；
   - **要单独权衡**：`import-index.json` 是剪藏去重的本机索引，不同步会导致同一网页在两端重复剪藏。
5. **mtime 判据换成内容哈希**：`fileStates.seedFromScan`（`fileStates.ts:52-73`）与 `library.ts:1059-1060` 的
   `stamp.mtimeMs > seen.stat.mtimeMs` 在跨设备/网盘场景不可靠。

### 5.6 如果不想依赖 GitHub：三条更贴合本仓的替代

GitHub 只是「远端」的一个实现。把 §5.2 的 `SyncProvider` 抽出来之后，有三条成熟路线可以低成本接上：

1. **哑存储 + 本地同步历史（零远端元数据）** —— Remotely Save 模型。
   远端用 S3 兼容桶 / WebDAV（甚至局域网），客户端只在本地记「上次成功同步的状态」，
   用 local/remote × unchanged/modified/deleted/created 决策表出 push/pull/delete/conflict 计划（含删除保护）。
   → 对本仓：`.opennote/github.json` 已经是这份「本地历史」，换掉 provider 即可，
   **不需要服务端写任何逻辑**。代价是「远端变了什么」要列一次全树（对象存储很便宜），
   或在桶里放一个 manifest 文件、对它发条件请求。
   WebDAV 上还可以用 **RFC 6578 的 `sync-collection` + `sync-token`** 只取增量列表（但仍无推送）；
   S3 上则必须自带 manifest——**ETag 不是内容指纹**，只有非 multipart 且未加密时才是 MD5。
   CAS 用 `If-Match`/`If-None-Match`（S3 条件写、WebDAV 乐观锁都支持），正好落成 `SyncProvider.put` 的 `baseRev`。
2. **内容寻址仓库 + 快照** —— 思源 dejavu 模型（§3.2 范式 E）。
   `Index / File / Chunk / Ref` 全部 SHA-1 寻址，只传缺失 chunk；快照 = 带 tag 的 index。
   → 对本仓：当「增量 + 版本回溯 + 图片去重」变成硬需求时，这是比 CRDT 便宜得多的模型，
   并且能和现有 `.opennote/history/` 的快照语义合并成一套。
3. **云盘开放 API 当远端（唯一「不自建服务端、却仍有推送」的选项）** —— provider 实现成 Dropbox / OneDrive / Google Drive。
   增量天然（`rev` / `/delta` 的 `deltaLink` / `changes.list` 的 pageToken），冲突副本由服务端保留；
   且 **OneDrive 与 Google Drive 提供服务端变更订阅**（change notification / `changes.watch` notification channel），
   网页端可以做到秒级。代价是 OAuth 授权、厂商锁定、API 配额，且浏览器端不能放长期密钥（走 PKCE）。

三条的共同点：**都不需要新协议**——分别是「把基线指向哑存储」「把历史快照换成内容寻址仓库」「把 provider 换成云盘 API」。

## 六、风险与已否决项（不要重复造轮子）

- **不引入 CRDT**：与「文件是唯一真相」冲突；且需求只要时序错开的文件级同步。见 §一.1。
- **不做纯 P2P 实时**：LiveSync 的经验是「信令中继仍需、且对端必须在线」，换来的复杂度不划算。
- **不放开桌面端 CSP 去直连 https**：桌面端策略不放任何 https（`electron/main.cjs` 的 `cspPolicy()`），
  远端请求必须走主进程（现有 `net.downloadImages` 是同类先例，`src/desktop/bridge.ts` 里那一节）。
- **不要把令牌写进 `.opennote/`**：`baseline.ts:1-13` 已经写明理由——那目录会被同步/导出/拷贝。
- **不要动 `.opennote/state.json` 的既有格式**：设计文档第 5 行的硬纪律「数据变化只做加法」，
  新同步元数据另开文件（如 `.opennote/sync.json`），旧版本 App 打开不受影响。
- **@parcel/watcher 的打包结论仍有效**：4 件套与「node_modules 整体排除」冲突，打包版退化 `fs.watch`
  （设计文档 P1c-2；`electron-builder.yml` 内有配方注释）。加同步不要顺手把它带回打包版。
- **浏览器/Android 上的 git（已查证一部分）**：isomorphic-git 能跑在浏览器（fs 用 BrowserFS/IndexedDB 或自建适配层，
  HTTP 传输是可插拔插件、受 CORS 约束），是 Capacitor 里更现实的选择；libgit2 是 C99 库，
  Android 需 FFI/JNI 绑定，不便于 Capacitor 直接用（[isomorphic-git](https://isomorphic-git.org/docs/en/fs) · [libgit2](https://libgit2.org/)）。
  仍待 spike 的是两者的移动端体积与性能。
- **其余待验证**：各云厂商 API 的 CORS 细节与 OAuth 配额；iOS 后台同步的具体额度。这些在 P4 动工前应各自做 spike。
