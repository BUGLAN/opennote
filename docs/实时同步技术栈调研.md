# 多端实时同步技术栈调研

> 前提（取自本仓库 `docs/设计-同步层与索引重构-2026-10-10.md`）：**文件是唯一真源**、无中心数据库、同一篇笔记不并发写（磁盘赢）、倾向自托管或零运维。每项给出一句「能否用在本项目」的结论；来源均为官方文档/规格/源码，URL 附在每节末尾。

## A. CRDT / OT 协同引擎

### A1 Yjs

- **更新模型**：`Y.Doc` 内含 Y.Text / Y.Map / Y.Array 等 shared type，变更编码为 *document update*；官方明确 update 是 **commutative + idempotent**（可任意顺序、可重复应用）。同步靠 `Y.encodeStateVector` 算 state vector，`Y.encodeStateAsUpdate(doc, targetSV)`、`Y.diffUpdate`、`Y.mergeUpdates` 生成差量，`Y.applyUpdate` 应用；二进制分 V1/V2，官方称 V2「compression 好很多」但「尚未被所有 provider 使用」。
- **Providers**：`y-websocket`（官方自带极简 WebSocket 后端）；`y-webrtc`（P2P，signaling server 找 peer，同浏览器标签页走 BroadcastChannel，默认最多约 `20 + rand(15)` 条连接）；`y-indexeddb`（update 持久化到 IndexedDB，「文档立即可用，网络只需同步 diff」）；绑定 `y-prosemirror`、`y-codemirror.next`。
- **一个 Markdown 文件 = 一个 Y.Doc**：Y.Doc 是同步最小单元，官方 README 未提供 subdocument 概念，只能「一个文件一个 Doc + 路径当 room name」；文件数 = Doc 数 = 连接数与持久化条目数。正文用 Y.Text 时，编辑器发的就是字符级 insert/delete。
- **持久化**：官方明确 JSON 不能当主存储。y-prosemirror README 原话：*"Serializing and deserializing to JSON will not store collaboration history steps and as such should not be used as the primary storage. You will still need to store the Y.Doc binary update format."* 即磁盘 `.md` 之外必须再存一份 Y.Doc 二进制。
- **服务端可自建**：`node ./node_modules/y-websocket/bin/server.cjs` 即可；Hocuspocus 是同一套 Y.js 的独立 WebSocket 后端，官方支持 Node/Bun/Deno/Cloudflare Workers、Redis 扩展，以及 Database/SQLite/S3 扩展。
- **移动端/浏览器**：依赖的都是标准 Web API（WebSocket / WebRTC / IndexedDB），Capacitor WebView 与 Electron 均可运行；后台挂起问题见 C3。
- **结论：能用**（Yjs + y-websocket 或 Hocuspocus 自建最省心，y-webrtc 可省服务器），**但代价是「文件不再是唯一真源」——必须额外维护永久的 Y.Doc 二进制状态。**

### A2 Automerge 与 Loro

- **Automerge**：不可变 CRDT，官方称并发修改可「无须中心服务器」自动合并、network-agnostic；automerge-repo 提供 `NetworkAdapter`（WebSocket、BroadcastChannel 等）与 `StorageAdapter`，文档明确 *sync protocol 是 point-to-point*；落盘为二进制 chunk（snapshot / incremental）。
- **Loro**：`LoroDoc` + `export({mode:'update'|'snapshot'})` / `import(bytes)`；官方卖点是 offline editing、P2P、time travel（`checkout(version)`）。官方同时列出「不该用 CRDT」的场景：需要强一致、数据不是 JSON-like（如大二进制/媒体流）、简单 C/S 同步就够、在意包体积（WASM 约 970KB gzip）。
- **结论：同样能用**（Automerge 的 storage adapter 可落文件系统，对 Electron 友好；Loro 需权衡 WASM 体积），**但「额外状态 + 第二真源」与 Yjs 完全一致，且大附件官方明确不推荐由 CRDT 承载。**

### A3 CRDT 用在纯文本 Markdown 的已知坑

1. **与「文件即真源」冲突**：CRDT 靠自己的历史/墓碑状态合并，`.md` 只是投影；官方要求额外存二进制（见 A1）。
2. **round-trip 失真**：绑定层依赖 schema/delta（y-prosemirror 的 `pmnodeToDelta`、Rich Text Schema、`CAVEATS.md`），纯文本 Markdown 无官方「字节级无损往返」保证；字符级合并还可能把 `**bold**`、表格、代码围栏切在语法中间。**（属推断）**
3. **额外状态体积**：官方承认 CRDT「only grow in size」，只能靠 struct 合并、删除内容、GC tombstone 缓解；V2 与 Loro 的 Document Size 页说明各家都在为此优化。
4. **front-matter 与附件**：元数据可放 Y.Map；附件不是 CRDT 强项——Yjs 无 blob 类型，Loro 把大二进制列为不适用场景。附件应继续走文件系统/对象存储，CRDT 内只放引用。
- **结论：在「同一篇不并发写、磁盘赢」的极简 md 笔记里，CRDT 合并收益接近于零，却要付出双份真源与永久 tombstone 的体积代价，不建议作主同步路径。**

## B. 本地优先同步引擎（非 CRDT 路线）

### B1 Replicache / Zero（Rocicorp）

- **Replicache**：浏览器内持久化 KV（底层 git-like）；mutator 先本地乐观执行并排队，push 后服务端按 `mutation id` 重放，pull 用 cookie + `lastMutationIDChanges` 算 patch，再 rewind → rebase 重放未确认 mutation；**poke** 是无内容的「该 pull 了」提示（可走 SSE/WebSocket/Pusher）。冲突逻辑写进 mutator，官方口径是 **server 权威**，文档示例的 canonical 状态放在 Postgres。
- **Zero**：Rocicorp 现行方案，把 UI 所需查询结果同步到本地 normalized store；官方文档以 **Postgres** 为源库，另有 self-host 与 Cloud Zero 章节。
- **结论：不适合**「无中心数据库、文件即真源」——它假定服务器持有 canonical 状态。

### B2 TinyBase

`MergeableStore` + `Synchronizer`：`createWsSynchronizer` / `createLocalSynchronizer` / `createCustomSynchronizer`，Synchronizer 被定位为 Persister 的扩展（*"persisting your MergeableStore to another client"*）；合并用 HLC 时间戳（同毫秒冲突靠 uniqueId 区分），官方称合并结果是确定性的。内置 persister 覆盖 IndexedDB、file、Capacitor SQLite、Durable Objects、PartyKit、PowerSync、yjs 等。

- **结论：可用作「元数据/索引/设置」的合并同步层**（本地 file persister + 可选 DO/WS），但它不是文件同步，Markdown 正文仍由文件层负责。

### B3 ElectricSQL / PowerSync / RxDB

- **ElectricSQL**：官方定位 *"read-path sync engine for Postgres"*，用 **Shape** 把 Postgres 数据经 HTTP 同步到客户端，**写路径由开发者自己的 API 负责**，因此必须有 Postgres 中心库，冲突由应用层处理。
- **PowerSync**：server-authoritative reconciliation；客户端写进 **upload queue** 顺序上传到自家后端；官方冲突规则是「某字段最后一次到达服务器的更新获胜、delete 永远获胜」，要别的行为需自定义；需要源数据库 + PowerSync Service（支持自托管）。
- **RxDB**：`replicateRxCollection({pull:{handler, stream$}, push:{handler}})`，checkpoint 迭代 + event observation 两种模式，断线重连发 `RESYNC` 回退 checkpoint；默认 conflict handler **永远丢弃 fork、采用 master 状态**（文档级 last-write-wins），删除必须用 `_deleted` 软删；官方明确 backend 不必是 RxDB，可为任意 HTTP/GraphQL/WebSocket 服务。
- **结论：三者都需要一个中心权威存储**（Postgres 或既有服务端）；RxDB 协议最薄、可把远端做得很小，但仍不是「无中心库」。

### B4 PouchDB / CouchDB 复制协议（Obsidian LiveSync 的基础）

- **模型**：`_rev` 形如 `N-sig`（N 正整数 + 签名），是 MVCC token；并发写产生多个 leaf revision，组成 **revision tree**（类似 Git 的 fork）。CouchDB **不丢弃**冲突分支，只用确定性算法选 winner；`GET doc?conflicts=true` 返回 `_conflicts`，`?open_revs=all` 拿全部 leaf；解决冲突 = 在 winner 上写合并后的新 rev，并对其余 leaf 写 `_deleted:true`。文档级、多主（官方：*"they all are"* source of truth），无 master/follower。
- **协议算法**：`HEAD /{db}` 验证两端 → `GET /{db}` 取 `update_seq` → 生成 replication ID → `GET /{db}/_local/{id}` 读 replication log（`history`/`recorded_seq`/`session_id`/`source_last_seq`）取共同 checkpoint，无共同祖先则全量 → `GET /{db}/_changes?style=all_docs&since=<checkpoint>&feed=continuous&heartbeat=10000`（continuous 靠 heartbeat 保活，长轮询用 `feed=longpoll`）→ `POST /target/_revs_diff` 询问缺哪些 rev → 只拉缺失 revision 的文档 → `POST /target/_bulk_docs` 写入以保留原 revision id（`new_edits=false`）→ `PUT /{db}/_local/{id}` 记录新 checkpoint。方向单向，双向同步 = push + pull。
- **PouchDB**：官方称「完全实现 CouchDB 的复制算法」，`sync({live:true, retry:true})` 自带断线重试，「适合移动设备」。**Obsidian LiveSync** 的 README 则明确走 **自托管 CouchDB**（或 MinIO/S3/R2 对象存储）。
- **结论：最贴近本项目约束**——CouchDB 只是「其中一个 peer」、可自托管、协议是公开 REST，冲突是显式的整篇叶子（不做隐式合并，符合「不丢数据、不静默覆盖」）；代价是要维护一台 CouchDB（或兼容服务），且**冲突粒度是整篇文档**。

## C. 实时传输与「网页端实时显示」

### C1 四种传输对比

| 传输 | 浏览器支持 | NAT 穿透 | 移动端后台 | 能否走 CDN | 官方来源 |
| --- | --- | --- | --- | --- | --- |
| WebSocket | 全支持 | 出站 TCP，一般可通 | 被挂起（见 C3） | 可以（Workers/DO 可终结 WS） | RFC 6455；WHATWG WebSockets Standard |
| SSE | 全支持（EventSource） | 同普通 HTTP | 被挂起 | 最顺：普通 HTTP 长响应 | WHATWG HTML §9.2 |
| WebRTC DataChannel | 全支持 | 需 ICE/STUN，对称 NAT 需 TURN 中继 | 被挂起 | 不经 CDN（需自建 TURN） | RFC 8826/8827、RFC 8445、RFC 8656 |
| HTTP 长轮询 | 全支持 | 同普通 HTTP | 被挂起；恢复后可续 | 可以 | CouchDB `feed=longpoll` |

- SSE 是**单向** server→client，客户端回写需另发请求；WHATWG 规格明确警告 HTTP/1.1 per-server 连接数限制——多页面各挂一个 `EventSource` 会撞上限，建议用 SharedWorker 共享。SSE 自带重连与 `Last-Event-ID` 续传，是「网页端只读实时显示」最省事的方案。
- **Cloudflare Durable Objects**：官方称一个实例可作 WS 服务器连接数千客户端，Hibernation API 让实例空闲休眠而不断开——目前最省运维的自托管 WS 落点。
- **Supabase Realtime**：Elixir/Phoenix 集群，`postgres_changes` 依赖 Postgres 逻辑复制槽（WAL），故需要 Postgres/Supabase。**Ably / Pusher** 为托管 pub/sub，零运维但引入第三方与成本。
- **结论**：自托管首选 WebSocket（y-websocket / Hocuspocus / DO）；网页端只做「实时显示」用 SSE 最省事；WebRTC 只在想省服务器时用；长轮询只作兜底。

### C3 移动端后台限制

- **WICG Page Lifecycle** 把 **Frozen** 定义为「lifecycle state for CPU suspension」，并写明「Normally HIDDEN pages will be frozen to conserve resources」；页面需监听 `freeze` / `resume`，官方示例甚至在 freeze 时「关闭所有打开的 IndexedDB 连接」。冻结即 JS、定时器、网络回调全部停止。
- **Apple 官方**：用户退出前台后 App 先进入 background，随后 *"UIKit suspends it"*；*"Apps don't normally receive any extra execution time after they enter the background"*；进后台要做的事包括 *"Suspend dispatch and operation queues"*。Capacitor 的 WebView 跑在 App 进程内，后台即等同挂起。
- **Capacitor 官方 App 插件**：`appStateChange`（Android 上由 Activity 的 `onResume`/`onStop` 触发）、`pause` / `resume`、`getState()`——移动端唯一可靠的「回到前台」信号。
- **Android 官方**：Doze（低电耗模式）推迟后台 CPU 与网络活动，只在维护窗口放行，App Standby 同样延迟后台网络。
- **工程结论**：移动端不能依赖后台常驻 WebSocket/定时器，正确形态是「**前台事件（resume / appStateChange / visibilitychange）+ 增量拉取（since / checkpoint / cookie）**」；这正是 CouchDB `_changes?since=` 与 RxDB checkpoint 模式在移动端的价值。后台唤醒只能靠 APNs/FCM 之类的系统推送，而非 JS 长连接。
