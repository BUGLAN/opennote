## 高严重度

### H1. 推送/推送删除的 CAS 冲突在下一轮同步被静默"本地赢",远端并发修改无用户裁决即被覆盖

- **位置**:
  - `src/sync/engine.ts:465-472`(put 冲突后把账本 `remoteHash` 更新为远端当前值)
  - `src/sync/engine.ts:515-517`(delete 冲突同样更新)
  - `src/sync/diff.ts:114`(`planPush` 判"本地改了"只看 `localHash`)
  - `server/src/routes/v1.ts:499-505`(服务端 `If-Match` 与当前值相等即放行覆盖)
- **描述**:put/delete 返回 409 时,引擎把冲突列入 `pushConflicts` 并把账本 `remoteHash` 刷新为远端当前哈希,但 `localHash` 保留旧值。下一轮同步(去抖 1.2s 后的 local-write、任意 SSE 信号、retry 均可触发)`planPush` 再次判该文件 "modified",以更新后的 `remoteHash` 作 CAS 依据——此时 `If-Match` 必然命中,服务端接受写入,本地版本直接覆盖远端并发修改。删除侧同理:删除冲突后下一轮 `provider.delete` 以刷新后的 baseHash 重发,远端被修改的版本被墓碑。冲突从发现到被覆盖只有一个触发周期的窗口,而 runner/controller 对"存在冲突"没有任何暂停下一轮的闸门(`src/sync/runner.ts:217` 只更新计数)。
- **影响**:直接违背设计文档与代码注释反复声明的"只报不猜/让用户裁决"(§6.1 L2、红线 5)。设备 B 的编辑在用户看到冲突对话框之前(通常 1~2 秒内)就被设备 A 静默覆盖;对 B 而言表现为下次同步被拉回 A 的版本,修改内容仅存于 CouchDB revision tree 的落败 leaf,用户不可见。删除冲突场景下 B 的修改被整篇删除。

#### 核实（2026-10-22 复核）

**结论：属实**（严重度成立；两处细节需要更正，见「描述偏差」）

**验证结果与依据（逐行核对）**
- **冲突后推进了 CAS 依据**：`src/sync/engine.ts:465-472` 把 `remoteHash` 写成 `remoteEntry?.hash`（远端**当前**值），
  而 `localHash` 保留 `existing?.localHash`（**上次同步**的本地值，不是当前本地值）。删除侧同款：`engine.ts:515-517`。
- **下一轮必判「本地改了」**：`src/sync/diff.ts:114` —— `if (known.localHash !== file.hash) modified.push(file)`。
  判据只有 `localHash`，而它在冲突时没有被更新 ⇒ 这一条**必然**再次进入 `modified`。
- **下一轮 CAS 必然命中**：`engine.ts:433` 用 `known?.remoteHash` 作 `baseHash`；
  服务端 `server/src/routes/v1.ts:499-505` 只在「`If-Match` 与当前内容标识**不等**」时回 409，相等则放行覆盖。
- **没有任何闸门**：`src/sync/runner.ts:217` 只把冲突数放进状态；`appSync.ts`、`ConflictPanel.tsx` 都不影响下一轮是否开跑；
  引擎不 import `conflicts.ts`（该模块唯一的生产调用点是 `src/data/library.ts:1325` 的外来磁盘改动处置）。
- **测试反向证明**：`src/sync/engine.test.ts:374-394` **明确断言**「冲突后账本 `remoteHash` 被刷新成远端当前值」，
  注释写的是「下一次不会拿过期依据再撞一次」。也就是说，这个行为是**被当成修复写进去的** ——
  它解决的「死循环」与它引入的「下轮静默覆盖」是同一处改动的两面。

**描述偏差（需更正）**
1. 「修改内容仅存于 CouchDB revision tree 的**落败 leaf**」—— 不准确。这里的 `If-Match` 是**命中**的
   （否则不会写入成功），所以这次写是**同一条分支上的普通更新**，不产生并发 leaf；B 的版本只是变成**祖先 revision**，
   compaction（`_revs_limit` 默认 1000）之后正文不可得。**结论比原描述更严重：覆盖之后不可从 revision tree 找回。**
2. 「用户看到冲突对话框之前就被覆盖」—— 方向对，但实际窗口比"看到对话框"更短：引擎发现的冲突**从未进入**
   `src/sync/conflicts.ts` 的持久账本（见文末 N1），UI 只从 `last.conflicts`（`appSync.ts:245-258`）读，
   下一轮成功同步就会把它覆盖掉。所以用户很可能**根本没机会看到**这条冲突。

**根因分析**
「远端现在是什么」（CAS 依据）与「这一条待裁决」（冲突状态）被压进同一对字段（`localHash` / `remoteHash`）。
为了让 409 不再每轮重复，代码把 CAS 依据前移到远端当前值 —— 这等于**替用户做了「保留本地」的决定**。
引擎里没有「待裁决」这个概念，冲突只存在于一次性返回值里，下一轮无从得知「这条还没裁决」。

**修复方案（具体改动点）**
1. `src/sync/engine.ts:465-472`、`:515-517`：**不再改写** `remoteHash` / `rev`。CAS 依据保持「上次同步时远端那一版」⇒
   下一轮 put/delete 仍会 409。这是**安全**的重复（服务端只做读校验，不产生写入），也正是「只报不猜」的正确实现。
2. `src/sync/state.ts`：`SyncLedgerFile` 增加可选 `pendingConflict?: { kind: ConflictKind; localId: string | null; remoteId: string | null; at: number }`。
   `readSyncLedger` 对 `files` 是整体 cast（`:175`），新字段会被保留，**不需要**升 `SYNC_LEDGER_VERSION`；
   但要补一条「读旧账本（无该字段）不炸」的用例。
3. `src/sync/engine.ts`：算出 `blocked = 有 pendingConflict 且本地 `localHash` 未变` 的路径集合，
   从 `pushAdded` / `pushModified` / `pushPlan.deleted` 里剔除（省掉每轮重复请求），
   但**每轮仍要把它们并入 `result.conflicts`**（从账本读，而不是只报本次新发现的）。
4. `src/sync/resolution.ts`：两个裁决函数成功后清 `pendingConflict`；
   `resolveConflictWithRemote` 在 `remote === null` 时改为「删除本地 + 清标记」（否则用户点了「用远端」也永远解不开）。
5. `src/sync/appSync.ts` + `src/components/SyncDialog.tsx`：冲突清单改为「账本里的 `pendingConflict` ∪ 本次结果」。
6. 测试：`src/sync/engine.test.ts` 新增「put 冲突后**再跑一轮**，远端字节不变」「delete 冲突后再跑一轮，远端不被墓碑」；
   `tests/sync.e2e.test.ts` 加两设备并发改的端到端用例。

**优先级与顺序**：**P0**，建议第 2 个修（先修 L2 拿到日志，它只有一行）。
与 H2 都落在 `engine.ts`，可以合并成一次提交但**分开写用例**。

**风险与注意事项**
- 若不做第 3 步，冲突期间每轮会多出「冲突条数」个 409 请求。这不危险，但会让限流更紧张；用 `pendingConflict` 标记可以消除。
- 标记一旦写下**必须保证有出路**（第 4 步）：否则用户不点裁决就永远推不上去。这是本方案唯一的"卡住"风险。
- **不要**用「推进 `remoteHash` + 同时把 `localHash` 写成当前 hash」这种取巧：那等于静默把本地标成已同步，本地改动会永久不上传。
- 新增字段要过 `src/sync/boundary.ts` 的字段闸门（`conflict` 不在禁止名单里，已核对）。

### H2. 忽略规则(.gitignore)与账本脱节:新被忽略的已同步文件被当作"本地删除"推送墓碑,导致其它设备删文件

- **位置**:
  - `src/sync/diff.ts:116-120`(`planPush.deleted` = 账本 imported 且不在本地扫描结果中)
  - `src/sync/engine.ts:511-547`(推送删除不做任何忽略过滤)
  - `src/sync/session.ts:135-138`(`knownPaths` 含账本路径,拉取侧 did 反查同样不滤忽略)
  - 语义声明:`src/sync/ignore.ts:31-41`(承诺"忽略 = 双向不存在:不 push、不 pull、**不删除**、不算本地删了")
- **描述**:`listLocal` 会把命中忽略规则的文件从扫描结果剔除,但账本 `ledger.files` 中它的条目(`imported: true`)原样保留。`planPush` 把"账本有、扫描无"判为用户删除 → `provider.delete` 远端墓碑。这违反 ignore.ts 明确承诺的忽略语义。反向同理:远端改动了该文件时,did 反查表因含账本路径而能翻回路径,`planPull` 会把被忽略文件重新拉下来写盘。
- **影响**:用户在设备 A 的 `.gitignore` 里新增一条规则(或同步了一个含该文件的仓库后添加规则),A 上该文件即被墓碑;不忽略该路径的设备 B 在下一轮同步中本地删除此文件——跨设备的静默数据丢失,且 `.gitignore` 本身不同步,B 侧无从得知原因。

#### 核实（2026-10-22 复核）

**结论：属实**（核心成立；「反向再把被忽略的文件拉下来」的具体触发描述不准确，见「描述偏差」）

**验证结果与依据**
- **扫描侧过滤**：`src/sync/workspaceFiles.ts:157-159`（`listLocal` → `selectSyncableEntries`）、`:104-122`；
  `src/sync/ignore.ts:190-192`。
- **账本侧不过滤**：`src/sync/session.ts:135-138` 的 `knownPaths` 直接拼 `knownPathsOf(ledger)`（`:109-111` = `Object.keys(ledger.files)`）。
- **删除推断只看账本**：`src/sync/diff.ts:116-120`（`imported` 且本地扫描里没有 ⇒ `deleted`）。
- **推送删除不做任何忽略过滤**：`src/sync/engine.ts:511-547` 整段没有一次 ignore 判定。
- **语义承诺**：`src/sync/ignore.ts:31-41`；设计文档 `docs/执行-三端同步-密钥即身份-2026-10-13.md:846-867`，
  其中第 864 行原文是「**忽略一个已有内容的文件，等于让它在其它设备上停更（不是删掉，只是不再传播）**」，
  第 68-69 行是「红线 8：被忽略的路径**双向不可见** —— 不 push、不 pull、不删、不参与 diff」。
- **跨设备后果链可复现**：A 推墓碑（`engine.ts:534-542` 成功后把账本改成 `localHash: null`，**条目保留**）
  → B 的 `planPull` 走「账本有、远端树无、本地未改」→ `removeLocal`（`diff.ts:206-213`）→ `engine.ts:656-675` 真删本地。

**描述偏差（需更正）**
1. 原文：「远端改动了该文件时……`planPull` 会把被忽略文件重新拉下来写盘」。
   核对：这条组合**不会**走到 `download` —— `planPull` 在「账本有 `imported`、本地没有这一条、远端 hash 变了」时
   进的是 `conflicts`（`diff.ts:173-176`，`deleted-locally-modified-remotely`），不是下载。
   **真正会「把被忽略路径写到盘上」的是「远端新增、本地忽略」的路径**：`download` 分支（`diff.ts:163-171`）
   没有任何忽略判定，`workspaceFiles.writeLocal` 也不判。这一条比原描述更低调、但确实违反红线 8。
2. 原文：「用户在 .gitignore 里新增一条规则，A 上该文件**即**被墓碑」。
   核对：忽略规则只在 **attach 时**编译一次（`src/sync/appSync.ts:288` 读文本 → `src/sync/session.ts:114` `createIgnoreRules`），
   所以生效点是**下一次 attach**（重开笔记本 / 改同步配置 / 重启），不是保存 `.gitignore` 的当下。
   这一点直接影响用户能否把现象与原因对上号，建议在修复时一并做「保存 .gitignore 后提示同步范围变化」。

**根因分析**
红线 8 要求「忽略」作用于 diff 的**全部输入**（本地扫描、账本视图、远端树），实际只落在「本地扫描」这一个入口上。
而删除推断恰好**只读账本**，于是「忽略」被读成了「本地不存在」⇒ 删除。
这是"判定只做了一半"的结构性问题，不是某个分支写错。

**修复方案（具体改动点）**
1. `SyncEngineDeps`（`src/sync/engine.ts:57-92`）新增可选 `isIgnored?: (path: string) => boolean`；
   `src/sync/workspaceFiles.ts` 的 `createWorkspaceEngineDeps` 用现成的 `rules`（`options.rules`）提供（`ignore.ts` 的 `shouldIgnore`）。
2. `src/sync/engine.ts`：把三类输入**过滤成视图**再喂 diff（`diff.ts` 保持纯函数、零改动）：
   - `localFiles` 去掉忽略路径；
   - `baselineView.files` 去掉忽略路径（`:329`）；
   - `remoteTree.entries` 在 **`did → path` 反解之后**去掉忽略路径（`:301-321`，注意要在反解之后，否则会误报 `unknownDids`）。
3. **账本不删条目**（用户解除忽略后能自然恢复）。
4. `src/sync/session.ts:135-138`：`knownPaths` **保持不变**（反解 did 需要它），但可以在注释里写明"它包含被忽略路径"，
   避免下一个人再一次把忽略判定加错地方。
5. 测试：`src/sync/diff.test.ts` / `src/sync/engine.test.ts` 各加两条 ——
   「账本里有、本地扫描无（被忽略）⇒ 不产生 delete」「远端新增、本地忽略 ⇒ 不下载、不写盘」。
6. 后续（不在本轮）：保存 `.gitignore` 后提示「新增忽略 N / 解除忽略 M」（设计文档 §3.11 第 866-867 行已要求）。

**优先级与顺序**：**P0**，建议与 H1 同批（两者都在 `engine.ts`，但用例分开）。H2 出现的是**跨设备删除**，建议排在 H1 之前或紧随其后。

**风险与注意事项**
- 语义要一次讲清：忽略后该路径**既不推也不拉也不删**，账本条目保留但 `localHash` 会变旧；
  解除忽略后的第一轮会按「本地改了」推上去 —— 这是期望行为，要有用例钉住。
- 过滤位置很关键：`remoteTree` 必须在 did 反解**之后**过滤，否则被忽略路径的 did 会进 `unknownDids`，
  状态栏会冒出「N 条远端记录认不出路径」的假警报。
- 不要把忽略判定塞进 `diff.ts`：那一层现在是纯函数、可单测；把谓词传进去会让它同时依赖忽略语义，测试成本上升。

### H3. 目录列举失败被静默吞掉,子树"消失"后被当作批量删除推送;推送侧删除没有删除预算守卫

- **位置**:
  - `src/sync/backendFiles.ts:66-71`(`catch { continue }` 跳过读不到的目录)
  - `src/sync/engine.ts:511`(`pushPlan.deleted` 直接执行,对比拉取侧 `src/sync/engine.ts:648-654` 有 `assertDeletionBudget`)
  - `src/lib/github/sync.ts:120-123`(GitHub 通道同款吞错)
- **描述**:某个子目录因权限/被占用(Windows 上杀毒、备份软件锁定目录是常态)`list()` 抛错时,整棵子树从 `listLocal` 中消失,与"用户删除"不可区分。这些已同步文件进入 `pushPlan.deleted`,被逐条 `provider.delete` 墓碑;而删除保护阈值(`assertDeletionBudget`,一次最多删 max(20, 25%))只在**拉取侧**调用,推送侧完全没有预算闸门,删除数量不受任何限制。
- **影响**:一次瞬时的目录读取失败演变成远端批量墓碑,再传播为所有设备的本地删除;拉取侧精心设计的防误删闸门被推送侧这条对称路径完全绕开。

#### 核实（2026-10-22 复核）

**结论：属实**

**验证结果与依据**
- `src/sync/backendFiles.ts:65-71`：`try { entries = await options.backend.list(current.path) } catch { continue; }` ——
  既不上报也不记录，注释只说明「跳过这一支，而不是让整轮同步失败」。
- 后果入口：`src/sync/diff.ts:116-120`（只看账本）+ `src/sync/engine.ts:511`（`runBounded(pushPlan.deleted, ...)` 直接执行）。
- **不对称已确认**：拉取侧 `engine.ts:643-654` 有 `applyTruncationGuard` + `assertDeletionBudget`；推送侧一行都没有。
- **服务端也没有**：设计文档 §6.3（`docs/执行-三端同步-密钥即身份-2026-10-13.md:1647`）要求「客户端 + 服务端**各一遍**」，
  但 `server/` 全目录 grep 不到 `assertDeletionBudget` 或任何删除预算逻辑（见文末 N2）。
- GitHub 通道同款：`src/lib/github/sync.ts:118-123`（`console.warn` + `continue`）。

**触发条件（需要说准）**
`backend.list()` 必须**真的 reject**。桌面端 Node 后端经 IPC 走 `fs.readdir`（`src/fs/nodeBackend.ts:17`），
Windows 上 `EPERM / EACCES / EBUSY` 现实存在；FSA / OPFS 后端多为「整体不可用」而不是「单目录失败」，
所以这条最可能出现在**桌面端 + 本机磁盘 + Windows**。
原文「杀毒、备份软件锁定目录是常态」属于合理推断，**本轮未实测**（见「复核说明」需要补充的证据 ②）。

**影响补充**
一旦某目录列不出来，它下面**每一条**账本条目都会进 `pushPlan.deleted`；推送是逐条 `provider.delete`（逻辑删），
于是远端会多出一批墓碑，其它设备下一轮按「远端显式删除」把它们删掉 —— 与原描述一致。
补充两点：
1. 墓碑是**永生**的（§6.4 规则 3），所以误删**不会**随下一轮自愈，只能靠 `.opennote/history` 或远端 revision 手工找回；
2. 因为推送删除没有预算，**只删 1 条也会发生**（目录里只有一篇笔记时根本不会触发任何阈值）—— 这是它比拉取侧更危险的原因。

**根因分析**
「**扫描是否完整**」没有作为一等信号在层间传递。拉取侧有 `truncated` 这个显式信号（远端说的），
本地扫描却没有对应的「这一轮我没看全」信号，于是删除推断把「没看见」当成「不存在」——
这恰好是红线 7（`docs/…:67`）明令禁止的那件事。

**修复方案（具体改动点）**
1. `src/sync/backendFiles.ts:52-88`：`catch { continue }` 改为收集 `{ path, message }`，返回 `{ entries, unreadable }`。
   `SyncFileBackend.list()`（`src/sync/workspaceFiles.ts:65-76`）相应扩展；为兼容现有适配器与用例，
   建议新增可选方法 `listDetailed?()`，引擎优先用它、没有就退回 `list()`（此时视为「完整」）。
2. `src/sync/engine.ts`：`scanIncomplete === true` 时**跳过 `pushPlan.deleted`**（计入 `suspendedDeletes` 或新增
   `suspendedPushDeletes`），其余（推送新增/修改、拉取）照常 —— 与 `applyTruncationGuard` 同一条纪律。
3. `src/sync/engine.ts:511` 之前加 `assertDeletionBudget(totalKnown, pushPlan.deleted.length)`；
   被拦时整批不删，写 `deletionGuardMessage`（`SyncOnceResult` 里已有 `blockedDeletes` / `deletionGuardMessage` 两个字段）。
4. `src/lib/github/sync.ts`：`collectLocalFiles` 收集 `unreadable`，`pushChanges` / `pullChanges` 见到非空就**拒绝删除**
   （抛 `GH-SCAN-INCOMPLETE`），并给 `pushChanges` 加同一个删除预算。
5. 因为加了预算，必须给用户一条「确认后继续」的路（否则「用户真想删 60% 笔记」会永久被拦）：
   `src/sync/appSync.ts` 暴露 `manualSync({ confirmDeletes: true })`，`SyncDialog` 在 `deletionGuardMessage` 非空时显示
   「确认删除 N 篇」按钮。
6. 测试：`src/sync/backendFiles.test.ts`（`list` 抛错 ⇒ 上报 unreadable）；
   `src/sync/engine.test.ts`（扫描不完整 ⇒ 不推删除；超预算 ⇒ 一条都不删）。

**优先级与顺序**：**P0**，与 M5 / M6 一起作为「防误删批次」的第 1 个补丁 ——
三者改的是同一条链路（扫描/树不完整 ⇒ 禁止删除推断），合并成一次提交能少一轮回归。

**风险与注意事项**
- 服务端预算（N2）建议**先不做**：当前协议是逐条 `DELETE`，没有"批次"概念，按时间窗统计容易误伤批量清理；
  等有批次端点再补。至少要先把设计文档里「服务端也跑一遍」标成**未实现**。
- `SyncFileBackend.list()` 的签名改动会波及三个后端适配器与多处用例；用「新增可选方法 + 回退」最稳。
- 「扫描不完整」不能一律变成**整轮失败**（Windows 上一个被占用的目录不该让整个笔记本停止同步）；
  只挂起删除推断，推送新增/修改和拉取继续。

## 中严重度

### M1. 服务端 PUT /v1/file 两步写非原子:文档元数据(hash)与附件(正文)可留下不一致状态

- **位置**:`server/src/routes/v1.ts:507-539`(先 `putDoc` 写入新 hash/size,再 `putAttachment` 写正文;CouchDB 文档更新会保留旧附件)
- **描述**:`putDoc` 成功后、`putAttachment` 完成前,文档已携带**新**内容标识而附件仍是**旧**字节。若此窗口内另一写入者介入导致 `putAttachment` 409,或进程在两步之间崩溃,库里留下"声明 hash 与实际正文不符"的损坏文档。另外附件冲突的 409 响应 `current: null`(`v1.ts:538-540`)会使客户端账本写入 `remoteHash: null`,此后 put 的 `baseHash` 为 null,而服务端规定"缺省 If-Match 只允许新建"(`v1.ts:502-505`),该文件陷入永久 409 死循环。
- **影响**:CAS 判定基于声明 hash,损坏文档使所有客户端读到与哈希承诺不符的字节;`hashCache`/账本基线被污染后表现为"同步永远冲突"或内容静默错乱;`current: null` 路径让单文件冲突无法自愈。

#### 核实（2026-10-22 复核）

**结论：部分属实** —— 「两步写非原子」属实且严重；「`current: null` 使该文件陷入**永久** 409 死循环」**不成立**（会在 1~2 轮内自愈），
真正致命的是另一个窗口（进程在两步之间崩溃），见下。

**验证结果与依据**
- `server/src/routes/v1.ts:507-525` `putDoc`（写 `hash` / `size`）、`:534-540` `putAttachment`（写正文）——
  两次**独立**的 CouchDB 请求，中间没有事务。
- CouchDB 语义（**这里要更正原描述**）：新 revision 只带请求体里给出的 `_attachments`；
  不带就是**没有附件**（旧附件只留在旧 revision，compaction 后不可得）。
  设计文档 §3.4 的文档形状里附件写成 `{"stub": true, ...}`（`docs/…:628-631`），正是为了在更新时保住附件。
  所以中间态通常是「**新 hash + 没有正文**」，而不是原描述说的「新 hash + 旧字节」。
- 附件冲突的 409 把 `current` 写成 `null`（`:538-540`）；删除冲突同样（`:572`）。
- 客户端：`src/sync/engine.ts:441-472` 在 `current === null` 时把 `remoteHash` / `rev` 写成 `null`；
  下一轮 `baseHash = null`（`:433`），服务端 `v1.ts:502-505` 对「缺省 `If-Match` + 远端已存在」回 409 ——
  但**这一次**的 409 体里带 `current: { hash, rev }`（`:504`），客户端据此把账本修正回来，再下一轮 CAS 成功。
  ⇒ 结论：**多两轮冲突后自愈**，不是死循环（前提是没有其它并发持续改写）。
- **真正会「永久」的是崩溃窗口**：`putDoc` 成功、`putAttachment` 之前进程挂掉 ⇒ 文档声明 `hash` 而**没有正文**：
  - 无附件：`GET /v1/file` 因 `getAttachment` 返回 null 直接 **404**（`v1.ts:373-374`），`POST /v1/files` 跳过它（`:430-431`）；
  - 客户端把它当「列树时还在、读的时候没了」→ `engine.ts:558-566` 记 `vanished` 并**跳过**；
  - 下一轮照旧（远端树的 hash 与账本 `remoteHash` 可能相等也可能不等），**每轮重复、永不收敛**，且不产生任何冲突或错误提示。
  这条比原描述的「永久 409」更隐蔽，也更符合「损坏文档」的实际表现。
- 补充：即使两步都成功，这个窗口里**别的客户端**读这一条也会拿到 404（表现为一次 `vanished`，下一轮重试即可）——
  那是**短暂**的；只有在崩溃 / 附件 409 时才变成永久。
- 另：`POST /v1/files`（批量取）对「有 hash 无附件」是 `continue`（`v1.ts:430-431`），
  所以批量路径会**静默少一条**，调用方拿不到"这条坏了"的信号 —— 这是修复时该补的第三个信号。

**根因分析**
内容标识（文档元数据）与正文（附件）在 CouchDB 里是**两次写**，`hash` 这个「承诺」没有和字节绑定在同一个 revision 里；
而客户端把 `hash` 当真值使用（`baseHash`、diff 判据）。一旦两次写之间出现任何中断/竞争，"承诺"与"字节"就会长期不一致。

**修复方案（具体改动点）**
1. **首选：服务端原子化**。`server/src/routes/v1.ts:507-541` 改成**一次** `putDoc`，把正文放进同一次写：
   `_attachments: { blob: { content_type: "application/octet-stream", data: base64(bytes) } }`，`baseRev` 仍是 `existing?._rev ?? null`。
   需要 `server/src/couch/client.ts:211` 的 `putDoc` 透传 `_attachments`。
   - 体积：CouchDB `max_document_size` 默认 8 MB，base64 膨胀约 33% ⇒ 需要 `maxFileBytes <= 约 6 MB`（落地前核对 `server/src/config.ts`）。
   - 好处：hash 与字节在同一个 revision 里，409 只有一个来源，`current` 永远拿得到。
2. **次选（保留两步时的补偿）**：`putAttachment` 冲突时（`:538-540`）**重读一次文档**，返回真实的 `{ hash, rev }`（不要 `null`）；
   并让客户端在 `current === null` 时**不改写** `remoteHash`（与 H1 的改动同一条）。
3. **兜底**：`GET /v1/file` 在「有 hash 但无附件」时返回 500 / `code: "corrupt"`，而不是 404，
   让客户端能把「损坏」与「删除」区分开（否则永远走 `vanished` 分支，静默跳过）。
4. 测试：`server/src/routes/v1.test.ts` 加「附件写失败后 hash 与正文一致」「有 hash 无附件时返回 corrupt」；
   `src/sync/providers/opennote.test.ts` 加 `current: null` 的处理用例。

**优先级与顺序**：**P0**（数据完整性）。客户端侧的第 2 条可与 H1 合成一个补丁；服务端原子化单独一个补丁（要跑 v1 契约用例）。

**风险与注意事项**
- 单次写大附件会放大 Node→CouchDB 的请求体（内网，且 `maxFileBytes` 有上限）；若某部署把上限调得很大，
  必须按 `max_document_size` 做一次校验并在写之前显式回 413，而不是让 CouchDB 回 500。
- 若保留两步写，**必须**同时修 `current: null`，否则 H1 的修复会退化成「每轮 409 但永远拿不到远端标识」。
- 「`current === null` 时不要改写账本」这条要写成注释，避免下一个人又把「刷新 CAS 依据」加回来（那正是 H1 的成因）。

### M2. fetchWholeTree 遇到"整页被过滤干净"的 truncated 页会提前放弃,删除被永久挂起

- **位置**:
  - `src/sync/engine.ts:862-868`(`tree.entries.at(-1)` 为空即返回 `truncated: true` 并停止翻页)
  - `server/src/routes/v1.ts:251-256`(`truncated` 按原始行数判定,但 `_design/`、`_local/`、`syncinfo`、墓碑、无 hash 条目在客户端可见前已被过滤)
- **描述**:服务端一页 500 行若全部是墓碑(did 按路径 base64 排序,同一目录批量删除 ≥500 个文件时 did 连续),客户端 provider 过滤后 `entries` 为空但 `truncated: true`,引擎视为"服务端状态可疑"直接放弃翻页并如实上报 truncated → `applyTruncationGuard` 挂起全部删除。
- **影响**:触发后每一轮同步都重复同样的放弃路径,`treeTruncated` 恒为 true、`suspendedDeletes` 永不消化;所有设备上"远端删除"永久停止传播,UI 持续提示树不完整,且没有任何自动恢复路径。

#### 核实（2026-10-22 复核）

**结论：部分属实** —— 机制属实；但**页大小不是 500**（当前客户端固定请求 1000 行/页），且影响面比原描述更大（不只是"删除挂起"）。

**验证结果与依据**
- `src/sync/engine.ts:857-872`：`if (!tree.truncated) return ...` → `const last = tree.entries.at(-1)` → `if (!last) return { truncated: true }`。
- `server/src/routes/v1.ts:251-256`（模式 A）与 `:266-271`（模式 B）：`truncated: page.rows.length >= limit` 是**过滤之前**判定的；
  随后才过滤 `_design/`、`_local/`、`syncinfo`、`deleted`、无 hash 的条目。
- `src/sync/providers/opennote.ts:132-155` 再过滤一次（tombstone / 无标识）⇒ 「整页被过滤干净」时 `entries` 为空而 `truncated` 为真。
- **页大小**：`engine.ts:828` `TREE_PAGE_SIZE = 1000`，`:852` 夹到 `[1, 2000]`；客户端**总是**带 `limit`（`opennote.ts:125-127`）。
  所以实际是 1000 行/页。原描述里的 500 是**服务端在没有 limit 时的默认值**（`v1.ts:225`），只对"不带 limit 的客户端"成立。

**描述偏差（需更正）**
1. 触发阈值：需要「一整页（默认 1000 行）全被过滤」才走到 `!last`；500 条墓碑不足以让当前客户端放弃翻页。
2. 影响面：放弃翻页时，**这一页之后的所有远端条目都拿不到**（不只是删除被挂起）—— 新增/修改也不会被拉下来；
   本地推送仍然正常（`planPush` 只看本地）。所以那台设备会变成「**只能推、不能拉**」。
   这比「删除永久挂起」更严重，也更难被用户描述清楚。

**根因分析**
分页锚点取自**过滤后的可见条目**（`tree.entries.at(-1)`），而「这一页是否装满」由**过滤前的原始行数**决定。
两个集合不一致时，锚点可能不存在（空页直接放弃），或大幅回退（部分过滤导致下一页重叠重取，见 N3）。

**修复方案（具体改动点）**
1. **服务端**：`/v1/tree` 额外返回 `nextStartKey = page.rows.at(-1)?.id`（原始行、过滤前）。
   `shared/contract.ts` 的 `treeResponseSchema` 加可选字段；`v1.ts:256` / `:271` 一并带上。
2. `src/sync/provider-types.ts` 的 `ProviderTree` 加可选 `nextStartKey`；`opennote.ts:150-155` 透传；
   `engine.ts` 的 `fetchWholeTree` 优先用它前进，缺省回退到 `entries.at(-1).did`（**旧服务端行为不变**）。
3. **服务端过滤前移**（可选、更彻底）：在 `_all_docs` 分页循环里「取到够 `limit` 条合格条目或到头」再返回，
   `truncated` 也按合格条目判。代价是多几次 CouchDB 往返；收益是 `nextStartKey` 不再需要。
4. **客户端兜底**：空页 + `truncated` 时写一条明确诊断日志（如 `tree.stalledAt`），让状态栏能说清「卡在哪一页」。
5. 测试：`server/src/routes/v1.test.ts` 加「整页墓碑仍能翻页」；`src/sync/engine.test.ts` 加「空页 truncated 不再永久挂起」。

**优先级与顺序**：**P1**。顺序在「防误删批次」之后 —— 它不丢数据，但会让一台设备长期静默失去拉取能力。

**风险与注意事项**
- 契约新增字段要考虑两个方向：老服务端 + 新客户端（回退到旧行为）、新服务端 + 老客户端（忽略多余字段）。都用可选字段，安全。
- `nextStartKey` **不能**是过滤后的 did（那就退回原问题）；服务端一定要取 `page.rows`（原始行）的最后一条。
- 若同时做第 3 条（过滤前移），注意 `truncated` 的语义会从「原始页满」变成「合格条目凑不够」—— 需要同步更新契约注释与用例。

### M3. SSE "连上比对游标"机制两端脱节:ready 永远不带有效游标,启动同步被跳过

- **位置**:
  - `src/sync/attach.ts:224`(事件流 URL 不带 `since`)
  - `server/src/routes/v1.ts:736`、`v1.ts:750-753`(ready 把客户端传入的 `since` 原样回显,而非服务端当前游标)
  - `src/sync/stream.ts:200-217`(`remote === null` 时静默跳过)

### M7. runBounded 失败后其余 worker 继续在后台运行,与下一轮同步并发写同一账本/文件

- **位置**:
  - `src/sync/engine.ts:1064-1073`(`Promise.all` 快速拒绝但不取消其余 worker)
  - `src/sync/runner.ts:262-288`(单飞只拦"入口",`inFlight` 置 null 后立即接受新请求)
- **描述**:任一 worker 抛错(如 429 耗尽重试、5xx)后整轮抛出,但仍在飞的其余 worker 会继续执行 `writeLocal`/`removeLocal`/账本写入。失败状态发布后 runner 立即可被再次触发(手动/信号),新一轮 `syncOnce` 与上一轮"僵尸 worker"并发读写同一个 `ledger` 对象与同一批文件,计划基于的快照与实际写盘交错。
- **影响**:失败高发场景(限流、网络抖动)下账本被交错更新:新一轮已重新拉取的文件可能被僵尸 worker 用旧数据覆盖,或账本记录与磁盘内容错位,表现为"拉下来的内容闪回旧版/下一轮又判本地已改"。

#### 核实（2026-10-22 复核）

**结论：属实**（且比原描述更进一步：失败后其它 worker 还会**继续领取新条目**）

**验证结果与依据**
- `src/sync/engine.ts:1056-1074` `runBounded`：`Promise.all` 里每个 worker 自己 `for (;;)` 取下一个 index；
  `await worker(...)` 抛错 ⇒ 该 worker 的 promise reject ⇒ `Promise.all` **立即** reject，
  但其它 worker 的循环**继续**（它们只是在 `await` 中，醒来后仍然 `cursor += 1` 取新条目）。
- `src/sync/runner.ts:211-237` `runOnce` catch → 发布状态 → `scheduleRetry` → 返回 `null`；
  `request` 的 `finally`（`:282-285`）把 `inFlight = null` —— 此时上一轮的 worker **仍在跑**。
- 第二轮 `syncOnce` 会重新 `listLocal` / `tree` 并**原地改写同一个 `ledger` 对象**
  （`engine.ts` 里所有 `ledger.files[...] = ...`），两轮交错 ⇒ 账本与磁盘都可能不一致。
- 补充：`runner.ts:267,277-280` 的 `pendingAgain` 会在一轮失败后再跑一轮 —— 同样与僵尸 worker 重叠。

**根因分析**
有界并发用了"快速失败"的 `Promise.all`，但没有「停止领取新条目 + 等所有 worker 收尾」这一步；
而调度器认为「`syncOnce` reject = 这一轮结束了」。两边的"结束"定义不一致。

**修复方案（具体改动点）**
1. `src/sync/engine.ts` `runBounded`：加 `let failed: unknown = null`；
   worker 循环开头 `if (failed !== null) return;`；
   `try { await worker(...) } catch (error) { failed ??= error; return; }`；
   最后 `await Promise.allSettled(workers)`，若 `failed !== null` 则 `throw failed`。
   ⇒ 「这一轮结束」的定义变成「所有 worker 都已收尾」，僵尸窗口消失。
2. 可选（更强，但改动大）：给 `SyncProvider` 的方法加可选 `AbortSignal`，失败时真正取消在飞请求；
   能把僵尸窗口压到毫秒级，但要改 provider 接口与所有调用点，列为后续。
3. 测试：`src/sync/engine.test.ts` 用「第 2 个 worker 立刻抛错、其余 worker 挂起 50ms」的假 provider，
   断言 `syncOnce` 拒绝**时**没有任何 worker 之后还会写账本；
   `src/sync/runner.test.ts` 断言失败返回后 `inFlight` 已清空、且没有并发第二轮。

**优先级与顺序**：**P1**（失败高发时才命中，但命中就是账本错乱）。建议排在 M1/M2 之后、M4 之前。

**风险与注意事项**
- `Promise.allSettled` 会让失败上报**变慢**（要等最慢的 worker）。必须有请求超时兜底（见 L6），
  否则一个挂死的连接会让「同步失败」迟迟不出现。
- 不要用「第一轮失败后直接丢弃 `ledger` 引用」来隔离：账本是调用方持有的对象（`appSync` 会落盘），
  换对象会让「已成功的那部分」丢失。正确做法是让上一轮**收尾完毕后**再允许下一轮开始。

4. 测试：`src/sync/http.test.ts` 用假 `fetch` 断言超时后抛出 `network` 而不是挂住。

**优先级与顺序**：**P2**（卡死比失败更糟：不进重试、状态栏永远「同步中」）。放在批次 3 末尾。

**风险与注意事项**
- 30s 对「慢但会成功」的大文件可能偏短；建议读 30s / 写 60s，或至少不小于桌面的值（否则两端行为又分叉）。

### L9. 每工作区独立 Pacer,多工作区并发时叠加速率可超服务端账号限额

- **位置**:`src/sync/http.ts:360-370`(Pacer 为 HttpTransport 实例私有,每个 attach 各建一个);对照服务端按**账号**限流 `server/src/ratelimit.ts`
- **描述**:同一账号挂多个工作区(或多窗口)时,各 12 req/s 的客户端限速互不知晓,合计请求速率可超过服务端账号桶,集中触发 429 并进入全局冷却。
- **影响**:多工作区用户同步互相拖累、周期性变慢;与"客户端自己限速以免撞 429"的设计目标相悖。

#### 核实（2026-10-22 复核）

**结论：属实**（作用域不一致：客户端按"传输层实例"限速，服务端按"账号"限流）

**验证结果与依据**
- `src/sync/http.ts:355-370`：`HttpTransport` 构造时 `new Pacer(...)`，`Pacer` 是实例私有字段（`:358`，类定义 `:267-347`）。
- `src/sync/providers/opennote.ts:95-105`：每个 provider 一个 `HttpTransport`；
  `src/sync/attach.ts:175-184`：每个工作区一个 provider ⇒ **每个工作区一个 12 req/s 的桶**。
- 服务端：`server/src/ratelimit.ts:160-166` 的键是 `bearer: + sha256(token)`（令牌的 sha256 前 16 位）⇒
  **按账号**（所有设备、所有工作区共享一个桶）。
- 默认值：客户端 12/s、`burst` 24（`http.ts:69-83`）；服务端 `perMinute` + `burst = max(20, perMinute/10)`（`ratelimit.ts:47-52`）。
- ⇒ N 个工作区并发时，客户端总速率上限约 N×12/s，而服务端桶不变 ⇒ 更容易撞 429；
  撞了之后每个 pacer 各自冷却、各自减半，互相不知道对方（原描述准确）。

**根因分析**
客户端限速器的作用域是「一个传输层实例」，而服务端限流的作用域是「一个账号」。两边作用域不一致，
所以客户端无法保证"账号级"的平滑 —— 这恰好是注释里写的那条设计目标（`http.ts:69-80`）。

**修复方案（具体改动点）**
1. `src/sync/http.ts` 增加模块级注册表：`const pacers = new Map<string, Pacer>()` +
  `function pacerFor(key: string, make: () => Pacer): Pacer`；`HttpTransport` 构造时按
  「baseUrl + 令牌 sha256 前 16 位」取共享实例（键里**不要**放明文 token，与 `server/src/ratelimit.ts:160-166` 同一手法）。
2. 或者更保守：在 `appSync` 层统计"同一账号下有几个工作区"，把 `requestsPerSecond` 均分下去
   （实现简单，但工作区数量变化时会抖动）。
3. 测试：`src/sync/http.test.ts` 加一条「两个 transport 用同一 key ⇒ 共享令牌桶（总速率不翻倍）」。

**优先级与顺序**：**P3**（多工作区 / 多窗口用户才会命中）。放在批次 4。

**风险与注意事项**
- 共享 `Pacer` 会改变测试的时钟注入方式（`now` / `sleep` 现在是构造参数）—— 需要给注册表加"是否共享"的开关，
  或让 key 里带上注入的时钟标识，避免单测互相污染。
- 注册表要有失效策略（工作区关闭后不能一直持有），否则长时间运行会积累 `Pacer`（量很小，但应当有 `dispose`）。
- 若将来支持多账号，key 必须带账号维度，否则会串味。

- `docs/复现报告-多设备同步.md:22-25` 引用了这一行（当时写作 `v1.ts:223`，行号已漂移到 225）。

**根因分析**

两个分支相同是静态检查就能发现的，但项目里没有这类 lint。

## 复核补充发现（原清单未列）

> 这四条是复核过程中顺带发现、**不在原清单里**的问题。它们与某些原条目同源，列在这里是为了不在修复时漏掉。

### N1. 引擎发现的冲突从未进入持久冲突账本，冲突只「活一轮」

- **位置**：`src/sync/conflicts.ts:81-89`（`recordConflict`）；唯一生产调用点 `src/data/library.ts:1325`；
  `src/sync/appSync.ts:245-258`（只写 `last.conflicts`）；`src/components/SyncDialog.tsx:65`（从 `ui.last` 读）。
- **描述**：引擎的 `conflicts` / `pushConflicts` 只进入本轮返回值，`handleSynced` 把它们放进 `last.conflicts`；
  下一轮成功同步会把 `last` 整个覆盖。`conflicts.ts` 的 `recordConflict` / `remapConflict` / `clearConflicts`
  只服务于「外部磁盘改动」那一条路径，与引擎完全无关。
- **影响**：① 冲突在 UI 上只存在**一轮**，用户很容易错过（与 H1 叠加后基本必然错过）；
  ② 改名 / 切换笔记本时的冲突清理（`remapConflict` / `clearConflicts`）对引擎冲突不起作用；
  ③ 与 L8 叠加，关闭工作区后旧冲突还会残留在 `last` 里被新工作区看到。
- **建议**：与 H1 的 `pendingConflict` 合并实现 —— **账本是唯一真源**，UI 从账本读；
  `conflicts.ts` 要么被账本取代、要么由 `handleSynced` 同步写入。属于批次 3。
- **严重度**：中（不丢数据，但会让「只报不猜」在体验层失效）。

### N2. 服务端删除预算从未实现（设计文档要求「客户端 + 服务端各一遍」）

- **位置**：设计文档 `docs/执行-三端同步-密钥即身份-2026-10-13.md:1647`；`server/` 全目录（无任何删除预算逻辑）；
  `server/src/routes/v1.ts:556-577`（`DELETE /v1/file` 逐条、无批次概念）。
- **描述**：设计明确要求删除保护「客户端 + 服务端各一遍」，实现里只有客户端拉取侧那一份（`engine.ts:649`）。
- **影响**：客户端预算被绕过（旧版本、脚本、第三方实现）时，服务端没有任何第二道闸门；
  而 H3 / M6 恰恰说明「客户端的推断」并不可靠。
- **建议**：短期在文档里把「服务端也跑一遍」标成**未实现**；中期在有批次端点或审计日志之后，
  加一个**按账号、按时间窗**的删除计数限额。**不建议**现在用时间窗硬限 —— 逐条 DELETE 没有"一次同步"的服务端视角，容易误伤批量清理。
- **严重度**：中（纵深防御缺失）。

### N3. 分页锚点取「可见条目最后一条」，有过滤时会反复重取同一段

- **位置**：`src/sync/engine.ts:864-869`；`src/sync/providers/opennote.ts:132-148`（过滤 tombstone / 无标识）。
- **描述**：服务端按**原始行**分页，客户端却用**过滤后的最后一条**当下一页的 `startKey`。
  一页里若有 N 条被过滤，下一页会从可见的最后一条之后开始 ⇒ 把被过滤的那一段**再取一遍**。
- **影响**：请求量放大；极端情况下每页只前进 1 条（不丢数据，但同步明显变慢）。与 M2 同源。
- **建议**：与 M2 的 `nextStartKey` 一起修（同一个改动，别分两次）。
- **严重度**：低（性能）。

### N4. `treeEntryFromDoc` 用 `doc.deleted` 判墓碑，而 CouchDB 的删除标记是 `_deleted`

- **位置**：`server/src/routes/v1.ts:83`（`if (doc.deleted === true) entry.deleted = true;`）；
  CouchDB 删除文档的字段是 `_deleted: true`。
- **描述**：这条判断永远不成立（字段名少了前缀下划线）。
- **影响**：**当前行为仍然正确** —— 墓碑没有 `hash` / `ehash`，会被 `validTreeEntry`（`v1.ts:111-114`）丢掉。
  但这是一条死代码；一旦将来给墓碑带上内容标识，它就会漏。
- **建议**：改成 `doc._deleted === true`（`CouchDocument` 有索引签名，可以直接访问），
  或在注释里写明「由 validTreeEntry 兜底」。属于批次 5 的顺手清理。
- **严重度**：低（潜在隐患）。

### N5. 「远端新增 + 本地也有同名文件（无共同基线）」以前会被**静默覆盖**

- **位置**：`src/sync/diff.ts` `planPull` 的 `!known` 分支（「远端新增 ⇒ 直接下载」）。
- **描述**：那一支只看「账本里有没有这一条」，**不看本地是否已经存在同名文件**。
  于是「两边都新建了同一路径、内容不同」被当成「远端新增」→ 下载覆盖本地。
- **真实触发**：把笔记本目录拷到另一台机器（本地有文件、账本为空）后联上一个已有同名笔记的远端；
  或 E2EE 下新设备重建 did↔path 映射后的第一次同步。
- **影响**：本地那一份**未经确认就被覆盖**（红线 5 的同一条：绝不静默覆盖）。
  它一直存在但没人报过 —— 因为"看起来就是下载"。
- **修复**（本轮已做）：`!known` 分支里若本地也存在且 hash 不同 ⇒ 记 `both-modified` 冲突、不下载；
  本地不存在、或内容恰好相同才下载。`known.imported === false`（上次没物化成功）仍然直接下载。
- **用例**：`engine.test.ts`「两边都新建同一路径且内容不同 ⇒ 冲突」「内容相同 ⇒ 不算冲突」；
  E2E 的 E2EE 用例改成「账本里有记录但从未物化」来表达「已知路径」，不再靠一个假的占位文件。
- **严重度**：高（静默数据覆盖），但触发面比 H1 窄。

### 五、跨条目依赖与注意事项

- **H1 ↔ M1（客户端）↔ N1**：三处都改「冲突后账本怎么写」，**必须一次设计、一次实现**；
- **H1 ↔ L3**：H1 新增的「跳过冲突路径」必须计入 L3 的"已处理"，否则进度条又回到 `done < total`；
- **H3 ↔ M5 ↔ M6 ↔ N2**：同一条纪律（不完整 ⇒ 不删）的三个落点 + 服务端那道缺失的闸门，建议抽一个共享判定函数；
- **M2 ↔ N3**：同一处翻页锚点，别分两次改；
- **M7 ↔ L6**：M7 的 `allSettled` 需要 L6 的超时兜底，否则失败上报可能被一个挂死的连接拖住；
- **L5 ↔ H3 的删除预算**：非 md 条目会计入 `plannedDeletes`，修 L5 之前它们可能把同批的真删除一起拦住。

### 六、暂不做 / 需要产品决策

1. **服务端删除预算**（N2）：需要"批次"或"会话"概念，逐条 DELETE 上做时间窗限额会误伤；
2. **provider 层 `AbortSignal`**（M7 第二步）：改动面大（`SyncProvider` 所有方法 + 三个宿主），当前用超时兜底够用；
3. **忽略范围变化提示**（H2 后续）：设计文档 §3.11 第 866-867 行已要求，但需要 UI 与 watcher 配合；
4. **CouchDB 单次写大附件的尺寸校验**（M1）：依赖部署的 `maxFileBytes` 与 `max_document_size`，落地前要对齐。
