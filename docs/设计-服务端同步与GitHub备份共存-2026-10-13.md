# 设计：服务端自动同步 与 GitHub 手动备份 如何共存

> 状态：**设计文档，未实施**。前提：走路线 C（自托管同步服务），同时保留现有的 GitHub 备份习惯。
> 现状依据：README:120-135（GitHub 通道的规则）、`src/lib/github/sync.ts`（`planPush`/`planPull`）、
> `src/App.tsx:803-892`（现有同步对话框）。
> 本文只回答一件事：**引入服务端自动同步之后，「手动同步」这套逻辑变成什么。**

---

## 0. 一句话

**心智模型从「GitHub 是同步通道」变成「服务端是收敛通道，GitHub 是备份 / 恢复出口」。**

日常的多端一致性不再需要手动操作；手动动作从每天可能点几次的「push / pull 同步」，
退化成低频的「**备份**」和「**恢复**」——而且它们不再是同一件事。

## 1. 三个角色，分清职责

| 层 | 是什么 | 谁负责收敛 | 频率 |
| --- | --- | --- | --- |
| **T0 本地文件夹** | 你正在编辑的工作副本 | —— | 每时每刻 |
| **T1 同步服务** | 收敛通道：按文件三方 diff、双向、冲突列出 | **自动** | 保存后防抖；打开/回前台时拉 |
| **T2 Git 仓库** | 备份与恢复出口：离机、异地、带历史 | **手动** | 时不时一次快照 |

关键纪律：**收敛只由 T1 负责，T2 不做日常同步。**
两个通道都当收敛通道，就会互相打架（下面 §6 的三个坑全是这么来的）。

## 2. 手动操作对照表

| 场景 | 今天（只有 GitHub） | 加了服务端之后 |
| --- | --- | --- |
| 日常多端一致 | A 手动 push，B 想起来才 pull | **全自动**：B 打开笔记/回前台时收敛 |
| A 改了，B 还是旧版 | B 手动 pull | 自动。B 的本地没改 → 直接换成最新，无需人 |
| A 改了，B 也改了同一篇 | pull 时列出「两边都改」 | 服务端同步时列**同一份冲突**（同一条规则） |
| 备份 | 手动 push（这同时是同步） | 手动 push，语义变成「把当前状态快照到 GitHub」 |
| 新设备 | 手动 pull（导入） | 优先连服务端全量拉；或先从 GitHub 恢复再连服务端 |
| 服务器挂了 | 无所谓 | 从 GitHub 恢复（复用原来的 pull 路径） |
| 换电脑 | 拷文件夹 / 从 GitHub 拉 | 同上，且 `.opennote/` 里的两份账本跟着走 |

**结论：真正需要人做的，只剩两类事——① 处理「同一篇两边都改了」的冲突；② 偶尔备份。**
「设备不是最新版本」不是异常，是同步层的常规输入。

## 3. 备份（push）应该是什么规则

- **语义**：把当前设备的笔记目录快照成一个提交（现有行为：一次推送 = 一个提交，`.opennote/` 永不推送，绝不 force）。
- **不阻塞**：备份按钮**永远可用**。服务器连不上也必须能备份——否则「服务器挂了」和「服务器还没配好」时你就没有备份了，那是本末倒置。
- **但要如实标注状态**（在按钮旁/对话框里）：
  - 服务器可达时：先顺手同步一次（很便宜），然后备份的是**收敛态**；若有未解决冲突或本机落后，明确写出来；
  - 服务器不可达时：写「无法确认本机是否为最新」，让用户自己决定。
- **可选**（后续）：一个「每次收敛后低频自动备份」的开关（如每 6/24 小时），但默认仍是手动——你现在的习惯就是手动，不必改。

## 4. 恢复（现在的「拉取」）应该换名字、收窄用途

**把「从远端拉取」改名为「从备份恢复」，并限定它只用于新设备 / 灾难恢复。**

理由是一个容易踩的坑：`.opennote/github.json` 这份账本记的是「**上次和 GitHub 同步时**本地长什么样」。
一旦服务端开始自动改本地文件，这份账本就过时了——此时如果还把它当日常同步用，
一堆文件会被判成「本地改过」，于是虚报一堆冲突。**备份（push）没这个问题**（它本来就是要推差异），
**拉取（pull）才会**。

具体规则：

| 在哪台设备上 pull | 行为 |
| --- | --- |
| **全新的、还没连服务端的设备** | 正常导入（现有逻辑，最优路径） |
| 已经在跑服务端同步的设备 | `planPull` 里 `remoteChanged=false`（没人推过）→ 基本是空操作；若仓库被别的设备推过，则应先收敛本地再比较 |
| 服务器已经没了、要用备份救回来 | 走现有的「只覆盖本地没动过的文件 + 两边都改的列出来」——这条规则本来就是为恢复设计的，保留不动 |

## 5. 多设备版本不一致时，同步层具体怎么走

三条互斥的情形，覆盖了全部情况：

1. **远端改了、本地没改** → 直接下载覆盖（设备旧=落后，自动补齐）；
2. **本地改了、远端没改** → 推送；
3. **两边都改了** → **不覆盖**，逐条列出等用户裁决。

所以「B 落后三天」在第 1 条里就被消化掉了；只有当你在 B 上**在同步之前又编辑过**，才会进第 3 条。

> ⚠️ 这正是 P0 必须修的东西：现有 `reconcileExternalChange`（`src/data/library.ts:1195`）是 D3「磁盘赢」——
> 会自动采纳磁盘、把内存改动塞进隐藏前像。单机没问题；跨设备时用户会「看到自己的改动消失」。
> 同步（服务端）路径必须走第 3 条：**列出，不自动采纳。**

## 6. 三个必须处理的坑

### 坑 1：只指定**一台**设备负责备份
今天两台设备都能 push。服务端到位后，若两台都点备份：A 推完仓库前进，B 再推就会撞上
**非快进 → 现有代码直接中止并让你先拉取**，每次都被打断。
**建议：明确「备份设备」就一台**（比如你主力那台桌面机）；其它设备不显示备份按钮，或显示但提示「建议在 <设备> 上备份」。

### 坑 2：给 `planPull` 加一条「两边内容相同 → 不算冲突」
现在 `planPull` 只要 `localChanged` 为真就报冲突，哪怕两边内容**已经一模一样**。
多设备备份 + 服务端同步的场景下这会产生大量假冲突。
rclone bisync 的官方定义里明确有这条：**内容当前相同就不算冲突**（即使两边都改过）。
这是个几十行的改动，能省掉绝大多数噪音。

### 坑 3：两份账本要分开，UI 也要分开
- `.opennote/sync.json` —— 「我对服务端」的基线（`hash` / `rev`）
- `.opennote/github.json` —— 「我对 GitHub」的基线（`localHash` / `remoteSha`）

它们对「本地改过没有」的答案**不同**，而且合法地不同。绝不要合成一份，也不要在 UI 上把两个状态揉成一个「已同步」。

## 7. 状态栏建议

两个独立指示器，别合并：

| 指示器 | 状态取值 | 可点的动作 |
| --- | --- | --- |
| **同步（服务端）** | 已同步 / 同步中 / 离线（N 项待推） / **N 个冲突待处理** | 立即同步、查看冲突 |
| **备份（GitHub）** | 上次备份：<时间> / 有 N 项变更未备份 / 无法确认是否最新 | 备份到 GitHub、从备份恢复（次要入口） |

冲突指示器要**持久**，不能只用一次性 toast——它是最需要人介入的状态。

## 8. 灾难恢复矩阵

| 丢了什么 | 恢复方式 | 代价 |
| --- | --- | --- |
| 一台设备 | 新设备连服务端全量拉 | 最省；需要服务器在线 |
| 服务器 | 从 GitHub 备份 `pull` 到本地，再重建服务端 | 丢失 GitHub 备份之后的内容 |
| 服务器 + 某设备 | 用另一台设备重建服务端，再从 GitHub 核对 | 需要至少一台设备还在 |
| 全都没了 | 从 GitHub 备份恢复 | 最后一次备份之后的内容不可恢复 → **这是「偶尔备份」的唯一价值主张** |

这张表说明一件事：**GitHub 备份的价值不是「同步」，是「服务器和自己都出问题时的那一份」**。
所以它值得保留，但值得低频、值得手动。

## 10. 笔记本目录里保留 `.git`（已采纳）

### 10.1 事实前提

opennote 的 GitHub 通道走的是 GitHub REST API，**从不读写 `.git`**
（`src/lib/github/*` 全是 blob / tree / commit / ref API；`.opennote/github.json` 是它自己的账本）。
所以「服务端同步了、但 `.git` 没变」这件事，只会发生在**你自己 `git clone` 过这个笔记本目录**的情况下。
本项目决定保留 `.git`，因此本节给出让两者共存的分工与纪律。

### 10.2 先把两个问题分开：排除 `.git/` 解决的不是你问的那个

| 问题 | 后果 | 排除 `.git/` 能解决吗 |
| --- | --- | --- |
| **A. 同步服务把 `.git/` 当普通文件搬走** | 仓库被搞坏（objects / index 跨设备冲突） | ✅ 就是为它，**必须排除** |
| **B. `HEAD` 漂移**：服务端改了 `笔记.md`，git 看见工作树变了 | `git status` 脏、`git pull` 被拒、重复提交 | ❌ **无关**。B 是「被跟踪的普通文件」的问题，与 `.git/` 无关 |

**结论：排除 `.git/` 是必须的，但它不解决 B。B 靠工作流解决（§10.7）。**

### 10.3 分工表：谁管什么

| 路径 | 同步服务（T1） | git | 说明 |
| --- | --- | --- | --- |
| 非隐藏内容（`*.md`、`assets/`） | ✅ 管（自动收敛） | ✅ 跟踪（快照/备份） | **唯一的重叠区**，靠 §10.7 的纪律 |
| `.git/` | ❌ 排除 | ✅ 独占 | §10.4 / §10.5 |
| `.opennote/` | ❌ 排除 | ❌ 必须 ignore | 设备本地态（基线 / 历史 / 收件箱） |
| `.gitignore` / `.gitattributes` | ❌ 排除（隐藏文件本就不在扫描范围） | ✅ 独占 | 由 git 维护，不会两边打架 |
| 其它隐藏文件 | ❌ 排除 | 视 `.gitignore` | |

一句话原则：**隐藏文件归 git，非隐藏文件归同步服务，`.opennote/` 谁都不碰。**

### 10.4 同步服务排除 `.git/`——好消息是基本已经免费

现有 `collectLocalFiles`（`src/lib/github/sync.ts:144-179`）遍历时用的是：

```ts
if (isHiddenPath(path) || skipDirs.has(entry.name)) continue;   // sync.ts:164
```

`.git` 是以 `.` 开头的隐藏路径 → **已经被排除**。所以只要服务端 provider 复用同一个扫描函数
（设计上就是这么定的），「清除 `.git/`」不需要新写规则；需要的是**测试钉住它**
（断言「笔记本里有 `.git/` 时，扫描结果不含它」）。

### 10.5 但 watcher 必须新增排除 `.git/`（这才是真正要改的地方）

现在主进程的 watcher 只跳过 `.opennote/**`。而**任何一次 `git commit` / `git fetch` / `git status`
都会改动 `.git/`**（objects、refs、index），于是：

- 制造大量无意义的变更事件 → 触发重扫 → 卡顿；
- 极端情况下撞上 `PATH_REFRESH_LIMIT`（`src/data/library.ts:923`）而退回整库重扫。

要改：`electron/main.cjs` 的 watcher 过滤加上 `.git`（建议同时覆盖 `node_modules` / `dist` / `release`，
与 `collectLocalFiles` 的 `skipDirs` 对齐）。

### 10.6 要不要尊重 `.gitignore`？要，但别自己写解析器

- **值得做**：`.gitignore` 正好表达「这些不是笔记的一部分」（`.DS_Store`、临时文件、大二进制）。
  让同步服务照它排除，既省流量又少噪音；做的话 **GitHub 通道与同步通道应共用同一份判断**，
  这样 API 备份的行为才和本机 git 一致。
- **不要自己写匹配**：`.gitignore` 语义比看起来复杂——`!` 取反、`**`、目录尾斜杠、行首斜杠，
  以及「被忽略的目录里还能用 `!` 重新包含文件」。自己实现极易在边缘出错。
  要么用 git 官方语义的现成实现（如 `ignore` 包），要么**明确只支持一个子集并写进文档**。
- **两个反直觉点**：① `.gitignore` 只影响**未跟踪**文件，已 `git add` 过的文件即使写进去仍被 git 跟踪——
  按它排除会出现「git 里有、同步服务里没有」的分歧；② **被排除的文件不会同步到其它设备**，
  用户可能以为会有。

### 10.7 推荐的工作流姿态：把 git 当「快照工具」，而不是「远端镜像」

这是 `.git` 与自动同步共存的关键——**不要试图让 HEAD 时刻追平远端**，而是承认：

> **`git status` 长期显示 modified 是预期状态，不是故障。** 它只表示「距上次快照又有改动」。
> 同步服务负责让内容收敛；git 负责在你想要的时候留下一个快照。

四条纪律：

1. **不要在跑同步的设备上 `git pull`。** 内容由服务端带来；pull 会撞上「工作树不干净」而被拒，
   或制造与上游内容重复的提交。拉取只留给「新设备引导」和「灾难恢复」。
2. **备份 = 提交 + 推送**：`git add -A && git commit -m "backup: <时间>" && git push`。
   这条永远可用，而且提交的就是「当前内容」，不需要 HEAD 事先对齐。
3. **git 操作只在主力设备上做**（与 §6 坑 1「只指定一台设备负责备份」是同一条规则）。
   多台设备各自 commit + push 会产生内容相同、历史分叉的提交，要 `git pull --rebase` 收拾，没必要。
4. **`git checkout .` / `git restore .` 是危险动作**：会把同步服务刚带来的内容退回旧版，
   服务端下次又同步回来，来回拉锯。**不要用它来「清理 git status」。**

### 10.8 备选姿态：坚持让 HEAD 追平远端（不推荐，但可用）

判据只有一条：**工作树内容是否已经等于远端提交内容。**

```bash
git fetch origin
git diff --quiet origin/main -- .   # 返回 0 = 工作树已与远端一致（把 origin/main 换成你的远端分支）
git reset --hard origin/main        # 只把 HEAD/index 对齐，内容不变
```

- 返回 **0** 时 `reset --hard` 是**无损**的（内容本来就一样，只是 HEAD 落后）；
- 返回**非 0** 说明本地还有远端没有的内容 → **不要 reset**，先单独处理那部分；
- `reset --hard` **不碰未跟踪文件** → `.opennote/`（基线 / history / inbox）安全；
- 顺序纪律：**先服务端同步，再对齐 git**；反过来会把内容推回去；
- ⚠️ **换行符会让判据失真**：若开了 `core.autocrlf`，`git diff` 可能因 CRLF/LF 判成不同，
  而 `reset --hard` 会按 git 的规则重写工作树 → 同步服务随即看到「内容变了」（哈希不同）→ 可能又推回去。
  笔记本目录里最好放 `.gitattributes`（例如 `* -text`）；
- ⚠️ **不要自动化它**：做成「每次同步后自动 `reset --hard`」会静默吃掉真正的本地新改动。

### 10.9 硬要求：`.opennote/` 必须进 `.gitignore`

现在「`.opennote/` 永不推送」是靠**应用逻辑**保证的（`src/lib/github/sync.ts:21-22`）。
一旦这个目录是 git 工作树，没有 `.gitignore`，一次 `git add -A` 就可能把 `history/`、`inbox/` 一起提交上去
（令牌不在里面——令牌在 `localStorage`——但历史快照和收件箱会）。

**已经确定的边界**：笔记本目录**允许**存在 `.git`；同步服务与备份通道都**不读写 `.git`**，并把它排除在扫描之外。
应用侧要做的三件事：① 扫描排除 `.git/`（复用 `isHiddenPath`，**加测试钉住**）；
② watcher 排除 `.git/`（§10.5）；③ 在界面上把 §10.7 的四条纪律说清楚——尤其是「这里不要 pull」
和「`git status` 脏是正常的」。
