## 十、验收后回归：state.json 写入路径（T12）

用户实测在真实桌面端看到控制台每次元数据落盘都刷一条：

```
Error occurred in handler for 'opennote:fs:move': Error: 目标路径已存在：.opennote/state.json
    at asUserError (electron/main.cjs:322:85)
```

根因：`writeStateFile` 用「写 tmp → `move(tmp, state.json)`」**以这次 move 的失败当「目标已存在」的探测**，而三种后端的 `move` 都不覆盖已存在目标（正是 D34/D07 契约化的语义），因此从第二次落盘起必然失败；渲染层 catch 得住（数据没坏），但 Electron 为每个被拒绝的 `ipcMain.handle` 打一条错误。Lead 的修复：`writeStateFile` 改为一次 `target.writeText(STATE_FILE, contents)` + 清理旧 `${STATE_FILE}.tmp`。

### 10.1 我先独立复现，再采信结论

**第一次复现尝试失败了**：我按「tmp → `remove(state.json)`（忽略失败）→ move」重建旧实现，结果 `library.meta.test.ts` **4 例全过** —— 因为 remove 成功后目标已不存在，第二次 move 就不会被拒。这说明「先 remove 再 move」不是刷屏的那段代码。改成忠实形态后立刻复现：

```ts
await target.writeText(tmp, contents);
try {
  await target.move(tmp, STATE_FILE);      // ← 第一次 move：以失败当探测（刷屏来源）
} catch {
  await target.remove(STATE_FILE, { recursive: false }).catch(() => undefined);
  await target.move(tmp, STATE_FILE);      // ← 回退路径（留下「文件不存在」窗口）
}
```

这条经历本身有记录价值：只按描述重建旧实现，很容易漏掉「哪一次调用才是探测」这个关键顺序。

### 10.3 (b) 「三种后端的 writeText 本来就自带 tmp + 替换」是否属实

| 层 | 机制（读代码） | 中途被杀后 `state.json` | 判定 |
