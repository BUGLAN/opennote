# 选型：自托管同步后端 C1–C4 详细对比

> 状态：**选型文档，未实施**。上一层的路线选择见
> [三端同步与网页端实时显示-方案调研.md](三端同步与网页端实时显示-方案调研.md) §四；
> 已定：走 C（自托管），一台小 VPS，**带宽充足**。
> 因此本文**不讨论**分块/去重/带宽优化（那是量了再说的事），只比较**服务端后端怎么选**。

---

## 0. 结论先行

> **已定（2026-10-13）**：选定 **C4 —— 自研服务端**，技术栈 **Node 22 + TypeScript**（与客户端同仓、共享契约类型与路径规则）。
> C1（CouchDB）与 C3（WebDAV）保留为备选。接口契约、存储布局与客户端改动清单见
> [设计-同步服务接口与客户端改动清单-2026-10-13.md](设计-同步服务接口与客户端改动清单-2026-10-13.md)。
> 下面的决策树与总表保留为**决策依据的记录**。

**三个问题就能定下来**，按重要性排序：

```
Q1「秒级」是硬需求吗？
   ├─ 否 → C3（WebDAV，服务端就是一个文件夹）最省事；C2 也行
   └─ 是 ─┐
          Q2 你更怕哪种风险？
             ├─ 怕「别人的协议出问题」 → C1（CouchDB）
             └─ 怕「自己的协议变成没人维护的私有格式」 → 见 Q3
          Q3 服务端的数据要不要保持「就是普通文件」？
             ├─ 要（本项目产品哲学） → C4（自研极小服务）
             └─ 无所谓 → C1
```

**我的建议**：

| 排序 | 候选 | 一句话理由 | 什么时候别选它 |
| --- | --- | --- | --- |
| **1** | **C4 自研极小服务** | 唯一同时满足「服务端就是文件 + 秒级 + 客户端协议简单 + 浏览器 CORS 自己说了算」 | 你不愿意为一个自有协议长期负责 |
| **2** | **C1 CouchDB** | 协议最多、久经使用，客户端代码最少，实时/检查点/冲突都不必自己设计 | 你不能接受服务端的数据是数据库形态 |
| 3 | **C3 WebDAV** | 服务端零自定义、数据就是文件夹，最贴近 `FileSystemBackend` 语义 | 你要秒级；或你的 WebDAV 托管在第三方（CORS 很可能过不了） |
| 4 | **C2 对象存储 + manifest** | 你不想要任何服务端进程、只用现成桶 | 你想秒级，或不想自己管 manifest 的一致性 |

> 一个反直觉但要记住的结论：**C2 / C3 单用都拿不到秒级**。
> S3 的事件通知只能投递到 SNS/SQS/Lambda，WebDAV 连 `RFC 6578` 都只是「增量列表」不是推送。
> 想要秒级，就必须再写一个通知端点——**那就已经是 C4 的一半了**。所以「C3/C2 少写服务端」这个优势，在「要秒级」的前提下会打折。

## 1. 四个候选长什么样

| | 服务端装什么 | 服务端存的是什么 | 客户端怎么列树 |
| --- | --- | --- | --- |
| **C1 CouchDB** | 官方 Docker 镜像（Erlang VM） | **文档**（一个文件 = 一条 doc，正文 base64） | view 投影 `path→hash`（见设计文档 §4.1） |
| **C2 对象存储** | 无进程（MinIO 或托管 OSS/COS） | **对象**（一个文件 = 一个对象）+ 一个 `manifest.json` | 拉 manifest（条件请求比 ETag） |
| **C3 WebDAV** | nginx dav / 自己写的小 WebDAV / 坚果云 | **文件夹**（和本地目录同构） | `PROPFIND`，或 `RFC 6578 sync-collection` |
| **C4 自研服务** | 你自己写的单进程小服务（约数百行） | **文件夹**（+ 一个序号/版本记录） | `GET /tree` 返回 `path→hash` |

四者的**客户端引擎完全相同**：`.opennote/sync.json` 基线 + `collectLocalFiles` + `planPush`/`planPull`（现有纯函数）+ 冲突列表。
差别只在 `SyncProvider` 的六个方法各自怎么实现。

## 2. 总表

| 轴 | C1 CouchDB | C2 对象存储+manifest | C3 WebDAV | C4 自研服务 |
| --- | --- | --- | --- | --- |
| **秒级推送** | ✅ `_changes?feed=continuous`/`eventsource` | ❌（事件只能进 SNS/SQS/Lambda） | ❌（RFC 6578 也只是增量列表） | ✅ 自己发 SSE（最简单的那种） |
| **增量列树成本** | view 查询，只回 `path→hash` | 一次条件 GET manifest（但 manifest 会随库增长） | `PROPFIND` 逐层，成本 ∝ 条目数；`sync-token` 可只取增量 | 一次 `GET /tree`（配合 seq，可只取增量） |
| **检查点原语** | ✅ 原生 `_local/<id>`（**不参与复制**） | ⚠️ 无，靠自己记 manifest 的 ETag | ⚠️ 无，靠 `sync-token`（支持才行）或本地基线 | ✅ 自增 `seq` 由自己定义 |
| **并发写 / CAS** | ✅ `PUT` 带 `_rev` → 409，**逐文档**、原生 | ⚠️ `If-Match`/`If-None-Match`（AWS 支持且不加价；**MinIO / OSS / COS 的支持度待核实**） | ✅ `PUT` + `If-Match`（RFC 4918 §7.2 明说协议本身防不住 lost update，只能靠客户端自保） | ✅ `If-Match: <hash>`，语义完全自己定 |
| **冲突时服务端是否留下另一版** | ✅ **会**：leaf revision 不丢，`?conflicts=true&open_revs=all` 可取全部 | ⚠️ 仅当开了 bucket Versioning | ⚠️ 取决于实现（Nextcloud 有版本；nginx dav 没有） | ✅ 可自己做（append-only 历史，成本很低） |
| **大文件** | ⚠️ base64 膨胀 33%；单文档大小需注意 | ✅ 对象存储天然适合 | ✅ 原样字节 | ✅ 原样字节 |
| **E2EE 可行** | ⚠️ 可行但**与 view 列树冲突**：view key 必须是明文 `path`。改用 `_id = hash(path)` + `_all_docs` 只取 id/rev、按需 GET 即可绕开（见 §8 待细化） | ✅ 对象本就是 blob | ✅ 最自然（服务端只见密文文件名/内容，但文件名需混淆） | ✅ 最自然 |
| **浏览器直连（CORS）** | ✅ 可配（`[chttpd] enable_cors` + `[cors]`） | ✅ 桶级 CORS | ⚠️ **最大陷阱**：第三方 WebDAV（如坚果云）通常不发 CORS 头且你改不了；自建才可控 | ✅ 自己想加就加 |
| **桌面端** | 需主进程代理（CSP 不放 https） | 同左 | 同左 | 同左 |
| **移动端** | 前台 `resume` + 增量 | 同左 | 同左 | 同左 |
| **备份 / 灾难恢复** | ⚠️ 数据库形态：要 CouchDB 自己的方式（replication 到第二台 / `_all_docs` 导出）。**不能直接 rsync**（可 rsync 数据目录，但要停机或接受不一致） | ✅ 桶就是文件，copy 即可 | ✅ **就是文件夹，rsync 即可** | ✅ **就是文件夹，rsync 即可** |
| **服务端常驻资源**（量级估计，需在目标小鸡上实测） | 量级最高（VM/数据库进程，数百 MB 级） | 无进程（托管）或 MinIO 数百 MB 级 | 最低（nginx 十 MB 级） | 很低（几十 MB 级） |
| **我们要写的代码** | 最少（只写客户端 + 文档模型） | 中（客户端 + manifest 一致性） | 中（客户端 + XML/ETag 摩擦；要秒级再写通知服务） | **最多**（客户端 + 服务端 + 协议） |
| **契约测试** | 需一个假 CouchDB HTTP 服务（可写），或 CI 起 docker | 需假 S3 / MinIO | 需假 WebDAV（XML 响应） | ⚠️ 自己的协议，测试也得自己写，但最直白 |
| **长期维护 / 生态** | ✅ 上游维护，有 LiveSync/PouchDB 等大量参考 | ✅ 上游维护 | ✅ 上游维护 | ⚠️ **只有你**（bus factor = 1） |

## 3. 每个候选「你必须自己写」的清单（真正的差异所在）

**C1 CouchDB**
- 文档模型与 `_id` 方案、逻辑 tombstone、view 投影、每设备 `_local` 检查点；
- CouchDB 服务的安装/加固：专用 DB 用户、`require_valid_user`、CORS 白名单、TLS、备份策略、`_revs_limit` 实测；
- **不需要**写：推送、检查点、增量、冲突保留——都是现成的。

**C2 对象存储 + manifest**
- manifest 的一致性：**先写对象、后写 manifest**，中间崩溃要靠下次同步自愈；manifest 本身是单文档热点，需要 CAS，且会随库增长；
- 「远端变了什么」= manifest 的条件 GET；对象级 ETag 不可信（multipart/加密后不是 MD5）；
- **要秒级还得再写一个通知端点**（= C4 的一半）；
- 浏览器端不能放长期密钥 → 要么用 presigned URL（**需要自建签名服务**），要么让用户把桶密钥填进浏览器（不推荐）。**所以「零服务端」在网页端也不成立。**

**C3 WebDAV**
- `PROPFIND` 的 XML 解析 + `Depth` 语义 + ETag 规则 + `If-Match`；`RFC 6578 sync-collection` 支持度因实现而异；
- 要秒级 → 再写一个 inotify → SSE 的通知端点；
- 若用第三方 WebDAV，**大概率因 CORS 直接出局**；自建 WebDAV 才可控。

**C4 自研极小服务**
- 服务端：`GET /tree`、`GET /file`、`PUT /file`（带 `If-Match: <hash>`）、`DELETE`、`GET /changes?since=`、`GET /events`（SSE）；
- 必须处理：**原子写**（临时文件 + rename）、序号/检查点一致性、并发写、鉴权（一个 bearer token 就够）、限流、备份、以及放开 SSE 的反代细节（nginx buffering、keep-alive、断线重连）；
- 好处：`seq`、`If-Match` 语义、CORS 头、E2EE 分层，全由你定，没有一样是逆着第三方设计走的。

## 4. 三个决定性问题，展开说

### Q1 「秒级」是硬需求吗
- 如果是：可选集合立刻缩到 **C1 / C4**（以及「C3+自己写通知端点」）。
- 如果不是（分钟级可接受）：**C3 的性价比最高**——服务端零业务逻辑、数据是纯文件夹、备份就是 rsync。
- 这里不要含糊：它直接决定要不要再写一个推送组件。

### Q2 服务端的数据要不要保持「就是普通文件」
这不是洁癖，是三个实际后果：

1. **备份/恢复**：C2/C3/C4 是 `rsync`；C1 需要 CouchDB 自己的方式（甚至要接受「停机才能保证一致」）。
2. **可迁移性**：哪天不想用这个同步了，C4/C3/C2 的对象/文件可以直接拷走；C1 要先导出。
3. **产品哲学**：这个项目的全部卖点是「笔记就是你磁盘上的 Markdown 文件」。**服务端是数据库**和这句话有张力——只有服务端是文件时才真正一致。

### Q3 E2EE 现在做吗
- 四个都能做客户端加密，但自然程度不同：**C3/C4/C2 的服务端本来就是 blob 存储**，加密只是把字节换掉；
- **C1 有一个不显然的摩擦**：设计文档 §4.1 用 view 投影 `path→hash`，而 **view 的 key 必须是明文 `path`**——开了 E2EE 就不能用。
  绕开的办法是：`_id` 本来就是 `hash(path)`，客户端可以自己算出 id，于是改用 `_all_docs` 只取 `{id, rev}`、
  只对 rev 变了的文档发 `GET`（届时才解密拿 `path`/`hash`）。这条路成立，但要改设计文档 §4.1 的方案（见 §8）。
- 结论：E2EE 不是选型的决定项，但**如果你已经决定要做 E2EE，C4/C3 会比 C1 顺**。

### 附：CORS 是最容易被漏掉的一票否决项
桌面端走主进程不受 CORS 约束，但**网页端是硬需求**：
C1 可配、C2 桶级可配、C4 自己写，**只有 C3 用第三方 WebDAV 时基本没救**（除非你在前面架反代加头——那又是写服务端）。

## 5. 组合与迁移路径

- **C3 → C3+通知**：先只有 WebDAV 跑通（分钟级），再加一个 inotify → SSE 的端点拿秒级。**增量式，随时可停。**
- **C2 → C1 / C4**：manifest 模型和 CouchDB 文档模型不冲突，`SyncProvider` 接口不变。
- **C4 → C1**：如果自研服务开始长成「CouchDB 的劣化版」（要加版本、要加冲突、要加多写者仲裁），**这就是该换 C1 的信号**。
- 因为四者共用同一个 `SyncProvider` 与同一套 `planPush/planPull`，**换后端是加一个文件，不是返工**。
  所以**不要为了选型而卡住**：先做 P1（抽 provider，GitHub 保留为调试 driver），再拿下面的一日 spike 决定 C 里的哪一个。

## 6. 一日可做的判别性 spike

同一套 provider 契约测试，跑两个实现，比较「你更愿意和哪种代码长期相处」：

1. **C4 路线（半天）**：写一个 ~150 行的服务（`/tree`、`/file`、`/events`），
   跑通「桌面改一篇 → 网页端 ≤1s 自动出现」；再把断网、重启、并发写三种情况过一遍。
2. **C1 路线（半天）**：`docker run couchdb`，配 CORS + 专用用户 + 一个 view，
   跑同一个测试集，再实测**内存占用、备份/恢复步骤、以及 E2EE 改造成本（§8）**。

判据不是「哪个更快」，而是：**哪一个的失败模式你更能接受**——C4 是「自己的 bug」，C1 是「别人的语义 + 自己不会配」。

## 7. 待核实项（动工前逐条确认，不要凭记忆写死）

1. **C2 的门槛**：MinIO / 阿里云 OSS / 腾讯云 COS 对 `PutObject` 的 `If-Match` / `If-None-Match`（条件写）支持到什么程度。
   AWS S3 明确支持且不加价；**兼容实现不一定**。这直接决定 C2 能不能做 CAS。
2. **C3 的门槛**：目标 WebDAV 实现是否支持 `RFC 6578`（`sync-collection`/`sync-token`）；
   第三方（坚果云等）的 CORS 头行为——若没有 CORS，C3 对网页端直接不可用。
3. **C1 的细节**：`_revs_limit` 默认值与是否需要调；`_bulk_docs` 批量写的收益；
   `[chttpd] max_http_request_size` 与单文档上限；3.x 加固清单（admin 用户 / `require_valid_user` / CORS 白名单）；
   以及 §4 Q3 里 `_all_docs` 替代 view 的方案是否成立（需实测 `_all_docs` 在含 tombstone 时的返回形状）。
4. **通用**：CSP `connect-src` 的具体域名清单；桌面端主进程代理的收窄范围（只允许配置的 base URL，防止被当成通用转发器）。
