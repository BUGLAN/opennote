# P0 详细

## D01 移动 / 重命名 / 删除文件夹期间输入的内容静默丢失

- **严重度**：P0（数据丢失 + 状态误报）
- **位置**：
  - `src/data/library.ts:778` `remapIds()`：只迁移 `notes` / `folders` / `trash` / `ui` / `meta`，**不迁移 `dirty` 与 `writeTimers`**
  - `src/data/library.ts:369`：`flushNote()` 在 `!note` 时直接 `await pendingWrites.get(id); return;`（不报错）
  - 调用 `remapIds` 的写操作：`renameNote:486`、`moveNote:519`、`renameFolder:665`、`deleteFolder:726`、`moveFolder:750`
- **触发**：上述任一操作进行中（每次都是多次 IPC 往返，大目录可达数秒）在编辑器里输入
- **影响**：内存与磁盘都没有这段输入；`dirty[新id] = false` → 状态栏显示「已写入磁盘」，无任何提示；`dirty` 里留下永远无法清除的幽灵键
- **证据（实测·harness）**：
  - `[15]` 拖拽移动中打字 → `移动结束后 内存正文="# 拖拽过程中敲的正文" dirty=["a.md"]`；`flushAll 之后 磁盘 资料/a.md="# 旧内容"`；`dirty[资料/a.md]=false`
  - `[16]` 重命名中打字 → `磁盘 新名.md="# 旧内容"`，`dirty=["旧名.md"]`
  - `[4]` 删除文件夹「只删文件夹，笔记上移」时打字 → 内存与磁盘都被 `rescanWorkspace` 回滚为旧内容
- **修法**：在 `remapIds` 内同步迁移 `dirty`（`delete next[oldId]; next[newId] = true`），并处理 `writeTimers`（`clearTimeout` 后按新 id 重新 `persistNoteSoon`）；或在上述操作开始时先 `await flushAll()` 并把 `dirty` 快照带入 remap。
- **状态**：已修复（工作区未提交，2026-09-29 修复批次；证据：remapIds 迁移 dirty/writeTimers，操作前 flushAll；新增回归 30 例，隔离副本修复前 25 失败）

## D02 `rescanWorkspace()` 的过期结果覆盖新工作区

- **严重度**：P0（跨工作区数据污染 + 静默覆盖）
- **位置**：
  - `src/data/library.ts:333`：只在扫描**前**校验 `target !== backend`，扫描结束后无条件 `setState`
  - `src/data/library.ts:289`：`openWorkspace` 先执行 `backend = resolved;` 再扫描
  - `src/data/library.ts:376`：真正写盘时用的是**当前** `backend`
  - 真实入口：`src/App.tsx:349`（⌘S → `void rescanWorkspace()`，无遮罩）、`src/data/library.ts:733`（删除文件夹后）
- **触发**：rescan 进行中切换笔记本（删除确认后无遮罩，用户可随手点侧栏）
- **影响**：旧工作区的整份 `notes/folders/trash/meta` 被灌进新工作区；此后任何一次自动保存都会写到错误的目录并覆盖同名文件；A 的星标/展开状态被写进 B 的 `.opennote/state.json`
- **证据（实测·harness）**：
  ```
  切到 B 之后 notes=["B-only.md","共享.md"]
  旧 rescan 结束后 workspace=wb notes=["A-only.md","共享.md"]
  B 磁盘上的 共享.md="# 被污染的内容"     ← 原有 "# B 的内容" 被覆盖
  ```
- **修法**：加代际标记 `let generation = 0`；`openWorkspace/closeWorkspace` 自增，`await` 之后 `if (myGen !== generation || target !== backend) return;`（`openWorkspace` 自身也应加同样校验——两个并发 `openWorkspace` 的同类竞态未单独构造复现，属推断）。
- **状态**：已修复（工作区未提交，2026-09-29 修复批次；证据：generation 代际校验，过期 rescan/open 结果不再发布）

## D03 `createNote` / 导入不预检磁盘已存在的同名文件

- **严重度**：P0（静默清空既有文件）
- **位置**：
  - `src/data/library.ts:436` `uniqueNotePath()` + `:452`：`taken` 只来自内存 `Object.keys(libraryStore.get().notes)`，且没有 `trashNote/moveNote/renameNote` 那样的 `while (await target.exists(...))` 循环
  - `src/lib/import.ts:50`、`:79`
- **触发**：Windows 上文件名大小写不敏感，文件在上次扫描之后出现（外部编辑器 / Git / 同步盘），随后新建同名笔记或导入
- **影响**：无提示丢失既有文件内容（用户可能从未在应用里见过该文件）
- **证据（实测·harness）**：

- **修法**：`createNote` / 导入复用「内存 `taken` ∪ `await target.exists()`」循环；或在扫描时缓存磁盘上全部文件名（含非 markdown）。
- **状态**：已修复（工作区未提交，2026-09-29 修复批次；证据：新增 resolveAvailablePath（后端 exists 复核），createNote 与导入共用）

## D20 渲染进程拥有宿主机任意读 / 写 / 删能力（IPC 边界形同虚设）

- **严重度**：P0（v2 由 P2 升级：补齐「任意读」「任意删」实测后重估）
- **位置**：
  - `electron/main.cjs:83` —— `root` 的唯一校验是 `typeof root !== 'string' || root.trim() === ''`，**任何目录都能当 root**
  - `electron/main.cjs:408-428` `opennote:dialog:saveFile` —— 只校验「非空、无 NUL、是绝对路径」，随后 `ensureParentDir` + `writeFile`，**无需用户选择、无需确认即可写入任意路径**
  - `main.cjs:63-92` 的 `resolveInsideRoot` 只约束「相对路径不逃逸**调用方自己给的** root」
- **触发/复现（实测·真实 `main.cjs` handler；我独立复跑确认）**：
  - 任意读：`fs:readText("C:\\Windows", "win.ini")` → 返回 `"; for 16-bit app support…"`
  - 任意写：`dialog:saveFile("<工作区外的路径>", "ATTACKER CONTENT")` → `true`，文件确实被创建
  - 任意递归删：见 D29（`remove(root, ".", {recursive:true})` 可删任意目录，因为 root 也是调用方给的）
- **影响**：`contextIsolation` / `sandbox` / `nodeIntegration:false` 全部开对的沙箱意义被抹平——渲染层只要出现一处脚本注入（笔记里的 HTML、导入的 HTML/SVG、开发态 dev server 被污染等），即可读取 `~/.ssh`、覆写启动目录、写 `.bashrc`/计划任务；渲染层还没有 CSP（见 D38）
- **对照（同一批实测的好消息）**：相对路径侧的校验本身可靠 —— `..`、`../`、`..\\`、`a/../../b`、`C:`、`C:ws`、`c:/x`、`//server/share/x`、`a\0b.md`、`%2e%2e/x`、`....//x` 全部被拒。问题出在「**root 由被约束方自己声明**」以及 `saveFile` 这条旁路
- **修法**：主进程维护「本次会话已授权的工作区 root 集合」（用户经系统对话框选定后登记），所有 fs IPC 的 `root` 必须命中集合；`saveFile` 只允许写入「本次会话 `pickSaveFile` 返回过的路径」
- **状态**：已修复（工作区未提交，2026-09-29 修复批次；证据：IPC 根目录授权白名单 + saveFile/addRecentWorkspace 门控；Lead 独立 harness 46/46，基线 19/27 失败）

## D29 `fs:remove` 的 `"."` 绕过根目录保护，可递归删除整个笔记本目录

- **严重度**：P0
- **位置**：`electron/main.cjs:286`
  ```js
  if (relPath === '' || relPath === undefined || relPath === null) throw new Error('不能删除笔记本根目录')
  ```
  但 `assertRelativePath`（`main.cjs:63`）把 `'.'` 原样放行，`resolveInsideRoot`（`main.cjs:82-92`）用 `path.relative(root, root) === ''` 判定「未越界」，于是 `main.cjs:290` 的 `rm(target, {recursive, force:true})` 作用在 root 本身
- **触发/复现（实测·真实 `main.cjs` handler；我独立复跑确认）**：
  ```
  remove(ws, ".", {recursive:true}) -> OK undefined
  ws exists after? false          ← 整个工作区目录被删除
  ```
  `"./"`、`".//"`、`".\\"`、`"././"` 同样删除根目录；`"sub/../."` 被拒。不带 `recursive` 时被 Node 的 `ERR_FS_EISDIR` 拦下（危险只发生在递归模式，而删除文件夹走的正是递归语义）
- **影响**：任何把空路径归一化成 `'.'` 的渲染层笔误（或在 D20 前提下的一次注入）都会静默清空用户整个笔记本目录；这与代码里显式的防护意图直接矛盾
- **修法**：`remove` 改为「解析后的绝对路径与 root 相等即拒绝」（`path.resolve(target) === path.resolve(root)`，Windows 下忽略大小写），而不是只比较空字符串
- **状态**：已修复（工作区未提交，2026-09-29 修复批次；证据：remove 判定「解析后路径 === root」即拒，覆盖 '.'/'./'/'.\'/'././'）
