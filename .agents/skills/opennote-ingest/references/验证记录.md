
实测回执：`action: "queued"`、`dirName: "20260930T175804-agent-2b"`、`entryStatus: "pending"`、
`bodyBytes: 484`。落盘形状（与 `src/data/inbox.ts` 的 `enqueueInbox()` 逐字段同形）：

```text

  entry.json   spec/importId/title/body:null/bodyFile:"body.md"/source/target/conflict/tags/assets/client/enqueuedAt
```

**「应用确实读了这条外部投递」的取证**（本技能最关键的一步，不是看文件在不在）：

1. 把同一条目复制成 `20991231T235959-agent-2b`（同 `importId`，目录名**排最后**）；
2. 等 5 秒；
3. 应用自己把**新目录**的 `state.json` 改写成
   `{"status":"failed","lastError":"IMP-4017",…}`，而原目录仍是 `pending`。

→ 证明运行中的应用的收件箱 watcher 真的读到了这份外部投递，走的是
`src/data/inbox.ts` 的 `refreshInbox()` 去重分支（同 `importId` 的第二条标 `failed` + `IMP-4017`）。
取证后该探针目录已删除。

**幂等实测**：同内容再投一次 → `action: "skipped"`、`reason: "already-in-inbox"`、退出码 0，
不产生第二条目录。

## 9. 第四次：端口发现顺序改为「显式 > 已公布 > 扫描」（2026-10-10）

### 9.1 触发它的真实现场（环境事实，不是脚本缺陷）

用户报「Opennote 在线但 `/opennote-ingest` 入不了库」。排查结果是**桥根本没在监听**：

```powershell
netsh int ipv4 show excludedportrange protocol=tcp   # → 8755–8854 被系统保留
netsh int ipv4 show dynamicport tcp                  # → Start 1024 / 13977 个（默认应为 49152 / 16384）
reg query "HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters" /v MaxUserPort   # → 0x3a98 = 15000
```

因果链：`MaxUserPort=15000`（遗留优化项）把 TCP 动态端口范围从默认 `49152–65535` 拉到
**`1024–15000`** → Hyper-V / WSL / Docker 的 `winnat` 保留段划进了 `8755–8854`
→ `8787–8796` 整段 `listen()` 返回 `EACCES` → 桥起不来 → 两条通道全断
（收件箱通道也断，因为「当前打开的笔记本」只能从桥问出来）。

逐端口实测：`8787/8788/8800/8854 → EACCES`，`8855/8856/9797/15001/18787 → OK`。

### 9.2 脚本侧改了什么

`probeBridge()` 的候选顺序从「只扫 `8787–8796`」改为：

**`--endpoint` > `bridge.json` 的 `port` > 扫 `8787–8796`**

`--check --json` 的 `bridge` 段新增 `how` 字段，如实说明这次是**怎么找到的**
（`--endpoint` / `bridge.json.port` / `scan`）。

### 9.3 实测证据（伪造 userData + 桥替身，不碰真实笔记本）

夹具：仓库脚本 `scripts/skill-port-discovery-smoke.mjs`（`node scripts/skill-port-discovery-smoke.mjs`，
可随时复跑）—— 它把 `APPDATA` 指到临时目录，写入 `bridge.json`（含 `port: 18787`）与
`recent-workspaces.json`，并起一个 HTTP 替身监听 **`18787`（冻结段之外）**应答
`/v1/health` 与 `/v1/imports/*`，最后核对 `--check --json` 的 `bridge.how`。

结果（退出码 0）：

```json
{ "ok": true,
  "bridge": { "endpoint": "http://127.0.0.1:18787", "how": "bridge.json.port", "spec": "opennote.import/v1", ... },
  "token":  { "present": true, "auth": "ok" },
  "workspace": { "root": "<临时目录>\\notes", "how": "桥的笔记本名匹配 recent-workspaces（notes）" } }
```

→ **改之前这个夹具必然失败**（旧脚本只会扫 `8787–8796`，永远摸不到 `18787`）。

### 9.4 诚实清单（本轮未验证 / 由人完成的）

1. **扫描兜底那条路（`how: "scan"`）在本机无法端到端验证**：本机 `8787–8796` 整段被系统保留，
   尝试绑定必然 `EACCES`，造不出「桥真的绑在冻结段里」的现场。该分支的逻辑由仓库侧
   `scripts/bridge-smoke.cjs` 的用例覆盖，但**没有真机端到端证据**。
2. **`EACCES` 的修复在应用侧，不在本脚本**：桥要「遇到 `EACCES` 继续扫下一个候选」，
   得靠新版 Opennote 桌面版（本技能只负责发现端口）。
3. **本机的根本解法是环境修复**：管理员删掉
   `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\MaxUserPort` 并重启，
   让动态端口范围回到默认 `49152–65535`（验收：`netsh int ipv4 show dynamicport tcp` →
   `Start Port 49152 / Number of Ports 16384`）。**这一步本技能不代做**（要提权，且属于用户环境）。
